Bloco 1 · Fronteira HTTP: rotas, Depends, middleware e lifespan

Uma API não começa na rota #

Um cliente precisa criar um link e recuperá-lo depois. Ele não deveria saber se o serviço usa um dicionário, PostgreSQL ou outro processo. Também não deveria receber uma exceção Python, uma página HTML ou uma resposta cujo formato muda a cada endpoint. A fronteira HTTP existe para estabilizar esse acordo.

Ela recebe bytes e metadados de HTTP, valida uma representação, chama a aplicação e devolve uma representação com status, headers e corpo. Isso é transporte. A regra que decide se um link pode existir pertence à aplicação. A persistência só aparece no bloco 2.

ASGI, Uvicorn e FastAPI fazem trabalhos diferentes #

ASGI é uma interface Python para servidor e aplicação assíncrona. Ela descreve como uma conexão HTTP, WebSocket ou lifecycle chega à aplicação. Uvicorn é um servidor que aceita conexões e chama uma aplicação ASGI. FastAPI é o adapter que interpreta rotas, tipos, dependências e respostas sobre essa interface.

Essa separação permite testar o app em memória por um transporte ASGI e trocar o servidor sem reescrever endpoints. Ela não transforma cada handler em paralelismo. Um endpoint async def continua sujeito às regras de I/O cooperativo do M02; uma operação bloqueante no handler continua bloqueando o trabalho daquele loop.

FastAPI usa a assinatura como parte do contrato #

FastAPI lê parâmetros e modelos Pydantic para decidir onde uma entrada vem e como documentá-la. Um parâmetro presente no caminho da rota é path parameter. Um modelo Pydantic normalmente representa o corpo. A anotação de retorno e response_model delimitam a forma exposta. O resultado entra em OpenAPI, uma descrição interoperável que pode alimentar documentação ou geradores de cliente.

Inferência reduz configuração repetida. Não elimina decisão. Aceitar campo extra, escolher o status de conflito ou publicar uma entidade do banco continuam sendo escolhas do autor da API.

Referência do conceito

@app.get registra uma rota; os modelos descrevem entrada e saída; Depends resolve dependências; middleware envolve o processamento; lifespan organiza abertura e encerramento de recursos da aplicação. Essas responsabilidades serão percorridas no exemplo abaixo.

Exemplo trabalhado: a fronteira antes do banco #

Este é um exemplo conceitual completo. Ele guarda links em memória para tornar visível a rota, o schema, a dependência e o erro. Não é o código do laboratório e não prova persistência, colisão concorrente ou segurança de slug. A referência executável só aparece no laboratório final.

from contextlib import asynccontextmanager
from collections.abc import AsyncIterator
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException, status
from pydantic import BaseModel, Field


class LinkIn(BaseModel):
    url: str = Field(min_length=8, pattern=r"^https?://")


class LinkOut(BaseModel):
    slug: str
    url: str


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    # startup: abrir pool de conexões, aquecer cache... (bloco 2 usa de verdade)
    print("subindo")
    yield
    # shutdown: fechar pool, drenar filas
    print("descendo")


app = FastAPI(title="Shortener", lifespan=lifespan)

_fake_db: dict[str, str] = {}          # até o bloco 2 chegar com Postgres


def get_repo() -> dict[str, str]:      # a "dependência" — troque por sessão de banco depois
    return _fake_db


Repo = Annotated[dict[str, str], Depends(get_repo)]   # alias reutilizável


@app.post("/links", response_model=LinkOut, status_code=status.HTTP_201_CREATED)
async def criar_link(body: LinkIn, repo: Repo) -> LinkOut:
    slug = f"demo-{len(repo) + 1}"  # visualização; B02 substitui por persistência/constraint
    repo[slug] = body.url
    return LinkOut(slug=slug, url=body.url)


@app.get("/links/{slug}", response_model=LinkOut)
async def obter_link(slug: str, repo: Repo) -> LinkOut:
    if slug not in repo:
        raise HTTPException(status_code=404, detail="slug não encontrado")
    return LinkOut(slug=slug, url=repo[slug])

Depends: a DI que é função, não container #

Depends não é um contêiner de injeção de dependências genérico. É uma instrução para FastAPI resolver uma callable para a operação e suas subdependências. O grafo fica próximo ao endpoint. Uma dependência pode ser síncrona ou assíncrona; a escolha deve seguir o trabalho realizado, não uma preferência estética.

O alias Repo = Annotated[dict[str, str], Depends(get_repo)] preserva o tipo que o endpoint recebe e evita repetir a mesma declaração. Ele não torna o dicionário seguro entre requests. A versão de banco troca esse adapter por uma sessão de escopo explícito.

  • Escopo por request é uma decisão visível. A dependência com yield modela preparo antes da operação e teardown depois. No bloco 2 ela abrirá, confirmará ou reverterá e fechará a sessão de banco; a limpeza precisa de oráculo, não de confiança no framework.
  • Override em teste é trivial: app.dependency_overrides[get_repo] = get_repo_fake — sem container de teste, sem builder (bloco 6 usa).
  • Autenticação/autorização são dependências também (uma função que lê o header, valida o token e devolve o usuário — ou levanta 401). O M12 constrói isso; a mecânica é a mesma do get_repo.
from collections.abc import AsyncIterator


async def get_request_resource() -> AsyncIterator[str]:
    resource = "aberto"
    try:
        yield resource
    finally:
        # O bloco B02 provará cleanup e rollback com PostgreSQL real.
        resource = "fechado"

O valor alterado no finally só visualiza o lifecycle. Um yield não torna uma sessão segura para várias tarefas concorrentes, não escolhe commit e não recupera uma falha remota. A responsabilidade continua sendo de quem abriu o recurso e de quem definiu o protocolo de encerramento.

Fundamento de engenharia · HTTP e REST — a reciclagem que o Swagger não faz por você

O framework automatiza o transporte, não o DESIGN. Recicle o que separa API sênior de API que funciona por acaso:

  • Semântica dos verbos e idempotência: GET/PUT/DELETE são idempotentes (repetir = mesmo efeito), POST não. Isso não é pedantismo: retry automático (do seu gateway do M05, do load balancer, do agente do M08) SÓ é seguro sobre operação idempotente. API que faz POST não-idempotente sem chave de idempotência é a fonte da dupla cobrança do M12.
  • Status codes como contrato: 400 (request mal-formado) ≠ 404 (não existe) ≠ 409 (conflito de estado) ≠ 422 (bem-formado, semanticamente inválido — o que o Pydantic devolve) ≠ 500 (culpa SUA). Cliente e agente decidem retry/fallback pelo código — errar o código é quebrar o contrato de erro.
  • Erros num formato só: padronize (RFC 9457, Problem Details) com exception_handler. Erro estruturado é o fator 9 do M01 aplicado a HTTP.
  • Versionamento e compatibilidade: campo novo opcional = seguro; remover/renomear = quebra. Some com o extra="forbid" do M02 e você tem contratos que evoluem sem sustos.
422 não é uma política de negócio

FastAPI devolve por padrão uma resposta estruturada quando a entrada não satisfaz o schema. Isso não torna toda resposta de erro aderente a RFC 9457. Se a API adota Problem Details, ela precisa definir explicitamente esse formato para erros de domínio e, quando necessário, para erros de validação. Não prometa um contrato que o framework não foi configurado para entregar.

Middleware e o pipeline #

import time
import uuid

from fastapi import Request, Response


@app.middleware("http")
async def request_id_e_tempo(request: Request, call_next) -> Response:  # type: ignore[no-untyped-def]
    received = request.headers.get("x-request-id")
    try:
        rid = str(uuid.UUID(received)) if received else str(uuid.uuid4())
    except ValueError:
        rid = str(uuid.uuid4())
    inicio = time.perf_counter()
    response = await call_next(request)            # o resto da cebola
    response.headers["x-request-id"] = rid
    response.headers["x-elapsed-ms"] = f"{(time.perf_counter() - inicio) * 1000:.1f}"
    return response

O middleware envolve o processamento: o que vem antes do call_next roda na ida, o que vem depois roda na volta, e a ordem de registro importa. O exemplo só preserva um UUID válido; confiar em qualquer header de um cliente permite conteúdo arbitrário no log. Em uma borda com gateway confiável, a política de confiança precisa ser declarada. O x-request-id é a semente da observabilidade do M06 — um request rastreável do edge ao banco.

Leitura aplicada: acompanhe uma requisição #

  1. POST /links chega com um JSON. Uvicorn entrega o evento ao FastAPI; o middleware cria ou normaliza o correlation id.
  2. FastAPI constrói LinkIn. Uma URL fora do pattern interrompe o caminho antes da função de rota. Isso é validação de representação, não decisão de negócio.
  3. A rota pede Repo. FastAPI chama get_repo, entrega o valor retornado e converte o resultado para LinkOut. Esse último passo impede que uma chave interna do dicionário vaze por acidente.
  4. Se GET /links/{slug} não encontra o valor, a rota declara uma condição de aplicação. A tradução para 404 pertence ao handler. O middleware acrescenta o mesmo ID à resposta.

Este exemplo serve à leitura do fluxo. O laboratório final ainda está pendente: falta criar a referência executável e verificar respostas e falhas. Você pode retomar por esta seção; o texto não representa uma prática já aprovada.

Bloco 2 · Sessão, transação e migration

Contexto e saída #

Pré-requisitos: bloco 1 (fronteira HTTP, Depends com yield, correlation id) e M02 (Pydantic em trust boundary, asyncio cooperativo, testes com caminho feliz e falha). Objetivo: decidir onde uma alteração é confirmada, o que acontece quando ela falha no meio e como o schema evolui sem perder dados. Saída observável: você descreve o ciclo de vida de uma sessão por request, o par upgrade/downgrade de uma migration e por que a constraint do banco — e não um if — fecha uma corrida. A execução fica reunida no Laboratório guiado M03, depois do bloco 8; este bloco é leitura com exemplos rotulados.

A situação: três falhas que só o banco resolve #

O dicionário em memória do bloco 1 perde tudo ao reiniciar, aceita o mesmo slug duas vezes se dois requests chegarem juntos e não tem resposta para "a tabela precisa de uma coluna nova sem apagar as linhas". Cada sintoma aponta para um mecanismo distinto: a transação delimita o que é confirmado junto e desfaz o que falhou no meio; a constraint proíbe o estado inválido mesmo sob concorrência; a migration versiona a evolução do schema com volta declarada. Nenhum dos três vive no framework HTTP; todos vivem entre a aplicação e o PostgreSQL, mediados pelo SQLAlchemy.

Vocabulário mínimo, ensinado aqui porque é usado aqui. Engine é o objeto que guarda o pool de conexões com o banco e é compartilhado pelo processo. Pool é o conjunto de conexões abertas e reutilizáveis; abrir conexão TCP+TLS a cada request seria o custo dominante da API. Sessão (AsyncSession) é a unidade de trabalho de um fluxo: guarda os objetos tocados, acumula alterações e as envia dentro de uma transação. Transação é o bloco atômico — tudo confirma (commit) ou tudo desfaz (rollback). Migration é um script versionado com upgrade e downgrade. Constraint é a regra gravada no schema (UNIQUE, chave estrangeira) que o banco impõe a toda escrita, venha de onde vier.

Referência do conceito

AsyncSession mantém o estado de uma unidade de trabalho. session.add registra um objeto; flush envia as alterações ao banco dentro da transação aberta sem confirmá-la; commit confirma a transação; rollback desfaz o que ainda não foi confirmado. Alembic registra a evolução do schema em revisions encadeadas. Uma sessão nunca é compartilhada por tarefas concorrentes.

Uma sessão por request, um pool por processo #

O exemplo abaixo é conceitual e completo para leitura: mostra engine, modelo, mapeamento e a dependência que delimita a transação. Não é o código do laboratório e não prova comportamento contra banco real.

# shortener/db.py — exemplo conceitual; a referência executável fica no laboratório final
from collections.abc import AsyncIterator
from datetime import datetime

from sqlalchemy import DateTime, String, func
from sqlalchemy.ext.asyncio import (
    AsyncSession, async_sessionmaker, create_async_engine,
)
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

from shortener.settings import settings          # pydantic-settings do M02

engine = create_async_engine(settings.database_url, pool_size=10, echo=False)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)


class Base(DeclarativeBase):
    pass


class Link(Base):
    __tablename__ = "links"

    id: Mapped[int] = mapped_column(primary_key=True)
    slug: Mapped[str] = mapped_column(String(16), unique=True, index=True)
    url: Mapped[str] = mapped_column(String(2048))
    hits: Mapped[int] = mapped_column(default=0)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )


async def get_session() -> AsyncIterator[AsyncSession]:
    """A dependência com yield: escopo de request, commit no sucesso, rollback no erro."""
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

Repare em três decisões que valem discussão de code review:

  • expire_on_commit=False: por padrão o SQLAlchemy "expira" os atributos dos objetos após commit, de modo que o próximo acesso recarrega do banco — mais um round-trip assíncrono escondido. Numa API, o comum é devolver o objeto que acabou de ser salvo sem nova consulta, por isso o laboratório desliga a expiração.
  • Pool no engine, sessão por request: o engine, com seu pool de conexões, é um singleton do processo, criado uma vez no startup. A AsyncSession é de escopo curto — uma por request, aberta na dependência e fechada no teardown. Compartilhar uma sessão entre tarefas concorrentes corrompe a unidade de trabalho; o laboratório prova isso com um oráculo negativo.
  • Commit na dependência, não no endpoint: o endpoint declara a intenção (criar, buscar); a fronteira transaciona. É o padrão unidade-de-trabalho-por-request: a rota nunca chama commit diretamente, então nenhum caminho esquece de confirmar ou de reverter.
Carregamento explícito em async: a regra que impede o N+1 silencioso

Neste mapeador, em contexto assíncrono, acessar um relacionamento que não foi carregado não dispara uma consulta silenciosa: falha com MissingGreenlet, porque o ORM não pode fazer I/O bloqueante no meio do event loop (o bloco 5 do M02 explica o mecanismo cooperativo). O antídoto é declarar o carregamento na consulta: select(Link).options(selectinload(Link.clicks)). O efeito colateral é didático — o custo de I/O deixa de ser invisível e passa a ser uma decisão escrita na query. O laboratório provoca o erro de propósito uma vez, para que o diagnóstico vire reflexo.

Fundamento · Atomicidade, consistência e isolamento
  • Atomicidade é o commit/rollback da dependência acima: ou todas as escritas do request confirmam, ou nenhuma. Durabilidade é garantia do PostgreSQL após o commit. As duas que exigem decisão sua: consistência e isolamento.
  • Consistência mora em constraints. unique=True no slug é a única garantia real contra duplicata: uma checagem "existe?" em código tem uma janela entre o SELECT e o INSERT por onde um request concorrente passa. A constraint fecha essa janela porque é verificada dentro da escrita, não antes dela.
  • Isolamento na prática: o padrão do PostgreSQL é READ COMMITTED — duas transações que fazem "ler, somar 1, gravar" sobre o mesmo contador perdem atualizações (lost update). Consertos, do mais simples ao mais forte: update atômico no banco (UPDATE links SET hits = hits + 1 — o banco soma, não o Python), SELECT ... FOR UPDATE (trava pessimista) ou coluna de versão (trava otimista: grava só se a versão lida ainda for a atual). O bloco 6 prova o lost update com teste concorrente.
  • Transação curta é regra de ouro: transação aberta atravessando uma chamada lenta (uma chamada de modelo no M05, por exemplo) segura uma conexão do pool pelo tempo da chamada. Pool esgotado é API morta. Transacione o banco, nunca o workflow.

Alembic: migrations com contrato #

Alembic é a ferramenta que versiona o schema do banco: cada mudança é uma revision, um arquivo Python numerado e encadeado com funções upgrade (aplica) e downgrade (desfaz). O comando alembic init -t async migrations cria o esqueleto já preparado para engine assíncrono; a configuração única é apontar target_metadata = Base.metadata no env.py e ler a URL do banco a partir das settings do projeto. Daí o ciclo é sempre o mesmo:

uv run alembic revision --autogenerate -m "create links table"
# REVISE o arquivo gerado em migrations/versions/ — autogenerate erra rename
# (vê drop+add), não vê mudança de server_default, e não escreve backfill.
uv run alembic upgrade head

Três regras separam migration revisada de incidente futuro. Primeira: migration é código revisado — o --autogenerate escreve um rascunho comparando modelos e banco, e rascunho se revisa. Segunda: todo upgrade tem downgrade testado, porque rollback de deploy depende dele (bloco 7). Terceira: migration destrutiva (remover coluna com dado) acontece em duas releases — primeiro o código para de usar a coluna, depois outra migration a remove. E a proibição que o laboratório verifica com oráculo: nenhum startup de produção cria schema com create_all; o schema nasce de migration, sempre.

Leitura aplicada: acompanhe um request com banco #

  1. POST /links chega validado pelo schema do bloco 1. A dependência get_session abre uma AsyncSession — uma unidade de trabalho vazia, presa a uma conexão do pool.
  2. A rota consulta select(Link).where(Link.slug == slug) e adiciona o novo objeto com session.add. Nada foi confirmado ainda; flush enviaria as escritas dentro da transação aberta, sem confirmar.
  3. Se um segundo request inseriu o mesmo slug entre a consulta e a escrita, a constraint UNIQUE rejeita a escrita com IntegrityError. A rota traduz para 409 Conflict. Nenhum if prévio seria capaz disso — a janela entre checar e inserir pertence a quem escreve por último, e só o banco a fecha.
  4. Se o service levanta exceção no meio, a dependência executa rollback e a sessão fecha sem deixar resíduo. Se tudo corre bem, commit confirma atomicamente.
  5. Semanas depois, o time precisa de uma coluna nova. Uma revision Alembic descreve upgrade e downgrade; upgrade head num banco vazio e downgrade de volta provam o caminho de ida e volta.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável — subir PostgreSQL, gerar e aplicar a migration, trocar o armazenamento em memória pela sessão real e provocar cada falha — fica no Laboratório guiado M03, depois do bloco 8, com resultado esperado e diagnóstico por passo.

Contraste: o que parece funcionar e quebra em produção
  • if exists: 409 antes de inserir parece prevenir duplicata, mas duas tarefas passam pela checagem antes de qualquer escrita — ambas inserem, uma quebra sem tratamento ou, pior, ambas passam sem constraint. Constraint + tradução de IntegrityError é o único fechamento.
  • create_all no startup parece simplificar o deploy, mas cria schema sem histórico, sem revisão e sem volta — e diverge do banco real na primeira alteração manual. Migration versionada é o único caminho de ida e volta.
  • Sessão global reutilizada parece economizar objetos, mas mistura unidades de trabalho de requests distintos e falha sob concorrência. Sessão nova por request, engine compartilhado.
Síntese do bloco 2
  • Sessão é unidade de trabalho de escopo curto; engine e pool são do processo. Uma sessão por request, nunca compartilhada entre tarefas.
  • Commit e rollback moram na dependência com yield: a rota declara intenção, a fronteira confirma ou desfaz. Transação curta — nunca atravessando I/O lento externo.
  • Consistência sob concorrência mora na constraint; checagem prévia em código tem janela de corrida. 409 vem da tradução de IntegrityError.
  • Em async, relacionamento se carrega por declaração explícita (selectinload); o erro MissingGreenlet é o sintoma do acesso implícito.
  • Alembic: autogenerate é rascunho revisado, todo upgrade tem downgrade testado, destrutivo em duas releases, nunca create_all em produção.

Bloco 3 · Postgres para valer: índices, planos, transações e JSONB

Por que isso importa #

O encurtador funciona com poucos links. Com centenas de milhares de linhas, três perguntas passam a decidir cada endpoint: existe um índice que sirva ao predicado da consulta, o plano de execução confirma que ele é usado e os atributos de formato variável têm um lar que não destrua o schema. Sem essas respostas, a API degrada em silêncio — latência que cresce com a tabela, contadores que perdem increments sob concorrência e uma coluna nova por semana para cada variação de payload. Este bloco ensina a prever o custo antes do deploy, a ler o plano depois dele e a separar o que é coluna relacional do que é documento.

Fundamento · Índices
  • B-tree é o padrão e serve a =, <, >, ORDER BY e prefixo de LIKE. Pense numa árvore de busca: O(log n) para localizar, mas cada INSERT/UPDATE paga a manutenção de TODOS os índices da tabela. Índice não é grátis — é troca de escrita por leitura.
  • Índice composto (a, b) serve a consultas por (a) e (a,b) — não por (b). A ordem das colunas segue a seletividade e o padrão de consulta: a coluna mais filtrada primeiro.
  • Índice parcial (WHERE status = 'active') e índice de expressão (ON lower(email)) indexam só o que se consulta, mantendo-se pequenos.
  • Seletividade decide tudo: índice em coluna com pouquíssimos valores distintos raramente compensa (o planejador escolhe varredura sequencial mesmo assim); em coluna quase-única, quase sempre. O planejador usa estatísticas (ANALYZE) — estatística desatualizada gera plano ruim.
  • GIN é o índice para o conteúdo "dentro" da coluna: arrays, texto integral e JSONB (abaixo). B-tree localiza A LINHA; GIN localiza O QUE HÁ NELA.

EXPLAIN: o raio-X da consulta #

EXPLAIN é o comando do PostgreSQL que mostra o plano que o planejador escolheu para uma consulta, sem executá-la. Com a opção ANALYZE, ele executa e acrescenta os tempos reais. A leitura é sempre a mesma comparação: o que o planejador estimou contra o que realmente aconteceu.

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM links WHERE slug = 'abc123';

Saída ilustrativa (exemplo variável — tempos e custos dependem de hardware, volume e estatísticas; o formato dos campos é o estável):

Como ler o resultado, de baixo para cima (nós internos consomem filhos):

Index Scan using ix_links_slug on links  (cost=0.29..8.31 rows=1 width=64)
                                          (actual time=0.041..0.043 rows=1 loops=1)
  Index Cond: (slug = 'abc123'::text)
Planning Time: 0.180 ms
Execution Time: 0.071 ms
  • cost=0.29..8.31: estimativa do planejador (custo de partida..custo total, em unidades abstratas). actual time: a realidade, em ms. Quando estimativa e realidade divergem muito (linhas estimadas 1, reais 80.000), o problema é estatística — ANALYZE tabela;.
  • Os quatro nós que resolvem a maioria das leituras: Seq Scan (leu a tabela inteira — aceitável em tabela pequena, alarme em tabela grande), Index Scan (percorreu a árvore), Index Only Scan (respondeu só com o índice, sem visitar a tabela) e Nested Loop / Hash Join (estratégia de junção; nested loop com milhares de iterações denuncia um N+1 no plano).
  • BUFFERS mostra páginas lidas de cache (shared hit) contra disco (read) — a diferença entre uma consulta de milissegundos e a mesma consulta em centenas de milissegundos.

A decisão que o plano sustenta: o predicado crítico — busca por slug, listagem recente por data — usa o índice escolhido, e isso se lê no nó do plano, não no cronômetro. Tempo absoluto varia por máquina; presença do nó Index Scan sobre o índice certo é o invariante.

JSONB: coluna relacional para o estável, documento para o variável #

Sistemas que consomem modelos produzem dado semiestruturado com frequência: respostas com campos que variam por versão, metadados de execução (modelo, tokens, custo, latência), configurações por tenant. Modelar cada variação como coluna significa uma migration por semana; despejar tudo num armazenamento sem schema significa perder junções, transações e validação. JSONB é a terceira via do PostgreSQL: colunas relacionais para o que é estável e consultado sempre; uma coluna JSONB para a cauda variável — indexável com GIN e consultável com operadores:

-- exemplo variável: o padrão núcleo relacional + cauda flexível
CREATE TABLE analises (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   bigint NOT NULL REFERENCES tenants(id),
    status      text   NOT NULL DEFAULT 'pending',
    custo_cents int    NOT NULL DEFAULT 0,
    resultado   jsonb  NOT NULL DEFAULT '{}'::jsonb,   -- a cauda variável
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ix_analises_resultado ON analises USING gin (resultado);

-- operadores que você vai usar:
SELECT resultado->>'modelo' FROM analises;                     -- extrai como texto
SELECT * FROM analises WHERE resultado @> '{"modelo": "gpt"}'; -- contém (usa o GIN!)
SELECT * FROM analises WHERE resultado ? 'warnings';           -- tem a chave?
Referência do conceito

JSONB armazena documentos JSON em representação própria do PostgreSQL e oferece operadores de consulta. O formato não elimina a necessidade de schema, validação e índices: o que se consulta sempre vira coluna; o schema do documento mora no Pydantic; o acesso por chave usa índice GIN. Usar JSONB como substituto do schema relacional — sem validação e sem índice — troca uma migration por semana por consultas sem plano estável.

Leitura aplicada: do sintoma ao conserto #

  1. A listagem "links recentes" ordena por created_at sem índice. O plano mostra Seq Scan + Sort: a tabela inteira lida e ordenada para devolver 20 linhas. O conserto é um índice (created_at DESC); o plano passa a Index Scan. O preço aparece do outro lado: cada índice novo torna cada escrita mensuravelmente mais lenta — a troca leitura×escrita, decidida por predicado, não por hábito.
  2. O contador hits é incrementado como "ler, somar 1, gravar" em Python. Sob concorrência em READ COMMITTED, duas transações leem o mesmo valor e uma sobrescreve a outra: updates perdidos sem nenhum erro. O conserto é somar no banco (UPDATE links SET hits = hits + 1), onde a operação é atômica. O laboratório prova os dois comportamentos com um teste concorrente.
  3. Metadados de origem e campanha chegam por link e variam a cada trimestre. Viram coluna meta JSONB com índice GIN e consulta por contenção (@>), adicionada via migration Alembic com downgrade — o ciclo do bloco 2 aplicado a um tipo novo.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável — popular massa de teste, comparar planos antes e depois do índice, provocar o lost update e consultar o JSONB com e sem GIN — fica no Laboratório guiado M03, depois do bloco 8, com resultado esperado e diagnóstico por passo.

Contraste: medir uma vez não é provar para sempre
  • Plano lido, estatística velha: um EXPLAIN de hoje não garante o plano de amanhã — sem ANALYZE após carga relevante, o planejador decide com mapa desatualizado.
  • Índice em tudo: cada índice acelera uma leitura e taxa todas as escritas. Índice sem predicado que o use é custo puro.
  • JSONB sem validação: documento sem schema Pydantic e sem GIN acumula chaves inconsistentes e consultas sequenciais — o pântano sem schema que o tipo prometia evitar.
Síntese do bloco 3
  • Prever custo é escolher índice pelo predicado (B-tree, composto, parcial, expressão, GIN) sabendo que escrita paga cada índice.
  • Ler plano é comparar estimativa e realidade (nós, linhas, buffers); o invariante é o nó certo sobre o índice certo, não o tempo absoluto.
  • JSONB recebe a cauda variável com validação e GIN; o que se consulta sempre é coluna relacional.
  • Lost update em READ COMMITTED se corrige somando no banco; concorrência se prova com teste, não com argumento.
  • Reflexo novo: consulta nova em tabela grande passa por EXPLAIN antes do deploy, não depois do incidente.

Bloco 4 · Fronteiras internas: camadas e guardrails

Por que isso importa #

Até aqui o encurtador vive em módulos planos — suficiente para aprender, frágil para crescer. Quando a regra de negócio mora na rota, cada endpoint novo duplica decisão; quando a rota importa o banco diretamente, trocar persistência exige reescrever HTTP; quando nada verifica a estrutura, ela decai no primeiro prazo apertado. Este bloco define as fronteiras que o laboratório usa daqui em diante: o que cada camada pode importar, como a aplicação troca a infraestrutura sem mudar de regra e como uma regra de arquitetura vira verificação executável em vez de convenção oral.

Contexto e saída #

Pré-requisitos: blocos 1–3 (contrato HTTP, sessão por request, constraints e índices). Objetivo: separar tradução HTTP, decisão de aplicação e acesso a dados em camadas com direção de import explícita, e tornar essa direção verificável por teste. Saída observável: você enuncia o que cada camada pode importar, demonstra a troca da infraestrutura por override sem tocar na regra e aponta onde a decisão está registrada (ADR). A execução fica no Laboratório guiado M03; este bloco é leitura.

A estrutura e o contrato de cada pacote #

src/link_shortener/
├── api/                # HTTP: app, rotas, tradução erro de domínio → status
├── services/           # regra: valida, orquestra repositório, decide
├── repositories/       # acesso a dados: queries, NADA de regra
├── composition.py      # raiz de composição: liga sessão → repositório
├── domain.py           # contratos e validações puras da fronteira
├── errors.py           # tradução erro de persistência → erro de domínio
├── counters.py         # políticas de incremento (ingênuo vs. atômico)
├── models.py           # entidades SQLAlchemy (o schema do banco)
└── db.py               # engine, sessões, fronteira transacional

O contrato inteiro é a direção dos imports — a seta só aponta para baixo:

  • api importa services, domain e errors. NUNCA repositories (a tentação aparece no CRUD simples; no dia em que o CRUD ganha regra, ela já tem lugar) e NUNCA models nem SQLAlchemy (entidade de banco não vaza para HTTP — um campo interno exposto por preguiça vira vazamento no M12).
  • services importa repositories (via protocolo), domain e errors. É o único lugar com decisão; recebe e devolve tipos de domínio, não Request/Response — service que importa FastAPI vazou HTTP para dentro.
  • repositories importa models e o necessário de SQLAlchemy. Query e persistência, zero regra ("se status for X então..." em repository é regra fugida de casa).
  • A raiz de composição (composition.py) é a única exceção documentada: ela liga a sessão ao repositório concreto para a rota. Todo o resto só conhece contratos.
  • domain e errors não importam framework nenhum. São a base da pirâmide: testáveis sem banco, sem HTTP, sem container.
Referência do conceito

Em Python, os imports tornam dependências entre módulos observáveis: o sistema de imports resolve nomes a partir de pacotes, e qualquer import proibido aparece como texto no fonte. Uma regra executável pode varrer a árvore sintática e rejeitar import de infraestrutura no domínio. Protocol descreve o contrato necessário ao consumidor sem herdar implementação; a composição escolhe qual objeto atende ao protocolo. Testes demonstram que substituir o adapter preserva o comportamento.

Fundamento · Coesão, acoplamento e direção de dependência
  • Coesão alta: o que muda junto, mora junto. Acoplamento baixo: o que muda separado, depende pouco. Camadas são essa ideia operacionalizada: cada pacote tem um motivo para mudar.
  • Direção para dentro: dependências apontam das bordas (HTTP, banco) para o centro (domínio, regras). O domínio não conhece HTTP nem banco; a versão pragmática admite o service conhecer o protocolo do repositório, nunca a implementação. A regra vale o custo quando a troca de adapter — provada em teste — continua possível.
  • Dependência estável: dependa na direção do que muda pouco. domain muda raramente e todos dependem dele; api muda sempre e ninguém depende dela. Inverter a seta faz cada mudança de rota sacudir a base.

Override: trocar a infraestrutura sem tocar na regra #

O service recebe um repositório que atende ao protocolo — no laboratório, a implementação SQLAlchemy; no teste, um fake em memória com o mesmo comportamento. Nada na regra muda entre os dois: a construção escolhe o objeto, a lógica só usa o contrato. No nível HTTP, o mesmo princípio aparece como dependency_overrides: a aplicação real atende requests com a sessão de teste injetada, sem startup alternativo e sem condicional de ambiente. É assim que isso se prova — mesma regra, duas infraestruturas, mesmos resultados.

Guardrail: arquitetura com exit code #

Convenção oral decai; verificação executável permanece. O laboratório varre a árvore sintática dos pacotes e rejeita imports proibidos: api não toca repositories nem models (a sessão atravessa como valor opaco da dependência); services não toca FastAPI, SQLAlchemy nem models; repositories não toca FastAPI; o núcleo não toca framework nenhum. Um import ilegal quebra a suíte com a violação apontada. O teste inclui seu próprio controle negativo — um trecho violador sintético que o verificador deve acusar — para que o oráculo não aprove tudo por acidente.

Leitura aplicada: seguir uma criação de ponta a ponta #

  1. POST /links chega à rota em api, que extrai slug e URL e chama o service. Nenhum SQL existe neste nível.
  2. O service valida pelo domain (422 se inválido), pede ao repositório via protocolo e traduz violação de unicidade em conflito (409). A decisão "criar" e o mapeamento de erro moram aqui.
  3. O repositório executa select/add na sessão que a dependência abriu. Se a constraint rejeita a escrita, o erro sobe já traduzido pelo errors.
  4. A resposta volta como contrato de saída; a entidade do banco nunca cruza a fronteira. Trocar o repositório SQLAlchemy pelo fake não altera nenhuma dessas linhas — só a construção.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável — service, repositório, app com override e guardrail verde — fica no Laboratório guiado M03, depois do bloco 8. A decisão de fronteiras, com custo e condição de revisão, está registrada no ADR do laboratório.

Síntese do bloco 4
  • Setas só para baixo: api → services → repositories; núcleo sem imports de framework.
  • Entidade de banco não vaza para HTTP; regra mora em service; repository é query pura.
  • Em Python a fronteira é import — então o import vira teste com exit code, com controle negativo próprio.
  • Override (protocolo no service, dependency_overrides no app) troca infraestrutura sem tocar na regra.
  • Decisão de fronteira se registra em ADR, com custo e condição de revisão explícitos.

Bloco 5 · Imagens, Compose e ambiente reproduzível

Por que isso importa #

Testes que passam na máquina de quem escreveu e quebram em qualquer outro lugar custam caro — e banco de desenvolvimento instalado à mão, com versão e configuração desconhecidas, é uma fonte clássica dessa divergência. Docker resolve a embalagem: aplicação, runtime e dependências do sistema viajam numa imagem imutável, e o ambiente inteiro (API + banco + rede + volume) viaja num arquivo Compose versionado. O laboratório usa os dois para que PostgreSQL, migrations e suíte executem no mesmo ambiente em qualquer máquina com Docker Engine.

Contexto e saída #

Pré-requisitos: blocos 1–4 (app HTTP em camadas). Objetivo: embalar o laboratório numa imagem reproduzível e declarar o ambiente local em Compose, com saúde observável e segredos fora da imagem. Saída observável: você explica cada estágio do Dockerfile, a função de volume/rede/healthcheck no Compose e o que impede um segredo de entrar na imagem. A construção e execução de containers exigem Docker Engine; sem ele, os oráculos estáticos do lab verificam os artefatos e a execução fica marcada como bloqueada.

Contexto · Imagem, camada, container, registry — o vocabulário
  • Imagem = o pacote imutável com aplicação, bibliotecas e arquivos necessários à execução. Identificada por tag: postgres:16.
  • Camada = cada instrução do Dockerfile gera uma fatia somente-leitura, com hash. Imagens compartilham camadas. Cache de build funciona por camada, de cima para baixo: mudou uma linha, tudo abaixo rebuilda. Essa frase explica a maioria dos builds lentos.
  • Container = uma instância em execução da imagem: processo isolado pelo kernel, não máquina virtual — por isso inicia em fração de segundo. Imagem está para container como classe está para objeto.
  • Registry = o repositório de imagens (Docker Hub, GHCR). docker push/pull publica e baixa.

O Dockerfile, linha a linha #

Exemplo de referência completo — corresponde ao Dockerfile do laboratório. Cada linha tem um porquê, e o checkpoint cobra todos:

# ---------- estágio 1: builder (ferramentas de build ficam AQUI e morrem aqui)
FROM python:3.14-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv

WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy

# 1º: SÓ os manifests. Enquanto pyproject/uv.lock não mudarem,
# esta camada (a instalação inteira de dependências) vem do cache.
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# 2º: o código (muda toda hora, por isso vem DEPOIS das dependências)
COPY src/ src/
RUN uv sync --frozen --no-dev

# ---------- estágio 2: runtime (só o necessário para RODAR)
FROM python:3.14-slim AS runtime
WORKDIR /app

# usuário não-root: um processo comprometido não opera como root
RUN groupadd -r app && useradd -r -g app app

COPY --from=builder --chown=app:app /app/.venv /app/.venv
COPY --from=builder --chown=app:app /app/src /app/src

ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
USER app
EXPOSE 8000

HEALTHCHECK --interval=15s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/health')"

CMD ["uvicorn", "link_shortener.serve:app", "--host", "0.0.0.0", "--port", "8000"]

Os porquês que o checkpoint cobra:

  • Multi-stage (AS builder → AS runtime): compiladores, headers e o próprio uv não viajam para produção. Imagem menor significa deploy mais rápido e superfície de ataque menor.
  • Manifests antes do código: a ordem das camadas segue a frequência de mudança — dependências mudam por semana, código por hora. Inverter a ordem reinstala tudo a cada build.
  • --frozen: usa o uv.lock exato e falha se estiver desatualizado — determinismo do build.
  • USER app: o processo não roda como root. Custa duas linhas e remove uma classe inteira de impacto em caso de invasão.
  • PYTHONUNBUFFERED=1: logs saem sem buffer, porque em container o log é stdout — quem captura é a plataforma. Arquivo de log dentro do container morre com ele.
  • HEALTHCHECK: o orquestrador precisa distinguir "processo vivo" de "app saudável" — o endpoint /health responde isso (os testes do laboratório o verificam).
  • .dockerignore (sempre, junto): .git, .venv, .env, __pycache__, tests/. Sem ele, um .env com segredos entra na imagem — e imagem é arquivável, inspecionável e frequentemente pública.

Compose: o ambiente inteiro, declarado #

Exemplo de referência — corresponde ao compose.yml do laboratório:

# compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: shortener
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data      # dados sobrevivem ao container
    networks: [shortnet]
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    build: .
    ports: ["8000:8000"]
    environment:
      APP_DATABASE_URL: postgresql+asyncpg://postgres:dev@db:5432/shortener
    depends_on:
      db:
        condition: service_healthy           # espera SAUDÁVEL, não só "subiu"
    networks: [shortnet]

volumes:
  pgdata:

networks:
  shortnet:

Três mecânicas para entender de verdade:

  • Rede e DNS: o Compose cria uma rede onde cada serviço é hostname — repare na URL: @db:5432, não @localhost. Dentro da rede, o nome do serviço resolve; localhost dentro do container é o próprio container.
  • Volume e rede nomeados: container é descartável; o volume pgdata é onde o dado persiste — sem ele, cada down apaga o banco. A rede shortnet declara o isolamento; a limpeza do laboratório só atinge esses recursos nomeados.
  • depends_on + service_healthy: "depois de" não é "pronto" — a API esperar o healthcheck do Postgres elimina o ConnectionRefused da corrida de inicialização.

Leitura aplicada: do build à degradação #

  1. O build copia manifests antes do código: enquanto pyproject/uv.lock não mudam, as camadas de dependência vêm do cache e só o código rebuilda. Tocar um arquivo de src/ e rebuildar mostra isso no log.
  2. A imagem final não contém ferramentas de build, roda como usuário app e não contém .env — três fatos verificáveis por inspeção, e o laboratório os verifica sem precisar executar nada.
  3. compose up sobe o Postgres primeiro; só quando o healthcheck acusa healthy a API sobe e aplica alembic upgrade head. GET /health responde o estado; com o banco parado, a API degrada com erro claro em vez de travar.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável — build, inspeção, subida, migrations no ambiente e observação da degradação — fica no Laboratório guiado M03, depois do bloco 8. Sem Docker Engine, a execução fica marcada como bloqueada e os oráculos estáticos verificam os artefatos.

Síntese do bloco 5
  • Imagem = pacote imutável em camadas; container = instância; cache por camada de cima para baixo leva manifests antes do código.
  • Multi-stage: build fica no builder, produção leva só runtime. Menor, mais rápido, menos superfície.
  • Não-root, log em stdout sem buffer, healthcheck de app (não de processo), .dockerignore sempre — segredo nunca entra na imagem.
  • Compose: serviços por nome na rede interna, volume para dados, service_healthy contra corrida de boot, limpeza só em recursos nomeados.
  • O ambiente inteiro é um arquivo versionado: mesma API, mesmo banco, mesma rede em qualquer máquina com Docker.

    app.dependency_overrides.clear()

A arquitetura das fixtures: pg_url caro e compartilhado pela sessão; schema criado uma vez por migration; cada teste recebe fábrica e cliente sobre o banco descartável; o teardown descarta o engine. O isolamento entre testes vem da transação-envelope — o teste roda dentro de uma transação que sofre rollback no teardown, sem recriar schema a cada teste. O cliente injeta a sessão de teste na API real via dependency_overrides.

Fundamento · O que faz um teste de integração ser bom
  • Isolamento: teste não depende de ordem nem de resíduo de outro teste. Teste que só passa rodando a suíte inteira é dívida.
  • Determinismo: relógio, aleatoriedade e rede são as três fontes de teste instável. Este lab elimina duas pela construção: o slug é entrada explícita (nenhum gerador aleatório no caminho) e nenhum teste depende da hora atual. Teste instável é pior que ausência de teste, porque ensina a ignorar vermelho.
  • Teste pela interface pública: chame a API (o client), não o repository por dentro — refatoração interna (bloco 4) não deve quebrar teste. Teste acoplado a implementação é âncora, não rede.
  • Pirâmide: integração cobre fluxos e fronteiras; a combinatória de regras fica nos unitários. Suíte de integração que ninguém roda porque demora protege menos que uma rápida que roda em todo commit.

Leitura aplicada: o que cada teste de integração prova #

  1. Criação e busca pela API (201/200), inexistente (404), URL inválida (422), duplicata (409): o contrato HTTP contra persistência real.
  2. Isolamento: dois testes criam o mesmo slug fixo em sequência e ambos passam — o rollback do envelope apagou o primeiro antes do segundo.
  3. Lost update resolvido: N increments concorrentes com sessões próprias totalizam exatamente N no update atômico.
  4. Migration como setup: o schema do banco de teste nasce de alembic upgrade head, então a suíte quebra se uma revision estiver inconsistente.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável fica no Laboratório guiado M03, depois do bloco 8. Sem Docker Engine, a execução fica marcada como bloqueada; a indisponibilidade do banco (erro observável com cleanup) tem oráculo parcial executável sem Docker no lab.

Síntese do bloco 6
  • Fronteira honesta: lógica pura em unitário; atravessou o banco, PostgreSQL real descartável. Simulação de ORM não prova integração.
  • Três fixtures: container por sessão, schema por migration, cliente ASGI com override de dependência; isolamento por transação-envelope.
  • Determinismo por construção: entradas explícitas, sem relógio nem aleatoriedade no caminho testado.
  • Concorrência se testa com sessões próprias e total exato — não se discute.

Bloco 7 · CI, imagem imutável e contrato de release

Por que isso importa #

Até aqui os gates (lint, tipos, testes) rodam na máquina de quem lembra de rodá-los. CI os promove a lei: todo push, todo pull request, sem exceção, numa máquina que não é a sua. E release fecha o ciclo: a mesma imagem verificada, endereçada por revisão imutável, com migrations aplicadas antes de promover e rollback ensaiado. Nada neste bloco exige conta externa: qualidade, imagem e contrato de release são locais e versionados; publicação externa é trilha opcional.

Contexto · GitHub Actions em 90 segundos

CI nativo do GitHub. Um workflow é um YAML em .github/workflows/; dispara por evento (push, pull_request); contém jobs (cada um numa máquina efêmera); cada job tem steps que rodam shell (run:) ou invocam actions reutilizáveis (uses:). Segredos ficam no cofre do repositório, expostos como ${{ secrets.NOME }} e mascarados no log — nunca em código, imagem ou saída.

Contexto e saída #

Pré-requisitos: blocos 1–6 (gates locais e suíte com e sem Docker). Objetivo: reproduzir os gates locais em workflow versionado, endereçar a imagem por revisão imutável e registrar o contrato de release (migrations, segredos, rollback). Saída observável: você explica o encadeamento qualidade → imagem, por que o PR não recebe caminho de deploy e quais são as três perguntas que todo release responde antes de existir.

O pipeline do laboratório #

Exemplo de referência — corresponde a .github/workflows/ci-m03.yml do repositório e a scripts/check.sh do lab (o equivalente local):

# .github/workflows/ci-m03.yml (referência)
name: ci-m03

on:
  push:
    paths: ["modulos/M03-fastapi-postgres-docker-ci/**"]
  pull_request:
    paths: ["modulos/M03-fastapi-postgres-docker-ci/**"]

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4
      - run: uv sync --frozen
        working-directory: modulos/M03-fastapi-postgres-docker-ci/lab
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run mypy src tests
      - run: uv run pytest -q
      # o runner tem Docker: a suíte postgres executa; sem Docker ela pula BLOCKED

  build-image:
    needs: quality
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    permissions:
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/build-push-action@v6
        with:
          context: modulos/M03-fastapi-postgres-docker-ci/lab
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:${{ github.sha }}

As decisões que importam:

  • needs: encadeia gates: imagem só existe se qualidade passou. O check.sh local executa os mesmos comandos — paridade dev↔CI; divergência entre os dois é onde defeito se esconde.
  • PR verifica, main endereça: o job de build só roda na main (if: github.ref == ...); nenhum caminho de deploy nem segredo de produção aparece no contexto de pull request.
  • Tag pela SHA além de latest: cada commit tem imagem imutável endereçável — é isso que torna rollback uma operação (redeployar a SHA anterior), não uma esperança.
  • Lock preservado: uv sync --frozen falha se o lock divergir — a imagem sempre corresponde ao lock revisado.
Migrations no release — a decisão que separa deploy de incidente

Nunca criar schema com create_all no startup em produção e nunca deixar a migration para "depois". O padrão é o comando de release: alembic upgrade head roda num passo efêmero ANTES de promover a versão nova. Se a migration falha, o release aborta e a versão anterior segue no ar. Combine com a regra do bloco 2 (migration compatível com a versão anterior — expandir/contrair em duas releases) e o banco deixa de ser o ponto sem volta.

Fundamento · Configuração, segredos e as três perguntas de release
  • Mesma imagem, configuração no ambiente: o que muda entre dev e produção é injetado, não rebuildado. Se trocar de ambiente exige rebuildar, o desenho está errado. Configuração obrigatória ausente deve falhar cedo e alto — e a mensagem de falha nunca revela o valor do segredo.
  • Segredo nunca em: código, imagem, log. Só no cofre da plataforma. O .dockerignore do bloco 5 e o mascaramento do CI são as redes; a disciplina é sua.
  • As três perguntas que todo release responde ANTES de existir: (1) como sei que quebrou? (health check + logs); (2) como volto? (redeploy da SHA anterior + downgrade compatível — ensaiado, não teórico); (3) o banco volta junto? (downgrade testado ou expandir/contrair). Sem as três respostas, não é release — é aposta.

Trilha opcional · Publicação externa #

Publicar o encurtador numa plataforma (PaaS com suporte a container e Postgres, qualquer fornecedor) é trilha opcional e não condiciona a aprovação do módulo. Quem a percorrer registra no contrato de release: ambiente, revisão publicada, método de rollback ensaiado e limite do ensaio. Conta, cartão e URL pública ficam fora do caminho obrigatório — por isso o laboratório nunca os exige.

Leitura aplicada: do push ao rollback #

  1. Um push abre o workflow: checkout, uv sync --frozen, lint, formato, tipos, testes. Quebrar um tipo propositalmente mostra o vermelho antes do merge — o gate mecânico do bloco 4, agora institucional.
  2. Na main, a imagem é construída e endereçada pela SHA do commit. A mesma SHA que passou nos testes é a que seria publicada: nada é rebuildado entre verificação e release.
  3. O release aplica migrations antes de promover; a versão anterior segue disponível pelo endereço imutável. Rollback é redeploy + downgrade compatível, com o tempo ensaiado anotado no contrato.

Este percurso é leitura: nenhum comando é executado aqui. O roteiro executável — workflow, script local equivalente, build do wheel e contrato de release — fica no Laboratório guiado M03, depois do bloco 8.

Síntese do bloco 7
  • CI é o gate local como lei: todo push, máquina neutra, needs encadeando qualidade → imagem.
  • Imagem imutável por SHA: rollback auditável. PR verifica, main endereça; segredo de produção nunca aparece no PR.
  • Release aplica migration antes de promover; create_all nunca cria schema em produção.
  • Mesma imagem, configuração no ambiente, falha cedo sem vazar segredo — e as três perguntas respondidas antes do release.
  • Publicação externa é trilha opcional registrada, não requisito.

Bloco 8 · Operação local: saúde, correlação e fechamento

Por que isso importa #

Serviço sem saúde observável é caixa-preta: quando algo degrada, ninguém sabe se o processo vive, se o banco responde ou qual request falhou. Este bloco fecha o módulo ligando três fios — um endpoint de saúde que verifica o banco de verdade, correlação que atravessa request e resposta, e degradação que vira erro estruturado em vez de travamento. Tudo local, tudo sem conta externa.

Contexto e saída #

Pré-requisitos: blocos 1–7. Objetivo: expor saúde com checagem de banco, propagar correlation id e degradar com sinal observável. Saída observável: você explica o que /health verifica, onde o correlation id nasce e é preservado, e por que a indisponibilidade do banco vira 503 estruturado em vez de timeout silencioso.

Saúde que verifica, não que finge #

Há duas saúdes diferentes e o laboratório separa as duas. A do processo (o HEALTHCHECK do Dockerfile) pergunta "o servidor HTTP responde". A do serviço (GET /health do app) executa select 1 no banco: 200 com {"status":"ok"} quando alcança, 503 com Problem Details quando não alcança — incluindo o caso em que o banco cai com a API no ar. Por que não trava: a sessão é aberta com o pool, a falha vira exceção capturada na borda, a sessão é encerrada e a resposta sai com status e corpo explícitos. O detalhe nunca vaza segredo nem stack trace — só o tipo do erro e a ação ("verifique a conexão").

Correlação de ponta a ponta #

O middleware do bloco 1 agora mora no app: preserva x-request-id quando o cliente envia um UUID válido, cria um quando ausente ou forjado. Toda resposta — 201, 409, 404, 422, 503 — carrega o id e o tempo decorrido. Na operação, isso significa que um 503 no log do cliente e uma entrada no log do servidor se encontram pelo mesmo id. É a semente da observabilidade do M06, plantada aqui com um middleware de vinte linhas.

Contraste: saúde de enfeite
  • /health que devolve ok sem tocar no banco declara saudável um serviço que não atende nada — o orquestrador mantém tráfego numa API morta.
  • Erro 500 com stack trace entrega ao cliente detalhes internos e nenhum id para o operador correlacionar.
  • Timeout sem limite segura worker e conexão até o cliente desistir; degradação com sinal libera os dois na hora.
Síntese do bloco 8
  • Saúde em dois níveis: processo (responde HTTP) e serviço (alcança o banco). Só a segunda autoriza tráfego.
  • Correlation id em toda resposta: preservado se válido, criado se ausente ou forjado.
  • Indisponibilidade vira 503 estruturado com sessão encerrada — degradação com sinal, nunca travamento.
  • Configuração ausente falha na construção, com mensagem que não ecoa segredos.
