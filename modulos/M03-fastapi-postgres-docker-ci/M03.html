Bloco 1 · FastAPI: rotas, Depends, middleware, lifespan

00:00–00:20 o mapa ASP.NET → FastAPI  |  00:20–01:00 rotas e a mágica dos type hints  |  01:00–01:35 Depends: a DI por função  |  01:35–02:00 middleware, lifespan e prática

Por que isso importa

FastAPI é o framework HTTP dominante do Python para APIs — e o motivo de ele ter vencido é uma ideia só: reutilizar os type hints que você já escreve (M02) como fonte de roteamento, validação, serialização e documentação. Você declara async def criar(dto: DocumentoCreate) -> DocumentoOut: e o framework extrai disso o binding, a validação Pydantic (com 422 estruturado), o schema OpenAPI e o Swagger UI. Nada de atributos [FromBody], nada de configuração de Swashbuckle: a assinatura É a configuração.

Contexto · ASGI e uvicorn — quem segura o socket

ASGI (Asynchronous Server Gateway Interface) é o contrato entre servidores HTTP e frameworks async do Python — o papel que o par Kestrel↔pipeline cumpre no ASP.NET, só que padronizado entre frameworks. uvicorn é o servidor ASGI que você vai usar: ele aceita as conexões, fala HTTP, e entrega cada request ao FastAPI como uma corrotina no event loop (o MESMO loop único do M02 bloco 4 — toda a teoria de lá vale aqui, request a request). Em produção, roda-se uvicorn com múltiplos workers (processos), cada um com seu loop: uvicorn app:app --workers 4 ≈ 4 cópias do seu app atrás do mesmo socket.

A gramática essencial, num arquivo

from contextlib import asynccontextmanager
from collections.abc import AsyncIterator
from typing import Annotated

from fastapi import Depends, FastAPI, HTTPException, status
from pydantic import BaseModel, Field


class LinkIn(BaseModel):
    url: str = Field(min_length=8, pattern=r"^https?://")


class LinkOut(BaseModel):
    slug: str
    url: str


@asynccontextmanager
async def lifespan(app: FastAPI) -> AsyncIterator[None]:
    # startup: abrir pool de conexões, aquecer cache... (bloco 2 usa de verdade)
    print("subindo")
    yield
    # shutdown: fechar pool, drenar filas
    print("descendo")


app = FastAPI(title="Shortener", lifespan=lifespan)

_fake_db: dict[str, str] = {}          # até o bloco 2 chegar com Postgres


def get_repo() -> dict[str, str]:      # a "dependência" — troque por sessão de banco depois
    return _fake_db


Repo = Annotated[dict[str, str], Depends(get_repo)]   # alias reutilizável


@app.post("/links", response_model=LinkOut, status_code=status.HTTP_201_CREATED)
async def criar_link(body: LinkIn, repo: Repo) -> LinkOut:
    slug = hex(abs(hash(body.url)))[2:10]
    repo[slug] = body.url
    return LinkOut(slug=slug, url=body.url)


@app.get("/links/{slug}", response_model=LinkOut)
async def obter_link(slug: str, repo: Repo) -> LinkOut:
    if slug not in repo:
        raise HTTPException(status_code=404, detail="slug não encontrado")
    return LinkOut(slug=slug, url=repo[slug])

Depends: a DI que é função, não container

A diferença conceitual para o IServiceCollection: não há registro central nem grafo resolvido no boot. Cada parâmetro com Depends(f) executa f por request, e f pode por sua vez depender de outras funções — o grafo é implícito e por endpoint. Três consequências práticas:

  • Escopo por request é o default natural. A dependência com yield é o scoped + Dispose: setup antes, teardown depois — é assim que a sessão de banco vai abrir/commitar/fechar no bloco 2 (compare com o AddDbContext scoped).
  • Override em teste é trivial: app.dependency_overrides[get_repo] = get_repo_fake — sem container de teste, sem builder (bloco 6 usa).
  • Autenticação/autorização são dependências também (uma função que lê o header, valida o token e devolve o usuário — ou levanta 401). O M12 constrói isso; a mecânica é a mesma do get_repo.
Fundamento de engenharia · HTTP e REST — a reciclagem que o Swagger não faz por você

O framework automatiza o transporte, não o DESIGN. Recicle o que separa API sênior de API que funciona por acaso:

  • Semântica dos verbos e idempotência: GET/PUT/DELETE são idempotentes (repetir = mesmo efeito), POST não. Isso não é pedantismo: retry automático (do seu gateway do M05, do load balancer, do agente do M08) SÓ é seguro sobre operação idempotente. API que faz POST não-idempotente sem chave de idempotência é a fonte da dupla cobrança do M12.
  • Status codes como contrato: 400 (request mal-formado) ≠ 404 (não existe) ≠ 409 (conflito de estado) ≠ 422 (bem-formado, semanticamente inválido — o que o Pydantic devolve) ≠ 500 (culpa SUA). Cliente e agente decidem retry/fallback pelo código — errar o código é quebrar o contrato de erro.
  • Erros num formato só: padronize (RFC 9457, Problem Details — o mesmo do ASP.NET) com exception_handler. Erro estruturado é o fator 9 do M01 aplicado a HTTP.
  • Versionamento e compatibilidade: campo novo opcional = seguro; remover/renomear = quebra. Some com o extra="forbid" do M02 e você tem contratos que evoluem sem sustos.

Middleware e o pipeline

import time
import uuid

from fastapi import Request, Response


@app.middleware("http")
async def request_id_e_tempo(request: Request, call_next) -> Response:  # type: ignore[no-untyped-def]
    rid = request.headers.get("x-request-id", str(uuid.uuid4()))
    inicio = time.perf_counter()
    response = await call_next(request)            # o resto da cebola
    response.headers["x-request-id"] = rid
    response.headers["x-elapsed-ms"] = f"{(time.perf_counter() - inicio) * 1000:.1f}"
    return response

Mesma cebola do ASP.NET: o que vem antes do call_next roda na ida, o que vem depois roda na volta, e a ordem de registro importa. O x-request-id que você acabou de propagar é a semente da observabilidade do M06 — um request rastreável do edge ao banco.

Bloco 2 · SQLAlchemy 2.0 async + Alembic

Por que isso importa

SQLAlchemy 2.0 é o EF Core do Python — ORM maduro, tipado e, desde a 2.0, async de primeira classe. Alembic é o Migrations. A boa notícia: o modelo mental transfere quase inteiro (DbContext→Session, DbSet→select, migrations→revisions). A má: as diferenças são sutis e ficam exatamente onde async encontra lazy loading — o erro MissingGreenlet que TODO dev .NET encontra na primeira semana. Este bloco te faz encontrá-lo de propósito, com o antídoto na mão.

Modelos e engine — o setup canônico

# src/shortener/db.py
from collections.abc import AsyncIterator
from datetime import datetime

from sqlalchemy import DateTime, String, func
from sqlalchemy.ext.asyncio import (
    AsyncSession, async_sessionmaker, create_async_engine,
)
from sqlalchemy.orm import DeclarativeBase, Mapped, mapped_column

from shortener.settings import settings          # pydantic-settings do M02

engine = create_async_engine(settings.database_url, pool_size=10, echo=False)
SessionLocal = async_sessionmaker(engine, expire_on_commit=False)


class Base(DeclarativeBase):
    pass


class Link(Base):
    __tablename__ = "links"

    id: Mapped[int] = mapped_column(primary_key=True)
    slug: Mapped[str] = mapped_column(String(16), unique=True, index=True)
    url: Mapped[str] = mapped_column(String(2048))
    hits: Mapped[int] = mapped_column(default=0)
    created_at: Mapped[datetime] = mapped_column(
        DateTime(timezone=True), server_default=func.now()
    )


async def get_session() -> AsyncIterator[AsyncSession]:
    """A dependência com yield: escopo de request, commit no sucesso, rollback no erro."""
    async with SessionLocal() as session:
        try:
            yield session
            await session.commit()
        except Exception:
            await session.rollback()
            raise

Repare em três decisões que valem discussão de code review:

  • expire_on_commit=False: por padrão o SQLAlchemy "expira" objetos após commit (próximo acesso recarrega do banco — mais um round-trip async escondido). Em API, você quer devolver o objeto que acabou de salvar sem nova query.
  • Pool no engine, sessão por request: o engine (e seu pool de conexões) é singleton do processo; a AsyncSession é scoped — exatamente como AddDbContext/AddDbContextPool.
  • Commit na dependência, não no endpoint: o endpoint declara a intenção; a fronteira transaciona. É o padrão unit-of-work-por-request — igual ao middleware de transação que você já escreveu em ASP.NET.
A pegadinha nº 1: lazy loading não existe em async

No EF, acessar pedido.Cliente não carregado dispara query silenciosa (N+1, mas funciona). No SQLAlchemy async, o acesso lazy fora de contexto async explode com MissingGreenlet — o ORM não pode fazer I/O síncrono no meio do seu event loop (M02 bloco 4 explica exatamente por quê!). O antídoto é declarar o carregamento na query: select(Pedido).options(selectinload(Pedido.itens)). Isso é um RECURSO disfarçado de dor: o N+1 que no EF era silencioso aqui é impossível de ignorar — o custo de I/O fica explícito no código.

Fundamento de engenharia · ACID e isolamento — a reciclagem de 10 anos de "o EF resolvia"
  • Atomicidade você usa via commit/rollback da dependência acima. Durabilidade é do Postgres. As que exigem o SEU cérebro: Consistência (constraints! unique=True no slug é a única garantia real contra duplicata — checagem em código tem race condition entre o SELECT e o INSERT) e Isolamento.
  • Isolamento na prática: Postgres default é READ COMMITTED — duas transações concorrentes incrementando hits com "ler, somar 1, gravar" PERDEM updates (lost update). Consertos, do mais simples ao mais forte: update atômico no banco (UPDATE links SET hits = hits + 1 — deixe o banco somar), SELECT ... FOR UPDATE (lock pessimista), ou coluna de versão (lock otimista, o RowVersion do EF). Você vai PROVAR o lost update no bloco 6, com teste.
  • Transação curta é regra de ouro: transação aberta atravessando chamada de LLM de 2 segundos (M05!) = conexão presa, pool esgotado, API morta. Transacione o banco, não o workflow.

Alembic: migrations com contrato

uv add alembic
uv run alembic init -t async migrations   # template async: env.py já preparado

Configure uma vez (em migrations/env.py): aponte target_metadata = Base.metadata e leia a URL do seu Settings. Daí o ciclo é o do EF:

uv run alembic revision --autogenerate -m "create links table"
# REVISE o arquivo gerado em migrations/versions/ — autogenerate erra rename
# (vê drop+add), não vê mudança de server_default, e não escreve backfill.
uv run alembic upgrade head

Regras de sênior que valem dobrado com agentes gerando migrations: (1) migration é código revisado, nunca "confia no autogenerate"; (2) todo upgrade tem downgrade testado — rollback de deploy depende dele (bloco 7); (3) migration destrutiva (drop de coluna com dado) é um processo em 2 releases: parar de usar → depois dropar. Deploy sem downtime agradece.

Síntese do bloco 2
  • AsyncSession = DbContext (UoW + tracking, escopo request via dependência com yield; commit na fronteira).

Bloco 3 · Postgres para valer: índices, EXPLAIN, transações, JSONB

00:00–00:30 índices e o modelo mental de custo  |  00:30–01:05 EXPLAIN ANALYZE: ler o plano  |  01:05–01:40 JSONB e por que ele salva produto de IA  |  01:40–02:00 prática de medição

Por que isso importa

Você usou SQL Server por dez anos, mas — seja honesto — quantas vezes o DBA resolveu? No mundo para onde você está indo não há DBA: você é o DBA. E o Postgres é o banco do ecossistema de IA por um motivo composto: é excelente banco relacional E, com JSONB + pgvector (M07), elimina duas peças de infraestrutura (document store e vector store) que você teria que operar separadamente. Este bloco te dá o kit de sobrevivência: prever custo de query, ler um plano de execução e usar JSONB sem transformar o banco num pântano sem schema.

Fundamento de engenharia · Índices — a reciclagem do que o DBA sabia
  • B-tree é o default e serve para =, <, >, ORDER BY, prefixo de LIKE. Pense numa árvore de busca: O(log n) para achar, mas cada INSERT/UPDATE paga a manutenção de TODOS os índices da tabela. Índice não é grátis — é troca de escrita por leitura.
  • Índice composto (a, b) serve consultas por (a) e (a,b) — não por (b). A ordem das colunas segue a seletividade E o padrão de consulta. É o mesmo do SQL Server; só recicle.
  • Índice parcial (WHERE status = 'active') e índice de expressão (ON lower(email)) são as armas subusadas — indexam só o que se consulta, mantendo-os pequenos.
  • Seletividade decide tudo: índice em coluna com 3 valores distintos raramente compensa (o planner vai de seq scan mesmo); em coluna quase-única, quase sempre. O planner usa estatísticas (ANALYZE) — estatística velha = plano ruim.
  • GIN é o índice para conteúdo "dentro" da coluna: arrays, full-text e JSONB (abaixo). B-tree acha A LINHA; GIN acha O QUE HÁ NELA.

EXPLAIN ANALYZE: o raio-X que você vai rodar toda semana

EXPLAIN (ANALYZE, BUFFERS)
SELECT * FROM links WHERE slug = 'abc123';

Como ler o resultado, de baixo para cima (nós internos consomem filhos):

Index Scan using ix_links_slug on links  (cost=0.29..8.31 rows=1 width=64)
                                          (actual time=0.041..0.043 rows=1 loops=1)
  Index Cond: (slug = 'abc123'::text)
Planning Time: 0.180 ms
Execution Time: 0.071 ms
  • cost=0.29..8.31: estimativa do planner (startup..total, em unidades abstratas). actual time: a realidade, em ms. Quando estimativa e realidade divergem muito (rows estimado 1, real 80.000), o problema é estatística — ANALYZE tabela;.
  • Os quatro nós que resolvem 90% das leituras: Seq Scan (leu a tabela inteira — ok em tabela pequena, alarme em grande), Index Scan (foi pela árvore), Index Only Scan (respondeu SÓ com o índice — o covering index), Nested Loop / Hash Join (como o join foi feito; nested loop com loops=50000 é o N+1 do plano).
  • BUFFERS mostra páginas lidas de cache (shared hit) vs. disco (read) — a diferença entre 2 ms e 200 ms da mesma query.

JSONB: por que ele salva produto de IA

Produto de IA produz dado semi-estruturado o tempo todo: resposta de LLM com campos que variam por versão de prompt, metadados de execução (modelo, tokens, custo, latência), configurações por tenant. Modelar cada variação como coluna = migration por semana; jogar tudo num document store = perder joins, transações e o resto do seu modelo relacional. JSONB é a terceira via: colunas relacionais para o que é estável e consultado sempre; UMA coluna JSONB para a cauda variável — indexável com GIN, consultável com operadores:

-- o padrão do Capstone: núcleo relacional + cauda flexível
CREATE TABLE analises (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    tenant_id   bigint NOT NULL REFERENCES tenants(id),
    status      text   NOT NULL DEFAULT 'pending',
    custo_cents int    NOT NULL DEFAULT 0,
    resultado   jsonb  NOT NULL DEFAULT '{}'::jsonb,   -- a cauda variável
    created_at  timestamptz NOT NULL DEFAULT now()
);

CREATE INDEX ix_analises_resultado ON analises USING gin (resultado);

-- operadores que você vai usar:
SELECT resultado->>'modelo' FROM analises;                     -- extrai como texto
SELECT * FROM analises WHERE resultado @> '{"modelo": "gpt"}'; -- contém (usa o GIN!)
SELECT * FROM analises WHERE resultado ? 'warnings';           -- tem a chave?
Tradução .NET

JSONB ≈ a coluna nvarchar(max) com JSON do SQL Server, MAS: binário decomposto (não re-parseia a cada consulta), com operadores nativos e índice GIN que torna @> tão rápido quanto um WHERE indexado. No EF você usava OwnsOne().ToJson(); aqui o SQLAlchemy mapeia Mapped[dict[str, Any]] = mapped_column(JSONB) — e o Pydantic (M02) valida a forma na fronteira da aplicação, que é onde schema de JSONB deve morar. Regra de sênior: o que você consulta/filtra/agrega em TODA query vira coluna; o que varia por caso fica no JSONB. JSONB de 50 KB por linha consultado por chave única é design errado — é um document store fingindo ser tabela.

Prática guiada · Medir, não achar (35 min)

1Povoe massa de teste — 500 mil links falsos direto no banco (SQL puro é a ferramenta certa para seed em massa): 
docker exec -it pg-shortener psql -U postgres -c "
INSERT INTO links (slug, url, hits, created_at)
SELECT md5(g::text), 'https://exemplo.com/' || g,
       (random()*1000)::int, now() - (g || ' seconds')::interval
FROM generate_series(1, 500000) g;"

Resultado esperado: INSERT 0 500000 em poucos segundos. generate_series é o gerador de massa nativo — guarde-o.

2Compare os planos. Rode EXPLAIN (ANALYZE, BUFFERS) para: (a) busca por slug (indexado); (b) busca por url (não indexado); (c) ORDER BY created_at DESC LIMIT 20 (não indexado).

Resultado esperado: (a) Index Scan, <0,1 ms; (b) Seq Scan (possivelmente Parallel), dezenas/centenas de ms varrendo 500k linhas; (c) Seq Scan + Sort — o pior padrão de "listagem recente" sem índice. Anote os três tempos.

3Conserte com índice e re-meça: 
CREATE INDEX ix_links_created_at ON links (created_at DESC);

Resultado esperado: a query (c) cai para Index Scan de ~1 ms — centenas de vezes mais rápido. Agora meça o custo do outro lado: \timing on e um INSERT único antes/depois de criar mais 3 índices dummy — a escrita fica mensuravelmente mais lenta. Você acabou de ver a troca leitura×escrita em números.

4JSONB com GIN: adicione (via Alembic! pratique o ciclo) a coluna meta jsonb em links, povoe {"origem": "api", "campanha": "c" || (g % 50)} para todos, e compare WHERE meta @> '{"campanha":"c7"}' sem e com o índice GIN.

Resultado esperado: Seq Scan de centenas de ms → Bitmap Index Scan de poucos ms. E o aprendizado de processo: a migration da coluna + índice passou pelo Alembic com downgrade escrito, como manda o bloco 2.

Síntese do bloco 3
  • Sem DBA: você prevê custo (B-tree, composto, parcial, GIN), lê plano (Seq vs Index vs Index-Only, estimado vs real) e mede com BUFFERS.
  • Índice troca escrita por leitura; seletividade decide se compensa; estatística velha = plano ruim.
  • JSONB = núcleo relacional + cauda variável indexável. O que se consulta sempre vira coluna; schema do JSON mora no Pydantic.
  • Postgres é o banco do curso porque JSONB hoje + pgvector no M07 = menos infraestrutura para operar.
  • Reflexo novo: query nova em tabela grande → EXPLAIN antes do deploy, não depois do incidente.

Bloco 4 · Estrutura que escala: api/ core/ services/ repositories/

00:00–00:25 por que não é MVC  |  00:25–01:00 as camadas e as regras de import  |  01:00–01:40 prática: reestruturar o encurtador  |  01:40–02:00 onde a IA encaixa nisso

Por que isso importa

Até aqui o encurtador vive em dois arquivos — ótimo para aprender, péssimo para crescer. Este bloco define a estrutura que o Capstone usa até o fim do curso. Ela importa DOBRADO na era dos agentes: estrutura previsível é context engineering — um agente acha o lugar certo de mexer num projeto bem estruturado com um décimo do contexto que gasta num monolito de arquivos gigantes. A spec do M01 dizia "restrições de camada"; este bloco é onde elas ganham forma física.

A estrutura e o contrato de cada pasta

src/app/
├── api/                # HTTP: routers, DTOs de request/response, dependências
│   ├── routers/        #   um arquivo por recurso: links.py, health.py
│   └── deps.py         #   Depends compartilhados (sessão, auth, paginação)
├── core/               # o "kernel": settings, erros de domínio, logging
├── models/             # entidades SQLAlchemy (o schema do banco)
├── schemas/            # contratos Pydantic (a fronteira — M02 bloco 3)
├── services/           # regra de negócio: orquestra repos, decide, transaciona
├── repositories/       # acesso a dados: queries SQLAlchemy, NADA de regra
└── workers/            # jobs assíncronos fora do ciclo request/response

O que cada camada PODE importar é o contrato inteiro — desenhe a seta e ela só aponta para baixo:

  • api importa services e schemas. NUNCA repositories direto (a tentação vai aparecer no CRUD simples; resista — o dia que o CRUD ganhar regra, ela terá lugar) e NUNCA models (entidade de banco não vaza para HTTP — o campo tenant_id exposto por preguiça é o vazamento do M12).
  • services importa repositories, models, schemas, core. É o único lugar com decisão de negócio; recebe e devolve tipos de domínio, não Request/Response — service que importa FastAPI está vazando HTTP para dentro.
  • repositories importa models e core. Query e persistência, zero regra ("se status for X então..." em repository é regra fugida de casa).
  • core não importa NINGUÉM das camadas acima. É a base da pirâmide.
Tradução .NET

É a sua Clean/Onion Architecture de sempre — Api/Application/Domain/Infrastructure — com duas diferenças pragmáticas do mundo Python: (1) sem projetos separados nem .sln: a fronteira é convenção de import, não fronteira de assembly — e por isso o lint (import-linter, ou as regras de isolamento do ruff) assume o papel que o compilador fazia de graça; (2) menos interface cerimonial: repository é classe concreta; quando precisar de dublê, o Protocol (M02) define o contrato NO CONSUMIDOR — sem projeto Abstractions, sem 40 interfaces de um método.

Fundamento de engenharia · Coesão, acoplamento e a Dependency Rule — a reciclagem
  • Coesão alta: o que muda junto, mora junto. Acoplamento baixo: o que muda separado, depende pouco. Toda arquitetura em camadas é só isso operacionalizado.
  • Dependency Rule (Clean Architecture): dependências apontam para dentro — o domínio não conhece o HTTP nem o banco. O par api→service→repository é a versão pragmática; a versão purista (domínio sem NENHUMA dependência) você adota quando o custo se justificar. Saber ONDE relaxar a regra é o que diferencia sênior de fanático.
  • Stable Dependencies Principle: dependa na direção do que é mais estável. core é o mais estável (muda pouco, todos dependem); api é o mais volátil (muda sempre, ninguém depende dele). Se você inverter — um core importando api — cada mudança de rota sacode a base inteira. Gancho: no M10 você vai CALCULAR isso (instabilidade I, abstratividade A, distância da main sequence) sobre o grafo real de um sistema — a régua numérica destes princípios.

Prática guiada · Reestruturar o encurtador (40 min)

Exercício de SDD completo — você vai usar o kit do M01, porque refatoração estrutural é exatamente onde agente sem spec destrói:

1Spec primeiro: docs/spec/005-restructure/ — o prd é curto (mover, não mudar comportamento: os testes atuais DEVEM passar sem edição); a spec técnica é a estrutura acima com as regras de import explícitas; o plan move uma camada por etapa (schemas → models+repositories → services → api), com bash check.sh + pytest como verificação de cada etapa.

Resultado esperado: sdd_check.py verde. Repare que "os testes passam sem edição" é o critério de refatoração honesta — se um teste precisou mudar, comportamento mudou.

2Execute com o agente, etapa por etapa. Na etapa dos services, a regra de negócio existente (gerar slug, tratar colisão) sai do router e vira LinkService.criar(url) -> Link; o router vira tradução HTTP pura (chama service, mapeia exceção de domínio para status code).

Resultado esperado por etapa: gate verde, commit atômico. Ao final, o api/routers/links.py tem ~30 linhas e zero import de sqlalchemy.

3Torne a regra mecânica (M01: inegociável vira exit code): uv add --dev import-linter e configure no pyproject: 
[tool.importlinter]
root_package = "app"

[[tool.importlinter.contracts]]
name = "layers"
type = "layers"
layers = ["app.api", "app.services", "app.repositories", "app.core"]

Adicione uv run lint-imports ao check.sh. Resultado esperado: tudo verde. Agora sabote: importe um repository dentro de um router e rode de novo — Contracts: 1 broken, exit code 1. A arquitetura agora tem guardrail: nem você às pressas, nem um agente confiante conseguem furá-la silenciosamente.

Síntese do bloco 4
  • api → services → repositories → core; setas só para baixo; models/schemas são vocabulário, não camada de passagem.
  • Entidade de banco não vaza para HTTP; regra de negócio mora em service; repository é query pura.
  • Em Python a fronteira é import — então o import vira lint com exit code (import-linter no check.sh).
  • Estrutura previsível é context engineering: agente acha o lugar certo com fração do contexto.
  • Coesão/acoplamento/estabilidade deixam de ser opinião no M10: viram métrica sobre o grafo.

Bloco 5 · Docker do zero: imagens, camadas, multi-stage, Compose

00:00–00:30 o modelo mental: imagem, camada, container  |  00:30–01:10 o Dockerfile de produção, linha a linha  |  01:10–01:45 Compose: o ambiente inteiro num arquivo  |  01:45–02:00 higiene e segurança

Por que isso importa

Este é o coração do seu gap de DevOps — e o bloco que faltava por inteiro na primeira versão deste material. Docker resolve o problema que você conhece como "funciona na minha máquina": empacota app + runtime + dependências do SO numa imagem imutável que roda idêntica no seu Windows, no CI e no servidor. Para o Capstone é inegociável: Postgres local sem instalar Postgres, deploy que é "envie a imagem", e (M09) distribuição do seu servidor MCP.

Contexto · Imagem, camada, container, registry — o vocabulário em 60 segundos
  • Imagem = o pacote imutável (pense: uma AMI/ISO minimalista, ou o zip de publish do .NET + o SO junto). Identificada por tag: postgres:16.
  • Camada = cada instrução do Dockerfile gera uma fatia somente-leitura, com hash. Imagens compartilham camadas — 10 apps sobre python:3.12-slim baixam a base UMA vez. Cache de build funciona por camada, de cima para baixo: mudou uma linha, tudo abaixo rebuilda. Esta frase explica 90% dos builds lentos.
  • Container = uma instância em execução da imagem (processo isolado por namespaces/cgroups do kernel — não é VM; por isso sobe em milissegundos). Imagem:container :: classe:objeto.
  • Registry = o NuGet de imagens: Docker Hub, GHCR. docker push/pull.

O Dockerfile de produção, linha a linha

Este é o arquivo do curso — cada linha tem um porquê, e o checkpoint cobra todos:

# ---------- estágio 1: builder (ferramentas de build ficam AQUI e morrem aqui)
FROM python:3.12-slim AS builder
COPY --from=ghcr.io/astral-sh/uv:latest /uv /bin/uv

WORKDIR /app
ENV UV_COMPILE_BYTECODE=1 UV_LINK_MODE=copy

# 1º: SÓ os manifests. Enquanto pyproject/uv.lock não mudarem,
# esta camada (a instalação inteira de dependências) vem do cache.
COPY pyproject.toml uv.lock ./
RUN uv sync --frozen --no-install-project --no-dev

# 2º: o código (muda toda hora, por isso vem DEPOIS das dependências)
COPY src/ src/
RUN uv sync --frozen --no-dev

# ---------- estágio 2: runtime (só o necessário para RODAR)
FROM python:3.12-slim AS runtime
WORKDIR /app

# usuário não-root: container invadido != root no host
RUN groupadd -r app && useradd -r -g app app

COPY --from=builder --chown=app:app /app/.venv /app/.venv
COPY --from=builder --chown=app:app /app/src /app/src

ENV PATH="/app/.venv/bin:$PATH" PYTHONUNBUFFERED=1
USER app
EXPOSE 8000

HEALTHCHECK --interval=15s --timeout=3s --retries=3 \
  CMD python -c "import urllib.request as u; u.urlopen('http://localhost:8000/health')"

CMD ["uvicorn", "app.api.main:app", "--host", "0.0.0.0", "--port", "8000"]

Os porquês que o checkpoint cobra:

  • Multi-stage (AS builder → FROM ... AS runtime): compiladores, headers e o próprio uv não vão para produção. Imagem menor = deploy mais rápido + superfície de ataque menor. Equivalente: a distinção SDK vs. runtime das imagens .NET.
  • Manifests antes do código: a ordem das camadas segue a frequência de mudança — deps mudam por semana, código por hora. Inverter a ordem = reinstalar tudo a cada build (o bug de performance nº 1 de Dockerfile).
  • --frozen: usa o uv.lock exato, falha se desatualizado — o restore determinístico atravessando o build.
  • USER app: processo não roda como root. Custa duas linhas; economiza um parágrafo no seu relatório de incidente.
  • PYTHONUNBUFFERED=1: logs saem na hora (sem buffer), porque em container log é stdout — quem captura é a plataforma (12-Factor App, fator XI: logs como stream de eventos; nada de escrever arquivo de log dentro do container, que morre com ele).
  • HEALTHCHECK: o orquestrador (Compose, e o deploy do bloco 7) precisa distinguir "processo vivo" de "app saudável" — o endpoint /health que você criará responde isso.
  • .dockerignore (crie junto, sempre): .git, .venv, .env, __pycache__, tests/. Sem ele, seu .env COM SEGREDOS entra na imagem — e imagem é arquivável, inspecionável e frequentemente pública. É o vazamento mais bobo e mais comum de 2026.

Compose: o ambiente inteiro, declarado

# docker-compose.yml
services:
  db:
    image: postgres:16
    environment:
      POSTGRES_PASSWORD: dev
      POSTGRES_DB: shortener
    ports: ["5432:5432"]
    volumes:
      - pgdata:/var/lib/postgresql/data      # dados sobrevivem ao container
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U postgres"]
      interval: 5s
      timeout: 3s
      retries: 5

  api:
    build: .
    ports: ["8000:8000"]
    environment:
      APP_DATABASE_URL: postgresql+asyncpg://postgres:dev@db:5432/shortener
    depends_on:
      db:
        condition: service_healthy           # espera SAUDÁVEL, não só "subiu"

volumes:
  pgdata:

Três mecânicas para entender de verdade:

  • Rede e DNS: o Compose cria uma rede onde cada serviço é hostname — repare na URL: @db:5432, não @localhost. Dentro da rede, o nome do serviço resolve; localhost dentro do container é O PRÓPRIO container (o erro clássico da primeira semana).
  • Volume: container é descartável; volume é onde dado persiste. Sem o pgdata, cada docker compose down apaga seu banco.
  • depends_on + service_healthy: "depois de" não é "pronto" — a API esperar o healthcheck do Postgres elimina o ConnectionRefused da corrida de inicialização.

Prática guiada · O encurtador containerizado (30 min)

1Escreva Dockerfile + .dockerignore + compose (adapte os acima; adicione o endpoint /health no router: devolve {"status":"ok"} e um SELECT 1 no banco).

Resultado esperado: docker build -t shortener . termina; docker images shortener mostra o tamanho — anote-o.

2Prove o valor do multi-stage: comente temporariamente o estágio runtime (build single-stage) e rebuilde com outra tag.

Resultado esperado: a imagem single-stage é visivelmente maior (tipicamente 1,5–3x). Volte ao multi-stage. Depois toque um arquivo de src/ e rebuilde: repare no log que as camadas de dependência vêm CACHED e só o código rebuilda — a ordem das camadas trabalhando.

3Suba tudo: 
docker compose up --build

Resultado esperado: o Postgres sobe primeiro, fica healthy, SÓ ENTÃO a API sobe. curl localhost:8000/health → {"status":"ok"}. Rode as migrations dentro do ambiente: docker compose exec api alembic upgrade head. POST/GET funcionam; docker compose down && up e os dados persistem (o volume).

4Mate e observe: docker compose stop db com a API no ar; bata no /health.

Resultado esperado: a API responde erro claro (500 com detail de conexão) e o healthcheck a marca unhealthy — degradação com sinal, não travamento. É o embrião do checkpoint do módulo.

Síntese do bloco 5
  • Imagem = pacote imutável em camadas; container = instância; cache por camada de cima para baixo → manifests antes do código.
  • Multi-stage: build fica no builder, produção leva só runtime. Menor, mais rápido, menos superfície.
  • Não-root, log em stdout (unbuffered), healthcheck de app (não de processo), .dockerignore SEMPRE (o .env fora da imagem!).
  • Compose: serviços por nome na rede interna, volume para dados, service_healthy contra corrida de boot.
  • O ambiente inteiro é um arquivo commitado — o fim do "roda na minha máquina".

Bloco 6 · Testes de integração com containers

00:00–00:25 unitário vs. integração: a fronteira honesta  |  00:25–01:00 a fixture de banco descartável  |  01:00–01:40 prática: a suíte do encurtador  |  01:40–02:00 o teste do lost update

Por que isso importa

O teste unitário do M02 prova a lógica pura. Mas o encurtador agora É integração: constraint de unicidade, transação, migration, JSON no banco. Mockar o SQLAlchemy para "testar" isso é teatro — o mock passa e a constraint que faltou explode em produção. A regra do curso: lógica pura testa com unitário; tudo que atravessa a fronteira do banco testa contra Postgres DE VERDADE, descartável, dentro do teste. Em 2026 isso é barato: um container sobe em segundos, e o CI (bloco 7) roda igualzinho.

Tradução .NET

É o padrão WebApplicationFactory + Testcontainers-dotnet que os times .NET maduros adotaram — a mesma ideia, com as mesmas decisões: banco real efêmero em vez de InMemoryDatabase (que mente sobre SQL, constraint e concorrência — o InMemory do EF ensinou essa lição a todo mundo da pior forma). Aqui: httpx.AsyncClient falando com o app via ASGI (sem porta! mais rápido e sem colisão) + testcontainers subindo o Postgres.

A fundação: três fixtures em camadas

# tests/conftest.py
from collections.abc import AsyncIterator, Iterator

import pytest
from httpx import ASGITransport, AsyncClient
from sqlalchemy.ext.asyncio import async_sessionmaker, create_async_engine
from testcontainers.postgres import PostgresContainer

from app.api.main import app
from app.api.deps import get_session
from app.models.base import Base


@pytest.fixture(scope="session")
def pg_url() -> Iterator[str]:
    """Um Postgres para a SESSÃO inteira de testes (subir custa ~3s; sobe 1x)."""
    with PostgresContainer("postgres:16", driver="asyncpg") as pg:
        yield pg.get_connection_url()


@pytest.fixture
async def db_session(pg_url: str) -> AsyncIterator[AsyncSession]:
    """Sessão POR TESTE, com isolamento por rollback: nada vaza entre testes."""
    engine = create_async_engine(pg_url)
    async with engine.begin() as conn:
        await conn.run_sync(Base.metadata.create_all)

    async with engine.connect() as conn:
        trans = await conn.begin()
        session = async_sessionmaker(bind=conn, expire_on_commit=False)()
        yield session
        await session.close()
        await trans.rollback()          # o teste inteiro é desfeito aqui
    await engine.dispose()


@pytest.fixture
async def client(db_session: AsyncSession) -> AsyncIterator[AsyncClient]:
    """API completa com o banco de teste injetado via dependency_overrides."""
    app.dependency_overrides[get_session] = lambda: db_session
    transport = ASGITransport(app=app)
    async with AsyncClient(transport=transport, base_url="http://test") as c:
        yield c
    app.dependency_overrides.clear()

Leia a arquitetura das fixtures (é composição do M02 bloco 6 em ação): pg_url caro e session-scoped; db_session barata e por teste, com o truque da transação-envelope — o teste roda inteiro dentro de uma transação que faz rollback no teardown, dando isolamento perfeito sem recriar schema a cada teste; client injeta a sessão de teste na API real via dependency_overrides — o container de DI trocado em uma linha, sem builder, sem startup alternativo.

Fundamento de engenharia · O que faz um teste de integração ser BOM
  • Isolamento: teste não depende de ordem nem de resíduo de outro teste (a transação-envelope garante). Teste que só passa "rodando a suíte inteira" é dívida com juros.
  • Determinismo: relógio, aleatoriedade e rede são as três fontes de flakiness. Injete-os (o slug aleatório do service recebe um gerador; em teste, um fixo) — flaky test é pior que ausência de teste, porque ensina o time a ignorar vermelho.
  • Teste pela interface pública: chame a API (o client), não o repository por dentro — refatoração interna (bloco 4!) não deve quebrar teste. Teste acoplado a implementação é âncora, não rede.
  • A pirâmide continua valendo: integração cobre os FLUXOS e as fronteiras; a combinatória de regras fica nos unitários. Suíte de integração de 20 min que ninguém roda protege menos que uma de 40s que roda em todo commit.

Prática guiada · A suíte do encurtador (40 min)

1Instale e escreva os básicos: uv add --dev testcontainers pytest-asyncio. Testes: criar link (201 + slug no formato), buscar (200), inexistente (404), URL inválida (422 com o campo apontado), duplicata (409 — provando a constraint + o handler de IntegrityError).

Resultado esperado: uv run pytest -q → primeiro run ~5–8s (o container subindo), depois cada teste em ms. Cinco verdes.

2Prove o isolamento: dois testes que criam o MESMO slug fixo, rodando em sequência.

Resultado esperado: ambos passam — o rollback da transação-envelope apagou o primeiro antes do segundo. Comente o rollback e rode de novo: o segundo falha com violação de unicidade. Descomente. Você viu o mecanismo, não decorou a receita.

3O teste do lost update (prometido no bloco 2): escreva o incremento de hits de dois jeitos no repository — (a) ler-somar-gravar em Python; (b) UPDATE links SET hits = hits + 1 atômico. Teste: dispare 50 incrementos CONCORRENTES com asyncio.gather (cada um com sessão própria — aqui use o engine direto, sem a transação-envelope) e leia o total.

Resultado esperado: versão (a): total < 50 — updates perdidos, o número exato varia por corrida (a assinatura da race condition: não-determinismo). Versão (b): exatos 50, sempre. Este teste vale mais que qualquer parágrafo sobre isolamento — e é o padrão que você reusará quando o assunto for idempotência de billing no M12.

Síntese do bloco 6
  • Fronteira honesta: lógica pura → unitário; atravessou o banco → Postgres real efêmero. Mock de ORM é teatro.
  • Três fixtures: container session-scoped (caro, 1x), transação-envelope por teste (isolamento grátis), client ASGI com override de DI.
  • Determinismo: injete relógio/aleatório/rede. Flaky ensina a ignorar vermelho.
  • O teste de 50 gathers provou o lost update e o conserto atômico — concorrência se testa, não se discute.

Bloco 7 · GitHub Actions e deploy em produção

00:00–00:30 anatomia de um workflow  |  00:30–01:00 o pipeline do curso, linha a linha  |  01:00–01:45 deploy real: Fly.io/Railway, domínio, HTTPS  |  01:45–02:00 rollback e o contrato de release

Por que isso importa

Até aqui os guardrails (M01) rodam na SUA máquina — protegem quando você lembra de rodá-los. CI é a promoção deles para lei: todo push, toda branch, sem exceção, numa máquina que não é a sua. E o deploy fecha o ciclo do seu gap: o "alguém configurou o resto" vira "eu configurei, está no ar, e sei fazer rollback". Nada aqui é novidade conceitual para você — Azure DevOps fazia isso — mas agora é você quem escreve, do zero, no ecossistema onde o Capstone vai viver.

Contexto · GitHub Actions em 90 segundos

CI/CD nativo do GitHub. Um workflow é um YAML em .github/workflows/; dispara por evento (push, pull_request, cron); contém jobs (paralelos por padrão, cada um numa VM efêmera — ubuntu-latest); cada job tem steps que ou rodam shell (run:) ou invocam actions reutilizáveis do marketplace (uses: actions/checkout@v4). Equivalente direto do azure-pipelines.yml — até o YAML parece. Segredos ficam em Settings → Secrets, expostos como ${{ secrets.NOME }}, mascarados no log.

O pipeline do curso

# .github/workflows/ci.yml
name: ci

on:
  push:
    branches: [main]
  pull_request:

jobs:
  quality:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: astral-sh/setup-uv@v4          # instala uv + cache de dependências
      - run: uv sync --frozen
      - run: uv run ruff check .
      - run: uv run ruff format --check .
      - run: uv run mypy --strict src/
      - run: uv run lint-imports              # a arquitetura do bloco 4, como lei
      - run: uv run pytest -q                 # inclui os de integração: o runner TEM Docker
        env:
          TESTCONTAINERS_RYUK_DISABLED: "true"

  build-image:
    needs: quality                            # só builda se a qualidade passou
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    permissions:
      packages: write
    steps:
      - uses: actions/checkout@v4
      - uses: docker/login-action@v3
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}
      - uses: docker/build-push-action@v6
        with:
          context: .
          push: true
          tags: |
            ghcr.io/${{ github.repository }}:latest
            ghcr.io/${{ github.repository }}:${{ github.sha }}
          cache-from: type=gha
          cache-to: type=gha,mode=max

  deploy:
    needs: build-image
    runs-on: ubuntu-latest
    if: github.ref == 'refs/heads/main'
    steps:
      - uses: actions/checkout@v4
      - uses: superfly/flyctl-actions/setup-flyctl@master
      - run: flyctl deploy --remote-only
        env:
          FLY_API_TOKEN: ${{ secrets.FLY_API_TOKEN }}

As decisões que importam:

  • needs: encadeia gates: deploy só existe se build passou, que só existe se qualidade passou. É o seu check.sh promovido a máquina de estados — e o mesmo grafo de dependências das waves do M01 bloco 4.
  • Os testes de integração rodam no CI sem mudar uma linha: o runner tem Docker, o testcontainers sobe o Postgres lá também. Paridade dev↔CI é o objetivo — divergência entre os dois é onde bug se esconde.
  • Tag pela SHA além de latest: cada commit tem imagem imutável endereçável — é isso que torna rollback trivial (redeployar a SHA anterior), e é o "versiono e faço rollback" das suas três perguntas de sênior.
  • PR roda qualidade mas não deploya (if: github.ref == ...): o gate de merge do M01, agora institucional.

Deploy real: Fly.io (ou Railway)

Os dois são a mesma categoria: PaaS que recebe container e devolve URL com HTTPS — o App Service sem o portal de 400 abas. O curso usa Fly.io (config como arquivo versionável; Postgres gerenciado básico; região gru = São Paulo). Railway é igualmente válido — se preferir UI, vá nele; os conceitos transferem 1:1.

flyctl launch --no-deploy      # gera fly.toml lendo seu Dockerfile
flyctl postgres create         # Postgres gerenciado
flyctl postgres attach         # injeta DATABASE_URL como secret no app
flyctl secrets set APP_ENV=production
flyctl deploy                  # builda, publica, health-checa, promove
flyctl logs                    # stdout do container (o fator XI trabalhando)

No fly.toml, o essencial a conferir: internal_port = 8000 (o EXPOSE do seu Dockerfile), a seção [[http_service.checks]] apontando para /health (o deploy só promove a versão nova se ela responder saudável — zero-downtime por health gate, o mecanismo que o slot swap do App Service fazia por você), e min_machines_running = 0 vs. 1 (0 = hiberna e economiza, com cold start; 1 = sempre quente — a decisão custo×latência que o M12 revisita com número).

Migrations no deploy — a decisão que separa deploy de incidente

NUNCA rode create_all no startup em produção (o lifespan de dev do bloco 1 morre aqui) e nunca deixe a migration para "depois". O padrão: release command — o Fly roda alembic upgrade head numa máquina efêmera ANTES de promover a versão nova ([deploy] release_command = "alembic upgrade head"). Se a migration falha, o deploy aborta e a versão velha segue no ar. Combine com a regra do bloco 2 (migration compatível com a versão anterior — expandir/contrair em 2 releases) e você tem deploy sem downtime e sem drama.

Fundamento de engenharia · Config, segredos e as três perguntas de release
  • Config no ambiente (12-Factor, fator III): a MESMA imagem roda em dev/staging/prod; o que muda é ambiente injetado. Se você precisa rebuildar para trocar de ambiente, o desenho está errado. Seu Settings do M02 já implementa isso — o Fly injeta, o Pydantic valida no boot, config faltando mata o deploy (e não a madrugada).
  • Segredo nunca em: código, imagem, log. Só no cofre da plataforma (flyctl secrets/GitHub Secrets). O .dockerignore do bloco 5 e o mascaramento do Actions são as redes; a disciplina é sua.
  • As três perguntas que todo release responde ANTES de ir: (1) como sei que quebrou? (health check + logs + o p95 do exercício); (2) como volto? (redeploy da SHA anterior — testado, não teórico); (3) o banco volta junto? (downgrade compatível ou expand/contract). Sem as três respostas, não é release — é aposta.
