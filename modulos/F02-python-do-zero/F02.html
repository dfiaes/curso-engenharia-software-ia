Diagnóstico rápido

Responda de cabeça, sem testar. Se acertar todas com segurança (mecanismo, não só o fato), leia apenas o "Em resumo" de cada bloco, faça o Checkpoint F02 e siga adiante. Qualquer resposta hesitante marca o bloco que vale ler inteiro.

  1. (Bloco 1) O mesmo arquivo imprime __main__ com python m.py e m com import m. Por quê, e para que serve o idioma if __name__ == "__main__":?
    Resposta

    O interpretador executa o módulo de entrada com o nome __main__; qualquer outro módulo recebe o nome do import. O teste separa "rodar como programa" de "ser importado": sem ele, importar o arquivo executaria o programa inteiro como efeito colateral.

  2. (Bloco 2) a = [1, 2]; b = a; b.append(3). O que vale a, e o que b = a copiou?
    Resposta

    [1, 2, 3]. A atribuição não copia objeto algum: cria um segundo nome para o mesmo objeto. Variável em Python é um rótulo preso a um objeto, não uma caixa com valor.

  3. (Bloco 2) Por que 0.1 + 0.2 == 0.3 é False, e o que usar para dinheiro?
    Resposta

    O float é binário (IEEE 754 de 64 bits) e 0.1 não tem representação finita em base 2; guarda-se o racional mais próximo. Para quantias, Decimal construído a partir de str (ou inteiro de centavos). Decimal(0.1) herda o erro do float.

  4. (Bloco 3) def f(x, acc=[]): acc.append(x); return acc. O que f(1) e f(2) devolvem, e por quê?
    Resposta

    [1] e depois [1, 2]. O default é avaliado uma vez, quando o def executa, e fica guardado em f.__defaults__. Todas as chamadas sem o argumento compartilham aquela lista. O idioma correto é acc=None e criar a lista dentro.

  5. (Bloco 4) Qual o custo de x in lista versus x in conjunto, e de lista.pop(0)?
    Resposta

    Busca linear O(n) na lista, por hash O(1) esperado no conjunto. pop(0) é O(n): desloca todos os elementos; para fila use collections.deque.

  6. (Bloco 5) Você percorre um gerador duas vezes com list(g). O que a segunda devolve?
    Resposta

    []. Um gerador é um iterador de passagem única; esgotado, só levanta StopIteration. Quem precisa percorrer de novo cria outro gerador ou materializa uma lista.

  7. (Bloco 6) Em que ordem rodam try, except, else e finally, e o que raise X from e acrescenta?
    Resposta

    try; se levantou e casa, o except; se não levantou, o else; finally sempre, por último. from e grava __cause__ e mantém a causa original no traceback; sem ele o Python registra só o __context__ implícito.

  8. (Bloco 7) open("a.txt") sem encoding= funciona na sua máquina e falha na do colega. Por quê?
    Resposta

    Sem encoding, o Python usa o padrão da localidade/plataforma, que muda de ambiente para ambiente (no Python 3.15 o modo UTF-8 se tornará o padrão, mas hoje não se deve depender disso). Texto exige encoding="utf-8" explícito.

  9. (Bloco 8) O que @dataclass gera por você, e por que tags: list = [] é recusado?
    Resposta

    __init__, __repr__ e __eq__ a partir dos campos anotados (mais __hash__ se frozen). O default mutável compartilhado seria a armadilha do bloco 3 por instância, então a classe levanta ValueError e exige field(default_factory=list).

Bloco 1 · Como o Python executa

Por que isso importa

Três falhas que parecem de "ambiente" e são de modelo. Um script chamado random.py quebra qualquer programa vizinho que importe random. O teste passa com python -m pytest e falha com pytest. O pip install "funcionou", mas o import não acha o pacote porque o pip pertence a outro Python. Em todas, ninguém sabia qual interpretador estava rodando, de onde ele carregava código e com que nome o módulo de entrada nascia.

O modelo cabe em cinco peças: interpretador (CPython), bytecode, módulo de entrada (__main__), caminho de busca (sys.path) e ambiente virtual.

CPython: compilador de bytecode mais máquina virtual

"Python" é a linguagem; CPython é a implementação de referência, escrita em C, e a que o curso usa (existem PyPy, MicroPython e outras com desempenho e compatibilidade diferentes). Contra a intuição de "linguagem interpretada", o CPython compila antes de executar. O caminho do texto ao resultado:

  1. Tokenização e parsing: o texto vira uma árvore sintática abstrata (AST). Erros de sintaxe aparecem aqui, antes de qualquer linha rodar.
  2. Compilação: a AST vira bytecode, uma sequência de instruções para uma máquina de pilha, guardada em um code object por função.
  3. Execução: um laço (o eval loop) lê instruções e despacha cada uma. Desde o Python 3.11 o interpretador é adaptativo: instruções quentes são especializadas por tipo observado (por exemplo, soma de dois int), o que explica boa parte do ganho de velocidade das versões recentes.

Para módulos importados, o bytecode é guardado em __pycache__/nome.cpython-314.pyc e reaproveitado enquanto o código-fonte não mudar (a validade é checada por data e tamanho da fonte, por padrão). O script de entrada não é cacheado: é compilado a cada execução. O .pyc é um cache descartável, nunca um artefato de distribuição confiável: ele depende da versão do interpretador, e o nome carrega essa versão (cpython-314).

Lendo bytecode com dis

O módulo dis mostra o que o compilador produziu. Não é algo que você usa todo dia; é a ferramenta que encerra discussões sobre "o que o Python faz nessa linha".

$ cat a.py
import dis
def soma(a, b):
    return a + b * 2
dis.dis(soma)
print(soma.__code__.co_consts, soma.__code__.co_varnames)
$ python a.py
  2           RESUME                   0

  3           LOAD_FAST_BORROW_LOAD_FAST_BORROW 1 (a, b)
              LOAD_SMALL_INT           2
              BINARY_OP                5 (*)
              BINARY_OP                0 (+)
              RETURN_VALUE
(2,) ('a', 'b')

Leia assim: empilha a e b (variáveis locais, acesso por índice, sem busca por nome), empilha o inteiro 2, multiplica, soma, devolve. Note a ordem: a multiplicação vem antes da soma porque a precedência já foi resolvida na AST. Os nomes exatos das instruções (LOAD_FAST_BORROW_LOAD_FAST_BORROW, LOAD_SMALL_INT) mudam entre versões menores: o bytecode é detalhe de implementação, sem garantia de compatibilidade. Use dis para entender, nunca para depender.

REPL, script e módulo: três jeitos de começar

O REPL (python sem argumentos) lê uma expressão, avalia e imprime; excelente para explorar uma API (help(obj), dir(obj), _ guarda o último resultado). Mas estado acumulado no REPL é a fonte clássica de "funciona aqui": um nome definido há duas horas continua vivo. Para qualquer coisa que importe, escreva o arquivo.

Há duas formas de executar um arquivo, e a diferença é como o módulo de entrada é localizado:

$ cat m.py
print("__name__ =", __name__)
$ python m.py          # caminho de arquivo
__name__ = __main__
$ python -m m          # nome de módulo, buscado em sys.path
__name__ = __main__
$ python -c "import m"
__name__ = m

Nos dois primeiros, o módulo vira __main__; no import, recebe seu nome. Daí o idioma:

def main() -> int:
    ...
    return 0

if __name__ == "__main__":
    raise SystemExit(main())

Ele separa o que é biblioteca (funções importáveis sem efeito colateral) do que é programa. O main() devolvendo o exit code e o SystemExit ligam este módulo ao F01: o código de saída do processo é o que o shell, o CI e o agente enxergam. É exatamente a estrutura de expenses/__main__.py no laboratório.

A diferença entre python arquivo.py e python -m pacote.modulo é o sys.path[0]: no primeiro, a pasta do script entra no início do caminho de busca; no segundo, o diretório corrente. Por isso python -m pytest enxerga o seu código quando o diretório corrente é a raiz do projeto e o pytest solto às vezes não. E por isso python -m pip garante que o pip pertence àquele interpretador.

$ cat random.py
print("meu random.py")
$ cat uso.py
import random
print(random.randint(1, 6))
$ python uso.py
meu random.py
Traceback (most recent call last):
  File "/tmp/f02x/sh/uso.py", line 2, in <module>
    print(random.randint(1, 6))
          ^^^^^^^^^^^^^^
AttributeError: module 'random' has no attribute 'randint' (consider renaming '/tmp/f02x/sh/random.py' since it has the same name as the standard library module named 'random' and prevents importing that standard library module)

A pasta do script vem antes da biblioteca padrão em sys.path, então o seu random.py ganhou. Note a primeira linha da saída: o print do seu random.py rodou durante o import. As mensagens novas do Python 3.13+ já apontam a causa. Defesas: nunca nomeie arquivo como módulo da stdlib; use python -P (ou PYTHONSAFEPATH=1) para não pôr a pasta do script no caminho; use python -I (modo isolado) para scripts de sistema.

Ambientes virtuais e uv

Cada instalação de Python tem um site-packages onde o pip grava dependências. Se todo projeto instalasse no mesmo lugar, as versões colidiriam. Um ambiente virtual (venv) é uma pasta com um pyvenv.cfg, um link para o interpretador-base e um site-packages próprio; "ativar" só reordena o PATH do seu shell (F01). Você nunca precisa ativar nada se chamar .venv/bin/python diretamente.

O curso usa o uv, que reúne instalação de Python, venv, resolução e lockfile em uma ferramenta. O ciclo mínimo:

$ uv init proj
Initialized project `proj` at `/tmp/f02x/proj`
$ cd proj && cat .python-version
3.14
$ grep -E "requires-python|build-backend" pyproject.toml
requires-python = ">=3.14"
build-backend = "uv_build"
$ uv run python -c "import sys; print(sys.prefix != sys.base_prefix, sys.prefix.split('/')[-1])"
True .venv

uv run cria o .venv se não existir, sincroniza com o uv.lock e executa dentro dele. uv sync --frozen instala exatamente o que o lockfile diz, sem reescrevê-lo: é o comando dos labs. (O uv init desta versão gera layout com src/ e backend uv_build; o formato do scaffold muda entre versões do uv.) O detalhe de dependências, versões e empacotamento é o primeiro bloco do M02; aqui basta o modelo: um projeto, um ambiente, um lockfile.

Exemplo trabalhado: "qual Python é esse?"

O sintoma: ModuleNotFoundError: No module named 'pytest' logo depois de um pip install pytest bem-sucedido. Investigue sem instalar nada:

$ python -c "import sys; print(sys.executable); print(sys.prefix != sys.base_prefix)"
$ python -m pip --version
$ python -c "import sys; print(*sys.path, sep='\n')"
$ command -v -a pip python

Compare o interpretador que roda (sys.executable) com o dono do pip (a saída de python -m pip --version mostra o caminho do site-packages). Se divergem, o pip do PATH instalou em outro ambiente. A correção é sempre a mesma: chamar o instalador pelo interpretador (python -m pip, ou uv add / uv run), nunca "reinstalar tudo". Este é o mesmo raciocínio do F01 sobre PATH e command -v, agora com sys.path no papel de segundo mapa.

Decisões e erros comuns

  • Script solto versus pacote com -m. Script de uma tela: arquivo. Qualquer coisa com mais de um arquivo: pacote e python -m pacote (ou entry point), porque imports relativos e testes dependem do pacote ser importável pelo nome.
  • pip global. Instalar no Python do sistema mistura dependências do projeto com as do SO e quebra ferramentas. Use sempre ambiente por projeto.
  • Versão do Python implícita. "Funciona na minha máquina" costuma ser 3.11 contra 3.14. Declare requires-python e .python-version.
  • Tratar .pyc como fonte. Apagar __pycache__ é sempre seguro; versioná-lo nunca é (está no .gitignore).
  • Desempenho "por intuição". Meça com python -m timeit e cProfile; o interpretador adaptativo torna palpite sobre custo de instrução pouco confiável.
Armadilha que pega sênior · a pasta do script entra antes da stdlib em sys.path

Um types.py, logging.py, queue.py ou test.py ao lado do seu código sombreia o módulo padrão, e o erro aparece longe, dentro de outra biblioteca que importa o módulo da stdlib. O traceback aponta para código de terceiros, não para o seu arquivo. Diagnóstico em dez segundos: python -c "import modulo; print(modulo.__file__)". Se o caminho cai na sua pasta, achou. Prevenção: nomes de módulo próprios nunca coincidem com a stdlib, e scripts de automação rodam com -I.

Em resumo

CPython compila para bytecode e executa numa máquina de pilha adaptativa; só módulos importados vão para o cache .pyc, e o bytecode é detalhe de versão. O módulo de entrada se chama __main__; python arquivo.py põe a pasta do script em sys.path[0], python -m põe o diretório corrente. Ambiente virtual é uma pasta com seu site-packages; o uv junta Python, venv e lockfile. Para saber "qual Python", olhe sys.executable e sys.path, não o que você acha que instalou.

Bloco 2 · Valores, tipos e o modelo de objetos

Por que isso importa

A maior parte dos defeitos "misteriosos" de Python vem de um modelo mental herdado de C ou Java: pensar que b = a copia o valor, que uma função recebe "uma cópia" ou "uma referência" do argumento, que float serve para dinheiro, que texto é uma sequência de bytes. Todas essas crenças funcionam em exemplos pequenos e quebram em produção: uma lista alterada à distância, um centavo que some em um total, um acento que vira Ã§.

Nomes são rótulos presos a objetos

Em Python, todo valor é um objeto no heap, com três atributos: identidade (nunca muda, no CPython é o endereço; id(x)), tipo (type(x)) e valor. Uma variável não contém o objeto: é um nome num espaço de nomes (um dicionário, na prática) que aponta para ele. Atribuir é ligar um nome a um objeto, sem copiar nada.

>>> a = [1, 2]; b = a; b.append(3)
>>> a, a is b, id(a) == id(b)
([1, 2, 3], True, True)

is compara identidade (mesmo objeto); == compara valor (chama __eq__). Regra: use is só para singletons (None, True, False, sentinelas suas) e == para o resto. O CPython até avisa quando você erra:

$ python -W default -c "x = 1; print(x is 1)"
<string>:1: SyntaxWarning: "is" with 'int' literal. Did you mean "=="?
True

Esse True é enganoso: inteiros pequenos e constantes iguais no mesmo trecho compilado são reaproveitados por otimização de implementação, não por contrato da linguagem. Dois inteiros iguais vindos de fontes diferentes (int("1000") is int("1000")) dão False. Nunca escreva código cuja correção depende disso.

O ciclo de vida é por contagem de referências: cada nome, elemento de contêiner ou frame que aponta para o objeto soma 1; quando chega a zero, o CPython libera a memória na hora. Um coletor de ciclos cuida dos casos em que objetos apontam entre si. Consequência prática: o __del__ e a liberação de arquivos "no fim do escopo" funcionam no CPython, mas não são garantia da linguagem (PyPy difere). Recurso se fecha com with (bloco 6).

Mutável versus imutável, e a passagem "por atribuição"

Imutáveis (valor não muda após criado)Mutáveis (mudam no lugar)
int, float, bool, complex, Decimal, str, bytes, tuple, frozenset, Nonelist, dict, set, bytearray, instâncias de classes comuns

Quando você passa um argumento, o parâmetro é um novo nome ligado ao mesmo objeto (semântica de atribuição). Daí duas consequências opostas que a mesma regra explica:

def f(lst):
    lst.append(1)     # muta o objeto compartilhado: o chamador vê
    lst = [9]         # religa só o nome local: o chamador não vê
    return lst

>>> q = []; f(q), q
([9], [1])

"Python passa por valor" e "passa por referência" estão ambos errados: passa-se a referência por valor, ou, mais limpo, chamada por atribuição. Mutar o objeto é visível; religar o nome não é.

Imutável não significa "profundamente imutável": a tupla guarda referências imutáveis, e o objeto apontado pode ser mutável.

>>> t = (1, [2, 3])
>>> t[1] += [4]
TypeError: 'tuple' object does not support item assignment
>>> t
(1, [2, 3, 4])

O += executa em duas etapas: primeiro t[1].__iadd__([4]), que muta a lista com sucesso; depois tenta atribuir o resultado em t[1], o que a tupla proíbe. O erro e o efeito acontecem juntos. Isso também define hashabilidade: só objetos cujo valor não muda podem ser chave de dict ou elemento de set (hash([1]) levanta TypeError: unhashable type: 'list'), e uma tupla com lista dentro herda a proibição.

Números: três famílias, três contratos

int tem precisão arbitrária. Não existe overflow: 2**100 é exato (1267650600228229401496703205376) e ocupa só os bytes de que precisa (28 bytes para o 1; 40 para 2**100). O custo é aritmética proporcional ao tamanho, e um limite de segurança: converter inteiros de mais de 4300 dígitos para str levanta ValueError (sys.get_int_max_str_digits()), defesa contra negação de serviço por entrada hostil. A divisão inteira e o módulo seguem o piso: 7 // -2 é -4 e 7 % -2 é -1, de modo que (a // b) * b + a % b == a sempre. bool é subclasse de int (True + True == 2).

float é o IEEE 754 binário de 64 bits: 53 bits de mantissa, cerca de 15–17 dígitos decimais significativos. A maioria dos decimais finitos não é representável em base 2, então o float guarda o racional binário mais próximo:

>>> 0.1 + 0.2, 0.1 + 0.2 == 0.3
(0.30000000000000004, False)
>>> (0.1).as_integer_ratio()
(3602879701896397, 36028797018963968)
>>> from decimal import Decimal
>>> Decimal(0.1)
Decimal('0.1000000000000000055511151231257827021181583404541015625')

O 0.1 real armazenado é 3602879701896397 / 255. Comparação com tolerância usa math.isclose, nunca ==. Acima de 253, inteiros consecutivos deixam de ser representáveis (float(2**53) + 1 == float(2**53)). Há ainda nan (que não é igual a si mesmo) e inf.

Decimal é aritmética decimal com precisão e arredondamento configuráveis (padrão: 28 dígitos, ROUND_HALF_EVEN). Regras que importam:

  • Construa de str ou int: Decimal("0.1"). De float, herda o erro acima.
  • Misturar com float é proibido de propósito: Decimal("1") + 1.5 levanta TypeError.
  • Arredonde com quantize, escolhendo o modo da regra de negócio:
>>> from decimal import Decimal, ROUND_HALF_UP
>>> d = Decimal("2.665")
>>> d.quantize(Decimal("0.01")), d.quantize(Decimal("0.01"), rounding=ROUND_HALF_UP)
(Decimal('2.66'), Decimal('2.67'))
>>> round(2.5), round(3.5), round(2.665, 2)
(2, 4, 2.67)

O round() embutido também arredonda metade para o par (2.5 vira 2). Em float, round(2.665, 2) dá 2.67 porque o valor binário real é um pouco maior que 2.665, ou seja, o resultado depende da representação, não da regra. Dinheiro pede Decimal (como no laboratório) ou inteiro de centavos; qual regra de arredondamento vale (fiscal, contratual) é decisão de negócio, não de biblioteca. Estatística e ML usam float de propósito: velocidade e erro relativo pequeno importam mais que exatidão decimal.

str versus bytes: texto não é byte

str é uma sequência imutável de pontos de código Unicode. bytes é uma sequência imutável de inteiros 0–255. A ponte é a codificação: str.encode(enc) produz bytes; bytes.decode(enc) volta. Sem saber a codificação, bytes não são texto.

>>> s = "café"
>>> len(s), len(s.encode("utf-8")), s.encode("utf-8"), s.encode("latin-1")
(4, 5, b'caf\xc3\xa9', b'caf\xe9')
>>> b"\xe9".decode("utf-8")
UnicodeDecodeError: 'utf-8' codec can't decode byte 0xe9 in position 0: unexpected end of data
>>> b"\xe9".decode("utf-8", errors="replace")
'�'

O mesmo "é" ocupa 1 byte em Latin-1 e 2 em UTF-8; o byte 0xE9 não é UTF-8 válido, e a falha explícita é melhor que o errors="replace", que troca o dado por � e esconde o erro. Há dois fatos de Unicode que um sênior precisa ter à mão:

  • Normalização. "é" pode ser um ponto de código (NFC) ou "e" mais acento combinante (NFD). Visualmente idênticos, == diz False e o comprimento difere (4 contra 5). Chaves, buscas e deduplicação pedem unicodedata.normalize("NFC", s) antes de comparar. O laboratório faz isso em normalize_category.
  • Caixa. Para comparar sem diferenciar maiúsculas use casefold(), não lower(): "ß".casefold() == "ss", enquanto "ß".lower() continua "ß".

E um aviso de modelo: len() conta pontos de código, não "caracteres que o usuário vê". Uma bandeira como 🇧🇷 tem 2 pontos de código; a família 👨‍👩‍👧 tem 5. Cortar uma str no meio desses clusters produz lixo visual; segmentar por grafema exige biblioteca externa.

Exemplo trabalhado: por que o laboratório rejeita ٣٤

No expenses/parsing.py, o valor é validado com [0-9]+(?:[.,][0-9]{1,2})?, e há um comentário explicando por que não \d. Em padrões de str, \d casa qualquer dígito Unicode, inclusive o árabe-índico, e int("٣") até converte sem erro ("٣".isdigit() é True). Resultado: um campo "valor" com dígitos de outro sistema numérico passaria pela validação e viraria número. Com a classe explícita [0-9], o dado é recusado na borda com mensagem precisa, que é o comportamento certo para entrada não confiável:

>>> parse_amount(1, "12,5"), parse_amount(1, " 7 ")
(Decimal('12.50'), Decimal('7.00'))
>>> parse_amount(3, "٣٤")
InvalidRowError: linha 3, campo 'amount': valor inválido: '٣٤'
>>> sum([0.1] * 10), sum([parse_amount(1, "0.10")] * 10)
(1.0, Decimal('1.00'))

A última linha guarda uma surpresa de versão: desde o Python 3.12, o sum() de float usa soma compensada e devolve 1.0, enquanto o laço manual t += 0.1 dez vezes dá 0.9999999999999999. O defeito do float não desapareceu: foi mascarado em sum e continua em qualquer acumulador escrito à mão. Mais um motivo para o tipo certo, em vez de depender de um truque de biblioteca.

Decisões e erros comuns

  • Dinheiro: Decimal de str (ou centavos inteiros), com quantize e modo de arredondamento explícitos. Medida física, estatística, ML: float, comparando com tolerância.
  • Igualdade: == para valores; is para None e sentinelas.
  • Texto: decodifique na entrada, trabalhe em str, codifique na saída, sempre com encoding= explícito. Normalize antes de comparar chaves.
  • Booleanos de contêiner: if not itens: é idiomático para "vazio"; mas if valor: trata 0, "", 0.0 e [] como falsos, o que é um bug quando 0 é um valor legítimo. Para ausência use is None.
Armadilha que pega sênior · Decimal(0.1) e json reintroduzem o erro do float

Dois caminhos trazem o float de volta sem aviso: construir Decimal a partir de um float (já arredondado em binário) e passar dinheiro por JSON, onde o número é um literal que a maioria dos leitores converte para float. Por isso o report_payload do laboratório serializa os Decimal como strings. A regra vale na fronteira: o dado monetário atravessa APIs, CSV e filas como texto decimal (ou centavos inteiros) e só vira Decimal dentro do domínio.

Em resumo

Nome é rótulo; atribuição liga, não copia; argumento é passado por atribuição, então mutar o objeto se vê de fora e religar o nome não. is é identidade, == é valor. Imutável não é profundamente imutável, e só valor estável é hashável. int é exato e ilimitado, float é binário aproximado, Decimal é decimal exato quando construído de str. str é texto Unicode, bytes são bytes, e a codificação é o contrato entre eles; normalize antes de comparar.

Bloco 3 · Controle de fluxo e funções

Por que isso importa

Funções são a unidade de reuso, de teste e de raciocínio do Python. Quase todo defeito sutil desta camada nasce de duas ideias mal absorvidas: quando cada coisa é avaliada (o def executa uma vez; a chamada, a cada vez) e onde cada nome é procurado (escopo). O default mutável e o lambda dentro de um laço são o mesmo problema visto de dois lados: avaliação adiantada versus avaliação tardia.

Fluxo: o que tem de específico em Python

Blocos são definidos por indentação, e if/elif/else avaliam truthiness: são falsos None, False, zeros numéricos e qualquer contêiner ou texto vazio; todo o resto é verdadeiro. Três recursos fogem do que um veterano de C/Java espera:

  • for percorre um iterável (bloco 5), não um contador: for item in itens, for i, item in enumerate(itens), for a, b in zip(xs, ys). Prefira zip(xs, ys, strict=True) quando os tamanhos devem ser iguais: sem strict, o mais longo é truncado em silêncio.
  • for ... else e while ... else: o else roda se o laço terminou sem break. Útil para "procurei e não achei", e confuso para quem lê; comente quando usar.
  • Operador morsa := atribui dentro de uma expressão: if (n := len(dados)) > 10: .... Use quando evita calcular duas vezes; não use para compactar linhas.

O match (Python 3.10+) é casamento estrutural, não um switch de igualdade: o padrão descreve a forma do dado e já extrai partes dele.

def kind(cmd):
    match cmd:
        case ["go", ("north" | "south") as d]:
            return f"go {d}"
        case ["take", item, *rest] if rest:
            return f"take {item} +{len(rest)}"
        case {"type": "pt", "x": x}:
            return f"pt {x}"
        case int(n) if n > 0:
            return "pos"
        case _:
            return "?"

>>> kind(["go", "north"]), kind(["take", "a", "b"]), kind({"type": "pt", "x": 3, "y": 1}), kind(5), kind("x")
('go north', 'take a +1', 'pt 3', 'pos', '?')

Pontos que enganam: um nome simples em case (case x:) captura qualquer valor, não compara com a variável x; para comparar com constante use nome pontilhado (Cor.VERMELHO) ou literal. Padrões de mapeamento casam com chaves extras (o "y": 1 acima não atrapalhou); padrões de sequência não casam com str/bytes. Use match para despachar sobre dados estruturados (mensagens, ASTs, comandos); para uma comparação simples, if.

Escopo: a regra LEGB

Ao ler um nome, o Python procura em quatro escopos, nesta ordem: Local (a função atual), Enclosing (funções que a envolvem), Global (o módulo) e Built-in (len, print...). A decisão de qual escopo é estática: o compilador olha o corpo da função inteira e, se há qualquer atribuição ao nome, ele é local em toda a função.

x = 10
def g():
    print(x)     # lê x ... mas x é atribuído abaixo, logo é LOCAL aqui
    x = 1

>>> g()
UnboundLocalError: cannot access local variable 'x' where it is not associated with a value

Para atribuir a um nome de escopo externo é preciso declarar global x (módulo) ou nonlocal x (função envolvente). Ler nunca precisa de declaração; mutar um objeto externo (lista.append) também não, porque não é atribuição ao nome. Variáveis de for e de with vazam para o escopo da função (i existe depois do laço); as de comprehension não (bloco 4).

Uma função sem return devolve None; uma que às vezes devolve valor e às vezes cai no fim é bug esperando acontecer.

O default mutável

O def é uma instrução executada em tempo de carga: ela cria o objeto função e avalia os defaults naquele momento, uma vez, guardando-os em f.__defaults__.

def add(item, bag=[]):
    bag.append(item)
    return bag

>>> add(1), add(2), add.__defaults__
([1, 2], [1, 2], ([1, 2],))      # as DUAS listas impressas são o MESMO objeto

def add2(item, bag=None):
    if bag is None:
        bag = []
    bag.append(item)
    return bag

>>> add2(1), add2(2)
([1], [2])

Note o primeiro resultado: a tupla de retorno contém o mesmo objeto duas vezes, por isso ambos exibem [1, 2]; a lista só foi impressa depois das duas chamadas. A regra: default só imutável (None, número, string, tupla). Se None for um valor legítimo, use um objeto sentinela próprio (_MISSING = object() e is _MISSING). O mesmo mecanismo faz o dataclass recusar tags: list = [] (bloco 8).

Closures e a ligação tardia

Funções são objetos de primeira classe: podem ser atribuídas, passadas e devolvidas. Uma função definida dentro de outra captura os nomes da envolvente que usa (variáveis livres), guardados em "células". Capturam-se variáveis, não valores:

def counter():
    n = 0
    def inc():
        nonlocal n
        n += 1
        return n
    return inc

>>> c = counter(); c(), c(), c.__closure__[0].cell_contents, c.__code__.co_freevars
(1, 2, 2, ('n',))

Por capturar a variável, e não o valor do momento, o clássico:

>>> fs = [lambda: i for i in range(3)]; [f() for f in fs]
[2, 2, 2]
>>> fs = [lambda i=i: i for i in range(3)]; [f() for f in fs]
[0, 1, 2]

Todas as lambdas leem a mesma célula i, que vale 2 ao fim do laço. A correção trava o valor agora como default (i=i, avaliação adiantada) ou usa functools.partial. É o espelho do default mutável: lá o valor era adiantado demais; aqui, tardio demais.

lambda é apenas uma função anônima de uma única expressão. Ótima como key: sorted(xs, key=lambda t: t[1]). Sem docstring e com nome <lambda> nos tracebacks, então qualquer coisa com mais de uma expressão merece um def.

Exemplo trabalhado: um decorador que conta chamadas

Um decorador é uma função que recebe uma função e devolve outra: o closure aplicado. O @contar abaixo mantém um contador na célula n, e functools.wraps copia nome, docstring e __wrapped__ para que a função decorada continue identificável.

import functools

def contar(fn):
    n = 0
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        nonlocal n
        n += 1
        wrapper.chamadas = n
        return fn(*args, **kwargs)
    wrapper.chamadas = 0
    return wrapper

@contar
def dobro(x: int) -> int:
    """Devolve o dobro."""
    return 2 * x

>>> dobro(2), dobro(5), dobro.chamadas, dobro.__name__, dobro.__doc__, dobro.__wrapped__.__name__
(4, 10, 2, 'dobro', 'Devolve o dobro.', 'dobro')
>>> dobro.__code__.co_freevars
('fn', 'n', 'wrapper')

Sem o wraps, triplo.__name__ seria 'w' e a docstring, None: ferramentas de teste, logs e documentação passariam a ver a função errada. A mesma técnica, com cache, está pronta na biblioteca padrão: functools.lru_cache transforma o Fibonacci recursivo de exponencial em linear (fib(80) = 23416728348467685, CacheInfo(hits=78, misses=81, ...)). Atenção: o cache guarda referências aos argumentos, que precisam ser hashable, e vive tanto quanto a função (vazamento de memória em processos longos se a chave cresce sem limite).

Recursão e anotações

O CPython não faz otimização de chamada de cauda; o limite padrão é sys.getrecursionlimit() == 1000 e estourá-lo levanta RecursionError. Para estruturas profundas, converta a recursão em laço com pilha explícita (F03). As anotações de tipo (x: int, -> int) não são verificadas em execução: são metadados para ferramentas (mypy, editores, Pydantic). No Python 3.14 elas passaram a ser avaliadas sob demanda (PEP 649): uma anotação que nomeia algo ainda não definido não quebra o def.

>>> def fa(a: Undefined) -> None: ...
>>> import annotationlib
>>> annotationlib.get_annotations(fa, format=annotationlib.Format.STRING)
{'a': 'Undefined', 'return': 'None'}

O curso usa from __future__ import annotations nos módulos do laboratório por compatibilidade com ferramentas e leitores; a tipagem de verdade (genéricos, Protocol, narrowing) é assunto do M02.

Decisões e erros comuns

  • Funções pequenas e puras quando possível: entrada por parâmetro, saída por return, sem ler/escrever globais. Testam-se sem preparar mundo (bloco 8).
  • Retornar vários valores é devolver uma tupla; passou de três, devolva um dataclass/NamedTuple com nomes.
  • Não mute argumentos sem que o nome da função diga (ordenar_no_lugar); devolva objeto novo ou documente.
  • Evite global; estado compartilhado vira parâmetro, atributo de objeto ou closure explícita.
  • *args/**kwargs "por garantia" esconde a API: o erro de digitação em um nome passa em silêncio. Use só em decoradores e delegação.
Armadilha que pega sênior · finally com return/continue engole a exceção e o retorno

Um return, break ou continue dentro de finally descarta a exceção em voo e o return do try. No Python 3.14, o compilador avisa (PEP 765): SyntaxWarning: 'continue' in a 'finally' block. Em um teste real, uma função com for i in range(2): try: return i finally: continue devolveu None, não 0. Código assim passa em revisão distraída e apaga erros de produção. Trate esse SyntaxWarning como erro (-W error nos testes) e deixe o finally só limpar.

Em resumo

def executa uma vez: defaults são avaliados ali, então só imutáveis, ou None mais criação interna. Um nome é local em toda a função se houver atribuição a ele (LEGB). Closures capturam variáveis, não valores: o lambda no laço lê a última; trave com i=i. Parâmetros só-nomeados deixam a API legível. match casa a forma do dado, não igualdade, e nome simples captura. Anotações são metadados, avaliados sob demanda desde o 3.14.

Bloco 4 · Coleções por dentro

Por que isso importa

Escolher a coleção errada é o erro de desempenho mais comum em código Python de produção: um if x in lista dentro de laço transforma O(n) em O(n²); um pop(0) em "fila" faz cada retirada custar o tamanho da fila; uma lista usada como chave de cache lança TypeError só em runtime. Conhecer o mecanismo de cada estrutura (não só a API) permite prever custo e comportamento. A análise formal de complexidade e as implementações à mão (array dinâmico, tabela de hash, colisões) ficam no F03; aqui o objetivo é o que o CPython faz com as suas estruturas embutidas.

list: um vetor dinâmico de referências

Uma list é um array contíguo de ponteiros para objetos (nunca os valores em linha), com capacidade reservada além do tamanho. append usa a folga; quando acaba, aloca um bloco maior e copia os ponteiros. O custo é O(1) amortizado: raras cópias grandes diluídas em muitos append baratos. Dá para ver o crescimento em passos:

>>> import sys
>>> l = []; prev = -1
>>> for i in range(40):
...     l.append(i); s = sys.getsizeof(l)
...     if s != prev: print(len(l), s, end=" | "); prev = s
1 88 | 5 120 | 9 184 | 17 248 | 25 312 | 33 376 |

Em vez de crescer 1 a 1, a capacidade salta (4, 8, 16, 24, 32, 40 posições nesta versão; a fórmula exata é detalhe de implementação). O tamanho em bytes inclui só os ponteiros (8 bytes cada), não os objetos apontados.

dict e set: tabelas de hash

Um dict guarda pares chave→valor numa tabela de hash: hash(chave) escolhe uma posição; se há colisão, a sonda segue a sequência de endereçamento aberto; ao achar um slot com hash igual, confirma com ==. Daí o contrato que une tudo: se a == b, então hash(a) == hash(b), e o hash não pode mudar durante a vida do objeto, razão pela qual só imutáveis (e objetos com __hash__ estável) servem como chave. A consequência é por vezes surpreendente:

>>> {1: "a", 1.0: "b", True: "c"}
{1: 'c'}
>>> 1 in {1.0}, hash(1) == hash(1.0)
(True, True)

1, 1.0 e True são iguais e têm o mesmo hash, logo são a mesma chave; a primeira chave é mantida e o último valor vence. Desde o Python 3.7, o dict preserva a ordem de inserção (garantia da linguagem): re-inserir uma chave removida a coloca no fim.

>>> d = {"b": 1, "a": 2}; d["c"] = 3; del d["b"]; d["b"] = 9; list(d)
['a', 'c', 'b']
>>> for k in d: d[k + "x"] = 1
RuntimeError: dictionary changed size during iteration

Alterar o tamanho enquanto se itera é erro detectado; alterar valores de chaves existentes é permitido; para modificar a estrutura, itere sobre uma cópia (list(d)). Atualização e mescla: d.update(...) muta; d1 | d2 cria novo, com o da direita vencendo ({"a": 1} | {"a": 3, "b": 2} → {'a': 3, 'b': 2}).

O set é um dict sem valores: pertinência O(1), álgebra de conjuntos (&, |, -, ^) e sem ordem garantida. Não use set para deduplicar quando a ordem importa; use dict.fromkeys(itens), que deduplica preservando a ordem. Custo de memória: um dict de 1000 itens ocupa cerca de 37 KB neste CPython, bem mais que uma lista; troca-se espaço por tempo. A ordem de iteração de set de str varia entre execuções (hash randomization de texto): nunca dependa dela.

Na biblioteca padrão, collections acrescenta: deque (fila de duas pontas), Counter (contagem: Counter("abracadabra").most_common(2) → [('a', 5), ('b', 2)]), defaultdict (valor padrão por chave ausente: defaultdict(list)) e OrderedDict (raro hoje). tuple é a sequência imutável: ideal para registros curtos e chaves compostas.

Ordenação

sorted(iterável, key=..., reverse=...) devolve nova lista; lista.sort() ordena no lugar e devolve None (confundir os dois é bug clássico: x = x.sort() apaga x). O algoritmo é o Timsort: O(n log n), estável (elementos de chave igual mantêm a ordem relativa) e rápido em dados parcialmente ordenados. O key é chamado uma vez por elemento e as chaves é que são comparadas; a estabilidade permite ordenar por vários critérios em passadas, ou usar tupla como chave:

>>> sorted(["b", "A", "a", "B"])
['A', 'B', 'a', 'b']
>>> sorted(["b", "A", "a", "B"], key=str.casefold)
['A', 'a', 'b', 'B']
>>> sorted([("x", 2), ("y", 1), ("z", 2)], key=lambda t: -t[1])
[('x', 2), ('z', 2), ('y', 1)]

Texto é ordenado por ponto de código (maiúsculas antes de minúsculas, acentuadas depois de z); ordem alfabética "humana" exige locale ou ICU. Veja o uso real em total_by_category, que ordena por (-total, nome): maior total primeiro, e o nome desempata de forma determinística.

Comprehensions, unpacking e geradores de coleção

Comprehensions constroem coleções a partir de iteráveis numa expressão: [f(x) for x in xs if p(x)], {k: v for ...}, {x for ...}. Têm escopo próprio (a variável não vaza) e, quando o resultado é consumido de uma vez, uma expressão geradora (f(x) for x in xs) evita materializar a lista: sum(x*x for x in xs). Em memória, a diferença é a de 208 bytes (o gerador) contra 8856 bytes (lista de 1000 quadrados). Legibilidade manda: dois for aninhados na mesma comprehension já são o limite.

O desempacotamento generaliza a atribuição: primeiro, *meio, ultimo = range(5) → 0, [1, 2, 3], 4; troca sem temporária a, b = b, a; e em chamadas e literais [*xs, *ys], {**d1, **d2}.

Cópia: rasa versus profunda

Como contêineres guardam referências, copiar "a lista" copia os ponteiros, não os objetos apontados. lista.copy(), list(lista), lista[:] e copy.copy são cópias rasas; copy.deepcopy percorre recursivamente (e trata ciclos), com custo proporcional ao grafo inteiro.

>>> import copy
>>> n = [[1, 2], [3]]; s = n.copy(); d = copy.deepcopy(n)
>>> n[0].append(9); s, d
([[1, 2, 9], [3]], [[1, 2], [3]])
>>> a = [[0] * 2] * 3; a[0][0] = 1; a
[[1, 0], [1, 0], [1, 0]]
>>> b = [[0] * 2 for _ in range(3)]; b[0][0] = 1; b
[[1, 0], [0, 0], [0, 0]]

A cópia rasa s compartilha a sublista com n; a profunda d não. E [[0]*2]*3 repete a mesma sublista três vezes (o * copia a referência): o idioma correto para matriz é a comprehension. O laboratório tem o caso fixado em test_shallow_vs_deep_copy.

Exemplo trabalhado: agregação do laboratório

O núcleo do relatório é uma agregação por categoria. Leia aggregate.py com o que este bloco ensinou:

def total_by_category(expenses: Iterable[Expense]) -> dict[str, Decimal]:
    totals: dict[str, Decimal] = {}
    for expense in expenses:
        totals[expense.category] = totals.get(expense.category, Decimal(0)) + expense.amount
    return dict(sorted(totals.items(), key=lambda item: (-item[1], item[0])))

def monthly_totals(expenses: Iterable[Expense]) -> dict[str, Decimal]:
    def month(expense: Expense) -> str:
        return f"{expense.date:%Y-%m}"
    ordered = sorted(expenses, key=month)
    return {
        key: sum((e.amount for e in group), start=Decimal(0))
        for key, group in itertools.groupby(ordered, key=month)
    }

Decisões visíveis: o acumulador é um dict com get(chave, 0) (poderia ser defaultdict(Decimal); o get explícito deixa o valor inicial à vista); recebe qualquer Iterable (uma lista ou o gerador do bloco 5), consumido uma vez; sum(..., start=Decimal(0)) evita o 0 inteiro como ponto de partida; e o sorted antes do groupby é obrigatório, porque o groupby só junta chaves adjacentes. O teste test_groupby_without_sorting_splits_groups prova a falha sem o sort. O retorno é dict(sorted(...)): como o dict mantém a inserção, a ordem do resultado é o contrato que a CLI exibe.

Decisões e erros comuns

  • Pertinência repetida → set ou dict. Fila → deque. Contagem → Counter. Agrupar → defaultdict(list).
  • Chave composta → tuple (ou dataclass(frozen=True)), nunca list.
  • Mutar enquanto itera (for v in lst: lst.remove(v)) pula elementos: removendo pares, [1, 2, 3, 4] dá [1, 3] (certo por acaso), mas [2, 4, 1] dá [4, 1] (errado); filtre numa nova lista.
  • Retornar o contêiner interno de um objeto expõe o estado a mutação externa: devolva cópia, tupla ou iterador.
  • if lista: versus if len(lista) > 0: o primeiro é idiomático e vale para qualquer contêiner.
Armadilha que pega sênior · groupby sem ordenar, e o iterador que o groupby entrega

Dois defeitos com a mesma origem. (1) groupby("aabbaa") produz três grupos (a, b, a), porque agrupa corridas adjacentes, ao contrário do GROUP BY do SQL; sem ordenar, o total por mês sai fragmentado e não dá erro nenhum. (2) Cada grupo é um iterador compartilhado com o groupby: avançar para a próxima chave o invalida. Por isso a comprehension acima consome o grupo imediatamente (sum(... for e in group)); guardar group numa lista de "grupos" para usar depois dá grupos vazios.

Em resumo

list é vetor de referências com append amortizado; buscar nela é linear e tirar do início é linear. dict e set são tabelas de hash: pertinência O(1) médio, chaves hashable, dict ordenado por inserção. sorted é estável e usa key. Comprehension tem escopo próprio. Cópia rasa compartilha o que está dentro; [[0]*2]*3 repete uma só sublista. groupby exige entrada ordenada pela mesma chave.

Bloco 5 · Iteração: protocolo, geradores e itertools

Por que isso importa

O laço for é a construção mais usada da linguagem e raramente é entendido por dentro. Quem o entende escreve pipelines que processam arquivos maiores que a memória com poucos KiB, consegue compor transformações sem listas intermediárias, e reconhece de longe os três defeitos do tema: o iterador consumido duas vezes, o gerador que falha só quando alguém o percorre, e o recurso aberto que um gerador abandonado segura. É também a base do que vem depois: async for, streaming de respostas de LLM e leitura de datasets são o mesmo protocolo.

O protocolo: iterável versus iterador

Dois papéis, dois métodos:

  • Um iterável sabe produzir um iterador: implementa __iter__(). Exemplos: list, str, dict, range, arquivos.
  • Um iterador entrega os itens um a um: implementa __next__() (devolve o próximo ou levanta StopIteration) e __iter__() devolvendo a si mesmo.

O laço for x in obj: corpo é, em essência:

it = iter(obj)            # chama obj.__iter__()
while True:
    try:
        x = next(it)      # chama it.__next__()
    except StopIteration:
        break
    corpo

A diferença importa porque o iterável é reutilizável (cada iter() dá um cursor novo) e o iterador é de passagem única (o estado do cursor está nele).

>>> r = iter(range(3)); list(r), list(r)
([0, 1, 2], [])
>>> list(range(3)), list(range(3))          # range é iterável: cada list() pede um cursor novo
([0, 1, 2], [0, 1, 2])
>>> m = map(str, [1, 2]); list(m), list(m)  # map devolve iterador
(['1', '2'], [])
>>> it = iter([1, 2, 3])
>>> for x in it:
...     if x == 2: break
>>> list(it)
[3]

O último caso é o que pega: o break não "fecha" o iterador; ele já consumiu o 2, e o que sobra é [3]. Um iterador passado para duas funções é dividido entre elas. Um iterador próprio mínimo mostra o contrato (e a razão de __iter__ devolver self):

class Cnt:
    def __init__(self, n): self.n, self.i = n, 0
    def __iter__(self): return self
    def __next__(self):
        if self.i >= self.n:
            raise StopIteration
        self.i += 1
        return self.i

>>> list(Cnt(3))
[1, 2, 3]

Geradores: iteradores escritos como funções

Escrever a classe acima à mão é verboso. Uma função com yield no corpo é uma função geradora: chamá-la não executa o corpo; devolve um objeto gerador, que implementa o protocolo de iterador. O corpo roda sob demanda, e em cada yield a função suspende, preservando variáveis locais e ponto de execução, até o próximo next().

def gen():
    print("start")
    x = yield 1
    print("got", x)
    yield 2
    print("end")

>>> g = gen()                 # nada impresso: o corpo ainda não rodou
>>> next(g)
start
1
>>> g.send("oi")              # retoma; "oi" vira o valor da expressão yield
got oi
2
>>> next(g)
end
StopIteration

O gerador passa por estados observáveis (inspect.getgeneratorstate): GEN_CREATED, GEN_SUSPENDED, GEN_RUNNING, GEN_CLOSED. O return do gerador encerra com StopIteration. E, por desenho (PEP 479), um StopIteration levantado dentro do corpo é convertido em erro, para que um bug interno não pareça "fim normal":

>>> def g():
...     yield 1
...     raise StopIteration
>>> list(g())
RuntimeError: generator raised StopIteration

Outros recursos: yield from outro delega a outro iterável (e propaga send/close), ideal para recursão sobre estruturas; g.close() injeta GeneratorExit no ponto suspenso para que blocos finally/with limpem. As expressões geradoras (f(x) for x in xs) são a forma curta, e o sum(1 for _ in range(10**6)) conta sem criar lista.

def flat(xs):
    for x in xs:
        if isinstance(x, list):
            yield from flat(x)
        else:
            yield x

>>> list(flat([1, [2, [3]], 4]))
[1, 2, 3, 4]

Geradores podem ser infinitos, porque nada é produzido antes de ser pedido. O consumidor define quando parar:

def fib():
    a, b = 0, 1
    while True:
        yield a
        a, b = b, a + b

>>> list(itertools.takewhile(lambda v: v < 30, fib()))
[0, 1, 1, 2, 3, 5, 8, 13, 21]

Preguiça como ferramenta de memória

A vantagem central é memória constante: o dado flui um item por vez. Medição real com tracemalloc, contando as linhas de um arquivo de 1 milhão de linhas:

sum(1 for _ in open(p, encoding="utf-8"))          # pico: 145 KiB
len(p.read_text(encoding="utf-8").splitlines())    # pico: 59 032 KiB

Mesmo resultado (1 000 000), com a diferença de ~400 vezes no pico. O arquivo é um iterador de linhas. Em pipelines, cada estágio é um gerador consumindo o anterior (linhas → parse → filtro → agregação), sem lista intermediária. É exatamente a forma do laboratório: scan(path) lê e valida linha a linha, e quem consome decide se agrega, imprime ou para no primeiro erro.

Exemplo trabalhado: o leitor do laboratório

A função scan junta quase tudo deste bloco e do seguinte. Ela é um gerador que devolve erros como valores em vez de levantá-los, porque um erro de linha não deve matar a leitura do resto:

def scan(path: Path, *, encoding: str = "utf-8") -> Iterator[Expense | InvalidRowError]:
    try:
        with path.open(encoding=encoding, newline="") as handle:
            reader = csv.DictReader(handle)
            missing = [c for c in REQUIRED_COLUMNS if c not in (reader.fieldnames or [])]
            if missing:
                raise MissingColumnError(missing)
            for row in reader:
                try:
                    item: Expense | InvalidRowError = parse_row(reader.line_num, row)
                except InvalidRowError as err:
                    item = err
                yield item
    except UnicodeDecodeError as err:
        raise EncodingMismatchError(...) from err

Consequências verificáveis:

>>> g = scan(Path("nao-existe.csv")); type(g).__name__
'generator'
>>> next(g)
FileNotFoundError: [Errno 2] No such file or directory: 'nao-existe.csv'   # só aqui, no primeiro next(): a chamada não abriu nada

Primeiro, criar o gerador não abre o arquivo; o erro de arquivo inexistente aparece no primeiro next(), longe de onde você chamou scan(...). Isso é bom para memória e ruim para diagnóstico, e por isso a CLI trata FileNotFoundError no ponto em que consome. Segundo, o with está dentro do gerador: o arquivo fica aberto enquanto o gerador estiver suspenso e fecha quando ele termina, é fechado (close()) ou coletado. O teste test_scan_is_a_generator_and_does_not_open_the_file_early fixa a primeira propriedade; test_strict_reader_is_lazy_and_stops_at_first_bad_row, a segunda. Terceiro, o reader.line_num (e não um contador manual) dá o número de linha física mesmo com campos multilinha entre aspas.

Decisões e erros comuns

  • Quando materializar: se precisa de len, indexar, percorrer duas vezes ou ordenar, use list. Se só percorre uma vez, deixe preguiçoso.
  • Funções que aceitam Iterable (não list) funcionam com listas, geradores e arquivos; funções que percorrem duas vezes devem exigir Sequence ou materializar no início, documentando.
  • Gerador como API pública: documente que é de passagem única e que erros podem aparecer no consumo.
  • return no gerador: o valor vai para o StopIteration.value; raro, e quase sempre um sinal de que uma classe ou tupla final seria mais claro.
  • Efeitos colaterais dentro de map/comprehension: map(print, xs) não imprime nada até alguém consumir.
Armadilha que pega sênior · o gerador abandonado segura o recurso e o erro vem tarde

Um gerador que abre arquivo/conexão e é descartado antes de acabar só libera o recurso quando é coletado (imediato no CPython por contagem de referências, indeterminado em outras implementações e quando há referência em traceback ou lista). Em código de produção isso vira "too many open files" intermitente. Duas defesas: consumir dentro de with contextlib.closing(gerador): quando for possível abandonar no meio, e preferir passar o Path ao consumidor final a deixar um gerador aberto circulando. O segundo defeito é o simétrico: como o corpo só roda no consumo, validações e erros de configuração (arquivo ausente, coluna faltando) aparecem no primeiro next(), possivelmente num outro módulo ou thread; se quiser falhar cedo, valide numa função comum que devolve o gerador.

Em resumo

Iterável produz iterador; iterador é de passagem única e levanta StopIteration no fim. O for é iter mais next em laço. Função com yield devolve gerador: o corpo só roda sob demanda e suspende preservando o estado; dá memória constante (145 KiB contra 59 MiB na medição acima) e permite fluxos infinitos. itertools compõe sem listas intermediárias; groupby exige ordenação; batched faz lotes. Erros e abertura de recurso dentro de gerador só ocorrem no consumo.

Bloco 6 · Erros e exceções

Por que isso importa

Software de produção é, em boa parte, tratamento de falha: arquivo ausente, byte inválido, valor fora do domínio, disco cheio. A linguagem oferece exceções; o que separa código robusto de código frágil é quem captura o quê, onde, e que informação sobrevive até o ponto em que alguém pode agir. Dois extremos produzem os piores sistemas: o except: pass que apaga o erro, e o programa que despeja um traceback cru para o usuário.

O modelo: levantar, desenrolar, capturar

Uma exceção é um objeto (instância de BaseException) levantado com raise. Quando isso ocorre, a execução abandona a linha atual e desenrola a pilha: sobe frame a frame procurando um except cujo tipo case; se nenhum casa, o programa termina com o traceback e exit code 1 (F01). O objeto carrega a mensagem (args), o __traceback__ e, quando encadeado, __cause__ e __context__.

A hierarquia padrão tem uma divisão fundamental:

BaseException
 ├─ SystemExit, KeyboardInterrupt, GeneratorExit      (NÃO capture, em geral)
 └─ Exception
     ├─ ArithmeticError (ZeroDivisionError, OverflowError)
     ├─ LookupError (KeyError, IndexError)
     ├─ OSError (FileNotFoundError, PermissionError, ...)
     ├─ ValueError (UnicodeError → UnicodeDecodeError)
     ├─ TypeError, AttributeError, RuntimeError, ...
     └─ as suas, derivadas de Exception
>>> [c.__name__ for c in FileNotFoundError.__mro__]
['FileNotFoundError', 'OSError', 'Exception', 'BaseException', 'object']
>>> [c.__name__ for c in KeyError.__mro__]
['KeyError', 'LookupError', 'Exception', 'BaseException', 'object']

SystemExit e KeyboardInterrupt ficam fora de Exception de propósito, para que um except Exception não impeça o programa de terminar nem o usuário de interromper com Ctrl+C. Capturar a superclasse captura toda a família: except OSError pega FileNotFoundError e PermissionError; except LookupError pega KeyError e IndexError.

O finally roda antes do valor ser entregue ao chamador. O else existe para que o escopo do except seja estreito: se você colocar no try também a lógica posterior, um erro nela é capturado pelo handler pensado para outra coisa e mascarado. Regras de higiene:

  • Capture o tipo mais específico que você sabe tratar. except Exception só na fronteira de um processo ou de uma tarefa (para registrar e seguir ou terminar com código de erro), nunca no meio da lógica.
  • except: sem tipo captura inclusive KeyboardInterrupt; except Exception: pass apaga evidência. Se não sabe tratar, não capture: deixe subir.
  • Mantenha o try curto: a linha que falha, não a função inteira.
  • No Python 3.14 vários tipos podem ser listados sem parênteses (PEP 758): except ValueError, TypeError: (sem as); o formato com parênteses continua válido e é o que funciona em versões anteriores.

Encadear: raise ... from

Camadas de código traduzem erros: o parser vê um ValueError; o domínio quer um InvalidRowError com linha e campo. Se você levanta uma nova exceção dentro de um except, o Python guarda a original em __context__ ("durante o tratamento de X, ocorreu Y"). Com raise Nova from original, a relação é declarada: grava __cause__ ("Y foi causado diretamente por X"), e o traceback mostra as duas.

>>> try:
...     try: int("x")
...     except ValueError as e: raise RuntimeError("config inválida") from e
... except RuntimeError as e:
...     print(repr(e), "| cause:", repr(e.__cause__))
RuntimeError('config inválida') | cause: ValueError("invalid literal for int() with base 10: 'x'")

raise X from None suprime o encadeamento (use quando a causa é ruído, não informação). Para anexar contexto sem trocar de tipo: e.add_note("linha 9 do arquivo") e raise (as notas aparecem no traceback). Para vários erros simultâneos (tarefas concorrentes, validação em lote), existe ExceptionGroup com except*, que separa por tipo:

>>> try:
...     raise ExceptionGroup("lote", [ValueError("a"), TypeError("b"), ValueError("c")])
... except* ValueError as eg: print("VE", [str(e) for e in eg.exceptions])
... except* TypeError as eg: print("TE", [str(e) for e in eg.exceptions])
VE ['a', 'c']
TE ['b']

O uso principal é em concorrência estruturada (asyncio.TaskGroup, M02).

Exceções próprias: desenhe a hierarquia

Uma biblioteca ou módulo deve ter uma exceção-base sua, para que o chamador capture a família inteira sem capturar Exception. As subclasses carregam dados estruturados como atributos, além do texto, porque quem trata precisa de campos, não de regex sobre mensagem. Assim é o errors.py do laboratório:

class ExpensesError(Exception):
    """Base class for every error this package raises on purpose."""

class MissingColumnError(ExpensesError):
    def __init__(self, columns: list[str]) -> None:
        self.columns = columns
        super().__init__("colunas obrigatórias ausentes: " + ", ".join(columns))

class InvalidRowError(ExpensesError):
    def __init__(self, line: int, field: str, message: str) -> None:
        self.line, self.field, self.message = line, field, message
        super().__init__(f"linha {line}, campo {field!r}: {message}")

O nome termina em Error, descreve a falha (não o lugar), e a mensagem está em português porque a CLI a mostra ao usuário. A CLI mapeia a hierarquia para o contrato de exit codes do F01: 0 tudo válido; 1 dados inválidos; 2 problema de uso/ambiente (arquivo ausente, encoding errado, coluna faltando). Sem a base comum, esse mapeamento seria uma lista de tipos; com ela, except ExpensesError cobre o domínio e FileNotFoundError é tratado à parte.

EAFP versus LBYL

LBYL ("look before you leap") verifica antes: if path.exists(): ler(path). EAFP ("easier to ask forgiveness than permission") tenta e trata: try: ler(path) except FileNotFoundError: .... Python favorece EAFP, por razões mecânicas: a verificação prévia é uma corrida (o arquivo pode sumir entre o exists() e o open(), TOCTOU), duplica a lógica que o próprio open já faz, e não cobre as outras falhas (permissão, disco). Exceção à regra: quando a verificação é barata, sem corrida e melhora a mensagem (validar entrada de usuário antes de gastar trabalho). Bônus de desempenho: em CPython 3.11+ o try sem exceção custa praticamente zero; levantar custa mais, então use o fluxo normal para o caso comum (dict.get / in quando a ausência é frequente).

Há também o terceiro modo, usado pelo scan: erros como valores. Quando falhas são esperadas, numerosas e não devem interromper o fluxo (linhas inválidas num CSV), devolver o erro como item do resultado evita um try por elemento e deixa o chamador decidir (estrito ou tolerante). Lançar é melhor para o caso excepcional que torna o resto inútil (coluna ausente).

Context managers: limpeza como protocolo

O with garante que a limpeza ocorra, e é a forma correta de segurar recursos (arquivo, lock, conexão, transação, diretório temporário). O protocolo tem dois métodos: __enter__() (devolve o valor de as) e __exit__(tipo, valor, tb), chamado sempre ao sair do bloco; se __exit__ devolver verdadeiro, a exceção é suprimida.

class A:
    def __enter__(self): print("enter"); return self
    def __exit__(self, t, v, tb): print("exit", t.__name__ if t else None); return True

>>> with A(): raise RuntimeError
enter
exit RuntimeError
>>> print("seguiu: __exit__ engoliu")
seguiu: __exit__ engoliu

A forma curta é contextlib.contextmanager, em que um gerador com um único yield faz as vezes de enter/exit (o código antes do yield é o enter; o depois, dentro de try/finally, é o exit). contextlib.suppress(FileNotFoundError) ignora um tipo específico de forma explícita, e ExitStack compõe um número dinâmico de contextos.

from contextlib import contextmanager

@contextmanager
def cm():
    print("antes")
    try:
        yield 1
    finally:
        print("depois")

>>> with cm() as v: print(v)
antes
1
depois

Exemplo trabalhado: gravar um arquivo de forma atômica

Problema: gravar o relatório JSON sem nunca deixar um arquivo pela metade. Com open(alvo, "w"), o arquivo é truncado ao abrir; se o programa falhar no meio, o conteúdo antigo já foi destruído. A solução do laboratório é um context manager que escreve num temporário ao lado e só no fim renomeia sobre o alvo (os.replace é atômico no mesmo sistema de arquivos):

class AtomicWriter:
    def __init__(self, target: Path, *, encoding: str = "utf-8") -> None:
        self.target = target
        self.encoding = encoding
        self._tmp = target.with_name(target.name + ".tmp")
        self._handle: TextIO | None = None

    def __enter__(self) -> TextIO:
        self._handle = self._tmp.open("w", encoding=self.encoding, newline="\n")
        return self._handle

    def __exit__(self, exc_type, exc, tb) -> None:
        if self._handle is not None:
            self._handle.close()
        if exc_type is None:
            os.replace(self._tmp, self.target)      # sucesso: troca atômica
        else:
            self._tmp.unlink(missing_ok=True)       # falha: descarta o temporário

Três detalhes de projeto: o __exit__ devolve None, então a exceção original não é suprimida (um context manager de limpeza nunca deve esconder a falha); o newline="\n" e o encoding explícitos tornam a saída idêntica em qualquer sistema; e write_report traduz OSError para ExportError com raise ... from err, conservando a causa. Os testes cobrem os quatro papéis: caminho feliz (test_atomic_writer_commits_on_success), falha injetada (o corpo levanta RuntimeError("boom") e o arquivo antigo permanece, sem sobra de .tmp) e o controle negativo:

def test_naive_write_would_have_clobbered_the_file(tmp_path):
    target = tmp_path / "out.txt"; target.write_text("antigo", encoding="utf-8")
    with pytest.raises(RuntimeError), target.open("w", encoding="utf-8") as handle:
        handle.write("metade"); raise RuntimeError("boom")
    assert target.read_text(encoding="utf-8") == "metade"     # o antigo foi destruído

O controle negativo prova que o teste da versão atômica consegue falhar: a mesma falha, com open comum, destrói o conteúdo. Sem ele, não se sabe se o teste positivo verifica alguma coisa.

Decisões e erros comuns

  • Traduza na fronteira entre camadas (OSError → ExportError, ValueError → InvalidRowError), sempre com from.
  • Não use exceção para fluxo normal frequente nem para devolver status; também não devolva None/-1/False para sinalizar erro que o chamador pode esquecer de checar.
  • assert não é validação de entrada: some com python -O. Use-o para invariantes internas (e nos testes); valide entrada com if ... raise.
  • Log e relance, não log e engula; e registre a exceção uma vez só, na fronteira.
  • Mensagens com dados e ação: "linha 6, campo 'amount': valor inválido: 'abc'" diz onde e o quê.
Armadilha que pega sênior · __exit__ que devolve verdadeiro, e except largo demais, engolem bugs

Um __exit__ terminado em return True (ou um @contextmanager com except Exception: pass em volta do yield) transforma o bloco with em um buraco negro: qualquer erro do corpo, inclusive um NameError por typo, desaparece e o programa "segue". Revise todo gerenciador de contexto procurando o retorno e o que o except captura. A regra: suprima só um tipo conhecido (suppress(FileNotFoundError)), nunca "tudo". E vale o corolário do bloco 3: return/continue em finally faz o mesmo e hoje gera SyntaxWarning.

Em resumo

Exceção é um objeto que desenrola a pilha até um except que case; BaseException inclui o que não se captura, Exception é a raiz do que é seu. else mantém o try curto, finally sempre limpa. raise Y from X preserva a causa. Defina uma exceção-base por pacote e dê atributos às subclasses. Prefira EAFP; use erros como valores quando falhar é esperado e em volume. Context manager garante limpeza e não deve suprimir o que não conhece.

Bloco 7 · Arquivos, texto e módulos

Por que isso importa

Quase todo programa real lê dados de algum lugar e os escreve em outro, e quase todo defeito dessa fronteira tem uma de três causas: caminho montado como texto (separadores, diretório corrente), codificação assumida em vez de declarada, e formato tratado "na unha" (CSV com vírgula dentro do campo, JSON com número monetário). Do outro lado do mesmo bloco, o sistema de import decide como seu código se divide em arquivos sem se quebrar: quem o desconhece cria ciclos, sombreia a stdlib e depende de ordem de execução.

pathlib: caminhos como objetos

pathlib.Path representa um caminho como objeto imutável, com o operador / para compor, atributos para decompor e métodos para o sistema de arquivos. Substitui a manipulação de strings e a maior parte do os.path.

>>> from pathlib import Path
>>> p = Path("/tmp/f02x/dados") / "sub" / "arq.tar.gz"
>>> p.name, p.stem, p.suffix, p.suffixes
('arq.tar.gz', 'arq.tar', '.gz', ['.tar', '.gz'])
>>> p.parent, p.with_suffix(".zip").name
(PosixPath('/tmp/f02x/dados/sub'), 'arq.zip')
>>> Path("a") / "/etc"            # componente absoluto REINICIA o caminho
PosixPath('/etc')

O último caso é uma armadilha de segurança: base / nome_do_usuario com nome_do_usuario = "/etc/passwd" escapa da pasta-base (e .. também). Para entrada não confiável, resolva e confirme que o resultado continua dentro da base (resolved.is_relative_to(base.resolve())). Os métodos de uso diário: exists(), is_file(), mkdir(parents=True, exist_ok=True), glob("*.csv")/rglob, iterdir(), read_text(encoding=...), write_text(...), read_bytes(), unlink(missing_ok=True), stat(). Para arquivos temporários, tempfile (e, nos testes, o fixture tmp_path). Caminhos relativos dependem do diretório corrente (F01), não da pasta do script: ancore em Path(__file__).parent quando o dado viaja com o código.

Abrir, ler, escrever: texto versus binário

open(caminho, modo, encoding=..., newline=...) devolve um objeto de arquivo. Dois mundos, escolhidos pelo modo:

  • Texto ("r", "w", "a"): lê/escreve str, decodificando/codificando com encoding e traduzindo fins de linha.
  • Binário ("rb", "wb"): lê/escreve bytes sem tradução. Para imagens, hashes, protocolos e quando você controla a decodificação.

Sempre dentro de with (bloco 6) e sempre com encoding="utf-8" em texto. Sem o argumento, o Python usa a codificação da localidade (locale.getencoding()), que difere entre máquinas e CI; o resultado é o bug "só falha na máquina do colega". Na versão testada (3.14.7, Linux, locale UTF-8) o padrão acidentalmente coincide, e é por isso que o bug passa nos testes locais. (O PEP 686 torna o modo UTF-8 padrão a partir do Python 3.15; até lá, e para código que precisa rodar em várias versões, declare.)

>>> f = tmp / "x.txt"; f.write_text("ação\n", encoding="utf-8")
>>> f.read_bytes(), f.stat().st_size
(b'a\xc3\xa7\xc3\xa3o\n', 7)
>>> f.read_text(encoding="latin-1")          # leitura na codificação ERRADA: não falha, corrompe
'aÃ§Ã£o\n'
>>> import locale, sys; locale.getencoding(), sys.flags.utf8_mode

Ler UTF-8 como Latin-1 nunca falha (todo byte é válido em Latin-1), só produz mojibake silencioso; o contrário (Latin-1 lido como UTF-8) normalmente falha alto, com UnicodeDecodeError, o que é desejável. Daí a regra de decisão do laboratório: decodificação estrita por padrão, e erro com mensagem útil em vez de errors="replace".

Fins de linha: no modo texto, \r\n e \r lidos viram \n (universal newlines) e, na escrita, \n vira o separador da plataforma, a não ser que se passe newline="" (sem tradução) ou newline="\n". Um byte-order mark (BOM) de UTF-8, comum em CSV exportado do Excel, aparece como ﻿ grudado no primeiro campo se você abrir com "utf-8"; com "utf-8-sig" ele é removido. O teste test_bom_breaks_utf8_header_but_utf8_sig_reads_it fixa ambos os lados.

Leitura: for linha in arquivo itera preguiçosamente (bloco 5); .read() carrega tudo; .read(n) lê em blocos. Escrita: .write() não acrescenta \n sozinho. Gravar de forma que a falha no meio não corrompa o destino: bloco 6 (AtomicWriter); para durabilidade contra queda de energia seria preciso também flush() e os.fsync(), que o laboratório omite de propósito (fora de escopo).

CSV e JSON: nunca na unha

O módulo csv trata o que o split(",") erra: campos entre aspas, vírgulas e quebras de linha dentro do campo, aspas escapadas por duplicação.

>>> import csv, io
>>> buf = io.StringIO(); csv.writer(buf).writerow(['a,b', 'c"d', 'e\nf']); buf.getvalue()
'"a,b","c""d","e\nf"\r\n'
>>> list(csv.reader(io.StringIO('x;y\n"1,5";2\n'), delimiter=";"))
[['x', 'y'], ['1,5', '2']]

Dois requisitos: abrir o arquivo com newline="" (para que o csv, e não o modo texto, interprete as quebras dentro de campos) e escolher o delimiter conforme a origem: CSV de Excel em localidade brasileira usa ; porque a vírgula é separador decimal, e o valor "12,50" do arquivo de exemplo do laboratório existe por isso. DictReader devolve cada linha como dict pelo cabeçalho; reader.line_num dá a linha física. Tudo que sai do csv é str: converter para número/data/Decimal e validar é o seu trabalho (parsing.py).

O json converte entre texto e dict/list/str/int/float/bool/None. Comportamentos que viram bug:

>>> import json
>>> json.dumps({"s": "ação"}), json.dumps({"s": "ação"}, ensure_ascii=False)
('{"s": "a\\u00e7\\u00e3o"}', '{"s": "ação"}')
>>> json.dumps({"d": Decimal("1.1")})
TypeError: Object of type Decimal is not JSON serializable
>>> json.loads("1e400"), json.loads("NaN"), json.loads('{"a":1,"a":2}')
(inf, nan, {'a': 2})
>>> json.dumps(float("nan"), allow_nan=False)
ValueError: Out of range float values are not JSON compliant: nan
>>> json.dumps({1: "a", None: "b"}), json.loads(json.dumps((1, 2)))
('{"1": "a", "null": "b"}', [1, 2])

Pontos: ensure_ascii=True (padrão) escapa tudo que não é ASCII, válido mas ilegível; use False e grave em UTF-8. O JSON não tem Decimal, datas nem tuplas (viram lista); chaves viram str (1 e None → "1", "null", e podem colidir); o parser aceita NaN/Infinity (que não são JSON válido pela especificação) e chaves duplicadas (vence a última, em silêncio); números fora da faixa viram inf. Para a fronteira de uma API, a validação estrita é trabalho do Pydantic (M02). No laboratório, a regra é a do bloco 2: dinheiro trafega como string decimal.

O sistema de import

import x não é "incluir um arquivo". É uma operação com cache, em quatro passos:

  1. Procura x em sys.modules (um dict nome → módulo). Se está lá, devolve o objeto: o código do módulo não roda de novo.
  2. Se não, percorre os finders em sys.meta_path, que procuram nos diretórios de sys.path (pasta do script ou diretório corrente, stdlib, site-packages do ambiente, e o que o .pth de uma instalação editável acrescenta).
  3. Cria o objeto módulo vazio, registra-o em sys.modules e então
  4. executa o corpo do arquivo, de cima a baixo, no espaço de nomes do módulo. As funções e classes que existem são as que o corpo já definiu até aquele ponto.

Dois corolários: um módulo é um singleton por interpretador (estado global de módulo é compartilhado por todos que o importam), e o efeito colateral no topo (conexão, print, leitura de arquivo) acontece uma vez, no primeiro import, na ordem em que ele ocorrer. Mantenha o topo dos módulos só com definições; trabalho vai em funções.

$ python -c "import sys, pacote.d; print('pacote.d' in sys.modules, sys.modules['pacote.d'].__file__.split('/')[-1])"
init pacote
True d.py

Note init pacote: importar pacote.d importa antes o pacote pacote e executa seu __init__.py. Um pacote é uma pasta importável (tradicionalmente com __init__.py, que define a "cara" do pacote: o que reexporta, __all__); um módulo é um arquivo .py. __main__.py dentro do pacote é o que roda com python -m pacote. Pastas sem __init__.py viram pacotes de namespace, úteis em casos específicos e fonte de confusão nos demais: inclua o arquivo.

Duas formas de import: absoluto (from expenses.model import Expense, preferido: claro de qualquer lugar) e relativo (from .model import Expense, só dentro de pacote). Em projetos reais use o layout src/ (src/expenses/...), como o laboratório: o pacote só é importável depois de instalado (editável, via uv sync), o que impede o teste de passar "por acaso" porque a pasta corrente estava no sys.path e força a existência de um pacote instalável.

Estilo: import modulo e from pacote import item no topo do arquivo, agrupados (stdlib, terceiros, locais; o ruff com regra I ordena). Evite from x import * (polui o espaço de nomes e esconde a origem). Importar dentro de função é legítimo para dependência opcional ou pesada (custo de carga: python -X importtime mostra o tempo por módulo; import json custa ≈2 ms aqui) e para quebrar ciclos.

Import circular

Um ciclo ocorre quando A importa B e B importa A. Como o módulo é registrado em sys.modules antes de seu corpo executar (passo 3), o segundo import encontra um módulo parcialmente inicializado. O que acontece depende de como se importa:

# pacote/a.py                         # pacote/b.py
from pacote import b                   from pacote.a import fa
def fa(): return "a"                   def fb(): return fa()

$ python -c "import pacote.a"
  File ".../pacote/a.py", line 1, in <module>
    from pacote import b
  File ".../pacote/b.py", line 1, in <module>
    from pacote.a import fa
ImportError: cannot import name 'fa' from partially initialized module 'pacote.a'
(most likely due to a circular import)

Sequência: a começa e, na linha 1, importa b; b executa e pede o nome fa de a, mas o corpo de a ainda não passou da linha 1, e fa ainda não existe. Já a variante que importa o módulo e acessa o atributo só no momento do uso funciona:

# pacote/c.py                          # pacote/d.py
import pacote.d as d                   import pacote.c as c
def fc(): return d.fd()                def fd(): return "d"
                                       def uso(): return c.fc()
$ python -c "import pacote.c as c; print(c.fc())"
init pacote
d

Aqui nenhum módulo precisa de um nome do outro durante o import; os atributos só são resolvidos quando as funções rodam, com os dois módulos completos. Mas funcionar não significa estar certo: o ciclo é sintoma de acoplamento mal desenhado. Os remédios, em ordem de preferência:

  1. Extrair o que ambos precisam para um terceiro módulo que não importe nenhum dos dois (tipos, constantes, exceções). É por isso que errors.py e model.py do laboratório são folhas: todo mundo importa deles, eles não importam ninguém do pacote.
  2. Inverter a dependência: A recebe B por parâmetro (ou um Protocol, M02) em vez de importá-lo.
  3. Adiar o import para dentro da função que o usa, como paliativo.
  4. Para anotações de tipo, importar sob if TYPE_CHECKING: (M02).

Ordem de dependência do laboratório, sem ciclo: errors e model → parsing → reader → aggregate/export → cli.

Exemplo trabalhado: do arquivo ao domínio

Leia o caminho de um dado pelo laboratório, atribuindo cada decisão ao seu bloco: cli.py recebe um Path (argparse, type=Path); scan abre com encoding explícito e newline="" (bloco 7); csv.DictReader separa os campos; parse_row converte texto em Decimal/date/str normalizada (bloco 2) e levanta InvalidRowError com linha e campo (bloco 6); o resultado é um fluxo preguiçoso (bloco 5) agregado em dict (bloco 4); a saída vai em JSON com Decimal como string, via escrita atômica (blocos 2 e 6). Rodando com um arquivo em Latin-1 sem avisar a codificação:

$ printf 'date,category,amount,description\n2026-01-01,Caf\xe9,1.00,x\n' > lat.csv
$ python -m expenses report lat.csv; echo "exit=$?"
expenses: lat.csv não é utf-8 válido (byte 47: invalid continuation byte)
exit=2
$ python -m expenses report lat.csv --encoding latin-1; echo "exit=$?"

O byte 0xE9 ("é" em Latin-1) é recusado em UTF-8, o erro é traduzido para EncodingMismatchError, vira exit code 2 (problema de ambiente, não de dado) e a mensagem diz qual byte e onde. Com a codificação certa, o mesmo arquivo é lido, e a categoria é normalizada para café.

Decisões e erros comuns

  • Caminhos: Path, não concatenação de strings; ancore dados do pacote em __file__, dados do usuário em argumentos.
  • Texto: encoding="utf-8" explícito em toda leitura/escrita; utf-8-sig só para entrada de Excel; formato de saída decidido por você, não pela plataforma.
  • Formatos: csv e json da stdlib; um parser caseiro vira dívida.
  • Arquivos grandes: iterar linha a linha; read() só quando sabe que cabe.
  • Módulos: topo só com definições; dependências em uma direção; nomes que não colidem com a stdlib.
Armadilha que pega sênior · importlib.reload e estado de módulo não são o que parecem

Como o módulo é um singleton em sys.modules, "re-importar" não recarrega nada. importlib.reload(m) re-executa o corpo no mesmo objeto módulo, mas quem fez from m import f continua segurando a função antiga, e instâncias de classes velhas não viram instâncias das novas. Em REPL/notebook isso gera "corrigi o código e o comportamento não mudou" ou, pior, mistura de versões. Em testes, estado global de módulo (cache, singleton, configuração) vaza entre testes: isole com fixtures (monkeypatch) ou elimine o estado global. Reiniciar o processo é a única garantia.

Em resumo

Path compõe e decompõe caminhos; componente absoluto reinicia o caminho. Texto é str com encoding explícito, nunca o padrão da plataforma; decodificar na codificação errada pode falhar alto (UTF-8) ou corromper em silêncio (Latin-1). Use csv (com newline="") e json; dinheiro vai como string. import consulta sys.modules, executa o corpo uma vez e registra o módulo antes de terminar de executá-lo, o que explica o ciclo; o remédio é extrair a dependência comum.

Bloco 8 · Classes básicas e testes

Por que isso importa

Uma classe agrupa dados e o comportamento que os acompanha; um teste automatizado prova, repetidamente e sem custo humano, que esse comportamento continua o mesmo. Juntos são o que torna possível mudar código sem medo, e é o que faz um agente de código ser útil em vez de perigoso: sem testes, nem você nem ele sabem se a alteração quebrou algo. Este bloco cobre o mínimo sólido, o suficiente para o resto do curso; princípios de design (herança versus composição, SOLID, padrões, TDD) são o S01.

Classes: o que o class realmente faz

Uma classe é um objeto (instância de type) criado pela execução do bloco class; chamá-la cria instâncias. Cada instância tem seu __dict__ de atributos; a classe guarda o que é compartilhado. A busca de atributo vai da instância para a classe (e suas bases), e a atribuição sempre cria/atualiza na instância:

class Conta:
    taxa = 0.1                 # atributo de CLASSE (compartilhado)
    def __init__(self):
        self.saldo = 0         # atributo de INSTÂNCIA

>>> c1, c2 = Conta(), Conta(); c1.taxa = 0.5
>>> Conta.taxa, c1.taxa, c2.taxa, c1.__dict__
(0.1, 0.5, 0.1, {'saldo': 0, 'taxa': 0.5})

A atribuição c1.taxa = 0.5 não mudou a classe: criou um atributo na instância que sombreia o da classe. Um método é uma função comum guardada na classe; o acesso por instância produz um método ligado (a instância vira o primeiro argumento, self, por convenção, não por palavra reservada):

>>> type(Conta.__init__), type(c1.__init__), c1.__init__.__self__ is c1
(<class 'function'>, <class 'method'>, True)

Atenção ao mesmo problema do bloco 3 em forma de classe: um atributo de classe mutável (itens = [] no corpo) é compartilhado por todas as instâncias. Estado por instância se cria no __init__.

Métodos especiais (dunders): o protocolo de dados do Python

Os métodos de nome __x__ são os ganchos pelos quais a sintaxe da linguagem chama o seu objeto. Você não os chama; implementa-os, e o resto funciona:

class V:
    def __init__(self, x): self.x = x
    def __repr__(self): return f"V({self.x!r})"
    def __eq__(self, o): return isinstance(o, V) and self.x == o.x

>>> V(1) == V(1), V.__hash__
(True, None)

class W:
    def __init__(self, items): self.items = list(items)
    def __len__(self): return len(self.items)
    def __getitem__(self, i): return self.items[i]

>>> w = W("abc"); len(w), w[1], list(w), "b" in w, bool(W([]))
(3, 'b', ['a', 'b', 'c'], True, False)

Dois fatos aparecem nessa saída. Definir __eq__ sem __hash__ torna a classe não hashable (__hash__ vira None), exatamente para impedir o par incoerente "iguais com hashes diferentes" do bloco 4. E a classe W, com só __len__ e __getitem__, ganhou iteração, in e truthiness, porque o Python recorre a esses protocolos de fallback: é a tipagem estrutural em ação ("se anda como sequência..."), tema do Protocol no M02.

dataclass: classes de dados sem repetição

Escrever __init__, __repr__ e __eq__ à mão para cada registro é repetitivo e fonte de desalinhamento (um campo novo, esquecido no __eq__). O decorador @dataclass gera esses métodos a partir dos campos anotados no corpo.

from dataclasses import dataclass, field, replace

@dataclass
class P:
    x: int
    tags: list[str] = field(default_factory=list)

>>> P(1), P(1) == P(1), P.__hash__
(P(x=1, tags=[]), True, None)

>>> @dataclass
... class Q:
...     tags: list = []
ValueError: mutable default <class 'list'> for field tags is not allowed: use default_factory

As opções que importam: frozen=True (instâncias imutáveis: atribuir levanta FrozenInstanceError, e como o valor não muda, o __hash__ é gerado, permitindo chave de dict); slots=True (sem __dict__ por instância: menos memória e atributos novos proibidos, o que apanha erros de digitação); order=True (gera <, <=... comparando campo a campo, na ordem de declaração); kw_only=True (campos só por nome). dataclasses.replace(obj, campo=novo) cria uma cópia modificada: é como se "altera" um objeto imutável. Para validação ou campos derivados, __post_init__ roda logo após o __init__ gerado. Dataclass não valida tipos em execução (as anotações são metadados); para validação de fronteira há o Pydantic (M02).

O modelo do laboratório usa exatamente o conjunto defensivo:

@dataclass(frozen=True, slots=True)
class Expense:
    """One validated expense. Frozen: instances are hashable and cannot drift."""
    date: dt.date
    category: str
    amount: Decimal
    description: str = ""
>>> e = Expense(dt.date(2026, 1, 5), "x", Decimal("1.00"))
>>> e
Expense(date=datetime.date(2026, 1, 5), category='x', amount=Decimal('1.00'), description='')
>>> e.amount = 1
dataclasses.FrozenInstanceError: cannot assign to field 'amount'
>>> hash(e) == hash(dataclasses.replace(e))
True

Um Expense validado nunca "deriva" depois: quem o recebe confia nele. É a transposição do princípio do bloco 6 (validar na borda) para a modelagem: parse, don't validate: a borda converte texto bruto em tipos de domínio e, daí em diante, o sistema trabalha com valores que já não podem ser inválidos. Alternativas: NamedTuple/tuple (leves, desempacotáveis, sem nomes de campo ao desempacotar), dict (sem contrato), classe comum (quando há invariantes e comportamento próprios).

Testes com pytest

Um teste é uma função cujo nome começa com test_ em um arquivo test_*.py; o pytest as descobre, executa e reporta. A ferramenta central é o assert simples: o pytest reescreve o AST dos testes para mostrar, na falha, os valores intermediários.

$ python -m pytest -q test_x.py
..FF..                                                                   [100%]
___ test_soma[2-2-5] ___
a = 2, b = 2, esperado = 5
>   def test_soma(a,b,esperado): assert a+b == esperado
E   assert (2 + 2) == 5
___ test_lista ___
>   def test_lista(): assert [1,2,3] == [1,2,4]
E   assert [1, 2, 3] == [1, 2, 4]
E     At index 2 diff: 3 != 4
FAILED test_x.py::test_soma[2-2-5] - assert (2 + 2) == 5
FAILED test_x.py::test_lista - assert [1, 2, 3] == [1, 2, 4]
2 failed, 4 passed in 0.01s

Os quatro recursos que bastam para quase tudo:

  • pytest.mark.parametrize: o mesmo teste sobre uma tabela de casos; cada linha vira um teste independente com id próprio (test_soma[2-2-5]), então um caso vermelho não esconde os outros. No laboratório, test_parse_amount_rejects_ambiguous_or_exotic_input varre dez entradas ("", "-5", "1e3", "NaN", "1.234,50", "٣٤"...) com um corpo só.
  • pytest.raises(Tipo, match="regex"): afirma que o código levanta; as info expõe a exceção para checar atributos (info.value.line == 7) e a causa (__cause__). Sem raises, um teste que "espera erro" passa quando nada falha.
  • Fixtures: funções com @pytest.fixture que preparam (e, com yield, desmontam) o contexto; o teste as recebe pelo nome do parâmetro. As embutidas mais úteis: tmp_path (diretório temporário único por teste), monkeypatch (altera variável de ambiente, atributo ou cwd e desfaz sozinho), capsys (captura stdout/stderr). Fixtures compartilhadas vão em conftest.py; o escopo (function por padrão, module, session) controla o custo de montagem.
  • Marcadores e configuração: --strict-markers e --strict-config (usados no pyproject.toml do lab) transformam marcador/opção com typo em erro, em vez de ser ignorado.
@pytest.fixture
def make_csv(tmp_path: Path) -> CsvFactory:
    """Write a CSV file with the given data lines; encoding is explicit and overridable."""
    def factory(*lines: str, name: str = "d.csv", encoding: str = "utf-8", header: str = HEADER) -> Path:
        path = tmp_path / name
        path.write_bytes((header + "".join(line + "\n" for line in lines)).encode(encoding))
        return path
    return factory

Esta fixture é uma fábrica: devolve uma função, de modo que cada teste gera o arquivo que quer, no encoding que quer (make_csv("x,a,1.00,", encoding="latin-1")), dentro do tmp_path que o pytest descarta depois. Os testes ficam curtos e à vista do cenário.

O que torna um teste bom

  • Estrutura Arrange–Act–Assert: prepara, executa uma coisa, afirma. Um comportamento por teste; nome que diz o comportamento (test_wrong_encoding_is_reported_not_garbled), não a função.
  • Cobrir quatro papéis: caminho feliz (funciona), borda (vazio, limite, Unicode), falha injetada (o recurso quebra no meio) e controle negativo (prova que o teste consegue falhar). Um teste que nunca falha não prova nada.
  • Determinismo: nenhum teste depende de relógio, rede, ordem de execução, set ou diretório corrente. Datas e arquivos entram por parâmetro/fixture.
  • Isolamento: nada de estado global entre testes (bloco 7); tmp_path em vez de caminhos fixos.
  • Testar comportamento observável, não o jeito de implementar: um teste acoplado a detalhes interna quebra a cada refatoração sem ter achado bug.
  • Cobertura (%) é consequência, não objetivo: 100% de linhas executadas sem asserção significativa vale zero. A pergunta útil é "se eu estragar esta linha, algum teste fica vermelho?" (mutação, passo 6 do laboratório).

Na pirâmide de testes, a maioria é de unidade (rápidos, isolados, como estes); poucos de integração (vários módulos, arquivo real, como os testes de CLI do lab); pouquíssimos ponta a ponta. A estratégia completa, com contrato, propriedade e testes de aceitação, fica no M02 e no M02A.

Exemplo trabalhado: o teste da CLI como contrato

A CLI é a única parte com interface externa: argumentos, stdout, stderr e exit code (F01). O teste a trata como caixa-preta:

def test_cli_strict_stops_with_1_and_writes_no_json(make_csv, capsys, tmp_path):
    path = make_csv("2026-01-05,a,1.00,", "xx,a,1.00,")
    out = tmp_path / "r.json"
    assert main(["report", str(path), "--json", str(out)]) == 1
    assert "linha 3" in capsys.readouterr().err
    assert not out.exists()

Chama main(argv) como função (não precisa subprocesso, porque main recebe argv e devolve o código em vez de chamar sys.exit), afirma o exit code, afirma que o JSON não foi escrito no modo estrito e que a mensagem de erro, com o número da linha, foi para o stderr. Essa testabilidade foi decidida no bloco 1 (raise SystemExit(main()) só no __main__); projetar para testar é, em grande parte, não esconder efeitos colaterais no corpo do módulo. A única exceção é o erro de uso, em que o argparse chama sys.exit(2) por conta própria; test_cli_usage_error_exits_2_via_argparse o captura com pytest.raises(SystemExit) e confere info.value.code == 2.

Decisões e erros comuns

  • Classe ou função? Sem estado compartilhado e sem várias operações sobre o mesmo dado: função. Dados puros: dataclass. Estado mais invariantes mais comportamento: classe.
  • @dataclass mutável com __hash__ manual é perigoso: use frozen=True ou não use como chave.
  • Atributo de classe mutável compartilhado; __eq__ sem __hash__ (ou o inverso) quebra set/dict.
  • Herança por reuso de código costuma ser má ideia; composição primeiro (S01).
  • Teste que replica a implementação (calcula o esperado com o mesmo código) é tautologia: use valores esperados escritos à mão.
  • Testes dependentes de ordem e de print: use capsys e asserções.
Armadilha que pega sênior · teste que não pode falhar

Três formas comuns: (1) assert sobre tupla não vazia (assert (x, "mensagem") é sempre verdadeiro; o CPython avisa); (2) pytest.raises largo demais (Exception) que passa por causa de um NameError no seu próprio teste; (3) parametrização cujos ids ou valores são calculados a partir do código sob teste. A defesa é o hábito do controle negativo e da mutação manual: estrague de propósito o código de produção e confirme que o teste correspondente fica vermelho (passos 6 e 7 do laboratório). Um agente de código produz testes que passam com facilidade espantosa; a pergunta de revisão é sempre "esse teste falharia se o bug existisse?".

Em resumo

Classe é objeto; atributo de instância sombreia o de classe; método é função ligada à instância. Dunders ligam a sintaxe ao seu objeto, e __eq__ sem __hash__ desliga o hash. @dataclass gera __init__/__repr__/__eq__; frozen e slots dão imutabilidade e economia; default mutável exige default_factory. pytest: assert simples, parametrize, raises, fixtures (tmp_path, capsys). Um bom teste cobre feliz, borda, falha injetada e controle negativo, e pode falhar.

Conclusão — o essencial em 8 linhas

CPython compila para bytecode e executa; __main__ é o módulo de entrada e sys.path decide o que é importável.
Nome é rótulo; atribuição liga; mutar é visível de fora, religar não é; is é identidade e == é valor.
float é binário aproximado, Decimal de str é decimal exato, str é Unicode e bytes depende de codificação explícita.
O def executa uma vez (default mutável), closures capturam variáveis, e o escopo é decidido pelo compilador (LEGB).
list é vetor, dict/set são hash: escolha pela operação; sorted é estável; groupby pede entrada ordenada.
Iteradores são de passagem única, geradores rodam sob demanda e entregam memória constante.
Exceção tem hierarquia, causa preservada com from, e limpeza garantida por with; grave arquivos de forma atômica.
dataclass(frozen, slots) modela dados; um teste só vale se puder falhar: feliz, borda, falha injetada e controle negativo.
