Antes de começar: o contrato pedagógico #

O módulo separa cada tema em três níveis para preservar conhecimento transferível entre ferramentas:

  1. invariante: o problema de engenharia que continua existindo quando o produto muda;
  2. padrão: o contrato, artefato ou mecanismo verificável que reduz ambiguidade e aprisionamento;
  3. adapter: como uma ferramenta específica implementa o padrão na versão atual.
Regra de autoridade. Spec, código, teste, modelo e telemetria podem estar errados ou desatualizados. Nenhum deles vence por reflexo: classifique a divergência, reúna evidência e peça decisão humana quando intenção e comportamento aceitável não puderem ser inferidos com segurança.
Aviso de agnosticismo

O núcleo do módulo é independente de fornecedor: contrato JSON, parser Python, lista de argumentos, Git, testes e evidência persistida. GitHub Spec Kit, 12-Factor Agents e produtos de coding agent aparecem como implementações ou orientações comparadas — nunca como definição universal. Formas de invocação e permissões variam; descubra-as na versão instalada em vez de presumir nomes.

Bloco 1 · Da intenção ao contrato: SDD e drift bidirecional

1.1 Por que isso importa #

Você já viveu a cena no M00: pediu uma coisa ao agente, ele fez outra, você corrigiu no chat, ele corrigiu — e de quebra desfez uma parte boa que ele mesmo tinha escrito dois turnos antes. Esse ciclo tem nome: desenvolvimento chat-driven. Ele falha de forma previsível, e entender por que falha é o que justifica todo este módulo.

Exemplo trabalhado: a mesma mudança vista por seis artefatos

Uma equipe quer gerar um changelog semanal a partir do histórico Git. A intenção é reduzir trabalho manual na retomada de estudo. O requisito diz que cada linha deve conter data, hash curto e mensagem, sem publicar nada. A spec escolhe leitura local do Git, UTF-8 e uma mensagem clara quando não houver repositório. O plano separa parser, formatação e teste, declarando arquivos e comandos. O código implementa essas decisões. A evidência registra que o teste passou e qual versão do runtime o executou.

Agora mude uma regra: a semana passa a começar no domingo. Se o requisito muda e o código ainda agrupa de segunda a domingo, há spec_stale ou implementação atrasada a classificar. Se o contrato continua exigindo segunda a domingo, mas o teste de comportamento falha, há indício de code_incorrect. Se tickets, telemetria e intenção divergem, a resposta correta é decision_required, não uma “correção” inventada pelo agente. SDD existe para expor esse caminho de decisão.

O desenvolvimento chat-driven falha por três mecanismos que você já conhece do M00:

  • O requisito vive no lugar errado. No chat, o requisito existe espalhado por dezenas de mensagens. A janela de contexto é finita; quando ela enche, o harness resume ou trunca o histórico — e o requisito que você negociou na mensagem 12 evapora. Você não perde o requisito de uma vez: ele degrada, silenciosamente, até o agente fazer algo que contradiz o combinado.
  • Persistência não é implícita. O modelo-base não mantém estado de execução entre chamadas. Alguns harnesses persistem histórico, resumo ou checkpoint, mas isso é uma capacidade externa e precisa de contrato. Se “o que construir” vive só numa conversa, a retomada depende de um mecanismo frágil e pouco auditável.
  • Descoberta de requisito por tentativa e erro custa caro. Cada rodada de "não era isso" consome tokens, tempo e — pior — polui o contexto com versões erradas do código, que o modelo continua enxergando e das quais se "inspira".

Specification-Driven Development (SDD) externaliza intenção, requisitos, decisões, tarefas e evidências em artefatos versionados. Isso não torna a especificação infalível. Código legado, testes, migrações, telemetria e comportamento observado podem conter conhecimento que a documentação perdeu. O trabalho profissional é confrontar essas fontes, localizar a divergência e reconciliar contrato, implementação e evidência no mesmo change set.

Referência do conceito

Uma especificação declara comportamento e limites. JSON Schema descreve a forma dos dados; o parser valida a entrada; testes verificam resultados e falhas. Um documento pode ser ignorado ou interpretado incorretamente. Por isso, cada requisito precisa de exemplo, contraexemplo, oráculo e ligação com a evidência produzida.

Fundamento de engenharia · Requisitos — a reciclagem que a IA tornou urgente

Engenharia de requisitos é conteúdo de primeiro semestre que a maioria dos sêniores atrofiou, porque "o negócio manda o card no Jira". Com IA, ela volta a ser a habilidade que separa quem entrega do que pediu de quem entrega o que a IA achou que era. Recicle quatro conceitos:

  • Requisito funcional vs. qualidade/restrição. Funcional: o que o sistema faz ("encurta URLs"). Qualidade: condições mensuráveis, como p95 sob carga definida, disponibilidade e privacidade. O agente não pode inferir com segurança limiares, ameaça aceita ou obrigação regulatória ausente; explicite e teste o que importa.
  • Critério de aceitação verificável. "Deve ser rápido" não é critério; "p95 < 100 ms medido com k6 em 100 VUs" é. Regra prática: se não dá para transformar em teste automatizado ou em comando com saída esperada, não é critério — é desejo.
  • Escopo negativo. Dizer o que não construir limita scope creep humano e interpretações expansivas do agente. Combine não-objetivos com write set e capabilities; texto sozinho não impede efeitos.
  • Rastreabilidade. Cada item do plano aponta para requisito, decisão ou obrigação técnica que o justifica. Passo sem origem declarada pede revisão: pode ser gold plating, trabalho habilitador legítimo ou requisito ainda não registrado.

1.2 Os três níveis de artefato #

SDD maduro separa a especificação em três documentos encadeados, cada um respondendo uma pergunta diferente. A separação não é estética: cada documento muda por um motivo diferente, num ritmo diferente, e mistura-los é o que faz "a spec" virar um monólito que ninguém atualiza.

  1. PRD — Product Requirements Document (prd.md) — responde o quê e por quê. O problema, quem sofre com ele, os requisitos funcionais e não-funcionais, as regras de negócio invioláveis e — a seção mais importante — não-objetivos: o que este produto deliberadamente não faz. Não contém nome de tecnologia. Muda quando o produto muda.
  2. Especificação técnica (spec.md) — responde como, arquiteturalmente. Schemas de dados, contratos de API, decisões de arquitetura com justificativa, restrições de camada ("router não acessa banco diretamente"), estratégia de erro, dependências externas. Muda quando a arquitetura muda.
  3. Plano de implementação (plan.md) — responde em que ordem. Etapas pequenas com objetivo, dependências, read/write sets, capabilities, gate e evidência esperada. Seu ritmo tende a ser mais curto que o de intent/requisitos, mas cada mudança continua versionada e revisável.
Regra de reconciliação — sem soberania automática

Quando comportamento e documentação divergem, não escolha a spec nem o código por reflexo. Classifique: consistent, spec_stale, code_incorrect ou decision_required. Mitigue primeiro um incidente urgente; depois atualize contrato, implementação, testes e registro de decisão juntos. Se evidência operacional e intenção não bastarem, pare sem mutar e peça a decisão de produto.

1.3 O ciclo: pesquisar → planejar → implementar → verificar #

SDD não é só "escrever documentos antes". É um ciclo com quatro fases, e a primeira é a que quase todo mundo pula:

  1. Pesquisar. Antes de especificar, o agente (ou você) investiga o terreno: que código já existe? que padrões o repositório usa? que restrições reais existem? Saída: um resumo de contexto. Pular esta fase produz specs que contradizem o código existente — e aí o agente obedece a spec e quebra o sistema.
  2. Planejar. Escrever/atualizar PRD → spec → plan, nessa ordem, cada nível derivando do anterior. Você revisa cada documento antes de avançar. Revisar 2 páginas de spec custa 10 minutos; revisar 40 arquivos de diff gerado custa uma tarde — e você não revisa de verdade, só passa o olho.
  3. Implementar. O agente executa o plan.md etapa por etapa. Uma etapa por vez, com o gate de verificação rodando entre elas.
  4. Verificar. Mecanicamente (testes, type check, lint — o harness do bloco 2) e semanticamente (o diff faz o que a spec pede? — revisão sua). Divergência encontrada volta para o passo 2, não para um remendo no chat.

1.4 Ferramental: GitHub Spec Kit — e por que você vai construir o seu #

Contexto · O que é o GitHub Spec Kit

Spec Kit é uma implementação open source do GitHub, não a norma de SDD. A documentação consultada em julho/agosto de 2026 apresenta Spec → Plan → Tasks → Implement, dezenas de integrações e fallback genérico. A forma de chamar recursos varia por adapter — por exemplo, /speckit.* ou $speckit-*. O lab inspeciona snapshots e descobre essas formas sem executá-los. Confirme sempre a documentação Agentic SDD da versão usada.

Vale conhecer o Spec Kit para comparar decisões concretas. Neste curso você constrói um kit pequeno porque isso expõe contratos, políticas e gates que ferramentas prontas ocultam. O kit usa Agent Skills, contrato canônico e adapters mínimos. Regras de domínio vivem uma vez no núcleo; cada produto apenas traduz entrada e apresentação.

Panorama de prática vigente

O Octoverse 2025 do GitHub identificou mais de 1,1 milhão de repositórios públicos que importam SDKs de LLM, com crescimento anual de 178% na sua medição. Esse número não mede vagas, empresas privadas, qualidade de código ou adoção no Brasil. Ele mostra por que contratos revisáveis, gates e handoffs não podem ficar restritos a projetos experimentais: fluxos assistidos já produzem mudanças que precisam passar pelo mesmo processo de engenharia.

1.6 O que o laboratório tornará observável #

O experimento final usa uma feature pequena de changelog para atravessar intenção, requisitos, não-objetivos, tarefas, gates e evidência. A fixture válida mostra um contrato completo. A inválida contém requisito vago, não-objetivo ausente, path inseguro, string de shell e rastreabilidade quebrada. O ponto não é decorar diagnósticos: é entender por que o parser recusa ambiguidade sem reescrever a entrada em silêncio.

Mapa para a prática final. Você criará e validará a cópia do contrato; observará os quatro estados de drift; executará um runner por argv; e verá a integração Git falhar semanticamente apesar do merge limpo. Todo comando e arquivo aparecem apenas no laboratório ao fim do módulo.
Síntese do bloco 1
  • Chat-driven falha porque o requisito mora num lugar volátil (contexto) e a descoberta por tentativa e erro polui o que resta dele.
  • SDD externaliza intenção e decisões; spec, código, testes e produção são evidências reconciliadas, não autoridades automáticas.
  • Três níveis: PRD (o quê/por quê), spec (como), plan (em que ordem, com verificação por etapa). Ritmos de mudança diferentes.
  • Ciclo: pesquisar → planejar → implementar → verificar. Antecipar decisões reduz o custo cognitivo da revisão, mas o diff e os testes continuam indispensáveis.
  • Spec Kit é implementação de referência; o contrato portátil do lab preserva o conceito fora de qualquer produto.

Bloco 2 · Harness Engineering: guardrails mecânicos, não pedidos educados

2.1 Por que isso importa #

No M00 (bloco 2) você aprendeu na pele que instrução em prompt é pedido, não garantia: sua skill v1 mandava "não reescreva o código" e o agente reescreveu tudo. A v2 melhorou com técnica de prompt — mas prompt melhor continua sendo probabilidade melhor, não certeza. Harness Engineering é o passo seguinte: tirar as regras inegociáveis do prompt e colocá-las em mecanismos que não dependem de obediência.

A separação dos três níveis, que você vai usar o curso inteiro:

DisciplinaControlaPergunta que respondeNatureza
Prompt engineeringo que você diz"como formulo a instrução?"probabilística — o modelo pode desobedecer
Context engineeringo que o modelo vê"o que entra na janela, e o que fica fora?"probabilística — o modelo pode ignorar o que vê
Harness engineeringo que o sistema permite"o que acontece quando o modelo erra?"determinística — o erro é barrado por código
Referência do conceito

Uma instrução pede um comportamento; contexto fornece informação para escolhê-lo; um gate executa uma verificação e pode impedir o avanço. Pedir que o agente preserve o contrato é diferente de executar um teste que falha quando o contrato muda. O harness liga essas peças e define o que fazer quando a verificação falha.

2.2 Por que o agente degrada em tarefa longa #

Para desenhar o harness certo, você precisa do modelo mental correto do modo de falha. Agente em tarefa longa degrada por mecanismos conhecidos:

  • Context rot (apodrecimento de contexto). A janela enche com histórico de edições, saídas de comando e versões antigas de código. O sinal (a instrução original, a spec) dilui no ruído. O modelo passa a dar mais peso ao que está perto do fim da janela — as próprias ações recentes — e menos ao objetivo. Sintoma clássico: refatorar código que já estava pronto.
  • Degradação perto do limite de contexto. Não atribua uma intenção ao modelo a partir de uma resposta curta. Procure sinais: compactação registrada pelo harness, requisito antigo ausente da entrada, passos que crescem sem gate, checks omitidos ou retomada sem estado confirmado. O tratamento começa por unidade de trabalho menor, estado externalizado e medição; um prompt pedindo “não esqueça” não torna o diagnóstico confiável.
  • Falhas correlacionadas. Pedir ao mesmo modelo — ou a outro modelo semelhante — que verifique texto gerado não cria independência por si só. Priorize parser, type checker, teste com oráculo forte, controle negativo e revisão humana orientada por risco. Um segundo agente pode ampliar perspectivas, mas sua independência precisa ser demonstrada, não presumida.
  • Acúmulo de erro composto. Como ilustração matemática — não como taxa medida de agentes — vinte passos independentes com 95% de sucesso cada dariam 0,95²⁰ ≈ 36% de sucesso integral. Na prática as falhas não são independentes, o que reforça a necessidade de medir e criar gates entre estados.
Fundamento de engenharia · Fail fast, shift left e a economia do erro

Dois princípios clássicos sustentam todo harness — recicle-os, porque agora eles se aplicam a um "dev" que produz mil linhas por minuto:

  • Fail fast onde continuar é inseguro: invariantes quebradas, contrato inválido e autorização negada bloqueiam avanço. Falhas recuperáveis podem usar retry limitado ou degradação explícita. A política precisa distinguir essas classes em vez de aplicar “abortar tudo” universalmente.
  • Feedback próximo da mudança: quanto antes uma divergência observável aparece, menor tende a ser o blast radius e mais contexto local existe para diagnosticá-la. Não existe multiplicador universal. Meça tempo até feedback, retrabalho e escapes por tipo de controle.

2.3 Os cinco guardrails mecânicos #

O harness completo tem cinco camadas. A regra que as une: se uma propriedade é inegociável, ela precisa de controle executável, caso negativo e evidência. Exit code é um sinal de protocolo; sozinho, não prova que o oráculo representa a necessidade real.

Contexto · Exit code — a moeda dos guardrails

Processos comunicam estado por exit code, mas cada ferramenta define seus códigos. No pytest, por exemplo, zero significa testes coletados e aprovados; cinco significa que nenhum teste foi coletado — isso deve bloquear o curso, não virar aviso ignorado. O runner registra argv, versão, duração, saída e código. A documentação do Python subprocess recomenda argumentos como sequência e alerta para responsabilidades adicionais ao invocar shell explicitamente.

  1. Gates de qualidade por passo. Depois de uma unidade coerente de edição, rode as verificações rápidas adequadas ao risco: Ruff, mypy estrito e testes focados. O adapter pode ligar isso a hook, CI ou runner local, mas o contrato é o mesmo: resultado real, timeout e evidência persistida.
  2. Unidades de trabalho pequenas e verificáveis. Janela maior não corrige contexto irrelevante, truncamento ou objetivo mal definido. Cada etapa deve terminar em estado verificável e retomável; divida quando evidência, revisão ou rollback deixarem de ser locais.
  3. Estado externalizado, sessão substituível. Progresso confirmado mora em spec, checkpoint, diff, testes e evidência. Teste ácido: uma nova sessão consegue retomar do último estado confirmado sem repetir efeito? Conversa pode ajudar na exploração, mas não deve ser o único ledger operacional.
  4. Fronteiras de permissão. Declare capabilities mínimas, paths, comandos e aprovações por tarefa. O nome do campo varia entre produtos; a policy efetiva precisa ser testada. Para o lab, produção é inacessível e qualquer escape de root é negado.
  5. Verificação independente. Quem avalia não pode ser quem fez: suíte de testes escrita antes (ou revisada por você), revisor com contexto limpo (subagente revisor, com critérios de revisão Python explícitos), e — no limite — você, lendo o diff. Rubrica objetiva: a definição de "pronto" está no contract.md do bloco 5, não na opinião do executor.
O teste do prompt supérfluo

Pegue qualquer instrução do AGENTS.md e pergunte: "que evidência aparece se isto for ignorado?" Se a resposta é "nenhuma", transforme-a em policy, schema, teste ou aprovação — ou registre conscientemente que continua sendo orientação probabilística.

2.4 Leitura aplicada · runner, caso negativo e evidência #

O runner executável fica no laboratório final. Aqui fixe a sequência causal: a policy aceita apenas executáveis e diretórios permitidos; o runner usa lista de argumentos e shell=False; a evidência persiste argv, versão, duração, saída e exit code. O M02 aprofundará a linguagem; neste módulo, a questão é onde a autoridade de executar termina.

Responsabilidades das ferramentas

uv gerencia ambiente e lock; Ruff verifica formatação e padrões de código; mypy analisa anotações de tipo; unittest executa os testes. O runner passa argumentos separados com subprocess.run([...], shell=False), sem pedir ao shell para interpretar uma string. Cada ferramenta observa uma dimensão; nenhuma delas sozinha prova adequação do produto.

O que você observará no laboratório. O contrato válido passa; a fixture inválida retorna código 20 sem mutação; mypy localiza o erro de tipo semeado; o controle negativo elimina um mutante; timeout retorna 124; shell, path e executável não autorizados retornam 126. O arquivo de evidência registra o que ocorreu. Não existe passo de adivinhação entre esses resultados.
Síntese do bloco 2
  • Prompt = o que você diz; contexto = o que ele vê; harness = o que o sistema permite. Só o terceiro é determinístico.
  • Falhas aparecem por truncamento, contexto irrelevante, estados ocultos, passos longos e verificadores correlacionados; meça sinais observáveis.
  • Cinco guardrails: gates por passo, unidades pequenas, estado externalizado, fronteiras de permissão, verificação independente.
  • Regra inegociável vira controle executável com caso negativo e evidência; exit code é sinal, não prova semântica completa.
  • Teste ácido do estado: /clear a qualquer momento — dá para retomar só dos artefatos?

Bloco 3 · Estado, controle e 12-Factor Agents sob crítica

3.1 Por que isso importa e como ler o guia #

Os blocos 1 e 2 deram método e controles. Agora você estudará estado, efeitos, retomada e supervisão. O 12-Factor Agents, da HumanLayer, é um guia de practitioner útil para organizar perguntas — não uma norma, certificação nem consenso universal. Cada fator será aceito somente quando houver artefato, teste ou telemetria que o sustente, e você registrará contrapontos.

Contexto · O que é o 12-Factor Agents

O repositório foi publicado por Dex Horthy/HumanLayer em 2025 e reúne experiência prática. Sua tese — combinar software determinístico com passos probabilísticos estreitos — é consistente com o laboratório, mas continua sendo uma posição de engenharia a testar no contexto. “Stateless” aqui não significa “sem estado”: significa estado explícito e externalizado. O chamado fator 13, pre-fetch, aparece apenas como honorable mention; pré-carregar dependência conhecida e pequena pode ajudar, enquanto descoberta incerta deve permanecer sob demanda para reduzir custo e ruído.

Fundamento de engenharia · Funções puras, idempotência e event sourcing

O fator 12 só parece novidade. Recicle três conceitos que o sustentam:

  • Função pura: saída depende só da entrada; sem efeito colateral escondido. É o que torna teste trivial (entrada → saída esperada, sem mock de meio mundo). Agente-reducer é testável do mesmo jeito: dado este estado e este evento, o próximo estado é este.
  • Idempotência: executar duas vezes = executar uma (PUT vs. POST; a mesma mensagem processada duas vezes pelo consumer não duplica o débito). Agentes tornam isso obrigatório: retry é rotina, e um agente que "tenta de novo" uma transferência não-idempotente é o incidente do M12.
  • Event sourcing como analogia limitada: um reducer calcula estado a partir de eventos explícitos; uma janela de contexto não é event store confiável, pois pode truncar, resumir e conter texto não validado. Use ledger/checkpoint próprio para efeitos e trate contexto apenas como entrada da chamada.
Referência do conceito

Os fatores orientam responsabilidades de um workflow: entradas estruturadas, prompts versionados, estado explícito, interrupção e retomada, aprovação de efeitos, controle de fluxo e erros acionáveis. Use a tabela para localizar qual responsabilidade falta no seu sistema. O guia não substitui a demonstração de que cada controle funciona.

Bloco 4 · Decomposição, worktrees e integração por waves

4.1 Por que isso importa #

Um host pode executar uma ou várias unidades de trabalho, mas isolamento de processo não prova independência. O ganho aparece quando tarefas, contratos e recursos deixam de competir entre si. Enquanto o worker A implementa uma mudança de autenticação, o B escreve testes de billing e o C atualiza documentação, alguém ainda precisa manter a base estável, integrar e julgar o resultado. Paralelismo mal modelado aumenta colisões e retrabalho. Este bloco constrói o critério para decidir quando a execução simultânea ajuda.

Fundamento de engenharia · Concorrência — a reciclagem que decide se isso funciona

Tudo neste bloco é teoria clássica de concorrência aplicada a um novo tipo de worker. Recicle quatro peças:

  • Concorrência ≠ paralelismo. Concorrência estrutura tarefas que podem progredir independentemente; paralelismo executa algumas simultaneamente. Decomposição, integração e revisão frequentemente dominam o ganho, por isso precisam ser medidos.
  • Estado compartilhado mutável exige coordenação. Dois agentes editando o mesmo arquivo lembram uma race condition, mas conflitos também surgem por contrato e recurso externo. As opções incluem sequenciar, isolar, tornar alterações aditivas ou estabilizar a interface numa wave anterior.
  • Lei de Amdahl: o ganho do paralelismo é limitado pela fração sequencial. Com agentes, a fração sequencial é a sua revisão e a consolidação dos merges. Cinco agentes gerando código que você revisa sozinho: o gargalo é você. Paralelize também a verificação (testes, gates do bloco 2) ou o paralelismo é ilusão.
  • Custo de coordenação cresce com o quadrado dos participantes. Vale para times (Brooks) e para agentes: 2 workers = 1 fronteira para gerenciar; 5 workers = 10. Comece com 2.

4.2 Quando paralelizar — o checklist honesto #

Paralelize quando todas estas condições valem:

  • As tarefas não compartilham estado relevante. Write sets disjuntos são necessários em muitos casos, mas não bastam. Compare também read sets, contratos públicos, schema, lockfile, banco, cache, porta, fila, rate limit e dependências entre tarefas.
  • Cada tarefa tem contrato suficiente e condição de parada. Se surgir ambiguidade que altera produto ou contrato compartilhado, o worker pausa e devolve handoff; não decide sozinho para manter o paralelismo aparente.
  • Cada tarefa tem gate de worker e existe gate global. “Terminou localmente” não significa “integrou”: cada branch pode passar contra a base e falhar quando os dois novos comportamentos se encontram.
  • O custo compensa. Paralelizar duas tarefas de 10 minutos é overhead puro. Paralelize blocos de ≥ 30–60 min de trabalho de agente.

4.3 Arquitetura orquestrador-workers #

Um padrão frequente de orquestração tem três papéis. Produtos podem automatizá-los de formas diferentes; o contrato não depende dessa automação:

  • Orquestrador (sessão principal, contexto caro): decompõe a tarefa, escreve/distribui as specs, dispara os workers, consolida os resultados. Não implementa nada — implementar sujaria o contexto que precisa ficar limpo para julgar os resultados.
  • Workers (subagentes ou sessões paralelas, contexto descartável): recebem uma spec fechada, implementam, rodam o gate, devolvem um relatório compacto (fator 9!) — não o diff inteiro, que estouraria o contexto do orquestrador.
  • Consolidador (o orquestrador de chapéu trocado, ou você): merge das branches, resolução de conflito, gate final na integração.

Em tarefas grandes, os workers rodam em waves (ondas): wave 1 = fundações compartilhadas (schemas, contratos — sequencial, porque tudo depende delas); wave 2 = features em paralelo sobre a fundação; wave 3 = integração e polimento. É o mesmo raciocínio do grafo de dependências de um build: paraleliza-se o que está no mesmo nível do grafo.

4.4 Isolamento com Git worktrees #

Contexto · O que é git worktree

git worktree mantém árvores de trabalho ligadas ao mesmo repositório. Cada árvore tem working tree, HEAD e índice próprios, mas objetos, refs e partes da configuração continuam compartilhados. Isso isola arquivos; não isola serviços nem semântica. O laboratório centraliza Git com argv tokenizado, stage explícito e paths resolvidos sob uma pasta temporária marcada como pertencente ao lab.

Referência do conceito

Worktrees oferecem diretórios de trabalho distintos ligados ao mesmo repositório Git. Cada tarefa edita sua própria cópia; a integração ocorre por merge e testes. Banco, portas e outros recursos externos continuam compartilhados se o projeto não os isolar explicitamente.

4.5 O cenário que o laboratório executará #

O laboratório cria um repositório Git real somente dentro de um diretório temporário marcado como próprio. Duas worktrees alteram arquivos diferentes: uma produz amount=120; outra consome limit=110. Os merges são textualmente limpos. O gate global lê os dois valores e falha porque o contrato compartilhado é incompatível. O cleanup também recusa uma worktree suja. Assim você observa as três distinções relevantes: isolamento de diretório, integração textual e compatibilidade semântica.

Limite. Worktree não isola banco, porta, cache, lockfile ou contrato. O experimento prova a segurança do sandbox Git do laboratório; não prova que qualquer paralelismo de produção é seguro.
Multi-sessão com tmux — quando você verá isso

tmux é um multiplexador de terminal: uma tela dividida em painéis, cada um com um shell persistente que sobrevive à desconexão (equivalente mental: várias janelas do Windows Terminal que continuam rodando quando você fecha o notebook). Times que rodam 4+ agentes usam tmux para observá-los lado a lado. Não é pré-requisito do curso — dois terminais comuns bastaram aqui — mas você vai esbarrar no nome em todo post sobre "agent farm". Se quiser experimentar: tmux, Ctrl-b % divide vertical, Ctrl-b setas navega, tmux attach reconecta.

4.6 Resolução de conflito entre features #

Quando as specs não conseguem ser disjuntas (duas features precisam mexer no mesmo router.py), você tem três estratégias, em ordem de preferência:

  1. Re-decompor: extrair a fundação compartilhada para uma wave anterior e manter as partes seguintes independentes quando isso reduzir risco total.
  2. Contrato primeiro: estabilizar assinatura/schema e testes de compatibilidade na wave 1; mudanças aditivas reduzem algumas colisões, mas ainda exigem gate global.
  3. Integrar sequencialmente: mergear uma unidade, atualizar a base da seguinte, resolver com ambas as specs e executar toda a suíte. O agente pode ajudar a propor resolução; o orquestrador revisa sem assumir que merge textual preservou semântica.
Síntese do bloco 4
  • Paralelize quando o DAG, os contratos, os recursos e os read/write sets demonstrarem independência suficiente; use waves para fundações compartilhadas.
  • Orquestrador decompõe e julga (contexto limpo); workers implementam (contexto descartável); relatórios compactos sobem.
  • Worktrees isolam diretórios de trabalho, não banco, cache, porta, dependência, refs compartilhadas nem comportamento.
  • Gate roda por worker E na integração — conflito semântico não aparece no git.
  • Lei de Amdahl com agentes: o sequencial que limita tudo é a SUA revisão. Waves: fundação → paralelo → integração.

  • from pathlib import Path importa o tipo que representa caminhos. O operador / combina partes do caminho respeitando a plataforma; ele não lê o arquivo.
  • def nome(param: tipo) -> retorno: declara uma função; as anotações indicam os tipos do parâmetro e do retorno. Dois-pontos e indentação delimitam o corpo.
  • list[str], dict[str, list[str]] — List<string> e Dictionary<string, List<string>>.

# tools/sdd_check.py
"""Valida a estrutura mecânica dos artefatos SDD de uma feature.

Uso:  uv run python tools/sdd_check.py docs/spec/001-changelog
Exit: 0 = estrutura conforme; 1 = violação (mensagem indica qual).
"""

import sys
from pathlib import Path

# Seções obrigatórias por artefato. Alterar isto É alterar o processo:
# faça via PR, nunca no meio de uma tarefa.
REQUIRED: dict[str, list[str]] = {
    "prd.md": [
        "## Problema",
        "## Requisitos funcionais",
        "## Requisitos não-funcionais",
        "## Não-objetivos",
    ],
    "spec.md": [
        "## Decisões técnicas",
        "## Contratos",
        "## Restrições de camada",
        "## Estratégia de erro",
        "## Rastreabilidade",
    ],
    "plan.md": [
        "## Etapas",
        "verificação:",   # cada etapa declara seu comando de verificação
        "esperado:",      # ... e a saída esperada
    ],
}


def check_feature_dir(feature_dir: Path) -> list[str]:
    """Devolve a lista de violações encontradas (vazia = conforme)."""
    problems: list[str] = []
    for file_name, sections in REQUIRED.items():
        artifact = feature_dir / file_name
        if not artifact.is_file():
            problems.append(f"{file_name}: arquivo ausente em {feature_dir}")
            continue
        content = artifact.read_text(encoding="utf-8")
        for section in sections:
            if section not in content:
                problems.append(f"{file_name}: seção obrigatória ausente: '{section}'")
    return problems


def main() -> None:
    if len(sys.argv) != 2:
        print("uso: uv run python tools/sdd_check.py ")
        raise SystemExit(2)

    feature_dir = Path(sys.argv[1])
    if not feature_dir.is_dir():
        print(f"pasta não encontrada: {feature_dir}")
        raise SystemExit(2)

    problems = check_feature_dir(feature_dir)
    if problems:
        print(f"SDD CHECK FALHOU — {len(problems)} violação(ões):")
        for p in problems:
            print(f"  - {p}")
        raise SystemExit(1)

    print(f"SDD CHECK OK: {feature_dir} está estruturalmente conforme.")


if __name__ == "__main__":
    main()

2. Reconstrua a classificação de drift #

Copie este arquivo para src/sdd_lab/drift.py. A decisão não altera spec, código ou testes. Ela apenas classifica a evidência: consistente, spec antiga, código incorreto ou decisão humana necessária.

"""Classificação conservadora de drift: evidência antes de mutação."""

from dataclasses import dataclass
from enum import StrEnum


class DriftState(StrEnum):
    CONSISTENT = "consistent"
    SPEC_STALE = "spec_stale"
    CODE_INCORRECT = "code_incorrect"
    DECISION_REQUIRED = "decision_required"


@dataclass(frozen=True)
class DriftEvidence:
    spec_accepts_observed: bool
    tests_accept_observed: bool
    production_supports_observed: bool | None
    detail: str


@dataclass(frozen=True)
class DriftReport:
    state: DriftState
    evidence: DriftEvidence
    mutation_allowed: bool = False


def classify_drift(evidence: DriftEvidence) -> DriftReport:
    if evidence.spec_accepts_observed and evidence.tests_accept_observed:
        state = DriftState.CONSISTENT
    elif (
        not evidence.spec_accepts_observed
        and evidence.tests_accept_observed
        and evidence.production_supports_observed is True
    ):
        state = DriftState.SPEC_STALE
    elif evidence.spec_accepts_observed and not evidence.tests_accept_observed:
        state = DriftState.CODE_INCORRECT
    else:
        state = DriftState.DECISION_REQUIRED
    return DriftReport(state=state, evidence=evidence)

StrEnum define estados nomeados que continuam se comportando como strings. bool | None distingue “produção contradiz” de “produção não foi observada”. O valor padrão mutation_allowed=False é a fronteira importante: classificar não autoriza mudar o sistema.

Observe. Os quatro cenários passam e nenhuma transição libera mutação automática. Se a importação falhar, confirme que você colou o arquivo em src/sdd_lab/drift.py e que PYTHONPATH ainda vale nesta janela.
