O que muda ao final deste módulo

Todo módulo seguinte roda comandos, lê logs, encadeia ferramentas e guarda trabalho em Git. Um agente de código faz o mesmo: só enxerga o mundo por exit code, stdout, stderr e histórico versionado. Quem trata isso como receita perde horas em falhas de causa mecânica simples.

Ao terminar você consegue: (1) explicar o que acontece entre apertar Enter e o programa rodar, e prever o que um pipeline faz com exit codes e sinais; (2) compor ferramentas pequenas com pipes e redirecionamentos sem os acidentes clássicos (espaços em nomes, ordem de 2>&1, variável vazia em rm -rf); (3) abrir a pasta .git e ler cada objeto à mão, entendendo por que commit é snapshot e por que histórico é imutável; (4) escolher entre merge, rebase e cherry-pick sabendo o que cada um grava; (5) colaborar via remotes sem reescrever o que os outros já têm; (6) investigar uma regressão com log -S, blame e bisect run, e recuperar trabalho "perdido" com reflog.

O que este módulo NÃO é

Não é lista de comandos para decorar. Cada comando entra como consequência de um modelo: processos e descritores no bloco 1, nomes e inodes no 2, objetos e ponteiros no 3. Redes, cgroups, containers e produção ficam no LT01.

Diagnóstico rápido

Responda de cabeça, sem testar. Se acertar todas com segurança (mecanismo, não só o nome do comando), leia apenas o "Em resumo" de cada bloco, faça o Checkpoint F01 e siga para o F02. Qualquer resposta hesitante marca o bloco que vale ler inteiro.

  1. (Bloco 1) gerador | head -1 termina e o gerador acusa exit code 141. O programa tem bug?
    Resposta

    Não. head fechou o pipe; a próxima escrita do gerador gera SIGPIPE (13), e 128 + 13 = 141. É o fim normal de um produtor cujo consumidor desistiu.

  2. (Bloco 1) Você define X=1 no shell e roda bash -c 'echo $X'. O que imprime, e o que muda com export X?
    Resposta

    Vazio. O ambiente é uma cópia de pares NOME=valor entregue ao filho no execve; export marca a variável para entrar nela. Mudanças do filho nunca voltam ao pai.

  3. (Bloco 1) grep devolve exit code 1. Isso é erro?
    Resposta

    Não: 0 = achou, 1 = não achou, 2 = erro de verdade (arquivo ilegível, regex inválida). O mesmo vale para diff.

  4. (Bloco 2) Você cria um hard link e um symlink para app.py e apaga app.py. O que acontece com cada um?
    Resposta

    O hard link segue funcionando: é outro nome para o mesmo inode, e o dado só some quando a contagem de links chega a zero. O symlink guarda um caminho em texto e fica pendurado.

  5. (Bloco 3) O que existe em .git/objects logo depois de git add a.txt, antes de qualquer commit?
    Resposta

    Um blob com o conteúdo do arquivo, endereçado pelo SHA-1 de blob <tamanho>\0<conteúdo>, e uma entrada em .git/index. Nenhuma tree, commit ou ref: o commit é que cria a tree a partir do índice, o objeto commit e move o branch.

  6. (Bloco 3) Se commit guarda snapshot completo, por que o repositório não explode de tamanho?
    Resposta

    O snapshot é uma árvore de referências por hash: o que não mudou reaproveita o mesmo objeto. O gc ainda empacota objetos com compressão delta, uma otimização física invisível ao modelo lógico.

  7. (Bloco 4) Por que um git rebase muda o hash dos commits reaplicados, e quando é seguro?
    Resposta

    O hash inclui o hash do pai; trocar a base muda o primeiro commit e a mudança propaga em cadeia. Os antigos continuam existindo. É seguro em histórico que só você tem.

  8. (Bloco 6) Um git reset --hard HEAD~2 descartou dois commits. Como recuperar, e até quando?
    Resposta

    Só a ref andou: git reflog lista onde o HEAD esteve e git branch rescue <hash> o ancora. O reflog é local e expira (90 dias alcançável, 30 inalcançável). Edição nunca adicionada ao índice não tem objeto e não volta.

Bloco 1 · O sistema operacional visto do terminal

Por que isso importa

Um pipeline de CI mostra verde, mas o deploy não aconteceu: build.sh | tee build.log devolve o exit code do tee, não o do build. Um script funciona no terminal e falha no cron porque o PATH é outro. O agente de código roda o seu teste, lê "0" e declara sucesso, sem olhar o stderr. Nos três, o defeito está no modelo mental, não no comando.

O modelo cabe em cinco peças: processo, descritores de arquivo, exit code, sinais e ambiente. Tudo que o terminal faz é combinação delas.

Terminal, shell e processo são três coisas

O terminal (emulador) é a janela: recebe teclas e desenha caracteres; por baixo, o kernel expõe um tty (na prática, um pseudo-terminal) que a liga aos programas. O shell (bash, zsh, sh, PowerShell) é um programa comum que roda nesse tty, lê linhas e as interpreta: expande variáveis, aplica redirecionamentos, procura executáveis e dispara processos. Fechar o terminal envia SIGHUP ao shell.

Um processo é um programa em execução com identidade própria: um PID (número único), um PPID (o pai), um espaço de memória, um diretório corrente (cwd), um ambiente, uma tabela de descritores abertos e um estado de saída. Todo processo, exceto o primeiro, nasce de outro: o resultado é uma árvore de processos.

$ echo "este shell: $$   pai: $PPID"
este shell: 14   pai: 13
$ sleep 30 & echo "filho em background: $!"; ps -o pid,ppid,stat,comm -p $$,$!; kill $!
filho em background: 17
    PID    PPID STAT COMMAND
     16      15 S    bash
     17      16 S    sleep

O PPID do sleep é o PID do bash: a relação pai-filho é o que importa; os números mudam a cada execução.

Fundamento · fork e exec

Unix cria processos em dois passos. fork() duplica o processo atual (o filho começa como cópia do pai, com a mesma tabela de descritores). Depois o filho chama execve(), que substitui a imagem do programa pelo executável pedido, mantendo o PID, os descritores abertos e o ambiente que o pai montou. A separação é o que torna o redirecionamento barato: entre o fork e o exec o shell reorganiza os descritores do filho, e o programa executado nem sabe que sua saída vai para um arquivo.

Daí um fato que confunde veteranos: cd é builtin (executado dentro do próprio shell). O diretório corrente é atributo do processo, e um filho não altera o do pai. Se cd fosse um programa externo, mudaria o diretório de um processo que morre em seguida.

$ cd /tmp; (cd /; pwd); pwd
/
/tmp

Três descritores e a filosofia do fluxo

Para um processo, um arquivo aberto é um inteiro pequeno, o descritor de arquivo (fd), índice numa tabela mantida pelo kernel. Por convenção todo processo nasce com três: stdin (0), de onde lê a entrada; stdout (1), para onde escreve o resultado; stderr (2), para onde escreve diagnósticos. Os três apontam, por padrão, para o terminal. O ponto de separar 1 de 2 é que o resultado pode ser canalizado para o próximo programa enquanto os avisos continuam visíveis para a pessoa.

$ ls -l /proc/self/fd > saida.txt 2> erro.txt < /dev/null; awk "NR>1{print \$9, \$10, \$11}" saida.txt
0 -> /dev/null
1 -> /tmp/demo-b1/saida.txt
2 -> /tmp/demo-b1/erro.txt
3 -> /proc/21/fd

Com < /dev/null, > saida.txt e 2> erro.txt o shell religou os fds 0, 1 e 2 antes do exec. O fd 3 é o diretório que o próprio ls abriu para listar.

Exit code: a resposta de um processo

Quando um processo termina, deixa um inteiro de 0 a 255, o exit code (ou status). O pai o recolhe (wait) e o shell o expõe em $?. A convenção é universal: 0 significa sucesso; qualquer outro valor, falha ou resultado especial. Além disso, o shell reserva alguns:

A distinção importa ao ler logs: "exit 137" quase sempre é SIGKILL, e em container isso costuma significar que o kernel matou o processo por falta de memória.

Stdout, stderr e quem enxerga o quê

$ ls /nao/existe 2>/dev/null; echo "exit=$?"
exit=2
$ ls /nao/existe >/dev/null; echo "(a mensagem acima veio do stderr)"
ls: cannot access '/nao/existe': No such file or directory
(a mensagem acima veio do stderr)

Na primeira execução a mensagem sumiu (foi para /dev/null) e o exit code 2 permaneceu. Na segunda, o stdout foi descartado e a mensagem de erro continuou visível, porque ela nunca esteve no stdout. A regra de projeto para qualquer ferramenta que você escreva: dados no stdout, diagnóstico no stderr, resultado no exit code. É o contrato que permite compor programas, e é a interface pela qual um agente de código decide se o comando funcionou.

Sinais

Um sinal é uma notificação assíncrona que o kernel entrega a um processo. Ele interrompe o fluxo normal e dispara um handler; se o processo não instalou um, vale a ação padrão (quase sempre terminar). Os que importam no dia a dia:

  • SIGINT (2): Ctrl-C. O driver do tty, ao receber o byte 0x03, envia o sinal ao grupo de processos em primeiro plano, não só ao programa à frente; por isso Ctrl-C interrompe um pipeline inteiro.
  • SIGTERM (15): pedido educado de encerramento (kill PID). O processo pode capturá-lo e fazer limpeza.
  • SIGKILL (9): encerramento imposto pelo kernel. Não pode ser capturado nem ignorado; nenhuma limpeza roda.
  • SIGPIPE (13): escrita em pipe cujo leitor já fechou. A ação padrão mata o escritor; é o que encerra yes | head -1.

Shutdown gracioso, grace period e o papel do PID 1 em container estão no LT01, bloco 1. Aqui basta fixar que um programa bem-comportado trata SIGINT e SIGPIPE de propósito, e é isso que o laboratório faz. O trecho central do pgrep.py (um grep mínimo em Python):

def main(argv: list[str] | None = None) -> int:
    args = _build_parser().parse_args(argv)
    try:
        return _run(args)
    except KeyboardInterrupt:          # Python traduz SIGINT em exceção
        return EXIT_SIGINT             # 130 = 128 + 2
    except BrokenPipeError:            # leitor do pipe fechou (SIGPIPE ignorado pelo Python)
        os.dup2(os.open(os.devnull, os.O_WRONLY), sys.stdout.fileno())
        return EXIT_SIGPIPE            # 141 = 128 + 13

O Python ignora SIGPIPE por padrão e levanta BrokenPipeError na escrita. O dup2 para /dev/null evita um segundo erro quando o interpretador tenta descarregar o stdout ao sair. O teste do laboratório prova o contrato: fecha o lado de leitura do pipe e exige 141.

Ambiente: o que o filho herda

O ambiente é uma lista de pares NOME=valor que o processo recebe no execve. Ele é copiado para o filho; depois disso pai e filho divergem sem se afetar. O shell mantém dois conjuntos: variáveis de shell (internas) e variáveis exportadas (as que entram na cópia).

$ export SEGREDO=abc; bash -c "echo filho vê: \$SEGREDO"; unset SEGREDO; bash -c "echo filho vê: [\$SEGREDO]"
filho vê: abc
filho vê: []
$ X=1; bash -c "echo sem export: [\$X]"; export X; bash -c "echo com export: [\$X]"
sem export: []
com export: [1]

Duas consequências. Nenhum programa altera o ambiente de quem o chamou, e por isso source venv/bin/activate precisa ser sourced (executado no shell atual). E o ambiente não é cofre: todo filho herda tudo que foi exportado.

PATH: como um comando é encontrado

Quando você digita python3, o shell segue uma ordem: (1) apelido (alias); (2) função do shell; (3) builtin; (4) se o nome contém barra (./run.sh, /usr/bin/ls), usa o caminho direto sem procurar; (5) senão, percorre os diretórios de PATH, da esquerda para a direita, e executa o primeiro arquivo executável com esse nome. O resultado fica em cache (hash).

$ type -a python3 | head -3; command -v ls; type cd
python3 is /usr/bin/python3
python3 is /bin/python3
/usr/bin/ls
cd is a shell builtin
$ mkdir bin; printf "#!/bin/sh\necho meu ls\n" > bin/ls; chmod +x bin/ls; PATH="$PWD/bin:$PATH" ls; PATH="$PWD/bin:$PATH" command -v ls; ls | head -2
meu ls
/tmp/demo-b1/bin/ls
bin
erro.txt

O primeiro PATH que contém um ls vence. É assim que um ambiente virtual Python funciona: ativar apenas põe .venv/bin na frente do PATH, e python passa a resolver para o interpretador do projeto. O diretório corrente não está no PATH de propósito: se estivesse, entrar numa pasta com um ls malicioso o executaria. Para diagnosticar "qual binário é esse?", use type -a nome (todos os candidatos, em ordem) e command -v nome (o escolhido). Evite which em scripts: não é padronizado e não enxerga builtins nem aliases.

Se você usa Windows (PowerShell)

O modelo é o mesmo. Exit code do último programa externo: $LASTEXITCODE. Ambiente: $env:PATH (separador ;). Resolução de comando: Get-Command python. O pipe passa objetos, não bytes. Os comandos canônicos do módulo são de macOS/Linux; no Windows, o caminho mais simples é o WSL2.

Exemplo trabalhado: "qual Python é esse?"

Sintoma clássico: pip install funciona e o import falha. Quatro comandos, aplicação direta do bloco:

Decisões e erros comuns

  • Exit codes de ferramentas suas: 0 (ok), 1 (condição negativa esperada, como "não achei"), 2 (uso ou erro real). Evite 126, 127 e valores acima de 128, que o shell já usa.
  • sh ou bash? #!/bin/sh promete só POSIX; #!/usr/bin/env bash libera arrays e pipefail. Passou de umas 30 linhas ou ganhou estruturas de dados: reescreva em Python.
  • $? guarda só o status do último comando; salve com rc=$? se precisar dele duas vezes. E command not found (127) quase nunca é "não instalado": é "não está no PATH deste shell" (cron, systemd, IDE e container têm PATH próprio).
Armadilha que pega sênior · o status do pipeline é o do último comando

Em cmd_que_falha | tee log, o shell devolve o exit code do tee (0). O build falhou, o pipeline "passou". O mesmo ocorre em false | true:

$ false | true; echo "sem pipefail=$?"; set -o pipefail; false | true; echo "com pipefail=$?"
sem pipefail=0
com pipefail=1

Com set -o pipefail (bash, zsh, e POSIX desde a edição de 2024), o status do pipeline é o do último comando que falhou. Mas pipefail tem custo: o 141 de um produtor encerrado por head agora conta como falha. E há um segundo buraco no mesmo terreno: local x=$(cmd) devolve o status do local (0), mascarando a falha do cmd; declare e atribua em linhas separadas. Em script de CI, a combinação segura é set -euo pipefail mais teste explícito do que você espera que falhe.

Armadilha que pega sênior · variável de ambiente não é segredo

Exportar API_KEY a entrega a todo filho e a qualquer processo do mesmo usuário via /proc/<pid>/environ. Passe o valor só ao comando que precisa (API_KEY=... comando) ou leia de arquivo com permissão restrita. Mais no LT01, bloco 2.

Em resumo

Terminal exibe, shell interpreta, processo executa; todo processo tem PID, pai, ambiente e três descritores. Redirecionar é religar descritores antes do exec. O exit code é a resposta (0 = ok; 128+n = sinal) e o status de um pipeline é o do último comando, salvo pipefail. O ambiente é cópia entregue ao filho, nunca de volta. Comandos são achados pelo PATH, da esquerda para a direita; type -a mostra a verdade.

Bloco 2 · Sistema de arquivos e composição de ferramentas

Por que isso importa

Três acidentes reais, todos evitáveis. Um script de limpeza roda rm -rf "$BUILD_DIR/" com a variável vazia e apaga a raiz do que o usuário alcança. Um .sh editado no Windows falha no Linux com bad interpreter. Um find | xargs funciona por meses e quebra no dia em que alguém cria um arquivo com espaço no nome. Em todos, o erro é tratar nome de arquivo como texto simples e ignorar o que o sistema de arquivos e o shell realmente fazem.

Caminhos: absoluto, relativo e o diretório corrente

Um caminho absoluto começa em / (raiz) e aponta para um lugar inequívoco. Um caminho relativo é resolvido a partir do cwd do processo. . é o diretório corrente, .. o pai. Dois pontos importam na prática. Primeiro: o cwd pertence ao processo, então o mesmo script com o mesmo argumento relativo faz coisas diferentes conforme quem o chamou (cron, CI e IDE têm cwd diferentes). Segundo: a/../b não equivale a b quando a é symlink; o kernel resolve .. depois de seguir o link. realpath devolve o caminho canônico, com links resolvidos.

$ mkdir -p proj/src proj/docs; cd proj; echo "print(1)" > src/app.py; pwd; cd src; pwd; cd ..; ls ./src/../docs; realpath src/../src/app.py
/tmp/demo-b2/proj
/tmp/demo-b2/proj/src
/tmp/demo-b2/proj/src/app.py

Em scripts, ancore em algo estável (cd "$(dirname "$0")"; em Python, Path(__file__).resolve().parent) em vez de confiar no cwd herdado.

Nome, inode e link

No Unix, o nome de um arquivo não é o arquivo. Um diretório é uma tabela que mapeia nomes para inodes; o inode guarda o dono, as permissões, os tempos, o tamanho e a localização dos blocos de dados. Um hard link é outra entrada de diretório apontando para o mesmo inode; o inode mantém uma contagem de links. Remover um nome (rm é unlink) decrementa a contagem, e o dado só é liberado quando chega a zero e nenhum processo mantém o arquivo aberto. Um symlink é um arquivo à parte, cujo conteúdo é um caminho em texto, resolvido a cada acesso.

1676 lrwxrwxrwx 1 ada ada 6 Oct 11 17:16 soft.py -> app.py

Observe as duas escritas. O echo trocado > src/app.py truncou e reescreveu o mesmo inode, por isso o hard link viu a mudança. Já muitos editores gravam salvando num arquivo novo e renomeando por cima (a técnica de escrita atômica): o nome passa a apontar para outro inode, e hard links antigos continuam com o conteúdo velho. O mecanismo de rename atômico e o que o fsync garante estão no LT01, bloco 2.

Permissões e dono

Cada inode tem um dono (usuário), um grupo e nove bits: r, w, x para dono, grupo e outros. Em octal, r=4 w=2 x=1, então 644 é rw-r--r-- e 755 é rwxr-xr-x. Em arquivo, x permite executar. Em diretório, r permite listar os nomes e x permite atravessar (acessar entradas dentro dele); sem x você nem abre um arquivo cujo nome conhece.

$ ls -l src/app.py; stat -c "%n modo=%a (%A) dono=%U inode=%i links=%h tamanho=%s" src/app.py
-rw-r--r-- 1 ada ada 9 Oct 11 17:16 src/app.py
src/app.py modo=644 (-rw-r--r--) dono=ada inode=1655 links=1 tamanho=9
$ chmod 000 src; ls src; echo "ls=$?"; chmod 755 src
ls: cannot open directory 'src': Permission denied
ls=2

A umask é uma máscara subtraída das permissões de criação: com 0022, arquivos novos nascem 644; com 077, 600.

Duas ressalvas sobre o Git: ele registra só um bit de permissão (modos 100644 e 100755) e nenhum dono. E chmod 777 como "conserto" esconde que o dono ou o grupo estava errado.

Codificação e fim de linha

Um arquivo é uma sequência de bytes. Texto é uma interpretação desses bytes por uma codificação. A palavra café ocupa 5 bytes em UTF-8 (o é vale 2) e 4 em Latin-1. Abrir um com a codificação do outro gera mojibake (cafÃ©) ou erro de decodificação.

exit=0

O kernel leu a linha #!/bin/sh\r e procurou um interpretador chamado literalmente /bin/sh^M. O exit code 126 vem daí. A defesa é de repositório, não de memória: um .gitattributes com * text=auto eol=lf (ou regras por extensão, como *.sh text eol=lf) normaliza a escolha, independentemente do core.autocrlf de cada máquina. No lab, o pgrep preserva o \r de propósito: um padrão fim$ não casa com fim\r\n, o que faz o mesmo grep "falhar" em arquivos do Windows.

Achar e filtrar: find e grep

find percorre uma árvore e avalia uma expressão por entrada: -type f, -name '*.md' (glob entre aspas, para o shell não expandir antes), -mtime -7, -size +1M, e ações como -exec cmd {} + e -delete. grep filtra linhas por regex: -r recursivo, -n número da linha, -i sem distinção de caixa, -l só nomes, -c contagem, -E regex estendida, -F literal, -v inverte.

$ grep -rn "TODO" --include="*.md" . | sort
./docs/com espaco.md:1:TODO c
./docs/notas.md:1:TODO: a
./docs/notas.md:3:TODO: b

Ferramentas modernas (ripgrep, fd) são mais rápidas e respeitam .gitignore, mas não são padrão em todo lugar: scripts com find/grep, dia a dia com as modernas.

Redirecionamento, pipes e a filosofia Unix

Redirecionar religa um descritor (bloco 1): > arq (fd 1 para o arquivo, truncando), >> arq (anexa), < arq (fd 0 vem do arquivo), 2> arq (fd 2), 2>&1 ("fd 2 passa a apontar para onde o fd 1 aponta agora"). Um pipe a | b cria um canal em memória com buffer limitado (64 KiB por padrão no Linux): se o leitor é lento, o escritor bloqueia, o que dá contrapressão de graça. Os processos de um pipeline rodam ao mesmo tempo, não um após o outro.

A ordem dos redirecionamentos é lida da esquerda para a direita, e é aí que veteranos tropeçam:

$ ls /nao/existe > log.txt 2>&1; echo "--- log.txt:"; cat log.txt
--- log.txt:
ls: cannot access '/nao/existe': No such file or directory
$ ls /nao/existe 2>&1 > log2.txt; echo "--- log2.txt:"; cat log2.txt
ls: cannot access '/nao/existe': No such file or directory
--- log2.txt:

Em > log.txt 2>&1, o fd 1 vai para o arquivo e depois o fd 2 copia o fd 1 (também o arquivo). Em 2>&1 > log2.txt, o fd 2 copia o fd 1 ainda apontando para o terminal, e só então o fd 1 vai para o arquivo: a mensagem de erro aparece na tela e o arquivo fica vazio.

A filosofia Unix (Doug McIlroy, Bell System Technical Journal, 1978): programas que fazem uma coisa bem, que trabalham juntos, com texto como interface universal. Daí sort | uniq -c | sort -rn | head: quatro ferramentas triviais, um ranking de frequência.

Trade-off · quando sair do shell

O texto é interface universal, mas perde estrutura: tudo vira "linhas separadas por espaço" e cada ferramenta reinterpreta. Regra prática: o shell é ótimo para compor programas existentes e ruim para modelar dados. Quando precisar de estrutura aninhada, tratamento de erro por caso ou testes, passe para Python (F02), e mantenha o contrato de exit code e stdout/stderr, que é o que torna seu programa composível de volta.

Exemplo trabalhado: espaços em nomes e o xargs

O xargs lê itens da entrada e monta a linha de comando de outro programa. Por padrão separa por qualquer espaço em branco, e é aí que quebra:

$ find . -name "*.md" | xargs wc -l 2>&1 | tail -3

wc: espaco.md: No such file or directory

$ find . -name "*.md" -print0 | xargs -0 wc -l

$ find . -name "*.md" -exec grep -c TODO {} +

O primeiro caso viu ./docs/com e espaco.md como dois arquivos. As saídas corretas: separar por byte nulo (find -print0 | xargs -0) ou dispensar o xargs com find -exec ... {} +. O mesmo erro aparece em for f in $(ls); itere sobre globs (for f in *.md) ou use while IFS= read -r f, e aspas duplas em toda expansão: "$f".

Erros comuns

  • Variável vazia em caminho destrutivo. O shell expande "$D/" para /: 
    $ D=; echo rm -rf "$D/"
rm -rf /
$ D=; echo rm -rf "${D:?D vazio}/"; echo "exit=$?"
bash: line 1: D: D vazio

    A defesa é ${D:?mensagem} (aborta se vazia ou não definida) e set -u (aborta em variável não definida). Ambos custam uma linha.

  • Esquecer que > trunca antes do comando rodar: sort arq > arq deixa o arquivo vazio. Use arquivo temporário e mv, ou sort -o arq arq.
Armadilha que pega sênior · o glob é expandido pelo shell, não pelo comando

find . -name *.md sem aspas funciona até o dia em que existe um .md no diretório corrente: o shell expande o glob antes do find rodar, que recebe -name README.md e silenciosamente procura só esse nome. O erro não aparece como erro; aparece como "faltou resultado". Em contrapartida, grep "TODO" *.py precisa da expansão do shell. A pergunta que resolve qualquer caso: "quem deve interpretar este padrão, o shell ou o programa?". Se for o programa, use aspas simples.

Em resumo

Nome é entrada de diretório que aponta para um inode; hard link compartilha inode, symlink guarda caminho. Permissão tem nove bits mais a umask; em diretório, x é atravessar. Texto é bytes mais codificação: UTF-8 e LF por convenção explícita. Redirecionamentos são lidos da esquerda para a direita; pipes rodam em paralelo com contrapressão. Aspas em tudo; -print0 ou -exec {} + em vez de xargs cego; ${VAR:?} antes de rm.

Bloco 3 · Git por dentro: objetos, hash de conteúdo, refs e índice

Por que isso importa

Quem aprende Git por receitas acumula crenças erradas: que commit é uma diferença, que branch é uma pasta, que apagar um arquivo o remove do histórico. Cada uma gera um incidente típico: segredo "removido" que continua baixável, commit "perdido" dado como morto, rebase que parece magia. O Git é, por baixo, uma pequena base de objetos imutáveis endereçados por conteúdo, mais alguns arquivos de texto com ponteiros. Lendo esses arquivos à mão, o resto do módulo deixa de ser receita.

Um armazém endereçado por conteúdo

O núcleo é um mapa chave-valor em .git/objects. A chave de cada objeto é o hash do conteúdo: SHA-1 da sequência <tipo> <tamanho>\0<conteúdo>. O valor é essa mesma sequência comprimida com zlib. Duas consequências estruturais: o mesmo conteúdo sempre gera a mesma chave (deduplicação automática), e um objeto nunca muda (mudar o conteúdo muda a chave, ou seja, cria outro objeto).

$ printf "olá, git\n" | git hash-object --stdin
9c07bea4318031a0450fd0e7eb55acde9f12fede
$ printf "blob 10\0olá, git\n" | sha1sum
9c07bea4318031a0450fd0e7eb55acde9f12fede  -

O sha1sum sobre blob 10\0olá, git\n (10 bytes de conteúdo) reproduz exatamente o hash do git hash-object. Não há mágica no cabeçalho, nem nome de arquivo no hash. O Git moderno usa uma variante de SHA-1 que detecta ataques de colisão conhecidos e tem suporte experimental a SHA-256 (hash-function-transition, nas fontes); neste módulo e no leitor do laboratório, SHA-1.

É otimização física: o modelo lógico segue sendo "snapshot por commit". O leitor do laboratório lê só objetos soltos e, depois de um git gc, acusa o que não encontra, de propósito.

Refs e HEAD: os únicos arquivos mutáveis

Objetos são imutáveis; o que muda é o ponteiro. Uma ref é um arquivo de texto com um hash. Um branch é refs/heads/<nome>; tag leve é refs/tags/<nome>; branch remoto rastreado é refs/remotes/origin/<nome>. O HEAD é uma ref especial: normalmente simbólica (ref: refs/heads/main, "estou no main"); se contém um hash cru, estamos em detached HEAD. Fazer um commit = criar o objeto commit e reescrever a ref à qual HEAD aponta.

Entre o diretório de trabalho e o histórico existe o índice (staging area): a tree que será o próximo commit, já materializada como lista de modo, hash, estágio, caminho. Isso dá três "versões" de cada arquivo ao mesmo tempo: a do HEAD (último commit), a do índice e a do diretório de trabalho.

Exemplo trabalhado: ler um repositório sem o Git

O leitor do laboratório (gitobjects.py, pouco mais de 200 linhas, só biblioteca padrão) faz o caminho inverso do git cat-file: descomprime com zlib, separa cabeçalho e corpo no primeiro \0, confere que o SHA-1 do conteúdo bate com o nome e interpreta tree e commit. Decisões, limites e consequências

  • Imutabilidade é a regra do jogo. "Reescrever histórico" (rebase, amend) nunca altera objetos: cria objetos novos e move a ref. Os antigos continuam no armazém até o gc descartá-los por inalcançáveis. É isso que torna a recuperação do bloco 6 possível.
  • Segredo commitado é segredo vazado. Remover o arquivo no commit seguinte cria uma tree sem ele, mas o blob segue acessível por qualquer commit anterior. A resposta é revogar a credencial; reescrever histórico (git filter-repo) é limpeza complementar, não remédio.
Armadilha que pega sênior · o hash do commit inclui data e autor

Dois commits com árvore idêntica e mensagem idêntica têm hashes diferentes se o autor, o committer ou o horário diferirem. Por isso cherry-pick e rebase geram novos hashes mesmo quando o conteúdo é igual, e por isso comparar "este commit já entrou?" pelo hash falha. O laboratório fixa autor e relógio justamente para tornar os hashes reproduzíveis. Para saber se um patch equivalente já foi aplicado, use git cherry ou git log --cherry-pick, que comparam o patch.

Em resumo

O Git é um armazém imutável de objetos (blob, tree, commit, tag) endereçados pelo SHA-1 do conteúdo, mais refs mutáveis. Commit aponta para uma tree completa; o que não mudou é reaproveitado por hash. Branch é um arquivo de 41 bytes; HEAD aponta para um branch ou, destacado, para um hash. add grava blob e entra no índice; commit transforma o índice em trees e commit e move o ponteiro.

Bloco 4 · Fluxo do dia a dia: branches, merge, rebase e conflitos

Por que isso importa

Sexta, 18h: dois branches tocaram o mesmo arquivo e o merge acusa conflito. Quem vê branch como "pasta de código" entra em pânico; quem sabe que branch é um ponteiro e que merge é uma operação sobre três árvores resolve em minutos e, mais importante, sabe quando não reescrever o que os colegas já têm.

Branch é ponteiro; trocar de branch é mover HEAD

No bloco 3, um branch era um arquivo com um hash. Criar um branch escreve esse arquivo; git switch aponta o HEAD para outro branch e reescreve o diretório de trabalho e o índice para casar com a tree do commit de destino. Nada é copiado.

$ git switch -q -c feature; echo F1 > f.txt; git add f.txt; git commit -qm "F1"; git log --oneline --graph --all
* f386880 F1
* f337fba C1 base

Fast-forward: se o branch que recebe é ancestral direto do que chega, não há nada a combinar. O Git só avança o ponteiro e não cria commit.

git stash guarda o trabalho em andamento para trocar de contexto. Por baixo, é um commit (ou melhor, dois: um para o índice, outro para o diretório de trabalho), apontado por refs/stash:

$ git stash push -m "wip de a e b"; git status -sb; git stash list

Os dois pais são o HEAD e o commit do índice. Por padrão o stash não leva arquivos não rastreados (-u inclui-os). stash pop pode conflitar como um merge. Para mais que um dia de trabalho, prefira um branch, que tem nome e não some em stash clear.

Armadilha que pega sênior · merge limpo não é merge correto

O Git detecta conflito textual. Se um lado renomeia uma função e o outro adiciona uma chamada ao nome antigo em outro arquivo, o merge passa sem aviso e o build quebra. Por isso o fluxo saudável tem teste e CI depois do merge (ou, melhor, antes: "merge queue" e CI sobre o resultado da integração, não só sobre o branch). A mesma lógica vale para rebase: reaplicar com sucesso não garante que o código compile.

Armadilha que pega sênior · git pull faz merge sem perguntar

Por padrão, pull é fetch seguido de merge. Quem puxa com commits locais ainda não publicados ganha um commit de merge "Merge branch 'main' of origin/main" que ninguém quis. Defina a política explicitamente: git config pull.rebase true (ou pull.ff only) e o comportamento deixa de depender de humor.

Em resumo

Branch é ponteiro. Merge compara três trees (base, minha, deles): fast-forward só move a ref; three-way cria commit com dois pais; conflito deixa marcadores e estágios 1/2/3 no índice, e --abort desfaz. Rebase copia commits para uma base nova, com hashes novos; use no que é só seu. Cherry-pick copia um patch; stash é um par de commits em refs/stash. Merge limpo ainda precisa de teste.

Bloco 5 · Colaboração: remotes, pull requests, convenções, hooks e assinatura

Por que isso importa

Git é distribuído: cada clone tem o histórico inteiro e é, tecnicamente, um repositório igual ao original. "Servidor central" é convenção humana. Quase todo incidente de colaboração (push rejeitado, histórico duplicado, trabalho do colega sobrescrito) vem de não saber o que fetch, pull e push realmente movem.

Remotes, branches de rastreamento e os três verbos

Um remote é um nome (origin) para uma URL mais um refspec, a regra que mapeia branches remotos para refs locais. O refspec padrão +refs/heads/*:refs/remotes/origin/* diz: "copie cada branch de lá para origin/<nome> aqui". Essas refs origin/main são um cache local do que o servidor tinha na última conversa. Você não commita nelas.

$ git remote -v; git branch -vv
origin	/tmp/demo-b5/origin.git (fetch)
origin	/tmp/demo-b5/origin.git (push)
* main 63444ae [origin/main] C1
$ cat .git/config | sed -n "/remote/,\$p"
[remote "origin"]
	url = /tmp/demo-b5/origin.git
	fetch = +refs/heads/*:refs/remotes/origin/*
[branch "main"]
	remote = origin
	merge = refs/heads/main
  • fetch: baixa objetos novos e atualiza as refs origin/*. Não toca em seus branches nem no diretório de trabalho. É seguro sempre.
  • pull: fetch mais integração (merge ou rebase) do branch rastreado no branch atual.
  • push: envia seus objetos e pede ao servidor que mova a ref remota. O servidor só aceita se for fast-forward (a nova ponta contém a antiga).

Uma colisão típica: Beto já empurrou o commit B1 para o servidor; Ana, sem saber, fez o A1 localmente.

$ git status -sb
## main...origin/main [ahead 1]
$ git fetch origin; git status -sb; git log --oneline --graph --all
From /tmp/demo-b5/origin
   63444ae..0c9a943  main       -> origin/main
## main...origin/main [ahead 1, behind 1]
* b33d6e0 A1 da ana
| * 0c9a943 B1 do beto
|/
* 63444ae C1
$ git push origin main 2>&1 | head -3
To /tmp/demo-b5/origin.git
 ! [rejected]        main -> main (non-fast-forward)
error: failed to push some refs to '/tmp/demo-b5/origin.git'

O status usa o cache: depois do fetch, mostra ahead 1, behind 1. O push foi rejeitado porque a ponta do servidor (0c9a943) não está no histórico da Ana. Integrar, depois enviar:

$ git pull --rebase origin main 2>&1 | tr "\r" "\n" | tail -2; git log --oneline --graph

Successfully rebased and updated refs/heads/main.
* 61c1f14 A1 da ana
* 0c9a943 B1 do beto
* 63444ae C1
$ git push origin main 2>&1 | head -3
To /tmp/demo-b5/origin.git
   0c9a943..61c1f14  main -> main

Reescrever o que já foi publicado

Quando é necessário reescrever um branch publicado (por exemplo, o seu branch de PR), o push precisa ser forçado. --force sobrescreve a ref remota sem olhar; --force-with-lease só sobrescreve se a ref remota ainda for a que você viu no último fetch:

$ git commit -q --amend -m "A1 reescrito"; git push --force-with-lease origin main
To /tmp/demo-b5/origin.git
 ! [rejected]        main -> main (stale info)
error: failed to push some refs to '/tmp/demo-b5/origin.git'

Depois do último fetch da Ana, o Beto empurrou outro commit; o lease dela estava velho (stale info) e o servidor recusou, poupando o trabalho dele. Um --force puro teria apagado o commit do Beto. Observe a ressalva: se você rodar git fetch automaticamente (IDE, hook) antes do push, o lease passa a ser "o que acabou de baixar" e perde a proteção; prefira a forma explícita --force-with-lease=main:<hash esperado>.

Pull requests e convenções

Pull request (GitHub, Bitbucket) ou merge request (GitLab) não é recurso do Git: é da plataforma, que junta um branch, a revisão, o CI e uma ação de integração. Há três integrações, com efeitos distintos no histórico: merge commit (preserva o branch), squash (um commit na principal) e rebase and merge (linear). Escolha uma por repositório. PRs pequenos são revisados; PRs enormes recebem "LGTM".

Mensagem de commit. Resumo no imperativo com até ~50 caracteres ("Add retry to payment client"), linha em branco, corpo com o porquê (o diff já mostra o o quê). O Conventional Commits 1.0.0 estrutura o resumo como tipo(escopo): descrição (feat, fix, ...), com ! ou BREAKING CHANGE: para quebras; mapeia para versionamento semântico (feat → minor, fix → patch). Só rende se alguma ferramenta consome o formato.

.gitignore, hooks e commits assinados

.gitignore lista padrões de arquivos não rastreados que o Git deve ignorar (*.log, .env, __pycache__/). A última regra que casa vence; !padrão reverte. Há três níveis: o .gitignore do repositório (versionado), .git/info/exclude (só seu) e core.excludesFile (global da máquina, bom para arquivos de editor). Não afeta o que já está rastreado:

$ git check-ignore -v a.log .env keep.log
.gitignore:2:*.log	a.log
.gitignore:1:.env	.env
.gitignore:4:!keep.log	keep.log
$ git status -sb | head -3; git check-ignore -v tracked.log; echo "check-ignore exit=$?"
## main...origin/main [ahead 1]
 M tracked.log
?? .gitignore
check-ignore exit=1

O tracked.log casa com *.log mas segue aparecendo como modificado, porque já estava no índice; check-ignore não o reporta como ignorado (exit 1). Para parar de rastrear: git rm --cached tracked.log.

Hooks são programas em .git/hooks/ executados em eventos (pre-commit, commit-msg, pre-push); se um pre-* sai com código diferente de zero, a operação aborta. Como .git/ não é versionado, hooks não viajam com o clone: use git config core.hooksPath .githooks com a pasta no repositório, ou o projeto pre-commit.

$ git commit -m "adiciona env"; echo "exit=$?"; git log --oneline -1
pre-commit: .env nunca entra no repositório
exit=1
47d9988 A1 reescrito
$ git commit --no-verify -q -m "pulando o hook"; git log --oneline -1; git rm -q --cached .env; git commit -q -m "remove env (o segredo continua no histórico)"; git log --oneline -3
37045c6 pulando o hook
26f1916 remove env (o segredo continua no histórico)
37045c6 pulando o hook
47d9988 A1 reescrito

O hook bloqueou o commit (exit 1). --no-verify o contorna, e é por isso que hook local é conveniência; o controle que vale é o mesmo teste no CI e a proteção de branch no servidor. Detalhe do hook acima: ele filtra com --diff-filter=AM (adicionado ou modificado). Sem o filtro, o commit que remove o .env também listaria o arquivo e seria bloqueado, impedindo o conserto.

Commits assinados. Assinar um commit adiciona um cabeçalho gpgsig ao objeto, com assinatura criptográfica sobre o conteúdo do commit. Desde o Git 2.34 a assinatura pode usar chave SSH (além de GPG), o que simplifica a vida de quem já tem uma:

A verificação exige um arquivo de allowed signers (e-mail e chave pública autorizados) e prova que o detentor da chave criou o commit com aquele conteúdo, não que a pessoa é quem diz ser. Plataformas exibem "Verified" quando você cadastra a chave pública na conta.

Armadilha que pega sênior · segredo que foi para o remoto já vazou

Após o push, o segredo está no servidor, nos clones dos colegas, em caches de CI e, em repositório público, em coletores automáticos que varrem commits em segundos. Remover o arquivo em outro commit (bloco 3) não remove o blob; reescrever histórico (git filter-repo) não alcança clones nem forks. A ordem correta é: revogar e trocar a credencial primeiro; só depois, limpar o histórico por higiene. Hook de pre-commit com detector de segredos reduz a chance; o scanner no CI e o push protection da plataforma fecham a porta.

Em resumo

Remote = nome + URL + refspec; origin/* é cache do último fetch. fetch é seguro; pull = fetch + integrar; push só avança por fast-forward. Para reescrever o publicado: --force-with-lease, nunca --force. PR é recurso da plataforma; escolha a estratégia de integração por repositório. Prefira fluxo com branches curtos. .gitignore não afeta rastreados; hooks locais são conveniência; assinatura prova a chave, não a pessoa; segredo publicado se revoga.

Bloco 6 · Investigação e recuperação

Por que isso importa

Produção quebrou e o último deploy juntou 40 commits. Ou alguém rodou o comando errado e o trabalho de dois dias "sumiu". Nos dois casos o histórico é a ferramenta: investigar é fazer perguntas ao grafo de commits; recuperar é lembrar que objetos são imutáveis e que só os ponteiros andaram.

Perguntar ao histórico: log, blame, bisect

git log -S<texto> (o pickaxe) lista os commits em que o número de ocorrências de um texto mudou: ou seja, quando ele foi introduzido ou removido. -G<regex> lista os commits cujo diff tem uma linha adicionada ou removida casando a regex, o que também pega alterações de valor. A diferença aparece num caso simples (a constante TAXA nasce com 0.10 e depois muda para 0.15):

$ git log --oneline -S"TAXA" -- pricing.py
499c9b9 pricing: aplica taxa
$ git log --oneline -G"TAXA = 0\.[0-9]+" -- pricing.py
541c8e5 pricing: taxa sobe para 15%
499c9b9 pricing: aplica taxa
$ git log --format="%h %s" -S"0.10"
541c8e5 pricing: taxa sobe para 15%
499c9b9 pricing: aplica taxa

O -S"TAXA" só vê a criação (a contagem de ocorrências não mudou no commit do 15%). O -G vê as duas alterações. E -S"0.10" acusa quem a introduziu e quem a retirou. Para uma função específica há git log -L :nome:arquivo, e --follow acompanha renomeações de um arquivo.

git blame mostra, para cada linha, o último commit que a alterou:

$ git blame -L1,4 pricing.py | sed -E "s/ [0-9]{4}-[0-9-]+ [0-9:]+ [+-][0-9]{4}//"
541c8e5e (Ada Lovelace 1) TAXA = 0.15
499c9b98 (Ada Lovelace 2)
^aded484 (Ada Lovelace 3) def total(items):
499c9b98 (Ada Lovelace 4)     return sum(i["price"] for i in items) * (1 + TAXA)

O prefixo ^aded484 marca o commit raiz. Blame aponta a última mudança, não a causa: para reformatações use -w, -M/-C (linhas movidas) e --ignore-revs-file.

git bisect é busca binária no histórico: você diz um commit bom e um ruim, o Git faz checkout do meio, você declara bom ou ruim, e a cada passo o intervalo cai pela metade. Com N commits, são ~log₂ N testes (40 commits: 6). Com git bisect run, um script faz o julgamento; o exit code do script é a resposta:

128 ou maiserro: aborta a busca

Reflog: o diário dos ponteiros

Cada vez que HEAD ou um branch se move, o Git anota no reflog (.git/logs/) de onde e para onde. O reset --hard que "perdeu" dois commits apenas moveu o branch; os objetos continuam lá, alcançáveis pelo reflog:

$ git reset --hard HEAD~2; git reflog --format="%h %gd %gs"
HEAD is now at d15a064 c1
d15a064 HEAD@{0} reset: moving to HEAD~2
ea3a018 HEAD@{1} commit: c3 precioso
e02ea3e HEAD@{2} commit: c2
d15a064 HEAD@{3} commit (initial): c1
$ git fsck --lost-found 2>&1 | head -3
dangling commit ea3a018c686d5014eb9710c15c739fecf5e668f3

O git fsck --lost-found acha objetos que nenhuma ref alcança ("dangling"), inclusive blobs que foram para o índice via git add e nunca viraram commit. É a rede de segurança para o stash drop acidental também.

Limites da recuperação

(1) O reflog é local: não vem com o clone nem vai com o push. (2) Expira: padrão de 90 dias para entradas ainda alcançáveis e 30 dias para as inalcançáveis (gc.reflogExpire, gc.reflogExpireUnreachable); depois o git gc pode apagar os objetos. (3) O que nunca passou por git add ou commit não tem objeto: um reset --hard ou git checkout -- . em arquivo só editado é irrecuperável pelo Git (o editor pode ter histórico local). A suíte do laboratório prova o item 2: após reflog expire e gc --prune=now o commit desaparece de fato.

Worktree: vários diretórios, um repositório

git worktree add cria outro diretório de trabalho ligado ao mesmo banco de objetos, com HEAD e índice próprios. Serve para atender um hotfix sem stash nem clone, ou para rodar duas tarefas em paralelo (o bloco 4 do M01 usa isso para agentes concorrentes).

$ git worktree add -q -b hotfix ../W-hotfix; git worktree list | sed -E "s/ +[0-9a-f]{7} / <hash> /"; cat ../W-hotfix/.git; ls .git/worktrees
/tmp/demo-b6/W <hash> [main]
/tmp/demo-b6/W-hotfix <hash> [hotfix]
gitdir: /tmp/demo-b6/W/.git/worktrees/W-hotfix
W-hotfix
$ git worktree add ../W-outra main 2>&1 | grep fatal
fatal: 'main' is already checked out at '/tmp/demo-b6/W'

Num worktree ligado, .git é um arquivo com o texto gitdir: ..., apontando para .git/worktrees/<nome> no repositório principal. Por isso o leitor do laboratório precisa seguir gitdir e commondir. A recusa do segundo comando é regra: o mesmo branch não pode estar em dois worktrees, porque cada um mexeria na mesma ref por baixo do outro.

Em resumo

O reflog é o diário local dos ponteiros (90/30 dias); objetos só somem depois do gc. Worktrees compartilham objetos e não repetem branch.

Conclusão — o essencial em 8 linhas

Terminal exibe, shell interpreta, processo executa; resultado vai no stdout, diagnóstico no stderr, veredicto no exit code.
O status de um pipeline é o do último comando; 128 + n é morte por sinal; 141 é um pipe que fechou.
Nome aponta para inode; aspas em tudo; redirecionamentos são lidos da esquerda para a direita.
Git é um armazém imutável de blobs, trees e commits endereçados por conteúdo, mais refs mutáveis.
Commit é snapshot; branch são 41 bytes; o índice é o próximo commit já montado.
Merge junta; rebase copia (hashes novos) e só vale no que é seu; conflito é decisão sobre três versões.
Remoto é cache no origin/*; force só com lease; hook local é conveniência; segredo publicado se revoga.
Investigue com log -S, blame e bisect run; recupere com reflog: só a ref andou.
