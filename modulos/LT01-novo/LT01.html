O que é um processo

Processo é um programa em execução com identidade própria, memória própria e recursos próprios. Três ideias separam "programa" de "processo": o programa é o arquivo no disco; o processo é o que o sistema cria para executá-lo, com um número de identidade (PID), um pedaço de memória reservado e uma tabela de recursos abertos. Dois processos rodando o mesmo programa não compartilham memória: cada um tem a sua.

Todo processo nasce de outro processo, por dois passos. fork duplica o processo atual: cria um filho quase idêntico, com PID novo, que continua executando da mesma instrução. exec substitui o programa na memória do processo atual por outro programa, mantendo o PID. A combinação cobre os dois casos: duplicar-se para delegar (só fork) e tornar-se outro programa ( fork seguido de exec). Em Python, o módulo subprocess encapsula os dois quando você lança um programa externo; o módulo os expõe fork diretamente — somente POSIX, e por isso a referência de zombies mora num script marcado POSIX.

Cada vez que este bloco recomendar processo contra thread, é essa troca que está em jogo: contenção de falha de um lado, custo de coordenação do outro.

Processo, thread, coroutine — e o scheduler no meio

Os três executam código; diferem no que compartilham e em quem decide a troca. Processo tem memória própria. Thread (fio de execução) mora dentro de um processo e compartilha a memória dele com as demais threads: mais barata de criar, e capaz de corromper o estado alheio com a mesma facilidade. Coroutine (async def em Python) mora dentro de uma thread e só troca de tarefa em pontos explícitos de await: é cooperação declarada no código, não interrupção.

Quem troca processo e thread é o scheduler do sistema operacional: ele interrompe (preempção) e retoma sem pedir licença ao código. Quem troca coroutine é o event loop: um laço, dentro da sua thread, que executa cada coroutine até ela devolver o controle num await e então passa à próxima pronta. O adjetivo que importa é cooperativo: o loop só anda se cada tarefa colaborar devolvendo o controle. Uma tarefa que nunca alcança um await — porque chama algo que bloqueia de verdade — segura o loop inteiro parado. É o mecanismo do AT-001, detalhado na próxima seção.

CPU-bound contra I/O-bound: a decisão entre processo e thread

I/O-bound é o trabalho que passa a maior parte do tempo esperando: resposta de banco, de upstream, de disco, de rede. CPU-bound é o trabalho que passa a maior parte do tempo computando: serialização pesada, compressão, cálculo, inferência local. A classificação é do gargalo, não do programa inteiro — a mesma API pode ser I/O-bound no handler de leitura e CPU-bound no endpoint de relatório.

Contraste"É CPU-bound, então jogo mais threads" — não. Thread divide memória e divide núcleos, mas não multiplica velocidade de computação quando o gargalo é CPU disputada com travas: mais threads que núcleos num laço de cálculo só adiciona troca de contexto e contenção. O sintoma que denuncia o erro é conhecido: CPU no teto, throughput parado, latência subindo com cada thread nova. CPU-bound paraleliza com processos; thread resolve espera, não conta.

O event loop cooperativo: time.sleep contra await

O event loop executa uma coroutine por vez na sua thread. Quando a coroutine alcança await asyncio.sleep(5), ela diz ao loop: "nada para fazer aqui pelos próximos 5 segundos, atenda as outras". O loop registra o despertar e passa adiante. Quando outra coroutine chama time.sleep(5) — a função síncrona do módulo time, que pausa a thread inteira —, não há mensagem alguma ao loop: a thread dorme, o loop dorme junto, e todas as conexões esperando naquele worker ficam paradas pelos mesmos 5 segundos. Nenhum erro é levantado. O sintoma é latência: todas as requisições do worker degradam juntas, mesmo as que nada têm a ver com a chamada lenta.

Trecho conceitual — o par mínimo. Ilustra o mecanismo; o programa completo com medição pertence à referência lab/bloqueio_event_loop.py:

import asyncio
import time

async def cooperativo() -> None:
    await asyncio.sleep(5)  # devolve o controle; o loop atende outras tarefas

async def bloqueante() -> None:
    time.sleep(5)  # pausa a thread; o loop inteiro fica parado 5 s

Com duas tarefas concorrentes de 5 segundos cada, a versão cooperativa conclui ambas em pouco mais de 5 segundos de relógio; a versão com uma chamada bloqueante no meio estica o conjunto para cerca de 10 segundos e atrasa tarefas inocentes. Sinais: SIGINT, SIGTERM, SIGKILL

Sinal é uma notificação numerada que o sistema entrega a um processo: não carrega dados, carrega um pedido — "interrompa", "termine", "recarregue". O processo pode ter um handler (tratador) registrado para aquele sinal: uma função que roda quando ele chega. Sem handler próprio, vale a disposição padrão: terminar, ignorar ou pausar, conforme o sinal. Em Python, o módulo signal registra handlers; em asyncio, a entrega precisa ser reconciliada com o loop, porque o handler roda num contexto onde nem toda operação assíncrona é permitida — a referência lab/shutdown_gracioso.py mostra o desenho correto.

Contraste"Não terminou? Manda SIGKILL logo de primeira" — não. SIGKILL como primeira opção troca um problema visível (processo lento para sair) por corrupção silenciosa: requisição respondida pela metade, arquivo escrito pela metade, transação sem confirmação nem rollback limpo, conexão abandonada que o outro lado descobre por timeout. O lento-para-sair é sintoma com causa — handler ausente, grace curto demais, trabalho que ignora cancelamento — e cada causa tem conserto neste bloco. SIGKILL é o último recurso do orquestrador, depois do grace period; usado como atalho operacional, ele garante que o próximo incidente seja pior que este.

Fundamento de engenharia · Sinais que podem ser ignorados não são comandos. SIGTERM pede; SIGKILL executa. A distinção organiza todo o desenho de deploy: o orquestrador primeiro pede (SIGTERM) e só depois impõe (SIGKILL após o grace period). Um programa que trata SIGTERM como detalhe — sem handler, sem deadline interno, sem cancelamento — converte todo deploy num pequeno desastre de cauda: a maioria das requisições passa, as que estavam no meio morrem. Aceitação do bloco (especificação §4): SIGTERM deixa de aceitar tráfego, encerra ou cancela o trabalho dentro do prazo e devolve o exit code esperado; SIGKILL é explicado como não recuperável.

Grace period e shutdown cooperativo

Grace period (período de graça) é o intervalo que o orquestrador concede entre o SIGTERM e o SIGKILL: o tempo contratado para o processo sair sozinho. Shutdown cooperativo é o que o processo faz com esse tempo, em ordem fixa:

  1. Parar de aceitar trabalho novo. Fechar a porta de entrada — recusar conexões novas, devolver "encerrando" — antes de qualquer outra coisa. Shutdown que aceita trabalho novo durante o grace period é defeito catalogado: cada requisição aceita depois do SIGTERM é uma requisição que o SIGKILL vai matar.
  2. Encerrar ou cancelar o trabalho em curso. Requisições curtas terminam normalmente; trabalho longo recebe cancelamento cooperativo — o mesmo mecanismo de asyncio do M02A — e libera seus recursos. Handler que ignora cancelamento é defeito catalogado: o grace period inteiro escorre sem que nada termine.
  3. Descarregar e sair com o exit code esperado. Fechar conexões, descarregar buffers, devolver 0 se o encerramento foi limpo. O exit code é a última mensagem do processo; deploy que termina em SIGKILL registra a morte, não a saída.

Zombies, coleta e o PID 1 do container

Quando um processo termina, ele não desaparece de imediato: vira zombie (zumbi) — corpo morto que guarda exit code e estatísticas, aguardando o pai ler esse resultado com a chamada wait. A coleta (wait/waitpid) é essa leitura: o pai recolhe o exit code do filho morto, e só então o sistema libera a entrada. Zombie não consome CPU nem memória de trabalho; consome uma vaga na tabela de processos — e, acumulado aos milhares, esgota a tabela.

Zombies existem porque o contrato é entre pai e filho: só o pai pode coletar. Se o pai morre antes, o filho é adotado pelo PID 1. Se o pai vive mas nunca chama wait — processo que lança filhos e ignora o resultado —, cada filho morto vira um zombie permanente. Processo que não coleta child é defeito catalogado, com oráculo próprio (LT01-AT-003: processo coletado e explicado).

DecisãoPID 1 do container: forma executável ou init que coleta. Se o processo principal do container lança filhos (workers, helpers) e não os coleta, os zombies se acumulam pelo tempo de vida do container — semanas, em produção. A defesa tem duas formas: o PID 1 instala coleta para os filhos que adota, ou o PID 1 é um init mínimo que faz isso por ofício. O que nunca é aceitável é descobrir a tabela cheia em incidente: contagem de zombies entra na observabilidade do Bloco 5.

"""Bloqueio do event loop: time.sleep contra await.

Referencia executavel do Bloco 1.
Implementacao verbatim na folha B01-L. So STDLIB (asyncio, time).
Roda em qualquer plataforma; a coleta de zombies e POSIX e mora em coleta_zumbis.py.
"""

from __future__ import annotations

import asyncio
import time


async def tarefa_cooperativa(duracao: float, nome: str) -> str:
    """Cede o loop durante a espera; libera as demais tarefas."""
    await asyncio.sleep(duracao)
    return f"{nome}: cedeu o loop por {duracao}s"


def etapa_bloqueante(duracao: float) -> str:
    """Pausa a thread inteira; o loop fica parado junto."""
    time.sleep(duracao)
    return f"etapa sincrona de {duracao}s concluida"


async def cenario_cooperativo(duracao: float = 1.0) -> dict[str, float]:
    """Duas tarefas cooperativas; mede o tempo de relogio do conjunto."""
    inicio = time.monotonic()
    await asyncio.gather(
        tarefa_cooperativa(duracao, "a"),
        tarefa_cooperativa(duracao, "b"),
    )
    return {"tarefas": 2.0, "relógio_s": time.monotonic() - inicio}


async def cenario_com_bloqueio(duracao: float = 1.0) -> dict[str, float]:
    """Etapa bloqueante no meio do loop; mede o atraso da tarefa inocente."""
    inicio = time.monotonic()
    tarefa = asyncio.create_task(tarefa_cooperativa(0.0, "inocente"))
    etapa_bloqueante(duracao)  # o loop fica parado aqui; a inocente espera
    await tarefa
    return {"tarefas": 2.0, "relógio_s": time.monotonic() - inicio}

"""Shutdown gracioso: fechar a entrada, cancelar, sair no prazo.

Referencia executavel do Bloco 1.

Sinais com semantica POSIX; em Windows, SIGTERM nao tem o mesmo
significado — ver a nota de plataforma do bloco.
"""

from __future__ import annotations

import asyncio
import signal
from collections.abc import Callable

CODIGO_SAIDA_LIMPA = 0
CODIGO_SAIDA_INTERROMPIDA = 130


class Servidor:
    """Guarda o estado do shutdown: entrada aberta ou fechada."""

    def __init__(self) -> None:
        self.aceitando = True
        self.concluidas = 0
        self.canceladas = 0

    def fechar_entrada(self) -> None:
        """Passo 1: nenhum trabalho novo depois do sinal."""
        self.aceitando = False

    async def atender(self, duracao: float) -> str:
        """Trabalho cooperativo: responde a cancelamento."""
        if not self.aceitando:
            raise RuntimeError("entrada fechada: trabalho novo recusado")
        try:
            await asyncio.sleep(duracao)
        except asyncio.CancelledError:
            self.canceladas += 1
            raise
        self.concluidas += 1
        return "concluida"


async def desligar(
    servidor: Servidor,
    em_curso: set[asyncio.Task[object]],
    prazo: float,
) -> int:
    """Passos 2 e 3: cancela, aguarda ate o prazo, devolve o exit code."""
    servidor.fechar_entrada()
    for tarefa in em_curso:
        tarefa.cancel()
    decurso, pendentes = await asyncio.wait(em_curso, timeout=prazo)
    _ = (decurso, pendentes)
    return CODIGO_SAIDA_LIMPA


def instalar_handlers(
    loop: asyncio.AbstractEventLoop,
    ao_sinal: Callable[[], None],
) -> None:
    """SIGTERM e SIGINT pedem shutdown; SIGKILL nao passa por aqui."""
    for numero in (signal.SIGTERM, signal.SIGINT):
        loop.add_signal_handler(numero, ao_sinal)

O nome não é o arquivo: path, inode, link e symlink

Path (caminho) é o nome que conduz a um arquivo; o arquivo em si é outra coisa. Path absoluto começa na raiz e vale por si: identifica o mesmo destino qualquer que seja o diretório atual. Path relativo só faz sentido contra o diretório de trabalho do processo — um estado mutável, herdado do pai e alterável a qualquer momento. Serviço que resolve dado importante por path relativo confia num estado que não controla: o diagnóstico honesto de "sumiu o arquivo" começa perguntando contra qual diretório aquele relativo foi resolvido.

Inode é o registro onde o filesystem guarda o que o arquivo é: tipo, dono, permissões, tamanhos, ponteiros para os blocos de dados e contador de nomes. O nome vive no diretório — uma tabela que liga nomes a inodes — não no inode. Essa separação explica os dois tipos de link. Hard link é um segundo nome, no mesmo filesystem, apontando para o mesmo inode: os dois nomes são o mesmo arquivo, com o mesmo conteúdo e as mesmas permissões; apagar um nome só libera o conteúdo quando o último nome some. Symlink (link simbólico) é um arquivo pequeno cujo conteúdo é outro path: cada abertura o resolve de novo, pode apontar para fora do filesystem, pode apontar para nada (dangling) e pode fechar loop com outro symlink — o sistema desiste com erro de loop após um limite de resoluções.

Montagem e volume: o disco que o programa enxerga

Mount (montagem) é a anexação de um filesystem num ponto da árvore: a partir daquele ponto, os paths servem o conteúdo montado, não o diretório que estava ali. Volume, no vocabulário do laboratório da trilha, é uma montagem com origem e opções declaradas — leitura e escrita, ou só leitura. O programa não distingue "disco local" de "volume montado" pelo path: distingue pelo comportamento — o que aceita escrita, o que recusa, o que sobrevive ao fim do container.

Três consequências organizam o desenho. Primeira: o código da aplicação mora numa árvore que deveria ser só de leitura; os dados moram num diretório declarado, o único gravável. Segunda: escrita em montagem read-only falha com erro de filesystem só de leitura — sintoma de arquitetura, não de permissão mal digitada; o conserto é apontar a escrita ao diretório de dados, nunca afrouxar a montagem. Terceira: /proc é um filesystem virtual de observação — /proc/<pid>/fd, cmdline, environ, limits — mantido pelo sistema: ler ali diagnostica, nunca controla; nenhum programa correto toma decisão de segurança lendo o próprio /proc como se fosse configuração.

Contraste"A escrita falhou, então monto tudo gravável" — não. Montagem gravável onde só leitura basta converte qualquer defeito de path — um escape, um nome mal formado — em escrita permanente no código ou na configuração. O sintoma que denuncia o erro é conhecido: o serviço "funciona" até o dia em que um pedido escreve onde o deploy mora, e a próxima atualização carrega o lixo junto. O desenho correto separa desde o início: árvore de código só de leitura, um diretório de dados gravável, e cada escrita confinada a ele pelo resolvedor do AT-011. Permissão restrita transforma bug em erro negado; permissão folgada transforma o mesmo bug em persistência.

Quem pode o quê: usuário, grupo, mode, umask e ownership

Usuário e grupo são as identidades que o sistema cobra: cada processo carrega um uid (e grupos), cada arquivo declara um dono e um grupo. Mode são as permissões — leitura, escrita, execução — fatiadas em três classes: dono, grupo e outros. Ownership é a resposta a "quem manda neste arquivo": o dono troca permissões e destino; quem não é dono pede licença ao mode. O detalhe que organiza a operação: o usuário total (uid 0, root) passa por cima da checagem de permissão — por isso defeito de permissão testado como root é invisível, e o oráculo AT-012 exige execução como non-root.

Umask é a máscara que o processo aplica a toda criação: permissões pedidas menos a máscara resultam nas permissões reais do arquivo novo. Máscara 022 retira a escrita de grupo e outros; arquivo criado como "leitura e escrita para todos" nasce, sob essa máscara, como "escrita só do dono". Como a máscara é herdada do lançador, serviço que depende da máscara ambiente herda a política de quem o lançou: o correto é declarar a máscara própria no boot, documentada junto do diretório de dados e do usuário de execução.

Escrita que nunca entrega meio-arquivo: temporário e rename atômico

Escrever direto no destino publica cada prefixo do conteúdo: leitor concorrente ou crash no meio entrega meio-arquivo com nome de arquivo íntegro — a corrupção mais difícil de detectar, porque o nome existe e o tamanho parece plausível. O protocolo correto tem três passos: escrever o conteúdo completo num arquivo temporário no mesmo diretório do destino, descarregar os dados, e trocar o nome por rename atômico. A chamada de rename, dentro do mesmo filesystem, troca o nome de uma vez: qualquer observador vê o velho ou o novo, nunca uma mistura. Crash antes do rename deixa o temporário órfão para limpeza; crash depois deixa o novo completo.

O temporário exige disciplina própria. Nome previsível — derivado de horário, PID ou contador — num diretório compartilhado permite que outro processo ocupe o nome primeiro (squatting) ou plante um symlink nele apontando para um alvo sensível: a escrita "temporária" aterrissa onde o atacante escolheu. O correto é criar com exclusividade (falhar se o nome já existir), em diretório privado ao usuário de execução, com nome aleatório, e remover o temporário em qualquer saída — sucesso, erro ou cancelamento.

Trecho conceitual — o protocolo em três passos. Ilustra a ordem; o programa completo pertence à folha B02-L, que executa a escrita e a leitura concorrente como evidência:

# 1. criar temporário exclusivo no mesmo diretório do destino;
# 2. escrever o conteúdo completo e descarregar;
# 3. renomear sobre o destino: observador vê velho ou novo, nunca metade.

Fundamento de engenharia · Atomicidade mora no filesystem, não na linguagem. Nenhuma biblioteca transforma escrita direta em atômica: a garantia vem da chamada de rename dentro de um único filesystem. Entre filesystems distintos o rename vira cópia — e a atomicidade some junto. Por isso o temporário nasce obrigatoriamente no mesmo diretório do destino: mesmo diretório implica mesmo filesystem, e a troca permanece indivisível. Leitor que precisa de consistência lê o nome final; escritor que precisa de durabilidade escreve ao lado e troca por cima.

O que o processo herda e consome: ambiente, descritores e limites

Environment (ambiente) é o bloco de pares nome-valor herdado do pai na criação: configuração que viaja com o processo sem morar no código. Herança é também exposição: o ambiente aparece em /proc/<pid>/environ para o mesmo usuário, é copiado para cada filho e costuma vazar para dumps e páginas de erro quando a aplicação o despeja inteiro no log. Regra do bloco: ambiente carrega configuração e referência a segredo no boot; valor de segredo jamais é impresso, persistido ou devolvido em resposta.

File descriptor (FD, descritor) é o inteiro que representa cada arquivo, socket ou pipe aberto pelo processo: 0, 1 e 2 nascem como entrada, saída e erro herdados. Cada abertura consome um número; cada fechamento o devolve. Vazamento de FD é abrir sem fechar no caminho quente: sob carga, a contagem só cresce até o teto, e novas aberturas — arquivos, conexões, accepts — passam a falhar com erro de limite. O sintoma distingue vazamento de pico legítimo pela direção: pico volta ao baseline quando a carga cessa; vazamento fixa um patamar novo a cada onda. O oráculo AT-010 cobra os dois lados: reproduzir o crescimento e mostrar o retorno ao baseline.

Ulimit / RLIMIT é o teto: cada processo carrega limites de recursos herdados — número de descritores, tamanho de arquivo, memória travada — ajustáveis até um teto rígido. Serviço que presume "descritor infinito" descobre o teto em produção, sob a primeira onda que o desenvolvimento nunca gerou. O desenho declara o limite esperado, mede a contagem real (/proc/<pid>/fd e o rastreador da referência) e dimensiona: limite estourado com contagem estável é capacidade; limite estourado com contagem sempre crescente é vazamento — diagnósticos diferentes, consertos diferentes.

Trecho conceitual — o par mínimo do vazamento. Ilustra o mecanismo; o programa completo com contagem e baseline pertence à referência lab/vazamento_fd.py:

# lado da correção: cada abertura fechada no mesmo caminho; a contagem volta à base.
# pico legítimo desce sozinho; vazamento, nunca.

DiagnósticoComo reconhecer o FD vazando. O padrão é inconfundível quando se sabe o que procurar: erros de abertura surgem sob carga sustentada mas não no teste curto, a contagem em /proc/<pid>/fd sobe em escada a cada onda e nunca desce no vale, e reiniciar "resolve" até a próxima onda. A confirmação vem da correlação — a escada começa junto com o deploy que introduziu a abertura sem fechamento no caminho quente — e a correção é fechar no mesmo caminho que abriu (bloco de fechamento garantido), nunca elevar o limite para acomodar o vazamento. Elevar RLIMIT sem fechar compra tempo e vende o diagnóstico.

Segredos: o que viaja com o processo e o que nunca viaja com o código

Secret exposure (exposição de segredo) é o segredo alcançando quem não deveria: linha de comando, log, resposta de erro, dump, repositório. Cada veículo tem um mecanismo de vazamento próprio. Argumentos da linha de comando são visíveis a qualquer usuário local via lista de processos e /proc/<pid>/cmdline: segredo em argv é segredo publicado na máquina. Logs persistem e replicam: segredo impresso uma vez mora em cada cópia do log daquele dia em diante. Ambiente é o veículo menos pior — visível ao mesmo usuário e herdado pelos filhos — e por isso carrega só a referência no boot, com o valor presente apenas na memória do processo que precisa dele.

Contraste"É só um token de desenvolvimento no código" — não. Segredo no código viaja para o repositório, para cada clone, para cada imagem construída e para cada log que despeja configuração na partida. A remoção posterior não recolhe as cópias: histórico de versão guarda, imagem antiga guarda, backup guarda. O custo de manter é rotação em pânico no dia do incidente; a conduta é fixa desde o primeiro dia — segredo chega pelo ambiente no boot, o código declara só o nome da variável, o valor nunca é impresso nem persistido, e a ausência rende erro explícito em vez de default embutido. O oráculo AT-012 verifica o negativo: segredo ausente em args, em log e no código versionado.

Fundamento de engenharia · Privilégio mínimo é decisão de blast radius. Non-root, diretório de dados único, segredo por ambiente: cada restrição responde à mesma pergunta — "quando (não se) este componente for comprometido, o que ele alcança?". Processo sem privilégio não reconfigura o sistema; escrita confinada não sobrescreve código; segredo fora do código não vaza pelo repositório. Nenhuma das três impede o bug; as três juntas convertem o bug em erro negado em vez de incidente. É a matriz SEC-03 operando: identidade, menor privilégio e auditoria antes do primeiro deploy, com o mapa de permissões e a ausência de segredo como evidência.

"""Descritores e vazamento: abrir rastreado, fechar, voltar ao baseline.

Referencia executavel do Bloco 2.
Implementacao verbatim na folha B02-L. So STDLIB (os).
Sem rede; opera em arquivos possuídos pelo laboratorio.
"""

from __future__ import annotations

import os


class RastreadorFD:
    """Conta descritores abertos por este modulo e ainda nao fechados."""

    def __init__(self) -> None:
        self._abertos: set[int] = set()

    def abrir(self, caminho: str) -> int:
        """Abre para leitura e registra o descritor."""
        fd = os.open(caminho, os.O_RDONLY)
        self._abertos.add(fd)
        return fd

    def fechar(self, fd: int) -> None:
        """Fecha e baixa do registro; fechar fora do registro e erro."""
        if fd not in self._abertos:
            raise ValueError("descritor fora do registro: feche por quem abriu")
        os.close(fd)
        self._abertos.discard(fd)

    def em_aberto(self) -> int:
        """Quantos descritores deste rastreador seguem sem fechar."""
        return len(self._abertos)


def listar_fd_visiveis() -> list[str]:
    """Nomes visiveis em /proc/self/fd; lista vazia onde nao ha proc."""
    try:
        entradas = os.listdir("/proc/self/fd")
    except OSError:
        return []
    return sorted(entradas)


def servir_sem_fechar(rastreador: RastreadorFD, caminho: str, vezes: int) -> int:
    """Lado da falha: abre N vezes sem fechar; publica o acumulado."""
    for _ in range(vezes):
        rastreador.abrir(caminho)
    return rastreador.em_aberto()


def servir_fechando(rastreador: RastreadorFD, caminho: str, vezes: int) -> int:
    """Lado da correcao: cada abertura e fechada; publica o restante."""
    for _ in range(vezes):
        fd = rastreador.abrir(caminho)
        rastreador.fechar(fd)
    return rastreador.em_aberto()

"""Resolucao confinada: pedido nunca escapa da base.

Referencia executavel do Bloco 2.
Implementacao verbatim na folha B02-L. So STDLIB (pathlib).
Sem rede; nega antes de qualquer I/O sensivel.
"""

from __future__ import annotations

from pathlib import Path


class EscapeNegado(ValueError):
    """Pedido resolve para fora da base: negado antes de abrir."""


def resolver_confinado(base: str, pedido: str) -> str:
    """Resolve o pedido contra a base e publica o absoluto confinado.

    Symlinks do caminho sao resolvidos; se o resultado ficar fora
    da base, levanta EscapeNegado sem tocar no destino.
    """
    raiz = Path(base).resolve()
    destino = (raiz / pedido).resolve()
    if destino != raiz and not destino.is_relative_to(raiz):
        raise EscapeNegado(f"fora da base: {pedido!r}")
    return str(destino)


def ler_confinado(base: str, pedido: str) -> bytes:
    """Resolve, nega escape e so entao le os bytes."""
    caminho = resolver_confinado(base, pedido)
    with open(caminho, "rb") as arquivo:
        return arquivo.read()

"""Execucao confinada: non-root, escrita permitida e segredo fora do codigo.

Referencia executavel do Bloco 2.
Implementacao verbatim na folha B02-L. So STDLIB (os, pathlib).
Sem rede; segredo so chega por ambiente, nunca pelo codigo.
"""

from __future__ import annotations

import os
from pathlib import Path


class SegredoAusente(RuntimeError):
    """Variavel de ambiente obrigatoria ausente ou em branco."""


class EscritaNaoPermitida(PermissionError):
    """Destino fora do diretorio de dados declarado."""


def rodando_como_root() -> bool:
    """True somente com uid 0; fora de POSIX nao ha uid 0."""
    geteuid = getattr(os, "geteuid", None)
    if geteuid is None:
        return False
    return bool(geteuid() == 0)


def exige_non_root() -> None:
    """Recusa operar com privilegio total; o oraculo exige non-root."""
    if rodando_como_root():
        raise PermissionError("recusado: execute como usuario sem privilegio")


def carregar_segredo(nome: str) -> str:
    """Le segredo do ambiente; nunca do codigo, de argv ou de log."""
    valor = os.environ.get(nome, "").strip()
    if not valor:
        raise SegredoAusente(f"defina {nome} no ambiente")
    return valor


def destino_escrita_permitido(diretorio_dados: str, nome: str) -> str:
    """Publica o destino somente dentro do diretorio de dados."""
    raiz = Path(diretorio_dados).resolve()
    destino = (raiz / nome).resolve()
    if destino != raiz and not destino.is_relative_to(raiz):
        raise EscritaNaoPermitida(f"fora dos dados: {nome!r}")
    return str(destino)


def relatar_contexto(variavel_segredo: str) -> dict[str, str]:
    """Publica contexto sem jamais incluir o valor do segredo."""
    tem_segredo = "sim" if os.environ.get(variavel_segredo, "").strip() else "nao"
    return {"root": str(rodando_como_root()), "segredo_presente": tem_segredo}

SínteseBloco 2 em seis frases.

  • Path é nome, inode é o arquivo: hard link multiplica nomes do mesmo inode, symlink guarda outro path e resolve para qualquer lugar.
  • Conferir prefixo sem resolver é teatro: a ordem correta junta, resolve tudo e nega fora da base antes de abrir.
  • Código mora em árvore só de leitura; escrita vive num diretório de dados declarado, sob usuário sem privilégio e máscara própria.
  • Escrita durável nasce ao lado e troca por cima: temporário exclusivo no mesmo filesystem mais rename atômico, nunca meio-arquivo publicado.
  • Descritor aberto sem fechar é dívida que a carga cobra: pico desce sozinho, vazamento fixa patamar — e o limite herdado não perdoa nenhum dos dois.
  • Segredo chega pelo ambiente no boot, nunca pelo código, pela linha de comando ou pelo log: o que viaja impresso, vaza.

O nome precisa virar número: hostname, resolver, records e cache

Hostname é o nome legível — localhost, o nome do serviço interno — que precisa virar endereço antes de qualquer byte viajar. Quem executa essa tradução é o resolver: a rotina do sistema que recebe o nome e devolve endereços, consultando fontes locais primeiro e a rede de nomes depois. A confusão que este bloco desfaz: resolver não é conectar. Um nome pode resolver perfeitamente para um endereço onde nada escuta; uma conexão pode recusar num endereço que resolveu sem erro. Cada etapa tem oráculo próprio, e o diagnóstico honesto nunca mistura as duas.

A rede de nomes guarda records (registros): respostas tipadas por nome. A responde com endereço IPv4; AAAA responde com endereço IPv6; CNAME responde com outro nome — um apelido que exige nova resolução até alcançar um A ou AAAA. Cada resposta carrega um TTL (tempo de vida): o prazo, em segundos, durante o qual a resposta pode ser reutilizada sem nova pergunta. Cache é essa reutilização guardada pelo resolver; negative caching é o mesmo mecanismo aplicado à resposta "este nome não existe": o sistema memoriza a ausência pelo TTL negativo para não repetir a pergunta a cada milissegundo.

Essa simetria organiza o diagnóstico: endereço errado após mudança aponta para cache dentro do prazo; nome novo que "não existe" aponta para negativo memorizado; lentidão antes do primeiro pacote aponta para resolver sem resposta, não para rede lenta. O oráculo AT-020 cobra os dois lados do par: nome inexistente identificado como resolução, e resposta lenta identificada como prazo — nunca como "instabilidade da rede".

O endereço precisa virar conversa: IP, porta e socket

IP é o endereço do destino na rede: identifica a máquina, não o programa. Porta é o número que identifica o programa dentro da máquina: o par IP mais porta identifica a conversa. Socket é o descritor que o processo segura para essa conversa — um file descriptor como os do Bloco 2, sujeito ao mesmo teto e ao mesmo vazamento, agora representando uma conexão em vez de um arquivo. Abrir socket sem fechar no caminho quente produz a mesma escada do AT-010; a diferença é o recurso contado do outro lado.

Localhost é o nome contratado deste bloco: resolve para a própria máquina, sem sair dela. Todo experimento de conexão e TLS aqui acontece contra localhost — servidor e cliente no mesmo host, tráfego que nunca atravessa rede externa. O contrato tem motivo duplo: determinismo (sem DNS externo, sem rota, sem firewall no caminho) e segurança do laboratório (nenhum byte de teste alcança serviço alheio). IPv6 aparece como segundo endereço do mesmo nome quando a pilha local o oferece; a referência publica a lista completa em vez de presumir uma família.

O transporte precisa virar acordo: handshake, retransmissão, close e reset

Handshake TCP é o acordo de três passos que abre a conversa: o cliente propõe com SYN, o servidor aceita com SYN-ACK, o cliente confirma com ACK. Só depois do terceiro passo existem bytes de aplicação — e só a partir daí faz sentido falar em TLS ou HTTP. A consequência diagnóstica é direta: falha antes do acordo completo pertence ao transporte; falha depois pertence à camada que assumiu a conversa.

Pacote pode se perder; a conversa não pode fingir que não. Retransmissão é o reenvio do segmento sem confirmação após um prazo (RTO, prazo de retransmissão): o remetente espera, reenvia, dobra a espera. Perda isolada vira latência — a conversa segue, mais lenta. Perda sustentada vira desistência — o prazo estoura e o erro sobe como timeout de transporte. O padrão distingue perda de recusa: perda silencia e demora; recusa responde de imediato.

Encerrar tem duas formas, e confundi-las é o defeito central do AT-021. Close (FIN) é o encerramento negociado: cada lado declara "terminei de enviar", o outro confirma, os dados já entregues permanecem válidos. Leitura após close limpo devolve os bytes restantes e depois o fim — EOF, sem erro. Reset (RST) é o abort: a conversa é descartada sem negociação — porta fechada que recebe tentativa, programa que morre com dados por ler, abort explícito pelo sistema. Leitura após reset levanta erro de conexão, não EOF. Refused (conexão recusada) é o reset do primeiro passo: tentativa contra porta sem escuta, respondida na hora.

SinalOnde nasceEvidência que distingue
RefusedNo connect: porta sem escuta responde recusando de imediato.Falha rápida no connect, sem bytes trocados. Aponta para programa ausente ou porta errada — nunca para nome.
Reset pós-aceiteNa leitura: a conversa foi aceita e depois abortada (RST).Connect passa, leitura levanta erro de conexão em vez de EOF. Aponta para crash, abort ou backlog estourado do outro lado.
Timeout de transporteNa espera: SYN sem resposta ou confirmação que nunca chega, até o prazo.Falha lenta, sem resposta. Aponta para silêncio no caminho — filtro, rota, perda sustentada — e pede investigação de caminho, não de porta.
Close limpoNa despedida: FIN negociado após os dados.Leitura devolve bytes e depois EOF, sem erro. É o fim saudável; tratar EOF como falha é o falso positivo deste bloco.

Contraste"Recusou, resetou, expirou — tudo é erro de conexão" — não. Cada sinal nasce num ponto distinto do acordo e prescreve conserto distinto: refused manda conferir programa e porta; reset manda investigar o abort após o aceite; timeout manda investigar silêncio no caminho; EOF manda aceitar o fim negociado. Colapsar os quatro num único "erro de rede" prescreve o conserto errado com confiança total: reiniciar serviço para problema de rota, conferir DNS para porta fechada, aumentar timeout para abort. O oráculo AT-021 cobra a separação por evidência — em qual chamada falhou, após quantos bytes, com que erro — nunca por palpite.

O canal precisa virar confiança: TLS 1.3, SNI, cadeia, hostname e validade

TLS 1.3 é o protocolo que transforma a conversa TCP em canal autenticado e cifrado — e roda antes de qualquer byte de aplicação: primeiro o TCP acorda, depois o TLS confia, só então o HTTP fala. O handshake negocia versão, cifras e chaves efêmeras, com sigilo futuro (forward secrecy) por construção: chaves de sessão descartadas após o uso não revelam o passado se o material de longo prazo vazar depois. Em uma ida e volta o cliente já envia dados — o servidor prova identidade com certificado, o cliente verifica, e a conversa segue cifrada.

O cliente conta ao servidor qual nome procura antes de ver o certificado: essa indicação é o SNI (indicação do nome do servidor), enviada em claro no início do handshake para que o servidor escolha o certificado certo entre os vários que pode servir. Certificado é a declaração assinada que liga um nome a uma chave pública, com janela de validade e assinatura de uma autoridade. Cadeia (chain) é a sequência de assinaturas do certificado do servidor até uma raiz confiável: cada elo assina o anterior, e a verificação percorre os elos até uma âncora que o cliente já confia. Cadeia quebrada — raiz desconhecida, elo ausente, assinatura inválida — reprova antes de qualquer checagem de conteúdo.

Com a cadeia íntegra, duas perguntas decidem a confiança — e são os dois oráculos do AT-022. Hostname: o certificado cobre o nome pedido? A verificação lê os nomes alternativos do certificado e recorre ao nome comum como legado; curinga vale só no rótulo mais à esquerda. Divergência reprova, mesmo com cadeia perfeita: o canal seria cifrado com o servidor errado. Validade: o agora está dentro da janela do certificado? Expirado ou ainda-não-válido reprova, mesmo com nome certo: declaração fora do prazo não declara nada. Relógio local errado reprova certificado certo — e o diagnóstico honesto confere o relógio antes de culpar a autoridade.

Contraste"O certificado atrapalha o teste, então desligo a verificação" — nunca. Desativar a verificação converte qualquer handshake em teatro: a cifra continua, a autenticação some, e o teste passa contra impostor, expirado ou interceptador sem registrar diferença. O sintoma que denuncia o erro é conhecido: a suíte fica verde no laboratório e o incidente chega em produção, onde o adversário existe. A conduta é fixa — verificação sempre ligada, cadeia contra âncora declarada, hostname e validade conferidos a cada handshake — e o oráculo AT-022 reprova qualquer "correção" que desligue a checagem. Falha de certificado se conserta no certificado, no nome ou no relógio; nunca no cliente que verifica.

Fundamento de engenharia · TLS autentica o servidor, não absolve a aplicação. Handshake verde declara três coisas e só três: o par possui a chave do nome pedido, a conversa está cifrada com chaves efêmeras, ninguém no meio lê ou altera sem detecção. Nada declara sobre autorização, correção dos dados ou saúde do serviço — essas camadas moram acima e têm oráculos próprios nos Blocos 4–6. Cada vez que este bloco mandar "falha de TLS", leia-se: a camada de confiança recusou a conversa antes da aplicação falar. O que a aplicação faria com a conversa nunca chegou a ser testado.

O atalho tem limite honesto: QUIC

QUIC é o transporte que carrega o HTTP/3: roda sobre UDP, integra o handshake TLS 1.3 na abertura da conexão e multiplexa fluxos independentes dentro dela. O problema que o tornou necessário mora no TCP: num conjunto de requisições sobre uma conexão, a perda de um pacote trava todas as demais até a retransmissão — bloqueio de cabeça de fila do transporte. QUIC move a recuperação para cada fluxo: perda num fluxo não pausa os outros, e a migração de conexão sobrevive à troca de endereço sem novo handshake completo.

O limite honesto deste bloco: a stdlib Python não implementa QUIC, e este bloco não finge o contrário. Nenhuma referência executável abaixo abre conexão QUIC; nenhum oráculo exige pacote UDP real. QUIC entra na teoria porque o diagnóstico precisa dele: diante de HTTP/3, "handshake", "reset" e "retransmissão" mudam de número de pacote sem mudar de significado — e o aluno que domina o acordo TCP transfere o raciocínio sem recomeçar do zero. A medição real de QUIC pertence a trilhas com pilha dedicada; aqui, o veredito sobre HTTP/3 usa o mesmo breakdown por camadas, com a camada de transporte lida nos sinais que a implementação expõe.

"""Resolução local: nome vira endereço sem rede externa.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L. So STDLIB (socket, time).
Opera sobre localhost e nomes .invalid; nenhum DNS externo.
"""

from __future__ import annotations

import socket
import time


class NomeInexistente(ValueError):
    """Hostname sem registro: equivalente local de NXDOMAIN."""


class ResolucaoExpirada(TimeoutError):
    """Resposta local mais lenta que o prazo contratado."""


def resolver_local(hostname: str, prazo: float) -> list[str]:
    """Resolve usando só recursos locais e publica os endereços.

    "localhost" resolve via getaddrinfo sem sair da máquina.
    Qualquer outro nome fora do contrato rende NomeInexistente
    sem tocar na rede. O prazo é validado na entrada.
    """
    if not prazo > 0:
        raise ValueError("prazo precisa ser positivo")
    nome = hostname.strip().lower()
    if not nome:
        raise ValueError("hostname vazio não resolve")
    if nome != "localhost" and not nome.endswith(".localhost"):
        raise NomeInexistente(f"sem registro: {hostname!r}")
    try:
        infos = socket.getaddrinfo(nome, None, type=socket.SOCK_STREAM)
    except socket.gaierror as erro:
        raise NomeInexistente(f"sem registro: {hostname!r}") from erro
    enderecos: list[str] = []
    for _, _, _, _, sockaddr in infos:
        ip = str(sockaddr[0])
        if ip not in enderecos:
            enderecos.append(ip)
    return enderecos


def resolver_com_atraso(hostname: str, prazo: float, atraso: float) -> list[str]:
    """Lado do timeout: atraso local excede o prazo e vira ResolucaoExpirada.

    O atraso acontece na máquina, nunca na rede: prova que o
    chamador respeita o prazo antes de qualquer resposta.
    """
    if not prazo > 0 or atraso < 0:
        raise ValueError("prazo positivo e atraso não negativo")
    inicio = time.monotonic()
    time.sleep(atraso)
    if time.monotonic() - inicio > prazo:
        raise ResolucaoExpirada(f"{hostname!r} excedeu {prazo}s")
    return resolver_local(hostname, prazo)

Referência executável 2 — lab/conexao_tcp.py. Separa refused no connect de reset na leitura, com servidores só em 127.0.0.1 e porta efêmera (oráculo LT01-AT-021: estados distinguidos por evidência). Só stdlib (socket, struct, threading); o socket devolvido pertence ao chamador:

"""Conexão TCP local: refused nasce no connect, reset nasce na leitura.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L. So STDLIB (socket, struct, threading).
Servidores só em 127.0.0.1 com porta efêmera; nenhum tráfego externo.
"""

from __future__ import annotations

import socket
import struct
import threading


class ConexaoRecusada(ConnectionError):
    """Porta fechada: o sistema recusou no connect."""


class ConexaoResetada(ConnectionError):
    """Conversa abortada: RST após o aceite, visível na leitura."""


def porta_livre_fechada() -> int:
    """Reserva uma porta efêmera e a libera: o próximo connect recusa."""
    with socket.socket(socket.AF_INET, socket.SOCK_STREAM) as sonda:
        sonda.bind(("127.0.0.1", 0))
        return int(sonda.getsockname()[1])


def servir_reset_uma_vez() -> int:
    """Aceita uma conexão em 127.0.0.1 e a aborta com RST; devolve a porta.

    O RST é forçado com SO_LINGER zerado: a leitura do cliente falha
    em vez de receber EOF limpo. Thread daemon; morre sozinha.
    """
    escuta = socket.socket(socket.AF_INET, socket.SOCK_STREAM)
    escuta.bind(("127.0.0.1", 0))
    escuta.listen(1)
    porta = int(escuta.getsockname()[1])

    def atender() -> None:
        with escuta:
            conn, _ = escuta.accept()
            with conn:
                conn.setsockopt(
                    socket.SOL_SOCKET,
                    socket.SO_LINGER,
                    struct.pack("ii", 1, 0),
                )
                # Sair do with fecha: com linger zero, o fechamento vira RST.

    processo = threading.Thread(target=atender, daemon=True)
    processo.start()
    return porta


def conectar(host: str, porta: int, prazo: float) -> socket.socket:
    """Conecta em host:porta; porta fechada vira ConexaoRecusada.

    O socket devolvido pertence ao chamador: feche após o uso.
    Reset pós-aceite não aparece aqui; aparece na leitura.
    """
    try:
        return socket.create_connection((host, porta), timeout=prazo)
    except ConnectionRefusedError as erro:
        raise ConexaoRecusada(f"{host}:{porta} recusou") from erro


def ler_ate_reset(conexao: socket.socket, prazo: float) -> None:
    """Lê até o abort: RST vira ConexaoResetada; EOF limpo retorna.

    Distingue o fim negociado (bytes vazios) do abort (reset).
    """
    conexao.settimeout(prazo)
    try:
        while True:
            parte = conexao.recv(4096)
            if not parte:
                return
    except ConnectionResetError as erro:
        raise ConexaoResetada("par abortou a conversa (RST)") from erro

Referência executável 3 — lab/tls_local.py. Verifica hostname e validade sobre o certificado publicado, e executa o handshake contra 127.0.0.1 com verificação sempre ligada (oráculo LT01-AT-022: falha validada; desligar a verificação nunca é correção). Só stdlib (socket, ssl, time); o material de certificado pertence à folha L:

"""TLS local: hostname e validade verificados, verificação nunca desligada.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L. So STDLIB (socket, ssl, time).
Handshake só contra 127.0.0.1 com material da folha L; sem rede externa.
"""

from __future__ import annotations

import socket
import ssl
import time


class HostnameInvalido(ValueError):
    """Certificado não cobre o hostname pedido."""


class CertificadoExpirado(ValueError):
    """Certificado fora da janela notBefore/notAfter."""


def _casa(padrao: str, nome: str) -> bool:
    """Curinga só no rótulo mais à esquerda; o resto é igualdade exata."""
    texto = padrao.strip().lower()
    alvo = nome.strip().lower()
    if texto.startswith("*."):
        sufixo = texto[1:]
        return alvo.endswith(sufixo) and "." in alvo[: -len(sufixo)]
    return texto == alvo


def verificar_hostname(cert: dict[str, object], hostname: str) -> None:
    """Confere SAN dNSName e recorre ao CN; divergência vira HostnameInvalido.

    Subconjunto contratado da verificação: SAN primeiro, CN como
    recurso legado, curinga restrito. Nada aqui toca na rede.
    """
    if not hostname.strip():
        raise ValueError("hostname vazio não verifica")
    nomes: list[str] = []
    alternativa = cert.get("subjectAltName", ())
    if isinstance(alternativa, tuple):
        for tipo, valor in alternativa:
            if tipo == "DNS" and isinstance(valor, str):
                nomes.append(valor)
    if not nomes:
        sujeito = cert.get("subject", ())
        if isinstance(sujeito, tuple):
            for bloco in sujeito:
                if not isinstance(bloco, tuple):
                    continue
                for chave, valor in bloco:
                    if chave == "commonName" and isinstance(valor, str):
                        nomes.append(valor)
    for candidato in nomes:
        if _casa(candidato, hostname):
            return
    raise HostnameInvalido(f"certificado não cobre {hostname!r}")


def verificar_validade(cert: dict[str, object], agora: float) -> None:
    """Confere notBefore/notAfter contra o relógio dado.

    Fora da janela vira CertificadoExpirado; relógio errado reprova
    certificado certo, e o diagnóstico confere o relógio primeiro.
    """
    antes = cert.get("notBefore")
    depois = cert.get("notAfter")
    if not isinstance(antes, str) or not isinstance(depois, str):
        raise ValueError("certificado sem janela de validade legível")
    inicio = ssl.cert_time_to_seconds(antes)
    fim = ssl.cert_time_to_seconds(depois)
    _ = time.gmtime(0)
    if agora < inicio:
        raise CertificadoExpirado("certificado ainda não válido para este relógio")
    if agora > fim:
        raise CertificadoExpirado("certificado expirado para este relógio")


def apertar_mao(
    host: str, porta: int, cafile: str, hostname: str, prazo: float
) -> dict[str, object]:
    """Executa o handshake TLS e publica o certificado do par.

    Contexto com check_hostname ligado e âncora da folha L: hostname
    divergente, expirado ou cadeia desconhecida falha aqui via
    ssl.CertificateError/SSLError e a conversa nunca segue adiante.
    """
    contexto = ssl.create_default_context(cafile=cafile)
    contexto.check_hostname = True
    contexto.verify_mode = ssl.CERT_REQUIRED
    with (
        socket.create_connection((host, porta), timeout=prazo) as bruto,
        contexto.wrap_socket(bruto, server_hostname=hostname) as tunel,
    ):
        tunel.settimeout(prazo)
        par = tunel.getpeercert()
        if not isinstance(par, dict):
            return {}
        return dict(par)

A mensagem não é o fio: semântica contra framing

Semântica é o significado da troca: o método declara a intenção (GET lê, POST entrega para processar, PUT substitui, DELETE remove), o alvo declara sobre o que, os campos (headers) carregam metadados, o código de status declara o desfecho, e o corpo carrega a representação. Framing é como esses elementos viajam codificados no fio: linha de requisição e campos em texto no HTTP/1.1, quadros binários numerados no HTTP/2, fluxos sobre QUIC no HTTP/3. A mesma semântica — o mesmo GET, o mesmo 200 — pode viajar em três framings distintos sem mudar de sentido.

A confusão que este bloco desfaz: tratar problema de framing como problema de aplicação. Conexão que não reutiliza, resposta que trava no meio, proxy que corta corpo grande — nenhum desses sintomas acusa o método ou o código de status; todos moram abaixo do significado, na codificação e no transporte da mensagem. O diagnóstico honesto pergunta primeiro "o que foi dito" e depois "como viajou", e nunca reescreve a aplicação para consertar o fio.

Quem separa as camadas diagnostica cada uma no seu oráculo; quem as confunde aumenta o pool para consertar a semântica.

O fio aprende a dividir: HTTP/1.1, 2 e 3

HTTP/1.1 fala uma requisição por vez em cada conexão: o keep-alive permite reutilizar a mesma conexão para a próxima requisição em sequência, mas enquanto uma resposta viaja, as demais esperam — o bloqueio de cabeça de fila (head-of-line blocking): a lentidão da primeira pune todas as enfileiradas atrás dela. A saída histórica foi abrir várias conexões em paralelo, e é dessa época que vem a intuição de que "mais conexões é mais velocidade" — intuição que o pool deste bloco aposenta com contagem.

HTTP/2 divide a conexão em streams (fluxos lógicos numerados): cada requisição-resposta ganha seu stream, e os streams viajam multiplexados — quadros intercalados daqui e dali na mesma conexão, sem que a lentidão de um trave os demais no nível do protocolo. O bloqueio de cabeça de fila do 1.1 some entre streams; resta o do transporte, pois todos os streams ainda viajam num único TCP, e a perda de um pacote continua pausando a conexão inteira até a retransmissão.

HTTP/3 troca o transporte: roda sobre QUIC, que integra o handshake TLS 1.3 na abertura e move a recuperação de perda para cada fluxo — perda num fluxo não pausa os outros, como visto no Bloco 3. O limite honesto continua valendo: a stdlib Python não implementa HTTP/2 nem HTTP/3, e nenhum programa deste bloco abre essas conexões; o que o diagnóstico transfere entre versões é o raciocínio por camadas, com cada framing lido nos sinais que a implementação expõe.

O meio tem opinião: reverse proxy

Reverse proxy é o servidor que recebe a requisição do cliente e a repassa ao serviço de trás — terminando o TLS da borda, escolhendo o destino, enfileirando e aplicando seus próprios prazos. Do ponto de vista do diagnóstico, o proxy é uma segunda aplicação com fila e relógio próprios: tem timeout de leitura do cliente, timeout de espera pelo upstream e timeout de escrita da resposta, e cada um deles pode disparar antes ou depois dos prazos do serviço. Proxy com prazo menor que o serviço aborta trabalho saudável; proxy com prazo maior que o serviço segura conexão morta ocupando slot.

A regra de coerência deste bloco: prazos se ordenam de fora para dentro em cadeia conhecida — cliente acima do proxy acima do serviço acima do upstream — e qualquer inversão produz um dos dois desperdícios: abortar o que ia concluir ou sustentar o que já morreu. O oráculo AT-031 cobra a cadeia declarada, não valores decorados: cada prazo tem dono, cada dono tem número, e a soma fecha dentro do deadline.

Contraste"O proxy devolveu 502/504, então o serviço quebrou" — não necessariamente. Erro na borda declara o ponto de vista da borda: o proxy desistiu de esperar, não viu o serviço morrer. A evidência que separa está nos dois lados do relógio — quanto o proxy esperou contra quanto o serviço levou — e na fila entre eles. Culpar o serviço pelo veredito do proxy prescreve o conserto errado: escalar aplicação para prazo de borda, reescrever handler para fila do meio. O diagnóstico lê os dois relógios antes de nomear o culpado.

O recurso é contado: pools de conexão

Pool de conexões é o conjunto contado e reutilizável de conexões abertas contra um destino: em vez de abrir e fechar TCP mais TLS a cada requisição, o cliente retira uma conexão livre, usa e devolve. Quatro parâmetros definem o pool — e os quatro aparecem no oráculo AT-030. Conexão: o que se guarda (contra qual destino, com qual custo de abertura). Tamanho: quantas conexões no máximo; acima do teto, o pedido espera. Fila: onde os pedidos excedentes aguardam um slot livre, em ordem de chegada. Timeout de aquisição: quanto um pedido pode esperar na fila antes de desistir com erro próprio — distinto do timeout da requisição, pois falha antes de qualquer byte viajar.

Esgotamento é o estado em que todos os slots estão ocupados e a fila cresce até o prazo: o sintoma é latência que sobe em degrau e erros de aquisição, nunca erro do serviço — o destino pode estar ocioso enquanto o cliente se recusa a ele por falta de slot. A armadilha clássica: pool menor que a concorrência transforma paralelismo em fila seriada com prazo, e a "correção" ingênua — aumentar o pool — transfere a pressão ao destino, que satura e devolve lentidão a todos. Dimensionar pool é declarar quanta concorrência o destino aguenta, não quanta o cliente deseja.

O tempo tem dono: timeouts por fase e deadline end-to-end

Timeout por fase é o teto de cada etapa — conectar, enviar, aguardar resposta, ler o corpo, adquirir slot no pool: cada fase tem relógio próprio porque cada fase falha do seu jeito. Timeout único e infinito é a falha catalogada da especificação: sem teto por fase, uma etapa presa segura todas as demais sem declarar onde, e o diagnóstico recebe apenas "lento" sem fase, sem número, sem dono.

Deadline end-to-end é o teto da operação inteira, do primeiro byte ao último: nenhuma fase, sozinha ou somada, pode ultrapassá-lo sem justificativa registrada. O orçamento por fase divide o deadline entre as etapas — conectar leva uma fração, ler o corpo leva outra — e cada fase recebe o menor entre seu orçamento e o restante do deadline. A aritmética é o oráculo AT-031: retry além do deadline reprova, fase sem orçamento reprova, operação que excede sem registro reprova.

Fundamento de engenharia · Prazo se divide de cima para baixo, nunca se soma de baixo para cima. O deadline nasce no dono da operação e desce como orçamento: cada camada — proxy, serviço, upstream — recebe sua fração e propaga o restante adiante. Quando cada camada escolhe seu próprio timeout sem conhecer o teto, a soma estoura o deadline por construção, e o retry multiplica o estouro. Orçamento declarado, propagado e checado nos limites: é assim que "nenhuma operação excede deadline sem justificativa" sai do slogan e vira teste com relógio controlado.

O não precisa viajar: cancelamento e retry seguro

Cancelamento é a propagação do "não precisa mais": o cliente desiste — fecha a conexão, encerra o stream — e o servidor precisa ficar sabendo para interromper o trabalho e liberar slot, memória e upstream. Sem propagação, trabalho cancelado segue consumindo recurso até o fim para entregar resposta a ninguém: o servidor trabalha de graça enquanto o pool sangra. A propagação atravessa as camadas como o sinal do Bloco 1 atravessa o processo: cada limite verifica e cada verificação decide — continuar ou soltar.

O cancelamento deste bloco é cooperativo: o sinal marca, o trabalho verifica nos limites e interrompe onde é seguro interromper — nunca à força no meio de uma escrita. É o mesmo padrão do M02A (B06/B08), agora entre cliente e servidor: verificar antes e depois, produzir item a item com checagem a cada passo, aguardar com prazo. O oráculo AT-032 cobra o observável: trabalho interrompido, recursos liberados, nenhum resíduo após o cancelamento.

Retry seguro responde a uma pergunta estreita: quando repetir é permitido. Três condições, todas obrigatórias. Idempotência: só método que repete sem duplicar efeito — o conjunto contratado; POST e desconhecidos nunca repetem. Teto de tentativas: número máximo declarado, pois cada repetição custa latência e carga. Prazo restante: repetir só com deadline de sobra, pois retry além do deadline é a tempestade catalogada — cada cópia estoura o teto e pede mais cópias. Retry que ignora qualquer das três amplifica a carga exatamente quando o sistema menos aguenta: a falha vira tempestade com a assinatura do remédio.

Contraste"Faliu, tenta de novo — tentar nunca piora" — piora. Repetir requisição não idempotente duplica o efeito no destino: duas cobranças, dois registros, dois envios. Repetir sem teto transforma um upstream lento em dez upstream lentos simultâneos. Repetir sem prazo empilha trabalho morto sobre deadline estourado. O oráculo AT-031 mede os três freios juntos: método no conjunto, tentativa abaixo do teto, restante acima de zero — faltando um, a repetição é amplificação, não correção.

"""Pool local de conexões: tamanho fixo, fila FIFO e prazo de aquisição.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L. So STDLIB (queue, threading).
Conexões nascem da fabrica contratada; nenhum socket externo aqui.
"""

from __future__ import annotations

import queue
import threading
from collections.abc import Callable


class PoolEsgotado(TimeoutError):
    """Nenhum slot livre dentro do prazo de aquisição contratado."""


class PoolLocal:
    """Pool de tamanho fixo com fila FIFO e prazo de aquisição.

    A fabrica cria o recurso sob demanda até o teto; a partir daí,
    adquirir espera um slot livre até o prazo e levanta PoolEsgotado.
    """

    def __init__(
        self,
        fabrica: Callable[[], object],
        tamanho: int,
        prazo_aquisicao: float,
    ) -> None:
        if tamanho < 1:
            raise ValueError("tamanho precisa ser ao menos 1")
        if not prazo_aquisicao > 0:
            raise ValueError("prazo_aquisicao precisa ser positivo")
        self._fabrica = fabrica
        self._tamanho = tamanho
        self._prazo = prazo_aquisicao
        self._livres: queue.Queue[object] = queue.Queue()
        self._criadas = 0
        self._trava = threading.Lock()

    def adquirir(self) -> object:
        """Devolve recurso livre ou recém-criado; sem slot no prazo: PoolEsgotado."""
        try:
            return self._livres.get_nowait()
        except queue.Empty:
            pass
        with self._trava:
            pode_criar = self._criadas < self._tamanho
            if pode_criar:
                self._criadas += 1
        if pode_criar:
            return self._fabrica()
        try:
            return self._livres.get(timeout=self._prazo)
        except queue.Empty:
            raise PoolEsgotado(f"sem slot livre em {self._prazo}s") from None

    def liberar(self, item: object) -> None:
        """Devolve o slot à fila; quem adquiriu devolve exatamente uma vez."""
        self._livres.put(item)

    def estatisticas(self) -> dict[str, int]:
        """Publica tamanho, livres e em_uso para o oráculo AT-030."""
        livres = self._livres.qsize()
        with self._trava:
            criadas = self._criadas
        return {"tamanho": self._tamanho, "livres": livres, "em_uso": criadas - livres}

    def fechar(self) -> None:
        """Esvazia os slots livres; recursos em uso voltam e são descartados."""
        try:
            while True:
                self._livres.get_nowait()
        except queue.Empty:
            return

Deadline end-to-end com orçamento proporcional por fase e retry só quando seguro: cada fase recebe o menor entre seu orçamento e o restante, e a repetição exige método idempotente, teto e prazo (oráculo LT01-AT-031: orçamento respeitado, sem tempestade de retry). """Deadline end-to-end com orçamento por fase e retry só quando seguro.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L. So STDLIB (time).
Relógio injetado pelo chamador: teste com relógio controlado.
"""

from __future__ import annotations

from collections.abc import Callable

METODOS_REPETIVEIS = frozenset({"GET", "HEAD", "OPTIONS", "PUT", "DELETE"})


class PrazoEstourado(TimeoutError):
    """Fase ou operação além do orçamento contratado."""


def orcamento_por_fase(prazo_total: float, pesos: dict[str, float]) -> dict[str, float]:
    """Divide o prazo total em orçamentos proporcionais aos pesos.

    Pesos precisam ser positivos; a soma dos orçamentos fecha no total.
    """
    if not prazo_total > 0:
        raise ValueError("prazo_total precisa ser positivo")
    if not pesos:
        raise ValueError("pesos vazio não orça fase alguma")
    total_pesos = 0.0
    for peso in pesos.values():
        if not peso > 0:
            raise ValueError("todo peso precisa ser positivo")
        total_pesos += peso
    return {fase: prazo_total * peso / total_pesos for fase, peso in pesos.items()}


def restante(inicio: float, prazo_total: float, agora: float) -> float:
    """Segundos que faltam do deadline; nunca negativo."""
    falta = inicio + prazo_total - agora
    return falta if falta > 0 else 0.0


def checar_prazo(inicio: float, prazo_total: float, agora: float) -> None:
    """Levanta PrazoEstourado quando o deadline já passou."""
    if agora - inicio >= prazo_total:
        raise PrazoEstourado(f"deadline de {prazo_total}s excedido")


def executar_fase[T](
    orcamento_fase: float,
    inicio: float,
    prazo_total: float,
    agora: Callable[[], float],
    trabalho: Callable[[float], T],
) -> T:
    """Executa o trabalho com o menor entre orçamento da fase e restante.

    Checa o deadline antes e depois; estouro vira PrazoEstourado.
    O trabalho recebe os segundos disponíveis e respeita o teto.
    """
    checar_prazo(inicio, prazo_total, agora())
    disponivel = restante(inicio, prazo_total, agora())
    teto = orcamento_fase if orcamento_fase < disponivel else disponivel
    saida = trabalho(teto)
    checar_prazo(inicio, prazo_total, agora())
    return saida


def pode_repetir(metodo: str, tentativa: int, max_tentativas: int, restante_seg: float) -> bool:
    """Retry só quando seguro: idempotente, dentro do teto e com prazo.

    POST e método fora do conjunto repetível nunca repetem;
    sem prazo restante, nunca.
    """
    if tentativa >= max_tentativas:
        return False
    if restante_seg <= 0:
        return False
    return metodo.strip().upper() in METODOS_REPETIVEIS

Sinal manual e idempotente com verificação nos limites: o trabalho decide onde parar, nunca é interrompido à força (oráculo LT01-AT-032: trabalho e recursos liberados). Só stdlib (threading); ponte com os padrões do M02A-B06/B08, aqui entre cliente e servidor:

"""Cancelamento cooperativo: o sinal viaja, o trabalho decide onde parar.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L. So STDLIB (threading).
Nunca interrompe thread à força: o trabalho verifica nos limites.
"""

from __future__ import annotations

import threading
from collections.abc import Callable, Iterable, Iterator


class Cancelado(Exception):
    """Trabalho interrompido num limite após cancelar()."""


class SinalCancelamento:
    """Sinal manual e idempotente: cancelar() uma vez vale para sempre."""

    def __init__(self) -> None:
        self._evento = threading.Event()

    def cancelar(self) -> None:
        """Marca o sinal; chamar duas vezes não muda nada."""
        self._evento.set()

    @property
    def cancelado(self) -> bool:
        """Verdadeiro depois de cancelar(), falso antes."""
        return self._evento.is_set()

    def verificar(self) -> None:
        """Levanta Cancelado se o sinal foi marcado; senão, retorna."""
        if self._evento.is_set():
            raise Cancelado("trabalho cancelado pelo chamador")

    def aguardar(self, prazo: float | None = None) -> bool:
        """Espera o sinal até o prazo; devolve True se cancelado."""
        return self._evento.wait(timeout=prazo)


def executar_cancelavel[T](sinal: SinalCancelamento, trabalho: Callable[[], T]) -> T:
    """Verifica antes e depois; o cancelamento aparece no limite seguinte."""
    sinal.verificar()
    saida = trabalho()
    sinal.verificar()
    return saida


def iterar_cancelavel[T](sinal: SinalCancelamento, itens: Iterable[T]) -> Iterator[T]:
    """Produz item a item, verificando o sinal a cada passo."""
    for item in itens:
        sinal.verificar()
        yield item

O trabalho tem três números: throughput, latência, concorrência

Throughput (vazão) é quantas operações concluem por segundo. Latência é quanto cada operação leva do início ao fim. Concorrência é quantas operações estão em curso ao mesmo tempo. Fila é onde a operação excedente espera por um slot livre — a mesma fila FIFO do pool do Bloco 4, agora como fenômeno geral: toda espera por recurso contado é fila, tenha ela nome de pool, backlog ou buffer.

Little's Law amarra os três números em regime estável: concorrência média é igual a throughput multiplicado pela latência média. Em símbolos, L = λ × W: L operações médias em curso, λ conclusões por segundo, W segundos por operação. A lei não prevê o futuro nem descreve transiente: vale para a média observada num intervalo em que entrada e saída estão equilibradas. O valor didático está no uso inverso — medir dois números e derivar o terceiro: throughput observado vezes latência p50 observada estima quanta concorrência o sistema sustenta sem fila; fila crescente com throughput parado declara que o recurso teto foi alcançado.

Knee pointO degrau de carga onde throughput para de subir e latência passa a subir: o joelho da curva carga → vazão.Joelho é do recurso que saturou primeiro, não do sistema em abstrato: a conclusão nomeia o recurso, com o relógio que o prova.

Fundamento de engenharia · Carga se aumenta por degraus, e cada degrau tem veredito. A prática da especificação — subir a carga por degraus e localizar o knee point — existe porque um único ponto de carga não separa folga de saturação: abaixo do joelho, throughput acompanha a oferta; acima, latência e fila absorvem o excedente sem entregar mais. Cada degrau publica os quatro números (carga oferecida, throughput, p95, erros e recursos) e declara se o sistema ainda converte oferta em conclusão. A evidência do bloco — gráfico carga → throughput/p95/erro/recursos com hipótese e limite de capacidade declarado — nasce desse procedimento, e a folha B05-L o executa sobre funções locais injetadas, sem rede.

Dois relógios para um trabalho: CPU contra parede

O mesmo trabalho pode ser medido por dois relógios, e a comparação entre eles classifica o gargalo. Tempo de parede (wall-clock) é o que o relógio da sala marcaria: do início ao fim, incluindo toda espera — rede, disco, fila, dormência. Tempo de CPU é quanto o processador de fato gastou executando aquele trabalho: soma dos intervalos em que houve conta, excluída a espera. Em Python, o módulo time expõe os dois: perf_counter para a parede com a melhor resolução do sistema, process_time para a CPU consumida pelo processo. Trabalho cujo tempo de parede excede em muito o tempo de CPU passou a vida esperando — I/O-bound; trabalho onde os dois andam juntos passou a vida computando — CPU-bound. É a decisão do Bloco 1, agora com instrumento.

Load average (carga média) é o número que costuma ser lido errado. Ele declara quantos processos estiveram prontos para rodar ou em espera ininterrupta, em média nos últimos 1, 5 e 15 minutos — um comprimento de fila do sistema, não um percentual de CPU. Load 4 numa máquina de 4 CPUs declara equilíbrio tenso; o mesmo 4 numa de 1 CPU declara fila permanente. Throttling (estrangulamento) é o teto imposto de fora — quota de CPU do container que pausa o processo ao esgotar a fração: o sintoma é CPU medida abaixo do esperado com latência subindo, e o diagnóstico lê a quota antes de culpar o código. Nenhum dos dois aparece nos três scripts do lab/ como leitura direta — quota e escalonador pertencem ao ambiente, não à stdlib —; aparecem aqui como vocabulário do veredito, para que o knee point venha com o recurso nomeado e o mecanismo declarado.

Contraste"CPU no teto, então o código é CPU-bound" — nem sempre. Laço de repetição sem prazo, retry sem teto e fila de reprocessamento mantêm a CPU ocupada sem concluir nada útil: o relógio de CPU sobe, o throughput fica parado, e o gargalo real é espera convertida em giro — o blocking call do Bloco 1 e a tempestade de retry do Bloco 4 vestidos de saturação. A separação honesta mede os dois relógios sobre o trabalho nomeado: CPU alta com parede proporcional acusa conta; CPU alta com throughput parado e fila crescendo acusa giro sobre espera. O oráculo AT-040 cobra os dois lados: o joelho localizado e o recurso limitante identificado — nunca correlação temporal apresentada como causa.

Memória: RSS, virtual, vazamento contra cache

RSS (resident set size) é quanta memória física o processo ocupa de fato — páginas residentes, não promessas. Memória virtual é o espaço de endereçamento reservado: inclui mapeamentos ainda não tocados, bibliotecas compartilhadas e reservas que podem nunca virar RAM. RSS cresce e encolhe com o uso real; virtual pode ser ordens de magnitude maior sem que nada esteja errado. Confundir os dois produz os dois falsos diagnósticos do catálogo: declarar vazamento porque o virtual é grande, e declarar saúde porque o virtual parou de crescer enquanto o RSS sobe sem voltar.

Em Python sobre POSIX, o módulo resource lê o pico de RSS do processo via getrusage: instrumento de observação da trilha, com a mesma honestidade de plataforma do Bloco 1 — existe onde o sistema o oferece, e a referência declara o limite. O procedimento do oráculo AT-041 tem três leituras: baseline (RSS em repouso antes da carga), pico (RSS sob carga) e pós-limpeza (RSS depois de liberar o que a carga alocou). Vazamento (leak) é crescimento que a limpeza não reverte: cada ciclo deixa o patamar mais alto, porque referência retida impede a liberação. Cache é crescimento que a limpeza reverte até a tolerância: o pico sob carga é comportamento — reter para reutilizar —, não defeito. O veredito mora na terceira leitura, nunca na segunda: pico alto sozinho não acusa nada; patamar que não volta acusa tudo.

Exhaustion (esgotamento) é o plural que o bloco exige decorar pelo mecanismo, não pela lista: cada recurso contado tem seu teto e seu sintoma. CPU esgotada converte oferta em fila; memória esgotada converte alocação em erro ou em morte pelo sistema; FD e socket esgotados recusam abertura nova — o AT-010 do Bloco 2 reaparece aqui como causa de saturação; pool esgotado falha na aquisição antes de qualquer byte — o AT-030 do Bloco 4; event loop saturado atrasa tarefas inocentes com CPU baixa — o AT-001 do Bloco 1; upstream lento prende slot local e converte espera externa em fila interna — o AT-042, adiante. A conclusão do bloco identifica o primeiro recurso saturado na cadeia, com o sinal que o prova e os demais declarados saudáveis.

A média esconde a cauda: percentis

Percentil é a latência abaixo da qual cai uma fração dada das amostras: p50 é a mediana — metade das operações concluiu até ali; p95 é o teto de 95% — apenas uma em vinte операции foi mais lenta. A média soma tudo e divide: dez respostas rápidas e uma catastrófica produzem média saudável e um usuário sem resposta. O p95 conta essa história porque ordena antes de resumir: ele pergunta "quanto sofreram os 5% piores", e fila, retry e bloqueio de cabeça de fila moram exatamente ali — nos piores, não nos típicos.

O contrato da folha B05-L computa percentis sobre amostras em memória, sem dependência externa: ordena a cópia, indexa pela posição correspondente à fração pedida e publica p50, p95, máximo e contagem. Amostras são latências medidas pelo relógio de parede do primeiro script — cada fase contribui com as suas, e o breakdown local contra upstream do AT-042 se lê em dois resumos lado a lado. Números citados neste bloco são exemplo variável: a distribuição real nasce da medição, com tamanho de amostra, warm-up e ambiente registrados na folha L.

DiagnósticoComo ler p50 contra p95. p50 parado com p95 subindo em degrau acusa contenção intermitente — fila que atinge poucos, loop bloqueado por rajadas, pool no limite: os inocentes da vez pagam pelos demais. p50 e p95 subindo juntos acusam degradação geral — CPU saturada, upstream lento para todos, throttling: ninguém escapa porque o recurso comum afundou. p95 oscilando sem carga correspondente acusa amostra pequena ou warm-up misturado ao regime: o conserto é método — mais amostras, descarte do aquecimento —, não arquitetura. O oráculo AT-040 lê o p95 contra a carga oferecida degrau a degrau; veredito sem percentil é palpite com gráfico.

Observar por método: USE e golden signals

USE method é o roteiro de Brendan Gregg para cada recurso: Utilization (utilização — fração do tempo em que o recurso esteve ocupado), Saturation (saturação — fila de trabalho esperando pelo recurso) e Errors (erros — falhas atribuídas ao recurso). A ordem importa: utilização sem saturação é folga ocupada, não problema; saturação sem utilização alta é espera por outro recurso — o disco que dorme porque a rede não entrega; erro sem os dois é defeito lógico, não falta de capacidade. O método se aplica recurso por recurso — CPU, memória, FD, pool, event loop — e cada aplicação termina numa das três sentenças: há folga, há fila ou há falha.

Golden signals são os quatro sinais do Google SRE para o serviço visto de fora: latência (quanto leva, com a cauda — p95, não média), tráfego (quanto pedem — throughput oferecido), erros (quanto falha — taxa e tipo) e saturação (quanto falta — fila e recursos no teto). Onde o USE olha cada recurso por dentro, os golden signals olham o serviço por fora: a ronda honesta alterna os dois — sinal dourado acusa o sintoma, USE localiza o recurso, breakdown separa o local do externo.

Semânticas OTel dão nome estável a cada sinal para que hipótese e evidência falem a mesma língua. As convenções semânticas do OpenTelemetry para sistema e processo nomeiam CPU, memória e carga com atributos comuns; as convenções para HTTP nomeiam método, rota, status e duração de cliente e servidor com os mesmos campos. O bloco não versiona campo algum — convenções em desenvolvimento mudam, e a especificação marca as fontes como alto risco de obsolescência: o que o bloco congela é o hábito — cada número publicado declara recurso, fase e instrumento — e a folha B05-L publica seus dicionários de medição com chaves estáveis documentadas no contrato.

Cardinalidade é custo: a métrica que come o observador

Cardinalidade é quantas séries distintas uma métrica produz: cada combinação de nome mais valores de rótulo é uma série que o backend armazena, indexa e consulta. Rótulo com poucos valores — método, status, fase — multiplica por constante pequena. Rótulo com valores por operação — id de requisição, id de usuário, path com segmento livre, mensagem de erro com texto embutido — multiplica por cada operação: milhares de séries novas por minuto, cada uma ocupando memória e disco no sistema que deveria observar o incidente. Cardinalidade explosiva é esse regime: a observação custa mais que o observado, e o primeiro sintoma é o observador degradando junto — ingestão lenta, consulta que expira, conta que estoura.

A defesa tem duas metades. Na escrita, a guarda de cardinalidade: teto declarado de séries por métrica, recusa explícita acima do teto com contador de recusadas, remoção cirúrgica da série problemática — nunca apagão do instrumento. Na modelagem, rótulos de baixa cardinalidade por construção: rota com template em vez de path bruto, código de status em vez de mensagem, balde em vez de valor contínuo. O oráculo AT-050 cobra as duas: a série problemática removida e o diagnóstico preservado — remover o rótulo explosivo sem perder a capacidade de separar as fases e os desfechos que o incidente exige.

Contraste"Quanto mais rótulo, melhor o diagnóstico" — até a conta chegar. Rótulo de alta cardinalidade parece precisão: cada série conta a história de uma operação. Na prática, ele troca diagnóstico por volume — milhares de séries de uma ocorrência cada, nenhuma com amostra suficiente para percentil, todas cobrando armazenamento. O diagnóstico que sobrevive à remoção é o agregado bem rotulado: p95 por fase e por desfecho, taxa por rota com template, contagem de recusadas pela guarda. Precisão sem custo declarado não é instrumentação; é vazamento com outro nome — e o veredito do AT-050 exige os dois números: quantas séries havia, quantas restaram, e o que cada corte preservou.

"""Carga e tempo: dois relógios, vazão, Little e breakdown local/upstream.

Referencia executavel do Bloco 5.
Implementacao verbatim na folha B05-L. So STDLIB (time).
Trabalho injetado pelo chamador; nenhuma rede, nenhum container.
"""

from __future__ import annotations

import time
from collections.abc import Callable


def medir_tempos[T](trabalho: Callable[[], T]) -> dict[str, float]:
    """Executa o trabalho uma vez; publica cpu_s (process_time) e parede_s (perf_counter)."""
    inicio_cpu = time.process_time()
    inicio_parede = time.perf_counter()
    trabalho()
    return {
        "cpu_s": time.process_time() - inicio_cpu,
        "parede_s": time.perf_counter() - inicio_parede,
    }


def taxa_vazao(concluidas: int, parede_s: float) -> float:
    """Conclusões por segundo; parede não positiva levanta ValueError."""
    if concluidas < 0:
        raise ValueError("concluidas não pode ser negativo")
    if not parede_s > 0:
        raise ValueError("parede_s precisa ser positiva")
    return concluidas / parede_s


def lei_little(vazao: float, latencia_s: float) -> float:
    """Concorrência média = vazão x latência; entradas negativas levantam ValueError."""
    if not vazao >= 0:
        raise ValueError("vazao não pode ser negativa")
    if not latencia_s >= 0:
        raise ValueError("latencia_s não pode ser negativa")
    return vazao * latencia_s


def dividir_latencias(local_s: float, upstream_s: float) -> dict[str, float]:
    """Breakdown do AT-042: publica local_s, upstream_s e total_s; negativos levantam ValueError."""
    if not local_s >= 0:
        raise ValueError("local_s não pode ser negativo")
    if not upstream_s >= 0:
        raise ValueError("upstream_s não pode ser negativo")
    return {"local_s": local_s, "upstream_s": upstream_s, "total_s": local_s + upstream_s}

"""Memória RSS: residente atual, crescimento e veredito em três leituras.

Referencia executavel do Bloco 5.
Implementacao verbatim na folha B05-L. So STDLIB (os, resource).
POSIX: fora de plataforma com resource, indisponibilidade registrada.
Conversão ru_maxrss em bytes na semântica Linux documentada no contrato.
"""

from __future__ import annotations

import os
import resource


def rss_bytes() -> int:
    """Residente atual do processo em bytes (semântica Linux: ru_maxrss x 1024)."""
    _ = os.getpid()
    pico = resource.getrusage(resource.RUSAGE_SELF).ru_maxrss
    return int(pico) * 1024


def crescimento_bytes(antes: int, depois: int) -> int:
    """Diferença entre duas leituras; entradas negativas levantam ValueError."""
    if antes < 0 or depois < 0:
        raise ValueError("leituras de RSS não podem ser negativas")
    return depois - antes


def classificar_crescimento(baseline: int, pico: int, apos_limpeza: int, tolerancia: int) -> str:
    """Veredito do AT-041: 'vazamento', 'cache' ou 'baseline'.

    Pico alto que a limpeza reverte até a tolerância é cache;
    patamar que não volta até a tolerância é vazamento;
    o resto é baseline. Entradas negativas ou tolerância negativa: ValueError.
    """
    for valor in (baseline, pico, apos_limpeza):
        if valor < 0:
            raise ValueError("leituras de RSS não podem ser negativas")
    if tolerancia < 0:
        raise ValueError("tolerancia não pode ser negativa")
    if apos_limpeza > baseline + tolerancia:
        return "vazamento"
    if pico > baseline + tolerancia:
        return "cache"
    return "baseline"

Referência executável 3 — lab/percentis_cardinalidade.py. Percentis sobre amostras e guarda de cardinalidade: ordena a cópia e indexa pela fração pedida, publica contagem com p50/p95/máximo, e recusa série nova acima do teto sem expulsar as existentes (oráculo LT01-AT-050: série problemática removida sem perder o diagnóstico). Só stdlib (threading para a guarda); sem rede, sem backend:

"""Percentis e cardinalidade: cauda resumida, custo contido.

Referencia executavel do Bloco 5.
Implementacao verbatim na folha B05-L. So STDLIB (threading).
Amostras em memória; guarda com teto declarado e recusa explícita.
"""

from __future__ import annotations

import math
import threading


def percentil(amostras: list[float], p: float) -> float:
    """Latência abaixo da qual cai p por cento das amostras.

    Ordena a cópia; p fora de [0, 100] ou lista vazia: ValueError.
    """
    if not amostras:
        raise ValueError("amostras vazia não tem percentil")
    if not 0 <= p <= 100:
        raise ValueError("p precisa estar em [0, 100]")
    ordenadas = sorted(amostras)
    if p == 0:
        return ordenadas[0]
    posicao = math.ceil(p / 100 * len(ordenadas)) - 1
    return ordenadas[max(0, min(posicao, len(ordenadas) - 1))]


def resumo(amostras: list[float]) -> dict[str, float]:
    """Publica contagem, p50, p95 e máximo para o oráculo AT-040."""
    return {
        "contagem": float(len(amostras)),
        "p50": percentil(amostras, 50),
        "p95": percentil(amostras, 95),
        "maximo": percentil(amostras, 100),
    }


class GuardaCardinalidade:
    """Teto declarado de séries; acima do teto, recusa sem expulsar.

    A chave da série é (nome, rótulos ordenados): path com segmento
    livre vira uma série por operação — a explosão do AT-050.
    """

    def __init__(self, teto: int) -> None:
        if teto < 1:
            raise ValueError("teto precisa ser ao menos 1")
        self._teto = teto
        self._series: set[tuple[str, tuple[tuple[str, str], ...]]] = set()
        self._recusadas = 0
        self._trava = threading.Lock()

    def registrar(self, nome: str, rotulos: dict[str, str]) -> bool:
        """True se a série cabe ou já existe; False se recusada pelo teto."""
        chave = (nome, tuple(sorted(rotulos.items())))
        with self._trava:
            if chave in self._series:
                return True
            if len(self._series) >= self._teto:
                self._recusadas += 1
                return False
            self._series.add(chave)
            return True

    def remover(self, nome: str, rotulos: dict[str, str]) -> None:
        """Remove a série problemática; diagnóstico das demais preservado."""
        chave = (nome, tuple(sorted(rotulos.items())))
        with self._trava:
            self._series.discard(chave)

    def contagem(self) -> int:
        """Séries distintas retidas no momento."""
        with self._trava:
            return len(self._series)

    def recusadas(self) -> int:
        """Total recusado pelo teto desde a criação."""
        with self._trava:
            return self._recusadas

Triagem: impacto e baseline antes da causa

Incidente é a degradação observada que exige resposta coordenada: latência fora do contrato, erros acima do teto, saturação que ameaça a operação. Problema é a causa ainda desconhecida por trás dele. A ordem entre os dois organiza tudo o que segue: primeiro se declara o que o usuário sente e desde quando, depois se investiga o porquê. Quem começa pela causa adivinha; quem começa pelo impacto mede.

Triagem é a primeira declaração, curta e datada: qual serviço, qual sintoma, qual alcance, quando começou. Impacto responde "quem sofre e quanto": fração de requisições afetadas, janelas de tempo, rotas atingidas — com o percentil do Bloco 5, não com a média. Baseline é o comportamento saudável de comparação: os mesmos quatro números da evidência do Bloco 5 (carga, throughput, p95, erros e recursos) em período sem incidente. Sem baseline, toda leitura é órfã: "p95 alto" não acusa nada até ser confrontado com o p95 do regime.

Timeline é o registro ordenado do incidente: quando cada sintoma apareceu, quando cada mudança entrou, quando cada leitura foi feita e o que ela concluiu. A timeline existe por dois motivos. Durante o incidente, ela impede a repetição: ninguém testa duas vezes a hipótese já refutada. Depois, ela sustenta o postmortem: cada afirmação do relatório aponta para uma linha datada, não para a memória de quem atendeu.

Fundamento de engenharia · Mudança recente é hipótese, não veredito. A pergunta "o que mudou?" abre quase todo diagnóstico porque deploys, configurações e dependências novas concentram causas — mas correlação temporal não é prova, como o Bloco 5 já estabeleceu para o knee point. Mudança recente entra na lista como uma hipótese entre as concorrentes, com o mesmo dever das demais: sinal esperado declarado e leitura que confirma ou refuta. O incidente que termina em "foi o deploy, revertemos" sem a leitura que liga o deploy ao sintoma aprendeu pouco: a próxima mudança idêntica passará pelo mesmo caminho sem guarda. O oráculo AT-060 cobra a cadeia completa — hipótese, evidência, correção, regressão — e nenhuma mudança escapa dela por ser óbvia.

Hipótese antes da leitura: eliminação por evidência

Hipótese é uma afirmação testável sobre a camada da falha, acompanhada do sinal que a leitura deveria mostrar se ela for verdadeira. "O pool esgotou" não é hipótese — é palpite. "O pool esgotou: a leitura de aquisição deve mostrar fila crescente com timeout, enquanto o destino responde no prazo" é hipótese: prevê um sinal, e o sinal decide. O contrato deste bloco exige no máximo três hipóteses iniciais: poucas o bastante para caber no orçamento, distintas o bastante para cobrir camadas diferentes — por exemplo, uma de recurso local, uma de dependência externa, uma de mudança recente.

A regra de ouro do bloco: nenhuma leitura sem hipótese registrada antes. Cada observação declara primeiro o que espera encontrar e por quê; depois lê; depois confronta. A disciplina existe porque leitura sem expectativa prévia é infinitamente reinterpretável: o mesmo número "prova" qualquer causa quando se escolhe a causa depois do número. Com a hipótese escrita antes, a leitura tem só três desfechos honestos — confirma, refuta ou inconclusiva — e cada um prescreve o próximo passo: confirmar manda mitigar e corrigir; refutar manda descartar e passar à próxima; inconclusiva manda refinar a hipótese, nunca forçar o veredito.

Diagnóstico por eliminação é a ordem fixa sintoma → hipótese → evidência → correção. O sintoma localiza o bairro — qual golden signal acusou, qual recurso a ronda USE marcou. A hipótese nomeia a casa — a camada suspeita com o sinal esperado. A evidência bate à porta — a leitura que confirma ou refuta, registrada com o observado e o veredito. A correção só entra depois que a evidência confirmou: patch mínimo sobre a causa provada, jamais sobre a suspeita. Pular a evidência e corrigir na suspeita produz o incidente duplo — a correção errada que adiciona sua própria timeline à primeira.

Contraste"Vou olhando até achar" — não. Leitura sem hipótese prévia parece velocidade: cada número sugere a próxima leitura, e a trilha anda. Na prática, ela troca diagnóstico por passeio — leituras que se sucedem sem refutar nada, cada uma reinterpretada para caber na suspeita favorita, até o orçamento esgotar com dez observações e zero vereditos. O sintoma que denuncia o erro é conhecido: o registro mostra muitas leituras e nenhuma hipótese descartada. A conduta é fixa — escreve-se a hipótese com o sinal esperado, lê-se, publica-se o veredito — e o oráculo AT-060 reprova o incidente cuja evidência não referencia hipótese prévia. Três hipóteses testadas valem mais que trinta leituras órfãs.

Mitigar sem esconder, depois corrigir

Mitigação contém o impacto sem remover a causa: conter a entrada, reverter a mudança, isolar o upstream lento, derrubar a série explosiva. Correção remove a causa: o patch mínimo sobre o defeito provado. A ordem entre elas é decisão de engenharia, não de coragem. Mitigar primeiro compra o tempo da correção certa: com o usuário protegido, o patch pode ser mínimo e a regressão pode ser escrita sem pressa. Corrigir primeiro, sob impacto aberto, produz o patch apressado — amplo demais, testado de menos, com sua própria regressão ausente.

O limite honesto: mitigação que apaga o sinal é esconderijo, não contenção. Elevar o limite de descritores sem fechar o vazamento, aumentar o pool sem drenar a fila, desligar a verificação de certificado para "passar o teste" — cada um desses gestos silencia o sintoma e preserva a causa, e todos foram vedados nominalmente nos Blocos 2–4. A mitigação legítima declara o que conteve, o que preservou e o que resta: a entrada contida, o diagnóstico preservado, a causa ainda aberta com dono e prazo. O runbook deste bloco só aceita passos com essas três declarações.

Patch mínimo é a menor mudança que remove a causa provada sem alterar comportamento saudável: uma condição, um fechamento, um prazo, uma guarda. Mínimo não é preguiça — é controle de blast radius: cada linha além da causa é uma hipótese não testada entrando em produção junto com a correção. Teste de regressão é a prova que falha antes do patch e passa depois: ele fixa a causa em código para que a próxima mudança idêntica seja barrada pelo oráculo em vez de reabrir o incidente. Correção sem regressão é relato; com regressão, é garantia.

O registro que sobrevive: incident.md, runbook e postmortem sem culpa

incident.md é o documento do incidente em seções fixas: identificação, impacto, baseline, timeline, hipóteses com sinais esperados, evidências com vereditos, mitigação, correção, regressão e restauração. Cada seção aponta para as demais — cada evidência referencia a hipótese que testa, cada correção referencia a evidência que a autorizou. Registros sanitizados acompanham: observações publicadas sem segredos, sem dados de usuário, sem detalhe que exponha a operação. Sanitizar não é enfeitar: segredo que vaza no relatório vira o segundo incidente, catalogado no Bloco 2.

Runbook é o procedimento que transforma o aprendizado em conduta repetível: passos nomeados, cada um com o sinal esperado e o limite que o aprova, na ordem que o incidente ensinou. Runbook que só se lê é lista de desejos: o passo "verificar o pool" sem o critério de esgotado contra saudável não decide nada sob pressão. Por isso a folha B06-L exercita o runbook contra degradação simulada local — cada passo executado contra um alvo que degrada de verdade, com prazo declarado e veredito de mitigação. O que passa no exercício pode ser confiado no incidente; o que só foi lido, não.

Postmortem sem culpa (blameless) é a análise posterior que pergunta pelo sistema, nunca pelo culpado: quais guardas faltavam para que a ação — razoável no momento — produzisse o incidente. A ausência de culpa não é gentileza; é instrumento. Onde o erro individual é punido, a timeline é editada antes de publicada, e o relatório perde exatamente as linhas que evitariam a repetição. O postmortem deste bloco registra causas sistêmicas, ações corretivas com dono e a regressão que as garante — e termina com o risco residual declarado: o que a correção não cobre e como será vigiado.

Contraste"Voltou ao normal" — não é veredito. Sintoma que some sem explicação é incidente em pausa, não incidente resolvido: a causa segue armada e a timeline segue aberta. O fechamento honesto exige os três artefatos encadeados — correção sobre causa provada, regressão que falha antes e passa depois, restauração com verificação verde. Qualquer um dos três ausente mantém o incidente aberto com dono, mesmo que o gráfico esteja calmo. O oráculo AT-060 cobra a cadeia; o oráculo AT-061 cobra a prova de que o ambiente voltou — todos os faults desligados, verificação verde. Calma no gráfico sem os três artefatos é silêncio, não saúde.

Restauração como oráculo: provar o baseline de volta

Restauração é o retorno controlado do ambiente ao estado anterior ao incidente: cada degradação ativada é desligada, cada mitigação temporária é revertida, cada recurso conta de volta ao baseline. A ordem importa como no shutdown do Bloco 1: primeiro desliga-se o que foi injetado, depois reverte-se o que foi contido, por fim lê-se o ambiente limpo. Restaurar fora de ordem — reverter a contenção com a degradação ainda ativa — reabre o impacto no meio da celebração.

O oráculo AT-061 tem duas metades inseparáveis. Faults desligados: cada cenário de degradação declara estado desligado, e o veredito exige todos desligados — nenhum resto de simulação vazando para o próximo exercício. Verificação verde: as sondas de saúde passam sobre o ambiente restaurado — latência dentro do contrato, erros no patamar do baseline, recursos sem fila. Uma metade sem a outra reprova: faults desligados sem verificação verde é fé; verificação verde com fault residual é teatro. "Restaurado" só se escreve com as duas publicadas lado a lado.

DiagnósticoComo reconhecer a restauração incompleta. O padrão é inconfundível quando se sabe o que procurar: a verificação passa no teste curto mas o patamar de recursos não coincide com o baseline — descritores acima do repouso, fila que não zera, p95 com degrau residual. A confirmação vem da comparação — os mesmos quatro números do baseline, lidos no ambiente restaurado, lado a lado com o repouso — e a correção é localizar o fault residual pelo recurso que não voltou, nunca declarar saúde pela verificação parcial. Restauração se prova com igualdade ao baseline, não com ausência de erro no teste curto.

"""Registro de incidente: hipótese antes da leitura, incident.md em seções fixas.

Referencia executavel do Bloco 6.
Implementacao verbatim na folha B06-L. So STDLIB (dataclasses).
Toda evidencia referencia hipotese previa; veredito em vocabulario fechado.
"""

from __future__ import annotations

from dataclasses import dataclass, field

VEREDITOS = ("confirma", "refuta", "inconclusiva")


@dataclass
class Hipotese:
    """Afirmacao testavel com o sinal que a leitura deve mostrar."""

    hipotese_id: str
    enunciado: str
    sinal_esperado: str


@dataclass
class Evidencia:
    """Leitura confrontada com a hipotese que a autorizou."""

    hipotese_id: str
    observacao: str
    veredito: str


@dataclass
class Incidente:
    """Registro vivo: impacto, baseline, hipoteses e evidencias em ordem."""

    identificador: str
    impacto: str
    baseline: str
    hipoteses: dict[str, Hipotese] = field(default_factory=dict)
    evidencias: list[Evidencia] = field(default_factory=list)


def criar_incidente(identificador: str, impacto: str, baseline: str) -> Incidente:
    """Abre o registro com impacto declarado e baseline de comparacao."""
    for nome, valor in (("identificador", identificador), ("impacto", impacto)):
        if not valor.strip():
            raise ValueError(f"{nome} não pode ser vazio")
    if not baseline.strip():
        raise ValueError("baseline não pode ser vazia")
    return Incidente(identificador=identificador, impacto=impacto, baseline=baseline)


def registrar_hipotese(
    incidente: Incidente, hipotese_id: str, enunciado: str, sinal_esperado: str
) -> Hipotese:
    """Registra a hipotese antes de qualquer leitura; id duplicado: ValueError."""
    if not hipotese_id.strip():
        raise ValueError("hipotese_id não pode ser vazio")
    if hipotese_id in incidente.hipoteses:
        raise ValueError(f"hipotese duplicada: {hipotese_id}")
    if not enunciado.strip() or not sinal_esperado.strip():
        raise ValueError("enunciado e sinal_esperado não podem ser vazios")
    hipotese = Hipotese(hipotese_id, enunciado, sinal_esperado)
    incidente.hipoteses[hipotese_id] = hipotese
    return hipotese


def registrar_evidencia(
    incidente: Incidente, hipotese_id: str, observacao: str, veredito: str
) -> Evidencia:
    """Confronta a leitura com a hipotese previa; sem hipotese: ValueError."""
    if hipotese_id not in incidente.hipoteses:
        raise ValueError(f"sem hipotese previa: {hipotese_id}")
    if veredito not in VEREDITOS:
        raise ValueError(f"veredito precisa estar em {VEREDITOS}")
    if not observacao.strip():
        raise ValueError("observacao não pode ser vazia")
    evidencia = Evidencia(hipotese_id, observacao, veredito)
    incidente.evidencias.append(evidencia)
    return evidencia

"""Runbook exercitado contra degradacao simulada local.

Referencia executavel do Bloco 6.
Implementacao verbatim na folha B06-L. So STDLIB (dataclasses, collections.abc).
O alvo degrada por modo declarado; mitigar contem, nunca apaga o sinal.
"""

from __future__ import annotations

from collections.abc import Callable
from dataclasses import dataclass, field

MODOS = ("saudavel", "latencia_alta", "erros_altos")
ACOES = ("conter_entrada", "reverter_mudanca", "isolar_upstream")


@dataclass
class AlvoLocal:
    """Degradacao simulada local: modo declarado, leitura por dicionario."""

    modo: str = "saudavel"
    mitigado: bool = False

    def __post_init__(self) -> None:
        if self.modo not in MODOS:
            raise ValueError(f"modo precisa estar em {MODOS}")

    def observar(self) -> dict[str, float]:
        """Publica p95_ms e taxa_erro do modo atual; exemplo variavel."""
        if self.modo == "latencia_alta":
            return {"p95_ms": 900.0, "taxa_erro": 0.01}
        if self.modo == "erros_altos":
            return {"p95_ms": 120.0, "taxa_erro": 0.25}
        return {"p95_ms": 80.0, "taxa_erro": 0.001}

    def aplicar_mitigacao(self, acao: str) -> dict[str, str]:
        """Contem o impacto com acao do vocabulario; fora dele: ValueError."""
        if acao not in ACOES:
            raise ValueError(f"acao precisa estar em {ACOES}")
        self.mitigado = True
        return {"acao": acao, "efeito": "impacto_contido_causa_aberta"}


@dataclass
class Passo:
    """Passo do runbook: nome e sinal esperado antes da leitura."""

    nome: str
    sinal_esperado: str


@dataclass
class ResultadoPasso:
    """Conformidade de um passo: o observado contra o esperado."""

    nome: str
    conforme: bool
    observado: dict[str, float] = field(default_factory=dict)


def executar_passo(
    alvo: AlvoLocal, passo: Passo, checagem: Callable[[dict[str, float]], bool]
) -> ResultadoPasso:
    """Executa um passo contra o alvo e publica a conformidade."""
    if not passo.nome.strip() or not passo.sinal_esperado.strip():
        raise ValueError("passo precisa de nome e sinal_esperado")
    observado = alvo.observar()
    return ResultadoPasso(passo.nome, bool(checagem(observado)), observado)


def veredito_runbook(resultados: list[ResultadoPasso]) -> str:
    """Mitigado só com lista não vazia e todos os passos conformes."""
    if not resultados:
        raise ValueError("runbook vazio não tem veredito")
    if all(resultado.conforme for resultado in resultados):
        return "mitigado"
    return "nao_mitigado"

from __future__ import annotations

from collections.abc import Callable


def desligar_faults(faults: dict[str, bool]) -> dict[str, bool]:
    """Desliga cada degradacao declarada; publica o mapa desligado."""
    return {nome: False for nome in faults}


def smoke_verde(sondas: dict[str, Callable[[], bool]]) -> dict[str, bool]:
    """Executa cada sonda sobre o ambiente restaurado; vazio: ValueError."""
    if not sondas:
        raise ValueError("sem sondas não há verificacao verde")
    return {nome: bool(sonda()) for nome, sonda in sondas.items()}


def veredito_restauracao(faults: dict[str, bool], resultados: dict[str, bool]) -> str:
    """Restaurado só com todos os faults desligados e todas as sondas verdes."""

    todos_desligados = all(desligado is False for desligado in faults.values())
    todas_verdes = all(passou for passou in resultados.values())
    if todos_desligados and todas_verdes:
        return "restaurado"
    return "pendente"
