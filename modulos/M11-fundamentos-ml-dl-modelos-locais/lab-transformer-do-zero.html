Tensor: forma, tipo e dispositivo

Tensor é um arranjo N-dimensional de elementos do mesmo tipo. Três atributos decidem quase todo diagnóstico. Shape (forma) lista o tamanho de cada dimensão, da externa para a interna. Dtype (tipo numérico) diz como cada elemento é guardado — float32 para pesos e ativações, long para índices de token. Device (dispositivo) diz onde o dado mora — cpu neste módulo; GPU só acelera, sem mudar o resultado.

Convenção B/T/C. Em modelo de linguagem, as dimensões têm nome estável. B (batch, lote) conta quantas sequências entram juntas. T (time, tokens) mede o comprimento da sequência. C (channels, canais) mede a dimensão do embedding. Ler (4, 16, 32) como "4 sequências, 16 tokens cada, 32 números por token" evita metade dos erros de junção.

Trecho conceitual — leitura de forma. Ilustra o mecanismo; a execução com oráculos pertence à folha L:

import torch

                  [4.0, 5.0, 6.0]])
assert x.shape == torch.Size([2, 3])
assert x.dtype == torch.float32

lote = torch.randn(4, 16, 32)  # B=4, T=16, C=32
assert lote.shape == torch.Size([4, 16, 32])

ContrasteForma certa não garante conta certa. (4, 16) + (16,) funciona: o vetor é tratado como (1, 16) e replicado por 4 linhas. (4, 16) + (4,) falha: 4 não casa com 16 na última posição. Autograd: o grafo dinâmico e o gradiente que soma

Autograd é o registro automático de operações para derivação. Cada operação sobre um tensor marcado com requires_grad=True anexa um nó ao grafo da passagem direta (forward). backward() percorre esse grafo de trás para frente aplicando a regra da cadeia. O grafo é dinâmico: reconstruído a cada passagem, aceita if e for comuns dentro do modelo.

Gradiente é o vetor das derivadas da perda em relação a cada peso. Cada componente responde "se este peso subir um pouco, a perda sobe ou desce, e a que taxa". O vetor aponta para a subida mais íngreme; treinar é andar no sentido oposto em passos. Sem limpeza por iteração, o acumulado diverge — até nan, conforme taxa e passos (no lab deste módulo, oscila em patamar alto).

Trecho conceitual — derivada sem fórmula escrita. Ilustra o mecanismo:

import torch

x = torch.tensor(3.0, requires_grad=True)
y = x ** 2 + 5.0 * x  # registra pow, mul, add
y.backward()  # dy/dx = 2x + 5 = 11.0
assert x.grad is not None

Contraste"Acumular gradiente é sempre bug" — não. backward() soma no .grad existente em vez de sobrescrever. Sem limpeza por iteração, gradientes de passos antigos se somam aos novos e a perda diverge — até nan, conforme taxa e passos. Esse é o bug por esquecimento. A mesma soma, feita de propósito, simula um lote grande quando a memória não comporta o lote de uma vez: acumula-se por K mini-lotes e só então se atualiza. O critério separa os dois: acumulação sem chamada correspondente a zero_grad() no ritmo certo é acidente; acumulação contada e zerada no ponto marcado é técnica.

O loop de cinco passos

Todo treino repete o mesmo ciclo. Forward calcula a saída a partir da entrada. Loss (perda) mede a distância entre saída e alvo. Backward preenche .grad de cada parâmetro. Step (passo do otimizador) desloca cada peso contra o gradiente. Zero_grad limpa o acumulado para a próxima iteração. Repetir o ciclo é treinar.

As três peças da regressão. nn.Linear(in, out) guarda weight e bias e calcula xW + b. nn.MSELoss calcula o erro quadrático médio; pune erro grande mais que proporcionalmente, o que convém à regressão de demonstração. torch.optim.SGD aplica peso -= lr * grad; lr (taxa de aprendizado) é o tamanho do passo. Passo grande oscila e diverge; passo pequeno demora; a escolha é decisão de engenharia, não propriedade do algoritmo.

ContextoO que Adam e AdamW fazem. SGD usa um passo único para todos os parâmetros. Adam guarda por parâmetro uma média móvel do gradiente (momento) e do gradiente ao quadrado (escala), e ajusta o passo de cada um: anda mais onde o terreno é plano, menos onde é íngreme. AdamW mantém o mesmo ajuste e corrige o weight decay (penalidade que puxa pesos para zero como regularização), aplicando-o fora do cálculo adaptativo. Adam e AdamW são o padrão em transformers; a regressão abaixo usa SGD porque um parâmetro por dimensão dispensa adaptação, e o seno usa Adam. Fonte: SRC-M11-11.

Sem ativação, profundidade colapsa

Ativação é uma função não linear aplicada entre camadas, como Tanh. Sem ela, duas camadas lineares em série equivalem a uma só: (xW1)W2 = x(W1W2). O produto W1W2 é outra matriz; nenhuma profundidade linear cria função nova. A ativação quebra a linearidade e dá poder expressivo ao empilhamento. A referência nao_linear.py mostra o colapso na prática: a reta não acompanha o seno, o MLP com Tanh acompanha.

Overfitting: o critério de parada, com ponte ao Bloco 4

Overfitting é decorar o treino e piorar fora dele. A perda de treino continua caindo enquanto a perda em dados separados — validação, o conjunto que o modelo não usa para atualizar peso — para de cair e começa a subir. O ponto de virada é o critério de parada: interromper ali preserva generalização (early stopping). O Bloco 4 torna o fenômeno visível com treino e validação separados sobre código. A regra atravessa domínios: nunca valide um sistema só com os dados que o construíram.

Referência executável 1 — lab/regressao.py. Aprende y = 3x + 2 com ruído, semente fixa, loop de cinco passos e impressão periódica. Tipagem estrita, só CPU:

"""Regressao linear y = 3x + 2 com ruido.

Referencia executavel do Bloco 2.
Implementacao verbatim na folha B02-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
"""

import torch
from torch import nn

SEMENTE: int = 1337
N_AMOSTRAS: int = 200
PASSOS: int = 500
IMPRIMIR_A_CADA: int = 100
TAXA: float = 0.1


def gerar_dados(n: int) -> tuple[torch.Tensor, torch.Tensor]:
    """Gera X e y = 3x + 2 + ruido gaussiano."""
    x = torch.randn(n, 1)
    ruido = 0.1 * torch.randn(n, 1)
    y = 3.0 * x + 2.0 + ruido
    return x, y


def construir_modelo() -> nn.Linear:
    """Modelo y = wx + b com um neuronio."""
    return nn.Linear(in_features=1, out_features=1)


def treinar(
    modelo: nn.Linear,
    x: torch.Tensor,
    alvo: torch.Tensor,
    limpar_grad: bool = True,
) -> nn.Linear:
    """Loop de 5 passos; retorna o modelo treinado."""
    criterio = nn.MSELoss()
    otimizador = torch.optim.SGD(modelo.parameters(), lr=TAXA)
    otimizador.zero_grad()
    for passo in range(PASSOS + 1):
        pred = modelo(x)  # 1. forward
        perda = criterio(pred, alvo)  # 2. loss
        perda.backward()  # 3. backward
        otimizador.step()  # 4. step
        if limpar_grad:  # 5. zero_grad
            otimizador.zero_grad()
        if passo % IMPRIMIR_A_CADA == 0:
            w = modelo.weight.item()
            b = modelo.bias.item()
            print(f"passo {passo:3d} | perda {perda.item():.4f}")
            print(f"  w={w:.2f} b={b:.2f}")
    return modelo


def main() -> None:
    """Caminho feliz: semente fixa e limpeza ligada."""
    torch.manual_seed(SEMENTE)
    x, alvo = gerar_dados(N_AMOSTRAS)
    modelo = construir_modelo()
    treinar(modelo, x, alvo, limpar_grad=True)


if __name__ == "__main__":
    main()

Variante de quebra. A mesma referência com limpar_grad=False é o caso negativo: o caminho feliz converge para perto de w = 3 e b = 2; sem limpeza o acumulado diverge. A folha L executa os dois caminhos a partir deste único parâmetro.

Referência executável 2 — lab/nao_linear.py. O seno separa o que é linear do que exige ativação: baseline Linear contra MLP Linear-Tanh-Linear. Tipagem estrita, só CPU:

"""Seno: reta contra MLP com ativacao.

Referencia executavel do Bloco 2.
Implementacao verbatim na folha B02-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
"""

import torch
from torch import nn

SEMENTE: int = 1337
N_PONTOS: int = 400
OCULTOS: int = 64
PASSOS: int = 2000
TAXA: float = 0.02


def gerar_seno(n: int) -> tuple[torch.Tensor, torch.Tensor]:
    """X em [-3, 3]; y = sin(x) + ruido."""
    x = torch.linspace(-3.0, 3.0, n).unsqueeze(1)
    y = torch.sin(x) + 0.05 * torch.randn_like(x)
    return x, y


def criar_linear() -> nn.Linear:
    """Baseline: uma reta y = wx + b."""
    return nn.Linear(1, 1)


def criar_mlp(ocultos: int = OCULTOS) -> nn.Sequential:
    """Linear -> Tanh -> Linear; a ativacao impede o colapso."""
    return nn.Sequential(
        nn.Linear(1, ocultos),
        nn.Tanh(),
        nn.Linear(ocultos, 1),
    )


def treinar(
    modelo: nn.Module, x: torch.Tensor, alvo: torch.Tensor
) -> float:
    """Treina com Adam e devolve a perda final."""
    criterio = nn.MSELoss()
    otimizador = torch.optim.Adam(modelo.parameters(), lr=TAXA)
    perda_final = 0.0
    for _ in range(PASSOS):
        pred = modelo(x)
        perda = criterio(pred, alvo)
        otimizador.zero_grad()
        perda.backward()
        otimizador.step()
        perda_final = perda.item()
    return perda_final


def main() -> None:
    """Treina os dois e imprime as perdas finais."""
    torch.manual_seed(SEMENTE)
    x, alvo = gerar_seno(N_PONTOS)
    perda_linear = treinar(criar_linear(), x, alvo)
    perda_mlp = treinar(criar_mlp(), x, alvo)
    print(f"linear perda final = {perda_linear:.4f}")
    print(f"mlp perda final = {perda_mlp:.4f}")


if __name__ == "__main__":
    main()

Teste rápido

Num loop de treino em PyTorch, você esquece zero_grad(). O que acontece?

  1. O PyTorch zera sozinho a cada backward(), então nada muda
  2. Os gradientes se acumulam entre iterações (o autograd soma em .grad), então cada passo usa um gradiente contaminado pelos anteriores
  3. O loss vira NaN já na segunda iteração, sempre
  4. Nada: zero_grad() só economiza memória
Os cinco passos são forward, loss, backward, step e zero_grad. O backward soma no .grad; sem limpar, o passo seguinte anda numa direção que mistura o erro de várias iterações. Não é erro de sintaxe: o treino roda e rende pior, silenciosamente.
Teste rápido

Duas camadas lineares em série, sem ativação entre elas, equivalem a quê?

  1. A uma rede mais expressiva, porque tem mais parâmetros
  2. A uma camada com ativação Tanh
  3. A uma só camada linear: (xW1)W2 = x(W1W2). Profundidade linear não cria função nova; a ativação quebra a linearidade
  4. A nada: só funcionam em GPU
O produto W1W2 é outra matriz. Ter mais parâmetros não basta: sem não linearidade, empilhar não adiciona poder. Por isso o transformer intercala atenção e MLP com ativação.

Este bloco combina os três: cada token é projetado em três papéis, a concordância entre papéis vira peso, o peso mistura conteúdo. O preço aparece na mesma operação que já era quadrática no papel.

O problema: o mesmo token, sentidos distintos

Um vetor fixo por token não distingue uso. A palavra Cliente em class Cliente (definição), em cliente.salvar() (instância em chamada) e em "o cliente reclamou do prazo" (pessoa fora do código) exigiria três significados; um embedding estático entrega um só. O modelo precisa de representação que depende da vizinhança.

A atenção resolve o impasse com mistura contextual: cada posição mede concordância com as demais e reescreve o próprio vetor como soma ponderada dos vetores vizinhos. Após a camada, o vetor na posição de Cliente carrega "Cliente neste contexto", não "Cliente em geral". O mecanismo é busca ponderada; o resto é aritmética com formas controladas.

Q, K, V: busca difusa por produto escalar

Cada token produz três vetores por projeção linear aprendida sobre a entrada. Query (Q) declara o que a posição procura. Key (K) declara o que cada posição oferece à procura alheia. Value (V) carrega o conteúdo que será misturado quando a posição for selecionada. Três projeções separadas permitem que "procurar", "ser encontrado" e "entregar" aprendam geometrias distintas.

A busca é difusa: nenhuma chave vence sozinha. O escore entre a posição i e a posição j é o produto escalar entre Q[i] e K[j] — a operação de concordância do Bloco 2, reaproveitada sem mudança. Escores altos viram pesos altos na mistura; escores baixos viram pesos próximos de zero. Difuso significa ponderado, não indeciso: a soma final carrega mais dos vizinhos relevantes.

Trecho conceitual — escores como concordância. Ilustra o mecanismo; a prova com oráculo pertence à folha L:

import torch

# Duas queries (T=2) contra tres keys (T=3), dim=4: (2, 4) @ (4, 3) -> (2, 3)
q = torch.randn(2, 4)
k = torch.randn(3, 4)
escores = q @ k.T
assert escores.shape == torch.Size([2, 3])

A fórmula, peça por peça

ContextoO que softmax faz, em números. Dado um vetor qualquer, devolve vetor positivo de mesma dimensão somando 1, por exp(x) / soma(exp(x)). [1, 2, 3] vira aproximadamente [0.09, 0.24, 0.67]: ordem preservada, distância exagerada. Com magnitudes grandes o exagero vira colapso (quase tudo no máximo). A divisão por sqrt(d) controla esse colapso na atenção; a temperatura controla o mesmo exagero na amostragem do Bloco 5.

Contraste"Softmax ordena por importância absoluta" — não. Softmax preserva a ordem relativa dos escores e exagera a separação; não atribui sentido absoluto a nenhum peso. Um peso 0.67 em [1, 2, 3] não significa "67% importante em geral": significa "maior que os vizinhos desta linha, nesta escala". Trocar a escala ou os vizinhos muda todos os pesos sem mudar nenhuma key. Comparar pesos entre linhas ou entre sequências distintas como se fossem escores universais produz leitura falsa do que o modelo julga importante.

EstabilidadeSubtrair o máximo não muda a conta; muda o estouro. exp(800) ultrapassa a faixa do ponto flutuante e contamina o treino com inf e nan. Implementações sérias calculam exp(x - max(x)) antes de normalizar: matematicamente idêntico, numericamente seguro, porque o maior expoente vira exp(0) = 1. A regra atravessa domínios: expressão reescrita "sem motivo" em código de produção costuma proteger faixa de tipo numérico, não elegância.

Trecho conceitual — softmax estável. Ilustra a reescrita; o oráculo de equivalência pertence à folha L:

import torch

def softmax_estavel(x: torch.Tensor) -> torch.Tensor:
    """Softmax com subtracao do maximo; mesma conta, sem estouro."""
    m = x.max(dim=-1, keepdim=True).values
    e = torch.exp(x - m)
    return e / e.sum(dim=-1, keepdim=True)

A implementação oficial e o que o kernel otimizado economiza

torch.nn.functional.scaled_dot_product_attention (SDPA) é a implementação oficial da fórmula: recebe Q, K e V e aplica escala, máscara causal opcional e mistura em caminho otimizado. A referência lab/atencao.py escreve a conta passo a passo e prova equivalência contra SDPA com tolerância explícita. SDPA é o oráculo; a versão manual é o instrumento de entendimento.

FlashAttention é o kernel otimizado que SDPA seleciona quando o hardware permite. A economia é de memória: em vez de materializar a matriz T×T inteira, processa em blocos e recomputa no backward. A contagem de operações continua quadrática. Em serving, o cache de chaves e valores evita refazer o prefixo estável; organizar esse cache em páginas responde por throughput (PagedAttention). Nenhuma dessas técnicas remove o termo dominante do prefill: dobrar a entrada continua multiplicando o trabalho por quatro (tempo ≈4× por dobra onde a computação domina; em contextos curtos o overhead de lançamento domina).

Contraste"FlashAttention elimina o O(n²)" — não. FlashAttention elimina a materialização da matriz T×T em memória; não elimina as comparações par a par que definem a atenção. Confundir pico de memória com contagem de operações leva a dimensionar contexto por VRAM e descobrir o estouro no relógio: cabe na placa, não cabe no TTFT. A decisão que decorre do contraste: medir tempo por dobra de contexto em vez de inferir custo por consumo de memória.

O custo quadrático e a decisão no gateway

O prefill (processar o prompt de entrada) cresce com o quadrado do comprimento: cada token novo compara-se com todos os anteriores. A referência lab/custo_quadratico.py varre comprimentos crescentes com repetição e aquecimento e publica a razão entre dobras sucessivas. CPU é o baseline; GPU opcional só acelera. A implicação atravessa o gateway do M05: tempo até o primeiro token (TTFT) dispara com prompts longos, enquanto a cobrança por token sugere crescimento linear. O cache de prompt evita refazer o trabalho quadrático sobre o prefixo estável; o orçamento de atenção do M08 poda o contexto porque cada token cortado remove uma linha e uma coluna da matriz.

DecisãoCortar 30% do contexto corta ~51% do trabalho de atenção. A conta é direta: 0.7² = 0.49. Podar prefixo estável, histórico redundante e instrumento verboso antes de chamar o modelo reduz o termo dominante do prefill; completar com cache quando o prefixo se repete reduz o restante. A referência de medição publica células T×T ao lado do tempo para a causa ficar visível: de 128 para 1024 tokens, as células crescem 64× para 8× mais tokens. Números ilustrativos seguem como exemplo variável; a folha L mede na máquina local.

Multi-head sem loop: a cabeça como dimensão de lote

Uma cabeça aprende um tipo de relação. Um token precisa consultar várias ao mesmo tempo — a quem um pronome se refere, qual o tipo de um identificador, onde o bloco atual começou. A solução executa h cabeças em paralelo, cada uma com projeção Q/K/V própria e dimensão C/h, e concatena as saídas. A referência lab/multihead.py usa uma projeção única que produz Q, K e V de uma vez, divide o resultado em três, reorganiza cada parte e aplica SDPA causal uma única vez.

O truque está na reorganização: (B, T, C) vira (B, h, T, d) por view seguido de transpose, de modo que a dimensão de cabeça ocupa a posição de lote. Uma multiplicação calcula todas as cabeças juntas. Na volta, transpose + contiguous() + view recola as cabeças em (B, T, C), e uma projeção linear de saída mistura as cabeças. Forma de saída igual à de entrada: a propriedade que permite empilhar camadas no Bloco 4.

Trecho conceitual — cabeça como lote. Ilustra a reorganização; a prova de forma pertence à folha L:

import torch

B, T, H, D = 2, 8, 4, 16
x = torch.randn(B, T, H * D)          # (B, T, C) com C = H * D
por_cabeca = x.view(B, T, H, D).transpose(1, 2)  # (B, H, T, D)
assert por_cabeca.shape == torch.Size([B, H, T, D])
junta = por_cabeca.transpose(1, 2).contiguous().view(B, T, H * D)
assert junta.shape == x.shape

Contrasteview após transpose exige contiguous() — sem exceção silenciosa. view e transpose devolvem visões sobre o mesmo buffer, com passos (strides) distintos; após transpose os elementos não estão em ordem linear, e view exige ordem linear. Omitir contiguous() levanta erro de stride em vez de conta errada. O diagnóstico é direto: erro de view após transpose pede contiguous() entre os dois; laço por cabeça em vez de dimensão de lote pede a reorganização acima.

"""Cabeca de atencao causal manual + prova contra SDPA.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
"""

import math

import torch
from torch import nn
from torch.nn.functional import scaled_dot_product_attention as sdpa

SEMENTE: int = 1337
LOTE: int = 2
TOKENS: int = 8
DIM_ENTRADA: int = 32
DIM_CABECA: int = 16
CONTEXTO_MAX: int = 64
ATOL: float = 1e-5


class CabecaAtencao(nn.Module):
    """Uma cabeca de self-attention causal, passo a passo."""

    mascara: torch.Tensor

    def __init__(self, dim_entrada: int, dim_cabeca: int, contexto_max: int) -> None:
        super().__init__()
        self.dim_cabeca = dim_cabeca
        self.para_query = nn.Linear(dim_entrada, dim_cabeca, bias=False)
        self.para_key = nn.Linear(dim_entrada, dim_cabeca, bias=False)
        self.para_value = nn.Linear(dim_entrada, dim_cabeca, bias=False)
        self.register_buffer("mascara", torch.tril(torch.ones(contexto_max, contexto_max)))

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        _, t, _ = x.shape
        q = self.para_query(x)
        k = self.para_key(x)
        v = self.para_value(x)
        escores = q @ k.transpose(-2, -1) / math.sqrt(self.dim_cabeca)
        escores = escores.masked_fill(self.mascara[:t, :t] == 0, float("-inf"))
        pesos = torch.softmax(escores, dim=-1)
        saida: torch.Tensor = pesos @ v
        return saida


def comparar_com_sdpa() -> float:
    """Roda a cabeca manual e SDPA sobre a mesma entrada; devolve o erro maximo."""
    torch.manual_seed(SEMENTE)
    x = torch.randn(LOTE, TOKENS, DIM_ENTRADA)
    cabeca = CabecaAtencao(DIM_ENTRADA, DIM_CABECA, CONTEXTO_MAX)
    manual = cabeca(x)
    q = cabeca.para_query(x)
    k = cabeca.para_key(x)
    v = cabeca.para_value(x)
    oficial = sdpa(q, k, v, is_causal=True)
    assert manual.shape == oficial.shape
    assert torch.allclose(manual, oficial, atol=ATOL)
    erro: float = (manual - oficial).abs().max().item()
    return erro


def main() -> None:
    """Prova AT-009: manual equivale a SDPA dentro da tolerancia."""
    erro = comparar_com_sdpa()
    print(f"formas iguais; erro maximo = {erro:.2e}")


if __name__ == "__main__":
    main()

"""Varredura do custo quadratico da atencao.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L.
CPU-only: mede na maquina local; GPU opcional.
"""

import time

import torch
from torch.nn.functional import scaled_dot_product_attention as sdpa

SEMENTE: int = 1337
REPETICOES: int = 5
CONTEXTOS: tuple[int, ...] = (128, 256, 512, 1024)
CABECAS: int = 4
DIM_CABECA: int = 32


def medir_ms(tokens: int) -> float:
    """Tempo medio em ms de uma chamada causal para o contexto dado."""
    q = torch.randn(1, CABECAS, tokens, DIM_CABECA)
    k = torch.randn(1, CABECAS, tokens, DIM_CABECA)
    v = torch.randn(1, CABECAS, tokens, DIM_CABECA)
    sdpa(q, k, v, is_causal=True)
    inicio = time.perf_counter()
    for _ in range(REPETICOES):
        sdpa(q, k, v, is_causal=True)
    return (time.perf_counter() - inicio) / REPETICOES * 1000.0


def varrer_contextos() -> list[tuple[int, float, int, str]]:
    """Varre CONTEXTOS; devolve (tokens, ms, celulas, razao)."""
    linhas: list[tuple[int, float, int, str]] = []
    anterior = 0.0
    for tokens in CONTEXTOS:
        ms = medir_ms(tokens)
        razao = f"{ms / anterior:.2f}x" if anterior > 0.0 else "--"
        linhas.append((tokens, ms, tokens * tokens, razao))
        anterior = ms
    return linhas


def main() -> None:
    """Imprime a tabela tokens | tempo | celulas | razao (AT-010)."""
    torch.manual_seed(SEMENTE)
    print(f"{'tokens':>7} | {'tempo(ms)':>10} | {'celulas T*T':>12} | {'razao':>6}")
    for tokens, ms, celulas, razao in varrer_contextos():
        print(f"{tokens:7d} | {ms:10.2f} | {celulas:12d} | {razao:>6}")


if __name__ == "__main__":
    main()

"""Atencao multi-cabeca causal sem loop por cabeca.

Referencia executavel do Bloco 3.
Implementacao verbatim na folha B03-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
"""

import torch
from torch import nn
from torch.nn.functional import scaled_dot_product_attention as sdpa

N_EMBD: int = 128
N_CABECAS: int = 8


class AtencaoMultiCabeca(nn.Module):
    """Multi-head causal; a cabeca vira dimensao de lote."""

    def __init__(self, n_embd: int, n_cabecas: int, dropout: float = 0.0) -> None:
        super().__init__()
        if n_embd % n_cabecas != 0:
            raise ValueError("n_embd precisa ser divisivel por n_cabecas")
        self.n_cabecas = n_cabecas
        self.dim_cabeca = n_embd // n_cabecas
        self.dropout = dropout
        self.qkv = nn.Linear(n_embd, 3 * n_embd, bias=False)
        self.saida = nn.Linear(n_embd, n_embd, bias=False)

    def forward(self, x: torch.Tensor) -> torch.Tensor:
        b, t, c = x.shape
        q, k, v = self.qkv(x).split(c, dim=2)

        def por_cabeca(tensor: torch.Tensor) -> torch.Tensor:
            return tensor.view(b, t, self.n_cabecas, self.dim_cabeca).transpose(1, 2)

        qh, kh, vh = por_cabeca(q), por_cabeca(k), por_cabeca(v)
        y = sdpa(qh, kh, vh, dropout_p=self.dropout if self.training else 0.0, is_causal=True)
        y = y.transpose(1, 2).contiguous().view(b, t, c)
        saida: torch.Tensor = self.saida(y)
        return saida


def main() -> None:
    """Forma preservada e contagem de parametros (exemplo variavel)."""
    torch.manual_seed(1337)
    bloco = AtencaoMultiCabeca(n_embd=N_EMBD, n_cabecas=N_CABECAS)
    x = torch.randn(4, 32, N_EMBD)
    total = sum(p.numel() for p in bloco.parameters())
    print(f"saida: {tuple(bloco(x).shape)}")
    print(f"parametros: {total}")


if __name__ == "__main__":
    main()

Tokenização BPE: de bytes a fusões por frequência

Token é o inteiro que o modelo enxerga; vocabulário é a tabela que converte trecho de texto em inteiros e de volta. BPE (Byte Pair Encoding) constrói essa tabela a partir de bytes: começa com um símbolo por byte, conta pares adjacentes no corpus, funde o par mais frequente num símbolo novo e repete por um número fixo de fusões. Palavra comum vira símbolo único; palavra rara segue quebrada em pedaços frequentes.

A propriedade que sustenta o treino: BPE nunca falha diante de texto novo. Símbolo ausente se decompõe até bytes, e byte sempre pertence ao vocabulário inicial. Compressão boa para o frequente convive com cobertura total para o raro. O preço aparece nos dígitos.

ContextoO que uma fusão aprende, em pequeno. Corpus com baixo baixa baixar: cada caractere começa separado; o par b+a domina a contagem e vira ba; em seguida ba+i vira bai; depois bai+x vira baix. O radical frequente comprime num token; os sufixos o, a, ar seguem separados. Frequência decide a fronteira, sem gramática.

Trecho conceitual — fusão por frequência. Ilustra o mecanismo; o oráculo offline com números pertence à referência lab/bpe_mini.py:

pares = Counter(zip(simbolos, simbolos[1:]))  # frequência decide
a, b = max(pares, key=pares.get)  # par vencedor vira símbolo novo
novo = a + b  # fusão registrada na ordem aprendida

Com a tabela pronta, segmentar aplica as fusões na ordem aprendida sobre a sequência de caracteres. Ordem importa: a mesma string se quebra de modo distinto conforme o corpus. O oráculo da folha L prova o caso crítico: 1234 e 1235 caem em segmentos distintos, com dígitos vizinhos em pedaços distintos.

Contraste"Mais dados consertam a aritmética" — não. Humano soma por algoritmo posicional sobre dígitos. O modelo recebe símbolos como 123 e 4, cuja relação numérica é estatística, aprendida de coocorrência, sem estrutura posicional garantida. Ele prediz a continuação mais provável de sequência que se parece com soma; acerta o frequente e erra o raro. O espaço de somas é infinito e a entrada não carrega o algoritmo, por isso volume de treino não remove a falha.

Mitigação. Duas respostas convivem. Na entrada, dígitos separados ou agrupamento fixo reduzem a arbitrariedade da fronteira, sem criar aritmética. Na arquitetura, terceirizar a conta para tool decide o caso exato: se a resposta precisa ser exata, o modelo chama cálculo em vez de completar texto. É a regra do M08, agora com mecanismo.

Encoder-only nunca aprende a prever o próximo token sem ver o futuro; posto para gerar, usa contexto proibido no treino e degrada fora da tarefa. Decoder-only gera por construção, mas como embedding perde contexto à direita e entrega vetor pior para busca. A teoria prevê a degradação nos dois sentidos.

Contraste"Encoder gera texto se pedir" — não. Pedir não cria cabeça de saída sobre o vocabulário nem remove a visão do futuro embutida nos pesos. A saída parece texto e viola causalidade: condiciona em posição que geração real ainda não produziu. A folha L executa o oráculo mecânico sobre lab/gpt.py: mesmos pesos e mesma semente, máscara causal ligada contra desligada; sem causalidade a posição futura contamina a predição e a geração degrada.

Passo a passo: o caminho de um token pelo transformer (decoder-only)

Gerar: recorte, temperatura, sorteio

Geração autoregressiva repete um passo: recorte de janela com os últimos contexto tokens, passagem direta, leitura só de logits[-1], divisão por temperatura T, softmax e sorteio. Recorte impõe a janela literal: nada além dos últimos tokens condiciona o próximo. Temperatura repondera sem inverter a ordem: T < 1 afia, T > 1 achata, com a massa redistribuída sobre a mesma ordenação. O Bloco 5 mede esse efeito por entropia.

torch.multinomial sorteia da distribuição. A mesma entrada e os mesmos pesos produzem continuações distintas entre chamadas, porque a saída é amostra, não máximo. Confundir amostra com escolha troca o objeto de estudo do próximo bloco.

Trecho conceitual — o passo de geração. Ilustra a ordem; o programa completo pertence à referência lab/gpt.py:

recorte = idx[:, -contexto:]  # janela literal
passo = logits[:, -1, :] / T  # só a última posição, reponderada
prox = torch.multinomial(softmax(passo), 1)  # sorteia, não escolhe

Contraste"Argmax é a geração correta" — não. Argmax devolve sempre o token de maior probabilidade e colapsa a distribuição num ponto; útil para depurar, pobre para texto. Amostragem preserva a incerteza aprendida e é o comportamento que o Bloco 5 controla com temperatura, top-p e top-k.

Referência executável 1 — lab/gpt.py. Config, embeddings de token e posição, N blocos Pre-LN com AtencaoMultiCabeca do B03 mais MLP e residual, ln_final, cabeça sobre o vocabulário sem viés, gerar() com multinomial. Tipagem estrita, só CPU:

"""GPT mínimo Pre-LN sobre a atenção do Bloco 3.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
"""
from dataclasses import dataclass
import torch
from torch import nn
from torch.nn import functional as F
from multihead import AtencaoMultiCabeca
@dataclass(frozen=True)
class Config:
    vocab: int
    contexto: int = 64
    n_embd: int = 128
    n_cabecas: int = 4
    n_camadas: int = 4
    dropout: float = 0.0
class MLP(nn.Module):
    def __init__(self, cfg: Config) -> None:
        super().__init__()
        self.rede = nn.Sequential(
            nn.Linear(cfg.n_embd, 4 * cfg.n_embd),
            nn.GELU(),
            nn.Linear(4 * cfg.n_embd, cfg.n_embd),
            nn.Dropout(cfg.dropout),
        )
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        saida: torch.Tensor = self.rede(x)
        return saida
class Bloco(nn.Module):
    def __init__(self, cfg: Config) -> None:
        super().__init__()
        self.ln1 = nn.LayerNorm(cfg.n_embd)
        self.atencao = AtencaoMultiCabeca(cfg.n_embd, cfg.n_cabecas, cfg.dropout)
        self.ln2 = nn.LayerNorm(cfg.n_embd)
        self.mlp = MLP(cfg)
    def forward(self, x: torch.Tensor) -> torch.Tensor:
        x = x + self.atencao(self.ln1(x))
        x = x + self.mlp(self.ln2(x))
        return x
class GPTMinusculo(nn.Module):
    def __init__(self, cfg: Config) -> None:
        super().__init__()
        self.cfg = cfg
        self.emb_token = nn.Embedding(cfg.vocab, cfg.n_embd)
        self.emb_posicao = nn.Embedding(cfg.contexto, cfg.n_embd)
        self.blocos = nn.ModuleList([Bloco(cfg) for _ in range(cfg.n_camadas)])
        self.ln_final = nn.LayerNorm(cfg.n_embd)
        self.cabeca = nn.Linear(cfg.n_embd, cfg.vocab, bias=False)
    def forward(
        self, idx: torch.Tensor, alvos: torch.Tensor | None = None
    ) -> tuple[torch.Tensor, torch.Tensor | None]:
        b, t = idx.shape
        pos = torch.arange(t, device=idx.device)
        x = self.emb_token(idx) + self.emb_posicao(pos)
        for bloco in self.blocos:
            x = bloco(x)
        logits = self.cabeca(self.ln_final(x))
        perda: torch.Tensor | None = None
        if alvos is not None:
            perda = F.cross_entropy(logits.view(b * t, self.cfg.vocab), alvos.view(b * t))
        return logits, perda
    @torch.no_grad()
    def gerar(self, idx: torch.Tensor, n: int, temperatura: float = 1.0) -> torch.Tensor:
        for _ in range(n):
            recorte = idx[:, -self.cfg.contexto :]
            logits, _ = self(recorte)
            passo = logits[:, -1, :] / temperatura
            probs = F.softmax(passo, dim=-1)
            prox = torch.multinomial(probs, num_samples=1)
            idx = torch.cat([idx, prox], dim=1)
        return idx
def main() -> None:
    torch.manual_seed(1337)
    cfg = Config(vocab=64)
    modelo = GPTMinusculo(cfg)
    x = torch.zeros((2, 8), dtype=torch.long)
    logits, perda = modelo(x, x)
    print(tuple(logits.shape), perda.item() if perda is not None else None)
if __name__ == "__main__":
    main()

Generalização, overfitting, holdout

Generalização é acertar fora do treino; overfitting é decorar o treino e piorar fora dele. O sinal é a divergência: perda de treino segue caindo enquanto perda em dados separados para de cair e começa a subir. O conjunto separado é a validação; o conjunto reservado para o fim é o holdout. Nenhum dos dois atualiza peso. A decisão é parada antecipada: interromper no ponto onde a validação vira.

A disciplina atravessa domínios: nunca valide um sistema só com os dados que o construíram. É a mesma razão do holdout nos evals do M06. A folha L declara overfitting com treino e validação impressos lado a lado e critério explícito.

"""Treino curto CPU do GPT mínimo sobre corpus local.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L.
CPU-only: sem `.to(cuda)`; GPU opcional.
Default offline: char-level local. Tiktoken/HF só em trilha
opcional com cache declarado, nunca como caminho único.
"""
from pathlib import Path
import torch
from gpt import Config, GPTMinusculo
CORPUS: Path = Path(__file__).with_name("fixtures") / "corpus.txt"
SEMENTE: int = 1337
CONTEXTO: int = 64
LOTE: int = 16
PASSOS: int = 600
TAXA: float = 3e-4
def carregar_texto(caminho: Path = CORPUS) -> str:
    return caminho.read_text(encoding="utf-8")
def construir_vocab(texto: str) -> tuple[dict[str, int], dict[int, str]]:
    chars = sorted(set(texto))
    stoi = {c: i for i, c in enumerate(chars)}
    return stoi, {i: c for c, i in stoi.items()}
def codificar(texto: str, stoi: dict[str, int]) -> torch.Tensor:
    return torch.tensor([stoi[c] for c in texto], dtype=torch.long)
def dividir(dados: torch.Tensor, fracao: float = 0.9) -> tuple[torch.Tensor, torch.Tensor]:
    corte = int(fracao * len(dados))
    return dados[:corte], dados[corte:]
def fazer_lote(origem: torch.Tensor, contexto: int, tamanho: int) -> tuple[torch.Tensor, torch.Tensor]:
    ix = torch.randint(len(origem) - contexto - 1, (tamanho,))
    x = torch.stack([origem[i:i + contexto] for i in ix])
    y = torch.stack([origem[i + 1:i + 1 + contexto] for i in ix])
    return x, y
def avaliar(modelo: GPTMinusculo, origem: torch.Tensor) -> float:
    modelo.eval()
    with torch.no_grad():
        _, perda = modelo(*fazer_lote(origem, modelo.cfg.contexto, LOTE))
    modelo.train()
    assert perda is not None
    valor: float = perda.item()
    return valor
def treinar(passos: int = PASSOS, demo_overfitting: bool = False) -> tuple[float, float]:
    torch.manual_seed(SEMENTE)
    texto = carregar_texto()
    if demo_overfitting:
        texto = texto[:2000]
        passos = passos * 4
    stoi, _ = construir_vocab(texto)
    treino, valid = dividir(codificar(texto, stoi))
    modelo = GPTMinusculo(Config(vocab=len(stoi), contexto=CONTEXTO))
    otim = torch.optim.AdamW(modelo.parameters(), lr=TAXA)
    final_treino = 0.0
    for passo in range(passos + 1):
        x, y = fazer_lote(treino, CONTEXTO, LOTE)
        _, perda = modelo(x, y)
        assert perda is not None
        otim.zero_grad()
        perda.backward()
        otim.step()
        final_treino = perda.item()
        if passo % 200 == 0:
            print(f"passo {passo} | treino {final_treino:.3f} | valid {avaliar(modelo, valid):.3f}")
    return final_treino, avaliar(modelo, valid)
def main() -> None:
    treinar()
if __name__ == "__main__":
    main()

"""BPE mínimo em Python puro sobre corpus-toy local.

Referencia executavel do Bloco 4.
Implementacao verbatim na folha B04-L.
Oráculo offline de AT-012: sem tiktoken, sem HF, sem rede.
"""
from collections import Counter
from itertools import pairwise
CORPUS_TOY: list[str] = (
    ["1234"] * 20
    + ["12"] * 10
    + ["34"] * 9
    + ["123"] * 8
    + ["5"] * 5
    + ["baixo"] * 5
    + ["baixa"] * 5
)
N_FUSOES: int = 8
def treinar_bpe(
    corpus: list[str] = CORPUS_TOY, n_fusoes: int = N_FUSOES
) -> list[tuple[str, str]]:
    palavras: list[list[str]] = [[c for c in w] for w in corpus]
    fusoes: list[tuple[str, str]] = []
    for _ in range(n_fusoes):
        cont: Counter[tuple[str, str]] = Counter()
        for p in palavras:
            for a, b in pairwise(p):
                cont[(a, b)] += 1
        if not cont:
            break
        melhor = sorted(cont.items(), key=lambda kv: (-kv[1], kv[0]))[0][0]
        fusoes.append(melhor)
        a, b = melhor
        novo = a + b
        for p in palavras:
            i = 0
            ref: list[str] = []
            while i < len(p):
                if i < len(p) - 1 and p[i] == a and p[i + 1] == b:
                    ref.append(novo)
                    i += 2
                else:
                    ref.append(p[i])
                    i += 1
            p[:] = ref
    return fusoes
def segmentar(texto: str, fusoes: list[tuple[str, str]]) -> list[str]:
    toks: list[str] = [c for c in texto]
    for a, b in fusoes:
        novo = a + b
        i = 0
        ref: list[str] = []
        while i < len(toks):
            if i < len(toks) - 1 and toks[i] == a and toks[i + 1] == b:
                ref.append(novo)
                i += 2
            else:
                ref.append(toks[i])
                i += 1
        toks = ref
    return toks
def provar_numeros_vizinhos() -> tuple[list[str], list[str]]:
    fusoes = treinar_bpe()
    return segmentar("1234", fusoes), segmentar("1235", fusoes)
def main() -> None:
    a, b = provar_numeros_vizinhos()
    print(f"1234 -> {a}")
    print(f"1235 -> {b}")
if __name__ == "__main__":
    main()

SínteseBloco 4 em seis frases.

  • BPE funde por frequência e nunca falha; dígitos vizinhos caem em pedaços distintos porque relação numérica é estatística.
  • Residual soma o delta, LayerNorm contém a escala, MLP 4× processa por posição, posição rompe a invariância à permutação.
  • Gerar recorta a janela, lê logits[-1]/T e sorteia por multinomial; amostra não é escolha.
  • Encoder entende, decoder gera, encoder-decoder transforma; trocar degrada porque máscara e objetivo divergem.
  • Treino que desce com validação que sobe declara overfitting; holdout que não atualiza peso decide a parada.
  • Conta exata pertence à tool; dígitos separados apenas reduzem a arbitrariedade da fronteira.
Teste rápido

Por que a tokenização por BPE ajuda a explicar um LLM errar 4871 × 39?

  1. O BPE converte números em float32 antes de entrar no modelo
  2. O BPE funde pares por frequência no corpus, sem considerar valor numérico: dígitos vizinhos podem cair em segmentos distintos e o modelo não enxerga o número como quantidade
  3. O BPE usa sempre um token por dígito, o que atrapalha a soma
  4. O BPE só afeta texto em português
Token é o inteiro que o modelo vê; o corte ignora palavra, número e sintaxe. Junte a isso a amostragem (o resultado é sorteado) e você tem o clássico do módulo. Mais dados de aritmética não conserta a causa.
Teste rápido

Por que a máscara decide a tarefa (encoder-only, decoder-only)?

  1. A máscara só afeta velocidade, nunca a tarefa
  2. Encoder-only gera texto normalmente se o prompt pedir
  3. Decoder-only usa máscara causal (cada token vê só os anteriores) e por isso gera token a token; encoder-only vê todos e serve para compreender, mas, posto a gerar, usaria contexto proibido no treino
  4. Encoder-decoder dispensa qualquer máscara
Pedir não cria cabeça de saída sobre o vocabulário nem remove a visão do futuro embutida nos pesos. Sem causalidade, a posição futura contamina a predição e a geração degrada.
Teste rápido

A perda de treino continua caindo, mas a perda de validação parou de cair e começou a subir. O que fazer?

  1. É overfitting: parar antecipadamente no ponto em que a validação vira (early stopping), em vez de continuar treinando
  2. Treinar mais, até a validação alcançar o treino
  3. Usar também a validação para atualizar os pesos
  4. Aumentar a taxa de aprendizado
Validação e holdout nunca atualizam peso: servem para medir generalização. A mesma disciplina vale nos evals do M06: nunca valide um sistema só com os dados que o construíram.
