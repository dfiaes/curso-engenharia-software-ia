Por que furar a abstração

Até aqui o modelo foi usado como serviço: entra prompt, sai texto, a conta chega. Esse contrato sustenta a pergunta "o que pedir". Ele quebra diante de "por que custou isso", "por que errou isso", "por que travou na ferramenta". Cada quebra cobra o mesmo preço: decidir no escuro.

A defesa é conhecer uma camada abaixo do uso. Uma camada explica o custo quadrático, o erro de contagem, a teimosia da temperatura, a trava do agente. Passou dessa camada, dispersão — salvo quando uma decisão do produto exigir descer mais, e o mapa abaixo marca essa fronteira caso a caso.

Fundamento de engenharia · A lei das abstrações que vazam. Joel Spolsky, 2002: "todas as abstrações não triviais, até certo ponto, vazam". TCP promete entrega confiável sobre um meio não confiável — e mesmo assim você precisa entender retransmissão quando a latência explode. ORM promete que você não escreve SQL — até o N+1 aparecer. A consequência prática que interessa aqui: o tempo que você economiza usando uma abstração é cobrado de volta, com juros, no dia em que ela vaza; e a única defesa é conhecer uma camada abaixo. Um LLM é a abstração mais vazante que você já usou na vida profissional — ela promete "entende linguagem natural" e vaza em tokenização, em janela de contexto, em formato de saída, em não-determinismo. Este módulo é o pagamento antecipado dessa dívida.

Fundamento de engenharia · Modelo mental × modelo de implementação. Alan Cooper distingue o modelo mental (como o usuário acha que a coisa funciona), o modelo de implementação (como ela de fato funciona) e o modelo representado (o que a interface sugere). Software bem projetado aproxima o representado do mental. O problema com LLM é que a interface — chat em linguagem natural — representa um modelo mental de interlocutor que sabe coisas, enquanto a implementação é amostragem de uma distribuição condicionada. Quase todo bug de produto de IA que você vai depurar mora nessa distância. Fixar o modelo de implementação correto na cabeça é a única correção duradoura, e é por isso que o bloco 5 existe.

O instrumento: logprobs

O gateway do M05 registra tokens e latência por chamada. Falta a probabilidade que o modelo atribuiu a cada token emitido. Esse número é o instrumento de confiança mais barato disponível.

ConceitoLogprob. Logaritmo natural da probabilidade do token emitido: lp = ln(p). Probabilidade vive em (0, 1]; o log vive em (−infinito, 0]. 0.0 é certeza; −0.05 ≈ 95%; −0.69 ≈ 50%; −1.0 ≈ 37%; −2.3 ≈ 10%. Log soma onde probabilidade multiplicaria: somar evita underflow de ponto flutuante em sequências longas.

Perplexidade. Exponencial da média negada: ppl = exp(−média dos logprobs). Valor 1.0 é certeza total; o número cresce com a dúvida. A média normaliza pelo tamanho: textos de comprimentos distintos ficam comparáveis na mesma escala. Perplexidade resume hesitação média; jamais substitui eval por tarefa.

Limiar −1.0. Token abaixo de −1.0 carrega menos de ~37% de probabilidade e conta como incerto em tokens_incertos. O limiar é convenção operacional deste módulo, não constante universal. Ele separa "o modelo hesitou aqui" do ruído de arredondamento.

Uso legítimo. Relativo e agregado: comparar a mesma tarefa entre entradas, acompanhar deriva ao longo do tempo, ordenar fila de revisão humana. O sinal nunca decide sozinho.

ContrasteAssertiva errada comum: "logprob alto é resposta certa; pode aprovar sozinho". Confiança mede coerência com o aprendido, não correspondência com a realidade. Modelo confiante-errado existe e custa caro: responde com fluência e logprobs limpos sobre fato inexistente. Grader de correção continua sendo o M06 — determinístico primeiro, juiz calibrado depois. Logprob prioriza olhar humano; jamais assina veredito.

"""Resumo de confianca por geracao.

Referencia executavel do Bloco 1.
Implementacao verbatim na folha B01-L.
"""

from dataclasses import dataclass
from math import exp

LIMIAR_INCERTEZA = -1.0  # ~37% de probabilidade


@dataclass(frozen=True, slots=True)
class ConfiancaGeracao:
    """Resumo de confianca derivado dos logprobs."""

    medio: float
    minimo: float
    incertos: int
    total: int

    @property
    def perplexidade(self) -> float:
        """exp(-media). 1.0 = certeza total."""
        return exp(-self.medio)

    @property
    def fracao_incerta(self) -> float:
        if not self.total:
            return 0.0
        return self.incertos / self.total


def resumir(logprobs: list[float]) -> ConfiancaGeracao | None:
    if not logprobs:
        return None
    return ConfiancaGeracao(
        medio=sum(logprobs) / len(logprobs),
        minimo=min(logprobs),
        incertos=sum(1 for lp in logprobs if lp < LIMIAR_INCERTEZA),
        total=len(logprobs),
    )

Referência executável 2 — lab/pct_incerto.sql. Consulta sobre llm_calls, o registro do gateway do M05; a folha B01-L a executa contra o schema versionado:

-- Compara chamadas recentes por confianca.
SELECT
  substring(prompt_hash, 1, 8) AS chamada,
  round(logprob_medio::numeric, 3) AS lp_medio,
  round(exp(-logprob_medio)::numeric, 2) AS ppl,
  tokens_incertos,
  round(100.0 * tokens_incertos
    / nullif(tokens_saida, 0), 1) AS pct_incerto
FROM llm_calls
WHERE criado_em > now() - interval '10 minutes'
ORDER BY logprob_medio ASC;

As três etapas: o que cada uma faz com o comportamento

Pré-treino ensina continuação: prever o próximo token sobre corpus amplo. O produto é linguagem, sintaxe, estilo e fatos frequentes. O objeto que sai daqui é um continuador: completa texto, não responde pergunta, não segue instrução, não recusa.

SFT (supervised fine-tuning) ensina formato: prever o próximo token sobre diálogos exemplares curados, já com marcadores de papel. O produto é o molde de assistente: responder em vez de continuar, separar system de user, encerrar no token de parada. É aqui que o chat template entra no comportamento.

RLHF/DPO ensina preferência: deslocar a distribuição para a resposta que avaliadores preferiram. O produto é tom e qualidade — útil, consistente, formatada. O preço é sistemático: o gradiente aponta para o que agrada avaliador, e avaliador premia concordância, confiança e fluência mesmo sem verdade.

ContextoRLHF contra DPO, pelo efeito. RLHF (Reinforcement Learning from Human Feedback) aprende um modelo de recompensa que imita o avaliador humano e depois empurra o modelo com reforço (PPO) para pontuações altas. São três peças móveis e treino instável. DPO (Direct Preference Optimization) deriva dos mesmos pares de preferência uma perda direta sobre o modelo final, sem modelo de recompensa. O efeito observável converge: distribuição deslocada para a resposta que avaliadores prefeririam. A diferença operacional está no custo e na estabilidade do treino, não no incentivo final — ambos compram agradar avaliador. Fontes: SRC-M11-04, SRC-M11-05.

ContrasteSycophancy é incentivo, não personalidade. Sycophancy é ceder quando o usuário insiste, mesmo com a resposta correta já emitida. Se o avaliador médio prefere concordância, o gradiente aponta para concordância. Pedir firmeza no prompt não remove o incentivo: a pressão do usuário continua na entrada e a recompensa aprendida continua nos pesos. A defesa é arquitetural: o número sai de código determinístico e o LLM redige o texto em volta. Resposta que precisa resistir a pressão nunca nasce de geração livre.

Por que ele alucina — a resposta em duas partes

Alucinação não é mentira nem falta de dado pontual. São dois mecanismos somados: um estatístico, que vem do objetivo do pré-treino; outro de incentivo, que vem de como se avalia e se premia resposta. A referência Kalai et al. 2025 articula os dois; citação registrada a confirmar nas fontes do bloco, sem número herdado como evidência.

Parte 1 — origem estatística. Pré-treino prevê o próximo token. Padrão regular (sintaxe, ortografia, forma de um if) é aprendível: há estrutura para generalizar. Fato arbitrário de baixa frequência não tem padrão que o prediga: aniversário específico, assinatura exata de método que apareceu três vezes no corpus. O modelo aprende a forma da resposta (data plausível, assinatura plausível) sem o conteúdo. Como geração é amostragem — a linha multinomial do Bloco 4 —, ele preenche a forma com o conteúdo mais provável, que frequentemente não existe.

Parte 2 — incentivo de avaliação. Prova com chute parcial e branco zerado premia chutar: deixar em branco garante zero, chutar às vezes acerta. Se pós-treino e seleção de prompt pontuam só acurácia, o modelo é treinado a chutar em vez de abster-se. O mesmo incentivo mora no seu M06: grader que dá zero para "não encontrei no contexto" e zero para resposta inventada trata honestidade e chute como iguais, e o gate de CI seleciona o prompt que chuta mais. Claims sobre SimpleQA e sobre a recomendação de penalizar erro confiante e creditar dúvida apropriada seguem a confirmar (SRC-M11-19); nenhum número do legado é herdado aqui como evidência.

FundamentoA medida que vira meta deixa de medir. Lei de Goodhart: cobertura como meta produz teste sem assert; ticket fechado como meta produz ticket fatiado; acurácia como meta produz chute. Em ML o efeito é literal, porque a otimização não interpreta espírito de métrica. A disciplina: antes de otimizar um número, escrever qual comportamento degenerado o maximiza e adicionar a contramedida no mesmo movimento.

ContramedidaRubrica assimétrica. Resposta certa recebe +1, abstenção recebe +0,5 pelo reconhecimento do limite, erro confiante recebe −1. Chutar passa a custar mais que calar. A referência lab/abstencao.py implementa o grader determinístico sobre lab/fixtures/abstencao.json, com casos sem resposta no contexto em que abster-se é a resposta correta (AT-019). O Bloco 8 roda a matriz completa com essa categoria.

O que temperatura, top-k, top-p e repetição fazem por dentro

Os quatro operam sobre a distribuição antes do sorteio, na ordem fixa: temperatura repondera, top-k e top-p cortam a cauda, penalidade de repetição ajusta o já emitido. A ordem nunca muda; cada estágio recebe a saída do anterior.

ParâmetroMecanismoEfeitoQuando usar
temperaturedivide logits por T antes do softmaxT<1 concentra no topo; T>1 achata; T→0 tende ao argmax0 para extração e classificação; 0,7–1,0 para redação
top-kzera tudo fora dos k mais prováveis e renormalizacorta a cauda por contagem fixalimite rígido de cauda; raramente sozinho

Nenhum estágio inverte a ordem: temperatura redistribui massa sem tornar o improvável em provável; top-k e top-p removem cauda sem promover ninguém. A referência lab/amostragem.py mede o efeito por entropia sobre listas de logits, sem modelo (AT-016).

ContrasteT=0 troca alucinação variável por reprodutível; não cura. T=0 remove o sorteio e fixa o token mais provável. Se o mais provável está errado — caso do fato arbitrário ausente —, o erro passa a se repetir com constância. Serve para depurar e testar; não corrige conteúdo. T=0 tampouco é determinismo bit a bit em API: batching muda ordem de redução em ponto flutuante, empate resolve de modo distinto, versão de modelo muda sem aviso. Teste que exige saída idêntica pisca; o M06 resolve com grader semântico (AT-017).

Contraste"T=0 elimina alucinação" e "abstenção é preguiça" — não. A primeira frase confunde remover sorteio com adicionar conhecimento. A segunda confunde reconhecer limite com recusar trabalho: sem incentivo à abstenção, o pipeline sempre devolve um valor em vez de sinalizar a falha; o chamador nunca sabe quando a resposta é chute. A rubrica assimétrica transforma o pipeline em sinalização honesta.

"""Amostragem sobre listas de logits; sem modelo, sem rede.

Referencia executavel do Bloco 5.
Implementacao verbatim na folha B05-L. So STDLIB (math).
"""

import math

LOGITS_EXEMPLO: list[float] = [3.2, 2.9, 1.4, 0.8, 0.1, -0.5, -1.2]


def softmax(logits: list[float]) -> list[float]:
    """Exponencial normalizada; preserva a ordem."""
    m = max(logits)
    exps = [math.exp(x - m) for x in logits]
    total = sum(exps)
    return [e / total for e in exps]


def aplicar_temperatura(logits: list[float], t: float) -> list[float]:
    """Divide por T e aplica softmax; T <= 0 vira greedy."""
    if t <= 0.0:
        return greedy(logits)
    return softmax([x / t for x in logits])


def top_k(probs: list[float], k: int) -> list[float]:
    """Zera fora do top-k e renormaliza."""
    idx = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)[:k]
    rec = [0.0] * len(probs)
    for i in idx:
        rec[i] = probs[i]
    total = sum(rec)
    return [v / total for v in rec]


def top_p(probs: list[float], p: float) -> list[float]:
    """Menor conjunto com massa >= p; renormaliza."""
    ordem = sorted(range(len(probs)), key=lambda i: probs[i], reverse=True)
    acc = 0.0
    keep: set[int] = set()
    for i in ordem:
        keep.add(i)
        acc += probs[i]
        if acc >= p:
            break
    rec = [probs[i] if i in keep else 0.0 for i in range(len(probs))]
    total = sum(rec)
    return [v / total for v in rec]


def entropia(probs: list[float]) -> float:
    """Entropia em nats; mede a dispersao."""
    return -sum(v * math.log(v) for v in probs if v > 0.0)


def greedy(logits: list[float]) -> list[float]:
    """One-hot no argmax; limite de T -> 0."""
    top = max(range(len(logits)), key=lambda i: logits[i])
    return [1.0 if i == top else 0.0 for i in range(len(logits))]

    partes: list[str] = []
    for papel, texto in papeis:

    partes.append(f"{marc['inicio']}assistant\n")
    return "".join(partes)

    """'base' se nao ha marcador; 'instruct' se ha."""
    marc = MARCADORES[familia]
    if marc["inicio"] not in texto:
        return "base"
    return "instruct"

    """'ok', 'base-sem-template' ou 'template-errado'."""
    if detectar_base_vs_instruct(texto, familia) == "base":
        return "base-sem-template"
    for outra, marc in MARCADORES.items():
        if outra != familia and marc["inicio"] in texto:
            return "template-errado"
    return "ok"

A conta de VRAM, feita antes de qualquer download

Três parcelas somam a memória de serving. Pesos são fixos por modelo e quant. Overhead cobre ativações e folga do servidor, ordem de 1–2 GB. Cache de KV cresce com cada token de contexto e cada requisição simultânea — é ele que transforma demonstração folgada em produção estourada.

memoria_gb = pesos_gb + overhead_gb + kv_gb
pesos_gb   = bilhoes * 1e9 * bytes_por_param / 1024**3
kv_bytes   = 2 * n_camadas * n_kv * dim_cabeca * ctx * batch * bytes_por_valor
# o fator 2 inicial: matrizes K e V guardadas por token e por sequência

Trecho conceitual — ler a fórmula. n_camadas é a profundidade; n_kv conta cabeças de chave/valor (igual às de consulta, ou menor com atenção agrupada); dim_cabeca é a dimensão por cabeça; ctx é o comprimento de contexto configurado; batch é a concorrência simultânea; bytes_por_valor é 2 para KV em 16 bits. Dobrar ctx dobra o KV. Dobrar batch dobra de novo. Pesos não se movem; KV multiplica.

DiagnósticoKV estoura com contexto × concorrência. Modelo que serve bem um usuário em 8k pode não caber com quatro simultâneos em 128k: o servidor descarrega camadas para CPU e a vazão cai uma ordem de grandeza sem mensagem de erro. Dimensionar com o contexto máximo real e a concorrência real, nunca com o caso de demonstração. No B07 essa conta vira parâmetro de servidor.

Exemplo variável, calculado pela fórmula — não evidência. Arquitetura ilustrativa com 32 camadas, 8 cabeças KV, dimensão 128, KV a 2 bytes: cada token de cada sequência ocupa 128 KiB de KV. Quantização e GGUF: o que cada letra declara

Quantizar é guardar cada peso com menos bits e recuperar a faixa com um fator de escala por bloco. Compressão com perda aplicada aos parâmetros: menos memória e mais velocidade de carga, fidelidade menor por arredondamento.

GGUF é o formato de arquivo do projeto aberto llama.cpp: um arquivo único com pesos, tokenizador, template e metadados, consumido por servidores locais. K-quants são os esquemas desse formato. Leitura do nome: Q fixa quantização; o número declara os bits por peso (3, 4, 5, 8); K declara escalas em dois níveis por bloco, contra _0/_1 uniformes mais antigos; o sufixo declara o mix — _S pequeno, _M médio, _L grande — isto é, quais tensores ganham bits extras por sensibilidade (atenção e embeddings recebem mais). Q4_K_M lê-se: 4 bits, esquema K, mix médio.

imatrix (importance matrix) é calibração, não compressão: mede num corpus quais pesos mais deslocam a saída e distribui os bits conforme a sensibilidade. Quants agressivos com imatrix preservam mais tarefa no mesmo tamanho. Sem corpus de calibração representativo do uso, o ganho inexiste.

Trecho conceitual — nome como contrato. Q3_K_S promete 3 bits com mix pequeno; Q5_0 promete 5 bits uniforme antigo; Q8_0 promete 8 bits uniforme. O nome declara tamanho e esquema. Não declara qualidade por tarefa — essa se mede.

A perda não é uniforme: raciocínio quebra primeiro

A pergunta que decide produto é quanto cada tarefa perde por quant, não quanto a média perde. Cadeia de raciocínio em várias etapas amplifica erro de arredondamento passo a passo; reconhecimento de senso comum decide por token isolado e absorve o ruído. A média entre tarefas esconde exatamente a capacidade que um agente de código vende.

Exemplo variável, fonte a confirmar — não evidência. Estudo de quantização citado no legado sem autoria (SRC-M11-20): números como Q4 próximo de FP16 com diferença inferior a 1 ponto, Q3 com queda próxima de 9 pontos em GSM8K e senso comum quase intacto, são ilustração do formato da curva, não medida herdada. A folha L mede no hardware local com os evals próprios do M06; perplexidade entra como sinal auxiliar, nunca como veredito.

Contraste"Q3 é suficiente porque a perplexidade subiu pouco" — não. Perplexidade mede surpresa média por token em texto corrido. Tarefa encadeada mede acerto após vinte decisões dependentes. Um quant pode manter a primeira quase intacta e destruir a segunda: cada passo desvia um pouco e o desvio se propaga. Defesa: rodar os evals próprios por categoria contra o quant específico; o B08 executa a matriz.

Contraste"Pesos abertos = código aberto" — não. Acesso aos números não concede direito comercial. Peso com licença própria exige leitura cláusula a cláusula; peso NC ou destilado de modelo fechado bloqueia produto pago. A checagem do cartão e o item de ADR precedem qualquer conta de VRAM.

FundamentoRepresentação barata é aceitável até a operação que amplifica o erro. Soma de milhões de linhas cobra centavos de float; cadeia de raciocínio cobra passos de quant agressivo. A disciplina é idêntica: identificar a operação amplificadora do domínio e testar nela, nunca na média.

"""Estimador de VRAM para servir modelo local; sem rede, sem pesos.

Referencia executavel do Bloco 6.
Implementacao verbatim na folha B06-L. So STDLIB (argparse, dataclasses).
"""

import argparse
from dataclasses import dataclass

BYTES_POR_PARAM: dict[str, float] = {
    "FP16": 2.00,
    "Q8_0": 1.06,
    "Q6_K": 0.82,
    "Q5_K_M": 0.70,
    "Q4_K_M": 0.58,
    "Q4_K_S": 0.55,
    "Q3_K_S": 0.44,
}
"""Bytes por parametro por esquema; valor de consulta, nao medida."""


@dataclass(frozen=True, slots=True)
class Orcamento:
    pesos_gb: float
    kv_gb: float
    overhead_gb: float

    @property
    def total_gb(self) -> float:
        """Soma das tres parcelas."""
        return self.pesos_gb + self.kv_gb + self.overhead_gb


def estimar(
    bilhoes: float,
    quant: str,
    ctx: int,
    batch: int = 1,
    n_camadas: int = 32,
    n_kv: int = 8,
    dim_cabeca: int = 128,
    bytes_valor: int = 2,
    overhead_gb: float = 1.5,
) -> Orcamento:
    """Aplica pesos + KV + overhead; levanta KeyError em quant desconhecido."""
    pesos = bilhoes * 1e9 * BYTES_POR_PARAM[quant] / 1024**3
    kv = (2 * n_camadas * n_kv * dim_cabeca * ctx * batch * bytes_valor) / 1024**3
    return Orcamento(pesos_gb=pesos, kv_gb=kv, overhead_gb=overhead_gb)


def main() -> None:
    """CLI: bilhoes posicionais; flags --quant, --ctx, --batch."""
    ap = argparse.ArgumentParser()
    ap.add_argument("bilhoes", type=float)
    ap.add_argument("--quant", default="Q4_K_M", choices=sorted(BYTES_POR_PARAM))
    ap.add_argument("--ctx", type=int, default=8192)
    ap.add_argument("--batch", type=int, default=1)
    a = ap.parse_args()
    o = estimar(a.bilhoes, a.quant, a.ctx, a.batch)
    print(f"pesos      {o.pesos_gb:6.2f} GB")
    print(f"cache KV   {o.kv_gb:6.2f} GB   (ctx={a.ctx}, batch={a.batch})")
    print(f"overhead   {o.overhead_gb:6.2f} GB")
    print(f"{'TOTAL':10s} {o.total_gb:6.2f} GB")


if __name__ == "__main__":
    main()

"""Provedor local atras da porta do M05; sem servidor, sem rede.

Referencia executavel do Bloco 7.
Implementacao verbatim na folha B07-L. So STDLIB.
"""

from __future__ import annotations

from collections.abc import Callable, Mapping
from dataclasses import dataclass
from typing import Any


Transporte = Callable[[str, Mapping[str, Any]], Mapping[str, Any]]
"""Recebe (url, corpo) e devolve o JSON ja decodificado."""


@dataclass(frozen=True, slots=True)
class ConfigOllama:
    host: str = "127.0.0.1"
    porta: int = 11434
    modelo: str = "local-8b-q4"
    n_ctx: int = 8192
    keep_alive: str = "5m"
    paralelo: int = 1
    exige_auth_no_proxy: bool = True


def politica_host(cfg: ConfigOllama) -> str:
    """Recusa 0.0.0.0 sem proxy autenticado; devolve base_url."""
    if cfg.host == "0.0.0.0" and cfg.exige_auth_no_proxy:
        raise ValueError("0.0.0.0 exige proxy autenticado")
    return f"http://{cfg.host}:{cfg.porta}/v1"


def validar_local(cfg: ConfigOllama, prompt_estimado: int) -> list[str]:
    """Valida knobs sem servidor; lista vazia aprova."""
    erros: list[str] = []
    if cfg.n_ctx < prompt_estimado:
        erros.append("num_ctx menor que o prompt: system sera truncado")
    if cfg.paralelo < 1:
        erros.append("paralelo minimo e 1")
    if cfg.keep_alive not in ("-1", "0") and not cfg.keep_alive.endswith("m"):
        erros.append("keep_alive deve ser '-1', '0' ou minutos")
    return erros


@dataclass(frozen=True, slots=True)
class Uso:
    entrada: int
    saida: int
    custo_usd: float = 0.0


@dataclass(frozen=True, slots=True)
class Resposta:
    texto: str
    uso: Uso
    confianca: float | None
    provedor: str
    modelo: str


class OllamaProvider:
    """Adapter OpenAI-compativel sobre transporte injetavel."""

    nome = "ollama"

    def __init__(self, cfg: ConfigOllama, transporte: Transporte) -> None:
        self._cfg = cfg
        self._transporte = transporte
        self._base = politica_host(cfg)

    def completar(self, mensagens: list[dict[str, str]]) -> Resposta:
        corpo: dict[str, Any] = {
            "model": self._cfg.modelo,
            "messages": mensagens,
            "options": {"num_ctx": self._cfg.n_ctx},
            "keep_alive": self._cfg.keep_alive,
        }
        bruta = self._transporte(self._base + "/chat/completions", corpo)
        uso = bruta.get("usage", {})
        lps = bruta.get("logprobs", [])
        conf = (sum(lps) / len(lps)) if lps else None
        texto = str(bruta.get("text", ""))
        return Resposta(
            texto=texto,
            uso=Uso(int(uso.get("prompt", 0)), int(uso.get("completion", 0)), 0.0),
            confianca=conf,
            provedor=self.nome,
            modelo=self._cfg.modelo,
        )

Modelo, harness e agente: três coisas, três culpados

Você vai viver esta cena, se ainda não viveu: pluga um modelo local bem avaliado em código dentro do seu harness de agente — o loop do M08, o servidor MCP do M09, ou uma ferramenta de linha de comando qualquer. O modelo responde bem quando você conversa. Mas em modo agente ele quase funciona: chama a ferramenta com um argumento a menos, repete a mesma chamada três vezes, ou escreve a chamada como texto no meio da resposta em vez de emitir a estrutura. O diagnóstico que a internet oferece é "põe um agente melhor em cima". Está errado, e custa semanas.

Modelo, harness e agente são três coisas. O modelo gera tokens. O harness é a máquina em volta: monta o prompt, serializa os schemas, faz o parse da saída, executa a ferramenta, devolve o resultado, controla o laço. O agente é o comportamento que emerge dos dois juntos. Empilhar mais harness sobre um modelo que não cumpre o protocolo não gera agente — gera mais lugares onde falhar.

Benchmark de código mede uma coisa: dado um enunciado, sai código correto. Modo agente exige um conjunto diferente, e a correlação entre os dois é mais fraca do que a intuição sugere.

A evidência: o BFCL, e a descoberta que muda o diagnóstico

Contexto · O que é o Berkeley Function Calling Leaderboard. Benchmark público mantido pelo grupo Gorilla, em Berkeley, dedicado a medir chamada de função — não código. Ele evoluiu em quatro gerações: V1 introduziu avaliação por AST (compara a árvore sintática da chamada gerada com a esperada, em vez de casar strings); V2 trouxe funções reais contribuídas por empresas; V3 adicionou interações multi-turno; e V4 (abril de 2026) passou a fazer avaliação agêntica holística — busca na web, memória e sensibilidade a formato. Ele reporta acurácia, custo em dólares e latência em segundos, e separa modelos com suporte nativo a function calling (FC) dos que precisam ser induzidos por prompt.

O que interessa aqui é o eixo novo do V4: sensibilidade a formato. A pergunta é enganosamente simples — o mesmo modelo, na mesma tarefa, com a mesma informação, mas apresentada em formato diferente: a acurácia muda? Deveria ser não. É sim.

O BFCL V4 testa cinco dimensões em 26 configurações de prompt: formato de retorno (Python, JSON, XML verboso, XML conciso), formato da documentação das funções (Python, XML, JSON), presença de tags de tool call, texto puro vs. Markdown, e enunciado original vs. reformulado. Os achados:

  • Formato de retorno: Python e JSON produzem acurácia mais alta que qualquer variante XML. Modelos menores e a família Claude tiveram queda significativa quando o retorno era pedido em XML.
  • Formato da documentação: tendência consistente em quase todos os modelos — JSON > XML > Python. Documentar as suas ferramentas em JSON Schema é uma escolha mensurável, não estética.
  • Tags de tool call: impacto pequeno na média — mas modelos pequenos (na faixa de 8B) sofreram queda significativa.
  • Markdown vs. texto puro e reformulação do enunciado: comportamento robusto, sem tendência geral.

Estatuto dos números. Detalhes de versão e contagens do BFCL seguem a confirmar contra o repositório do benchmark na folha L (SRC-M11-18); nenhum número do legado é herdado aqui como evidência. O que a folha L reproduz em escala reduzida é o experimento de formato: o mesmo modelo, a mesma tarefa, duas documentações — JSON Schema contra assinatura Python — com o delta registrado.

A consequência que reorganiza o seu diagnóstico. Se a acurácia do mesmo modelo na mesma tarefa muda conforme o formato de apresentação, então uma fração do que você atribuiria ao "modelo ser ruim" é, na verdade, a sua integração. Antes de trocar de modelo, troque de formato: documente as tools em JSON Schema, peça retorno em JSON e não em XML, e evite envelopes exóticos com modelos pequenos. Isso é barato, é reversível e frequentemente resolve. E há um corolário desconfortável para a sua régua: um eval de tool calling que testa um único formato mede o par (modelo, formato), não o modelo.

Fine-tuning: LoRA, QLoRA e a escada de decisão

Fine-tuning é continuar treinando um modelo pronto com dados seus. Fazer isso com todos os pesos exige memória para os pesos, os gradientes e os estados do otimizador — na prática, algo como 12 a 16 bytes por parâmetro, ou seja, mais de 100 GB para um modelo de 8B. Inviável fora de um cluster.

Contexto · LoRA e QLoRA, a ideia em duas frases. LoRA (Low-Rank Adaptation) congela os pesos originais e treina, ao lado de cada matriz W (dimensão d×k), duas matrizes pequenas A (d×r) e B (r×k) com r muito menor — tipicamente 8, 16 ou 32. A saída vira W·x + (α/r)·B·A·x. Como só A e B são treinadas, o número de parâmetros treináveis cai tipicamente para menos de 1% do total, e o adaptador resultante ocupa dezenas de MB em vez de dezenas de GB. QLoRA vai além: carrega o modelo-base já quantizado em 4 bits (congelado) e treina os adaptadores LoRA em cima — o que faz um fine-tuning de 8B caber numa única GPU de consumo. A hipótese por trás das duas: a atualização necessária para adaptar um modelo a uma tarefa tem posto baixo, mesmo que os pesos originais não tenham.

Trecho conceitual — LoRA com a biblioteca peft. Ilustra o mecanismo; sem treino, sem GPU, sem rede:

# Como isso se parece na pratica, com a biblioteca peft
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("modelo/base")   # + quantizacao 4-bit no QLoRA

cfg = LoraConfig(
    r=16,                       # posto. 8-32 cobre quase tudo; maior nao e melhor
    lora_alpha=32,              # escala = alpha/r; convencao comum e alpha = 2r
    lora_dropout=0.05,
    target_modules="all-linear",# estilo QLoRA; o default atinge so q_proj e v_proj
    bias="none",
    task_type="CAUSAL_LM",
    use_rslora=False,           # True troca a escala para alpha/sqrt(r): mais estavel com r alto
)
modelo = get_peft_model(base, cfg)
modelo.print_trainable_parameters()
# -> trainable params: 41,943,040 || all params: 8,072,204,288 || trainable%: 0.5196

Agora a parte que importa mais que a API. Fine-tuning é a resposta errada com muito mais frequência do que parece, e a razão é que ele ataca a categoria errada de problema. Suba esta escada e pare no primeiro degrau que resolver:

Os quatro motivos pelos quais o degrau 6 quase nunca é o certo. (1) Ele não ensina fatos de forma confiável — o mecanismo é ajuste de distribuição, não inserção em base de dados; conhecimento novo entra por RAG, e tentar enfiá-lo por fine-tuning produz um modelo que alucina com o estilo dos seus dados, o que é pior que antes. (2) Esquecimento catastrófico: ao especializar, o modelo piora em coisas que fazia bem, e você só descobre o que quebrou se tiver evals abrangentes — os do M06 servem justamente para isso. (3) O custo real é a manutenção: o adaptador é acoplado a uma versão específica do modelo-base; quando sair a próxima, você retreina, revalida e possivelmente rotula dados de novo. Você não fez um artefato, assinou uma dívida recorrente. (4) Dados são o gargalo: LoRA precisa de milhares de exemplos consistentes e de alta qualidade; se você tem 200 exemplos, eles rendem mais como few-shot no prompt ou como conjunto de eval.

E quando ele é o certo? Três sinais juntos: você já subiu os cinco degraus anteriores e mediu; o volume é alto o bastante para que a economia por chamada pague o retreino; e o que você quer é comportamento/formato consistente, não conhecimento. Exemplo legítimo no Cartógrafo: se o relatório final tem um formato rígido e proprietário e você processa dezenas de milhares por mês, um LoRA pequeno de formatação sobre um modelo local pode valer. Repare: mesmo aí, o conhecimento continua vindo do grafo e do RAG.

"""Custo por 1M de tokens de saida rodando local; sem servidor, sem rede.

Referencia executavel do Bloco 8.
Implementacao verbatim na folha B08-L. So STDLIB (argparse, dataclasses).
"""

from __future__ import annotations

import argparse
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class CustoLocal:
    preco_hw: float
    vida_meses: int
    watts: float
    kwh: float
    tok_s: float
    util: float = 0.25

    @property
    def horas_por_mtok(self) -> float:
        """Horas de geracao para emitir um milhao de tokens."""
        return 1_000_000 / self.tok_s / 3600

    def custo_por_mtok(self) -> tuple[float, float, float]:
        """(energia, hardware, total) em USD por milhao de tokens."""
        horas = self.horas_por_mtok
        energia = horas * (self.watts / 1000) * self.kwh
        horas_uteis = self.vida_meses * 30 * 24 * self.util
        hardware = horas * (self.preco_hw / horas_uteis)
        return energia, hardware, energia + hardware


def main() -> None:
    """CLI: --preco-hw USD --vida-meses N --watts W --kwh USD --tok-s T [--util F]."""
    ap = argparse.ArgumentParser()
    ap.add_argument("--preco-hw", type=float, required=True)
    ap.add_argument("--vida-meses", type=int, required=True)
    ap.add_argument("--watts", type=float, required=True)
    ap.add_argument("--kwh", type=float, required=True)
    ap.add_argument("--tok-s", type=float, required=True)
    ap.add_argument("--util", type=float, default=0.25)
    a = ap.parse_args()
    c = CustoLocal(a.preco_hw, a.vida_meses, a.watts, a.kwh, a.tok_s, a.util)
    energia, hardware, total = c.custo_por_mtok()
    print(f"energia    US$ {energia:7.2f} / Mtok")
    print(f"hardware   US$ {hardware:7.2f} / Mtok")
    print(f"TOTAL      US$ {total:7.2f} / Mtok")


if __name__ == "__main__":
    main()

        """Fracao de aprovados; 0.0 sem casos."""
        return self.aprov / self.total if self.total else 0.0


def tabela_markdown(resultados: list[ResultadoExec]) -> str:
    """Uma linha por configuracao: taxa, p50, p95 e custo."""
    linhas = [
        "| provedor | modelo | quant | taxa | p50 | p95 | custo |",
        "|---|---|---|---|---|---|---|",
    ]
    for r in resultados:
        linhas.append(
            f"| {r.config.provedor} | {r.config.modelo} | "
            f"{r.config.quant or '-'} | {r.taxa:.3f} | "
            f"{r.p50:.1f} | {r.p95:.1f} | {r.custo:.4f} |"
        )
    return "\n".join(linhas)


def break_even(
    relatorios_mes: int,
    tokens_relatorio: int,
    custo_api_mtok: float,
    custo_local_mtok: float,
    fixo_mensal: float,
) -> tuple[float, float, str]:
    """(custo_api, custo_local, veredito) no volume declarado."""
    mtok = relatorios_mes * tokens_relatorio / 1_000_000
    api = mtok * custo_api_mtok
    local = fixo_mensal + mtok * custo_local_mtok
    veredito = "local" if local < api else "api"
    return api, local, veredito

Conclusão — o essencial em 8 linhas

Fundamento vale até a camada em que ele muda uma decisão sua; abaixo disso é hobby.
Produto escalar é a operação única do campo: é a busca do M07 e é a atenção do transformer.
A matriz T×T é o O(n²) — cortar 30% do contexto corta 51% do trabalho, e isso aparece na fatura.
Tokenização explica a aritmética errada; amostragem explica a alucinação; nenhuma das duas se conserta com mais dados.
Se o seu grader dá zero para "não sei", você está comprando chute — a rubrica assimétrica é o conserto.
Até 4 bits a quantização custa quase nada por tarefa medida, mas o que ela quebra primeiro é justamente o raciocínio encadeado que o seu produto vende — perplexidade estável não aprova quant.
Modelo local entrou com um arquivo novo porque o M05 pôs a fronteira no eixo certo: essa é a lição de arquitetura do módulo.
Modelo ≠ agente ≠ harness — antes de trocar de modelo, desça sete degraus de diagnóstico; e fine-tuning é o degrau 6 de 6, quase sempre a resposta errada.
