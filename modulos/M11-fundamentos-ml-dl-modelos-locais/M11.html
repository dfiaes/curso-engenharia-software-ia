Fundamento de engenharia · A lei das abstrações que vazam. Joel Spolsky, 2002: "todas as abstrações não triviais, até certo ponto, vazam". TCP promete entrega confiável sobre um meio não confiável — e mesmo assim você precisa entender retransmissão quando a latência explode. ORM promete que você não escreve SQL — até o N+1 aparecer. A consequência prática que interessa aqui: o tempo que você economiza usando uma abstração é cobrado de volta, com juros, no dia em que ela vaza; e a única defesa é conhecer uma camada abaixo. Um LLM é a abstração mais vazante que você já usou na vida profissional — ela promete "entende linguagem natural" e vaza em tokenização, em janela de contexto, em formato de saída, em não-determinismo. Este módulo é o pagamento antecipado dessa dívida.

Fundamento de engenharia · Modelo mental × modelo de implementação. Alan Cooper distingue o modelo mental (como o usuário acha que a coisa funciona), o modelo de implementação (como ela de fato funciona) e o modelo representado (o que a interface sugere). Software bem projetado aproxima o representado do mental. O problema com LLM é que a interface — chat em linguagem natural — representa um modelo mental de interlocutor que sabe coisas, enquanto a implementação é amostragem de uma distribuição condicionada. Quase todo bug de produto de IA que você vai depurar mora nessa distância. Fixar o modelo de implementação correto na cabeça é a única correção duradoura, e é por isso que o bloco 5 existe.

Prática guiada · instrumentar o gateway para ver o modelo por dentro (35 min)

Antes de abrir a caixa, vamos coletar evidência com o que já existe. O gateway do M05 já registra tokens e latência na tabela llm_calls. Falta uma coisa: os logprobs — a probabilidade que o modelo atribuiu a cada token que escolheu. É o instrumento mais barato de diagnóstico de confiança que existe, e você já tem onde guardar.

Contexto · O que é logprob. O logaritmo natural da probabilidade que o modelo atribuiu ao token que ele emitiu. Como probabilidade vai de 0 a 1, o log vai de −∞ a 0: 0.0 significa "certeza absoluta", −0.05 significa ~95%, −2.3 significa ~10%. Usa-se log em vez de probabilidade crua por dois motivos: multiplicação de muitas probabilidades pequenas causa underflow em ponto flutuante, e soma de logs é numericamente estável. Nem todo provedor expõe logprobs — os locais expõem quase sempre, e é uma das vantagens práticas de rodar local.

from dataclasses import dataclass
from math import exp

LIMIAR_INCERTEZA = -1.0  # ~37% de probabilidade


@dataclass(frozen=True, slots=True)
class ConfiancaGeracao:
    """Resumo de confianca de uma geracao, derivado dos logprobs."""

    medio: float
    minimo: float
    incertos: int
    total: int

    @property
    def perplexidade(self) -> float:
        """exp(-media dos logprobs). 1.0 = certeza total; cresce com a duvida."""
        return exp(-self.medio)

    @property
    def fracao_incerta(self) -> float:
        return self.incertos / self.total if self.total else 0.0


def resumir(logprobs: list[float]) -> ConfiancaGeracao | None:
    if not logprobs:
        return None
    return ConfiancaGeracao(
        medio=sum(logprobs) / len(logprobs),
        minimo=min(logprobs),
        incertos=sum(1 for lp in logprobs if lp < LIMIAR_INCERTEZA),
        total=len(logprobs),
    )

Por que isso importa

O modelo que você treinou no bloco 4 só sabe continuar texto. Ele não responde perguntas, não segue instruções e não recusa nada — porque nada no treino pediu isso. Entre "continuador de texto" e "assistente que segue instruções, chama ferramentas e diz não" existem duas etapas de pós-treino, e conhecê-las explica praticamente todo comportamento estranho que você vai encontrar em produção: por que o modelo é bajulador, por que ele inventa em vez de dizer "não sei", por que o mesmo prompt funciona na API e falha no Ollama, e por que ele às vezes obedece a uma instrução no meio do contexto e ignora a mesma instrução no começo.

Contexto · RLHF e DPO, a diferença que importa. RLHF (Reinforcement Learning from Human Feedback) treina primeiro um "modelo de recompensa" que aprende a pontuar respostas como um humano pontuaria, e depois usa aprendizado por reforço (PPO) para empurrar o modelo na direção de pontuações altas. Funciona, mas são três modelos em jogo e o processo é instável. DPO (Direct Preference Optimization) mostrou que dá para pular o modelo de recompensa: com os pares de preferência, deriva-se uma função de perda que otimiza direto o modelo final. Mais simples, mais estável, e por isso predominante hoje. Para você, engenheiro de aplicação, a diferença é irrelevante — o que importa é a consequência compartilhada: o modelo foi otimizado para agradar avaliadores humanos, e humanos avaliam mal certas coisas.

De onde vem a bajulação (e por que ela é um risco de produto). Se avaliadores humanos preferem, na média, respostas que concordam com eles, o gradiente aponta para concordância. O resultado é sycophancy: o modelo cede quando o usuário insiste, mesmo estando certo antes. No Cartógrafo isso tem um alvo óbvio: se o relatório de saúde arquitetural diz "este módulo está na zona da dor" e o cliente responde "acho que não", um modelo bajulador reescreve a conclusão. A defesa não é prompt ("seja firme") — é arquitetural: o número vem do metricas.py do M10, calculado deterministicamente, e o LLM só redige o texto em volta. Sempre que a resposta precisa resistir a pressão, tire-a do caminho da geração.

O chat template: o contrato invisível

Durante o SFT, os diálogos são formatados com marcadores especiais que delimitam papéis. Esses marcadores fazem parte do que o modelo aprendeu — são tokens como quaisquer outros, e o modelo só se comporta como assistente quando os vê no formato exato do treino. Cada família de modelo tem o seu.

# O que voce escreve (API de chat, M05):
[{"role": "system",    "content": "Voce e um analista de codigo."},
 {"role": "user",      "content": "O que faz PedidoService?"}]

# O que o modelo realmente recebe, depois do chat template (formato ilustrativo):
<|im_start|>system
Voce e um analista de codigo.<|im_end|>
<|im_start|>user
O que faz PedidoService?<|im_end|>
<|im_start|>assistant

Tradução .NET · chat template é o wire format. Você chama um serviço com um objeto tipado; por baixo há um formato de fio — JSON, protobuf, SOAP — e um serializador que traduz. Se o cliente serializa em camelCase e o servidor espera snake_case, a chamada "funciona" e chega com todos os campos nulos. O chat template é exatamente isso: a API de chat é o objeto tipado, o template é o serializador, e os tokens especiais são o wire format. A diferença cruel é que não há erro de desserialização: se o template estiver errado, o modelo simplesmente responde pior — divaga, ignora o system prompt, não para de gerar — e você fica caçando o problema no seu prompt. Quando você for rodar local (bloco 7), o template é a primeira coisa a verificar.

Pegadinha real, e é a mais comum ao migrar para local. Um modelo baixado do Hub em formato base (sem SFT) não tem chat template nenhum — e vai continuar o seu prompt como texto em vez de responder. Um modelo instruct servido com o template errado responde, mas mal. Sintomas típicos: ignora o system prompt, não emite o token de parada e gera até o limite, ou começa a simular a fala do usuário depois de responder. Diagnóstico: ollama show <modelo> --template e comparar com o cartão do modelo no Hub. Isso vai para a tabela de diagnóstico deste módulo.

Por que ele alucina — a resposta em duas partes

Alucinação não é bug, nem falta de dados, nem "o modelo mentiu". São dois mecanismos somados, e o artigo Why Language Models Hallucinate (Kalai, Nachum, Vempala e Zhang, OpenAI, 2025) articula os dois com clareza.

Parte 1 — origem estatística. O objetivo do pré-treino é prever o próximo token. Padrões regulares (sintaxe, ortografia, a forma de um if) são aprendíveis: há estrutura para generalizar. Mas fatos arbitrários e de baixa frequência não têm padrão que os prediga — o aniversário de uma pessoa específica, a assinatura exata de um método que apareceu três vezes no corpus. Para esses, o modelo aprende a forma da resposta (uma data plausível, uma assinatura plausível) sem ter o conteúdo. E como a geração é amostragem — a linha torch.multinomial que você escreveu no bloco 4 —, ele produz a forma preenchida com o conteúdo mais provável, que frequentemente não existe.

Fundamento de engenharia · A métrica que você escolhe é o comportamento que você compra. Isto é a Lei de Goodhart aplicada com uma diferença desconfortável: "quando uma medida vira meta, ela deixa de ser uma boa medida". Você já viu isso em times humanos — meta de cobertura de testes produz testes sem assert; meta de tickets fechados produz tickets fatiados; meta de tempo de resposta produz respostas rápidas e inúteis. Em ML o efeito é mais rápido e mais literal, porque a otimização é automática e implacável: não existe "espírito da métrica", existe a métrica. A consequência prática é uma disciplina de projeto: antes de otimizar contra um número, escreva por extenso qual comportamento degenerado maximizaria esse número, e adicione a contra-medida no mesmo commit. Se você não consegue pensar no comportamento degenerado, você ainda não entendeu a sua métrica.

O que temperatura, top-p e top-k realmente fazem

Todos os três operam sobre a distribuição de probabilidade antes da amostragem — a linha probs = softmax(logits / temperatura) do bloco 4:

ParâmetroMecanismoEfeitoQuando usar
temperatureDivide os logits por T antes do softmaxT<1 concentra na cauda alta; T>1 achata. T→0 tende ao argmax.0 para extração e classificação; 0,7–1,0 para redação
top-kZera tudo fora dos k tokens mais prováveisCorta a cauda longa por contagem fixaRaramente sozinho; herdado de modelos antigos
top-p (nucleus)Mantém o menor conjunto cuja soma de probabilidade ≥ pCorta a cauda por massa, adaptando-se à forma da distribuição0,9–0,95 é o padrão sensato quando há criatividade envolvida
repetition / frequency penaltyPenaliza logits de tokens já emitidosReduz laços repetitivosEm modelos pequenos, que travam em loop com mais facilidade

Por que temperatura 0 não elimina alucinação — a resposta que faltava desde o M06. Temperatura 0 remove a aleatoriedade da amostragem: você passa a pegar sempre o token mais provável. Mas se o token mais provável estiver errado — e no caso de um fato arbitrário que o modelo não tem, ele está —, você agora vai buscar o mesmo erro de forma consistente. Temperatura 0 troca alucinação variável por alucinação reprodutível. É melhor para depurar e para testar; não é uma correção. E um detalhe operacional: temperatura 0 tampouco garante determinismo bit a bit em API — batching no servidor muda a ordem de redução em ponto flutuante, empates se resolvem de forma diferente, e a versão do modelo muda sem aviso. Se o seu teste depende de saída idêntica, ele vai piscar. O M06 já resolveu isso com graders semânticos; agora você sabe a causa.

import torch
from torch.nn import functional as F

logits = torch.tensor([3.2, 2.9, 1.4, 0.8, 0.1, -0.5, -1.2])

Três parcelas somam a memória necessária. A primeira domina, a terceira surpreende.

O cache de KV é o que estoura na hora errada. Os pesos são fixos; o cache cresce com o contexto e com a concorrência. Um modelo que roda liso a 4.096 tokens de contexto com um usuário pode não caber a 32.768 tokens com quatro requisições simultâneas — e o sintoma é o servidor decidir descarregar camadas para a CPU, o que derruba a vazão em uma ordem de grandeza sem nenhuma mensagem de erro. Regra prática: dimensione com o contexto máximo real e a concorrência real, não com o caso de demonstração. No bloco 7 isso vira configuração explícita.

Tradução .NET · working set, não tamanho do assembly. Você não dimensiona um servidor pelo tamanho do .dll; dimensiona pelo working set sob carga — heap, buffers por conexão, pools. Aqui é o mesmo raciocínio com nomes diferentes: os pesos são o assembly (fixo, carregado uma vez), e o cache de KV é o heap por requisição, com a agravante de que ele é proporcional ao comprimento da conversa. É a mesma classe de erro de quem dimensiona pelo Content-Length médio e esquece o upload de 200 MB.

Quantização: o que ela é, e o que ela realmente custa

Quantizar é armazenar cada peso com menos bits. Em vez de 16 bits por número, usa-se 4, 5 ou 8 — com um fator de escala por bloco de pesos para recuperar a faixa dinâmica. É compressão com perda, aplicada aos parâmetros.

Contexto · GGUF e o esquema de nomes dos K-quants. GGUF é o formato de arquivo do llama.cpp — um único arquivo autocontido com pesos, tokenizador, chat template e metadados. É o que o Ollama e o LM Studio consomem. Os nomes seguem um padrão: Q + bits + variante. Q4_K_M = 4 bits, esquema "K" (quantização por blocos com escalas em dois níveis), tamanho Medium — as variantes _S/_M/_L diferem em quais tensores recebem mais bits (atenção e embeddings costumam ganhar precisão extra, porque são mais sensíveis). Há também _0 e _1, esquemas mais antigos e uniformes. E existe a imatrix (importance matrix): um passo opcional que mede, num corpus de calibração, quais pesos mais afetam a saída, e distribui os bits de acordo — melhora a qualidade nos quants agressivos sem custar tamanho.

A conclusão prática que quase todo guia de quantização erra. A frase que você encontra em fóruns é "perplexidade quase não muda, pode quantizar à vontade". O estudo mostra por que isso é enganoso: perplexidade sozinha não prevê o comportamento nas tarefas que você usa. Um quant agressivo pode manter perplexidade e senso comum quase intactos enquanto destrói raciocínio em várias etapas — que é exatamente a capacidade da qual um agente depende. Para o Cartógrafo, cuja tarefa central é encadear "leia o arquivo → identifique a dependência → decida se está morta", isso significa: quantização agressiva degrada precisamente o que o seu produto vende, e o benchmark genérico não vai te avisar. A única defesa é rodar os seus evals do M06 contra o quant específico. Bloco 8.

Fundamento de engenharia · Precisão numérica é uma decisão de produto. Escolher Q4_K_M em vez de FP16 é a mesma família de decisão que escolher float em vez de decimal num sistema financeiro, int32 em vez de int64 numa chave, ou JPEG em vez de PNG. O padrão é sempre o mesmo: uma representação mais barata é aceitável até que uma operação específica amplifique o erro de arredondamento. Em finanças, a operação é a soma de milhões de linhas; em quantização, é a cadeia de raciocínio de muitas etapas, em que o desvio de cada passo se propaga. E a defesa é a mesma nos dois casos: não confie na média — teste a operação que amplifica. Quem já debugou um centavo de diferença num fechamento contábil reconhece o formato do problema.

1 Escreva a calculadora de orçamento — ela vira ferramenta de venda, não só script: 
# tools/orcamento_vram.py
"""Estima memoria necessaria para servir um modelo local.
Uso: uv run python tools/orcamento_vram.py 8 --quant Q4_K_M --contexto 32768
"""
import argparse
from dataclasses import dataclass

BYTES_POR_PARAM: dict[str, float] = {
    "FP16": 2.00, "Q8_0": 1.06, "Q6_K": 0.82,
    "Q5_K_M": 0.70, "Q4_K_M": 0.58, "Q4_K_S": 0.55, "Q3_K_S": 0.44,
}


@dataclass(frozen=True, slots=True)
class Orcamento:
    pesos_gb: float
    kv_gb: float
    overhead_gb: float

    @property
    def total_gb(self) -> float:
        return self.pesos_gb + self.kv_gb + self.overhead_gb


def estimar(
    bilhoes: float, quant: str, contexto: int, batch: int = 1,
    n_camadas: int = 32, n_kv: int = 8, dim_cabeca: int = 128,
) -> Orcamento:
    pesos = bilhoes * 1e9 * BYTES_POR_PARAM[quant] / 1024**3
    kv = (2 * n_camadas * n_kv * dim_cabeca * contexto * batch * 2) / 1024**3
    return Orcamento(pesos_gb=pesos, kv_gb=kv, overhead_gb=1.5)


if __name__ == "__main__":
    ap = argparse.ArgumentParser()
    ap.add_argument("bilhoes", type=float)
    ap.add_argument("--quant", default="Q4_K_M", choices=sorted(BYTES_POR_PARAM))
    ap.add_argument("--contexto", type=int, default=8192)
    ap.add_argument("--batch", type=int, default=1)
    a = ap.parse_args()
    o = estimar(a.bilhoes, a.quant, a.contexto, a.batch)
    print(f"pesos      {o.pesos_gb:6.2f} GB")
    print(f"cache KV   {o.kv_gb:6.2f} GB   (contexto={a.contexto}, batch={a.batch})")
    print(f"overhead   {o.overhead_gb:6.2f} GB")
    print(f"{'TOTAL':10s} {o.total_gb:6.2f} GB")

  • "Peso aberto" não quer dizer "livre para uso comercial" — a licença específica é item de ADR antes de prometer ao cliente.
  • Memória = pesos + ativações + cache de KV; o cache é o que estoura, e cresce com contexto × concorrência.
  • MoE economiza computação, não memória: os pesos todos precisam caber.
  • Até 4 bits, a perda é sub-1%; em 3 bits ela desaba — e desaba primeiro no raciocínio de várias etapas (−9,3 em GSM8K).
  • Perplexidade não prevê comportamento por tarefa: o quant que preserva senso comum pode destruir o que o seu produto vende.
  • Você tem uma calculadora de VRAM, um modelo local rodando e dois números medidos de vazão.

Por que isso importa

Este é o bloco em que uma decisão de arquitetura tomada no M05 rende juros. Lá, você não chamou a API do provedor diretamente do código de negócio: criou uma interface de ChatProvider e um adaptador. Na hora, isso pareceu cerimônia — uma indireção a mais para chamar a mesma coisa. Agora você vai adicionar um provedor completamente diferente, rodando em outra máquina, com outro modelo, e nenhum arquivo fora de services/llm/providers/ vai mudar. Um arquivo novo e uma linha de configuração.

Se você tivesse espalhado client.messages.create(...) pelo código, este bloco seria uma refatoração de duas semanas. Guarde a sensação: é o argumento mais concreto que você vai ter para defender inversão de dependência numa discussão de time.

As quatro opções, e o critério de escolha

Contexto · O que continuous batching e PagedAttention resolvem. Servir um LLM tem um problema de escalonamento peculiar: cada requisição gera um número diferente e imprevisível de tokens. Num batch tradicional, todas as requisições do lote esperam a mais longa terminar — a GPU fica ociosa segurando requisições que já acabaram. Continuous batching troca requisições dentro do lote a cada passo de geração: terminou uma, entra outra. PagedAttention ataca a outra metade: o cache de KV do bloco 6 é alocado em páginas de tamanho fixo, como memória virtual num SO, em vez de um bloco contíguo por requisição — o que elimina a fragmentação e permite muito mais requisições simultâneas na mesma VRAM. Juntos, explicam por que o vLLM entrega muito mais vazão que o Ollama no mesmo hardware. E também por que ele não faz diferença para você com um usuário só.

O critério, resumido: Ollama para desenvolver e para instalações de um usuário; vLLM quando houver concorrência real e GPU. Comece pelo Ollama mesmo que o destino seja vLLM — a API compatível com OpenAI é a mesma nos dois, então a troca depois é de configuração, não de código. Esse é justamente o ponto do gateway.

Ollama de verdade: as três armadilhas

Armadilha 1 — o contexto padrão é 4.096 tokens, e o excedente some sem aviso. Esta é a causa nº 1 de "o modelo local ignorou metade do meu prompt". Você monta um contexto de 20 mil tokens com os trechos recuperados do M07, manda para o Ollama, e ele trunca silenciosamente para 4.096 — descartando o começo, que é onde está o seu system prompt. Nenhum erro, nenhum aviso, apenas uma resposta pior. Conserto, em ordem de preferência: OLLAMA_CONTEXT_LENGTH=32768 ollama serve no servidor, ou "options": {"num_ctx": 32768} na requisição, ou PARAMETER num_ctx 32768 num Modelfile. E note o custo: aumentar num_ctx aumenta o cache de KV — a conta do bloco 6 volta agora, com números reais.

Armadilha 2 — o padrão é uma requisição paralela por modelo. OLLAMA_NUM_PARALLEL vale 1 por padrão. A segunda requisição concorrente enfileira; ela não falha, só demora o dobro. Se você medir latência com uma requisição por vez e depois ligar quatro workers, a p95 explode e a causa não aparece em lugar nenhum. Ajuste OLLAMA_NUM_PARALLEL — e lembre que cada slot paralelo tem seu próprio cache de KV, então num_ctx × num_parallel é a conta de memória real.

Armadilha 3 — o modelo descarrega depois de 5 minutos. Em ambiente de desenvolvimento, a primeira requisição depois de um intervalo paga o carregamento inteiro do modelo do disco: 5 a 30 segundos, dependendo do tamanho e do SSD. Isso destrói qualquer medição de latência p50 que você faça sem aquecer. Controle com keep_alive na requisição (-1 mantém carregado indefinidamente, 0 descarrega já) ou OLLAMA_KEEP_ALIVE no servidor. Em produção single-box: -1, sempre, e reserve a memória.

As variáveis que você vai realmente configurar:

OLLAMA_HOST=0.0.0.0:11434     # expor na rede (padrao e so 127.0.0.1) — ver aviso de seguranca
OLLAMA_CONTEXT_LENGTH=32768   # contexto padrao para todos os modelos
OLLAMA_NUM_PARALLEL=4         # requisicoes simultaneas por modelo
OLLAMA_MAX_LOADED_MODELS=2    # quantos modelos ficam residentes
OLLAMA_KEEP_ALIVE=-1          # nao descarregar
OLLAMA_MODELS=/dados/modelos  # onde guardar os GGUF (o padrao mora no home)

Segurança: OLLAMA_HOST=0.0.0.0 não tem autenticação. O Ollama não implementa autenticação. Expor a porta 11434 na rede significa que qualquer host que a alcance pode gerar texto, listar seus modelos e consumir sua GPU. Numa instalação no cliente, o servidor fica em rede interna atrás de um proxy autenticado — e o proxy natural é a sua própria API do M03, que já tem autenticação, rate limit e auditoria. O M12 volta a esse ponto com a checagem completa; por ora, a regra é: nunca 0.0.0.0 sem algo na frente.

# app/services/llm/providers/ollama.py
from __future__ import annotations

from dataclasses import dataclass

from openai import AsyncOpenAI

from app.services.llm.base import ChatProvider, Mensagem, Resposta, Uso
from app.services.llm.metrics import resumir


@dataclass(frozen=True, slots=True)
class ConfigOllama:
    base_url: str = "http://localhost:11434/v1"
    modelo: str = "qwen3:8b"
    contexto: int = 32768
    manter_carregado: bool = True


class OllamaProvider(ChatProvider):
    """Provedor local. Mesma interface dos provedores de API do M05 bloco 6.

    Custo em dinheiro e zero; custo em tempo, nao. O gateway registra os dois.
    """

    nome = "ollama"

    def __init__(self, cfg: ConfigOllama) -> None:
        self._cfg = cfg
        # api_key e obrigatoria pelo SDK e ignorada pelo Ollama.
        self._cliente = AsyncOpenAI(base_url=cfg.base_url, api_key="nao-usada")

    async def completar(
        self, mensagens: list[Mensagem], **kwargs: object
    ) -> Resposta:
        bruta = await self._cliente.chat.completions.create(
            model=self._cfg.modelo,
            messages=[m.para_dict() for m in mensagens],
            logprobs=True,
            extra_body={
                "options": {"num_ctx": self._cfg.contexto},
                "keep_alive": -1 if self._cfg.manter_carregado else "5m",
            },
            **kwargs,
        )
        escolha = bruta.choices[0]
        lps = (
            [t.logprob for t in escolha.logprobs.content]
            if escolha.logprobs and escolha.logprobs.content
            else []
        )
        u = bruta.usage
        return Resposta(
            texto=escolha.message.content or "",
            uso=Uso(
                entrada=u.prompt_tokens if u else 0,
                saida=u.completion_tokens if u else 0,
                custo_usd=0.0,          # local: custo em dinheiro por chamada e zero
            ),
            confianca=resumir(lps),
            provedor=self.nome,
            modelo=self._cfg.modelo,
        )

Bloco 8 · Modelo ≠ agente ≠ harness — avaliar com honestidade e quando fine-tuning é a resposta errada

Por que isso importa

Você vai viver esta cena, se ainda não viveu: pluga um modelo local bem avaliado em código dentro do seu harness de agente — o loop do M08, o servidor MCP do M09, ou uma ferramenta de linha de comando qualquer. O modelo responde bem quando você conversa. Mas em modo agente ele quase funciona: chama a ferramenta com um argumento a menos, repete a mesma chamada três vezes, ou escreve a chamada como texto no meio da resposta em vez de emitir a estrutura. O diagnóstico que a internet oferece é "põe um agente melhor em cima". Está errado, e custa semanas.

Modelo, harness e agente são três coisas. O modelo gera tokens. O harness é a máquina em volta: monta o prompt, serializa os schemas, faz o parse da saída, executa a ferramenta, devolve o resultado, controla o laço. O agente é o comportamento que emerge dos dois juntos. Empilhar mais harness sobre um modelo que não cumpre o protocolo não gera agente — gera mais lugares onde falhar.

As sete competências que o modo agente exige

Benchmark de código mede uma coisa: dado um enunciado, sai código correto. Modo agente exige um conjunto diferente, e a correlação entre os dois é mais fraca do que a intuição sugere.

A evidência: o BFCL, e a descoberta que muda o diagnóstico

Contexto · O que é o Berkeley Function Calling Leaderboard. Benchmark público mantido pelo grupo Gorilla, em Berkeley, dedicado a medir chamada de função — não código. Ele evoluiu em quatro gerações: V1 introduziu avaliação por AST (compara a árvore sintática da chamada gerada com a esperada, em vez de casar strings); V2 trouxe funções reais contribuídas por empresas; V3 adicionou interações multi-turno; e V4 (abril de 2026) passou a fazer avaliação agêntica holística — busca na web, memória e sensibilidade a formato. Ele reporta acurácia, custo em dólares e latência em segundos, e separa modelos com suporte nativo a function calling (FC) dos que precisam ser induzidos por prompt.

O que interessa aqui é o eixo novo do V4: sensibilidade a formato. A pergunta é enganosamente simples — o mesmo modelo, na mesma tarefa, com a mesma informação, mas apresentada em formato diferente: a acurácia muda? Deveria ser não. É sim.

O BFCL V4 testa cinco dimensões em 26 configurações de prompt: formato de retorno (Python, JSON, XML verboso, XML conciso), formato da documentação das funções (Python, XML, JSON), presença de tags de tool call, texto puro vs. Markdown, e enunciado original vs. reformulado. Os achados:

  • Formato de retorno: Python e JSON produzem acurácia mais alta que qualquer variante XML. Modelos menores e a família Claude tiveram queda significativa quando o retorno era pedido em XML.
  • Formato da documentação: tendência consistente em quase todos os modelos — JSON > XML > Python. Documentar as suas ferramentas em JSON Schema é uma escolha mensurável, não estética.
  • Tags de tool call: impacto pequeno na média — mas modelos pequenos (na faixa de 8B) sofreram queda significativa.
  • Markdown vs. texto puro e reformulação do enunciado: comportamento robusto, sem tendência geral.

A consequência que reorganiza o seu diagnóstico. Se a acurácia do mesmo modelo na mesma tarefa muda conforme o formato de apresentação, então uma fração do que você atribuiria ao "modelo ser ruim" é, na verdade, a sua integração. Antes de trocar de modelo, troque de formato: documente as tools em JSON Schema, peça retorno em JSON e não em XML, e evite envelopes exóticos com modelos pequenos. Isso é barato, é reversível e frequentemente resolve. E há um corolário desconfortável para a sua régua: um eval de tool calling que testa um único formato mede o par (modelo, formato), não o modelo.

# tools/custo_local.py
"""Custo por 1M de tokens de saida rodando local, amortizando hardware e energia."""
from dataclasses import dataclass


@dataclass(frozen=True, slots=True)
class CustoLocal:
    preco_hardware_usd: float
    vida_util_meses: int
    watts_sob_carga: int
    preco_kwh_usd: float
    tokens_por_segundo: float
    utilizacao: float = 0.25          # fracao do tempo realmente gerando

    def por_milhao_de_tokens(self) -> tuple[float, float, float]:
        segundos_por_mtok = 1_000_000 / self.tokens_por_segundo
        horas = segundos_por_mtok / 3600
        energia = horas * (self.watts_sob_carga / 1000) * self.preco_kwh_usd
        horas_uteis_no_periodo = self.vida_util_meses * 30 * 24 * self.utilizacao
        depreciacao_por_hora = self.preco_hardware_usd / horas_uteis_no_periodo
        hardware = horas * depreciacao_por_hora
        return energia, hardware, energia + hardware


if __name__ == "__main__":
    c = CustoLocal(
        preco_hardware_usd=2200,   # a maquina que roda o modelo
        vida_util_meses=36,
        watts_sob_carga=320,
        preco_kwh_usd=0.14,
        tokens_por_segundo=45,     # o numero que VOCE mediu no bloco 6
    )
    energia, hardware, total = c.por_milhao_de_tokens()
    print(f"energia    US$ {energia:7.2f} / Mtok")
    print(f"hardware   US$ {hardware:7.2f} / Mtok")
    print(f"TOTAL      US$ {total:7.2f} / Mtok")

Fine-tuning: LoRA, QLoRA e a escada de decisão

Fine-tuning é continuar treinando um modelo pronto com dados seus. Fazer isso com todos os pesos exige memória para os pesos, os gradientes e os estados do otimizador — na prática, algo como 12 a 16 bytes por parâmetro, ou seja, mais de 100 GB para um modelo de 8B. Inviável fora de um cluster.

Contexto · LoRA e QLoRA, a ideia em duas frases. LoRA (Low-Rank Adaptation) congela os pesos originais e treina, ao lado de cada matriz W (dimensão d×k), duas matrizes pequenas A (d×r) e B (r×k) com r muito menor — tipicamente 8, 16 ou 32. A saída vira W·x + (α/r)·B·A·x. Como só A e B são treinadas, o número de parâmetros treináveis cai tipicamente para menos de 1% do total, e o adaptador resultante ocupa dezenas de MB em vez de dezenas de GB. QLoRA vai além: carrega o modelo-base já quantizado em 4 bits (congelado) e treina os adaptadores LoRA em cima — o que faz um fine-tuning de 8B caber numa única GPU de consumo. A hipótese por trás das duas: a atualização necessária para adaptar um modelo a uma tarefa tem posto baixo, mesmo que os pesos originais não tenham.

# Como isso se parece na pratica, com a biblioteca peft
from peft import LoraConfig, get_peft_model
from transformers import AutoModelForCausalLM

base = AutoModelForCausalLM.from_pretrained("modelo/base")   # + quantizacao 4-bit no QLoRA

cfg = LoraConfig(
    r=16,                       # posto. 8-32 cobre quase tudo; maior nao e melhor
    lora_alpha=32,              # escala = alpha/r; convencao comum e alpha = 2r
    lora_dropout=0.05,
    target_modules="all-linear",# estilo QLoRA; o default atinge so q_proj e v_proj
    bias="none",
    task_type="CAUSAL_LM",
    use_rslora=False,           # True troca a escala para alpha/sqrt(r): mais estavel com r alto
)
modelo = get_peft_model(base, cfg)
modelo.print_trainable_parameters()

Agora a parte que importa mais que a API. Fine-tuning é a resposta errada com muito mais frequência do que parece, e a razão é que ele ataca a categoria errada de problema. Suba esta escada e pare no primeiro degrau que resolver:

#DegrauResolveCustoReversível?

Os quatro motivos pelos quais o degrau 6 quase nunca é o certo. (1) Ele não ensina fatos de forma confiável — o mecanismo é ajuste de distribuição, não inserção em base de dados; conhecimento novo entra por RAG, e tentar enfiá-lo por fine-tuning produz um modelo que alucina com o estilo dos seus dados, o que é pior que antes. (2) Esquecimento catastrófico: ao especializar, o modelo piora em coisas que fazia bem, e você só descobre o que quebrou se tiver evals abrangentes — os do M06 servem justamente para isso. (3) O custo real é a manutenção: o adaptador é acoplado a uma versão específica do modelo-base; quando sair a próxima, você retreina, revalida e possivelmente rotula dados de novo. Você não fez um artefato, assinou uma dívida recorrente. (4) Dados são o gargalo: LoRA precisa de milhares de exemplos consistentes e de alta qualidade; se você tem 200 exemplos, eles rendem mais como few-shot no prompt ou como conjunto de eval.

E quando ele é o certo? Três sinais juntos: você já subiu os cinco degraus anteriores e mediu; o volume é alto o bastante para que a economia por chamada pague o retreino; e o que você quer é comportamento/formato consistente, não conhecimento. Exemplo legítimo no Cartógrafo: se o relatório final tem um formato rígido e proprietário e você processa dezenas de milhares por mês, um LoRA pequeno de formatação sobre um modelo local pode valer. Repare: mesmo aí, o conhecimento continua vindo do grafo e do RAG.

Fundamento vale até a camada em que ele muda uma decisão sua; abaixo disso é hobby.
Produto escalar é a operação única do campo: é a busca do M07 e é a atenção do transformer.
A matriz T×T é o O(n²) — cortar 30% do contexto corta 51% do trabalho, e isso aparece na fatura.
Tokenização explica a aritmética errada; amostragem explica a alucinação; nenhuma das duas se conserta com mais dados.
