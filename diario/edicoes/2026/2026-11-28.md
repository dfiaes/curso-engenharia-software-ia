### 1. llama.cpp 1.0: o contrato de versão vale para a biblioteca, não para o llama-server

**O que aconteceu.** Uma análise da i-scoop de 27/11 detalha o contrato de versionamento do llama.cpp 1.0 (lançado em 13/11, coberto neste diário em 15/11). Mudança incompatível na API C pública (headers em `include/`) sobe o major; recurso novo, backend, suporte a modelo ou adição compatível sobe o minor; correção sem mudança de API sobe o patch. O contrato cobre só `libllama` e `libggml`. Ficam fora, segundo a matéria: a API HTTP do `llama-server`, as flags de linha de comando, o formato GGUF e qualquer janela de suporte para a linha 1.x. A 1.0 removeu `llama_set_warmup` e outras 35 funções obsoletas, renomeou a biblioteca para `libllama.so.1`, tirou a flag `--defrag-thold` e, segundo a própria matéria, não promete ganho geral de desempenho. A i-scoop lembra o contexto: a equipe do ggml entrou no Hugging Face em fevereiro de 2026, e a compra do Hugging Face pela Nvidia (anunciada em setembro, US$ 12,93 bi segundo o Computing, citado pela matéria) ainda depende de revisão regulatória e deve fechar no primeiro semestre de 2027; a licença MIT não muda. O The Batch (27/11) confirma a 1.0.0, nove dias depois da 0.9.0, mas não descreve o contrato nem cita a Nvidia. Um digest gerado por IA (agents-radar, 27/11) já lista uma v1.1.0 com suporte à família Inkling 2; não confirmado na página de releases.

**Por que importa para você.** A maioria das integrações em produção não linka `libllama`: fala com o `llama-server` por HTTP, ou com Ollama e LM Studio, que embutem o llama.cpp. Para esse uso, a 1.0 não é promessa de estabilidade. Um minor pode mudar flag ou campo da API HTTP sem violar o contrato.

**Como aplicar.** Fixe a versão do llama.cpp por tag (ou o build `bNNNNN`) no Dockerfile, no Homebrew ou no script de setup, nunca "latest". Escreva um teste de contrato pequeno contra o `llama-server` local: suba o servidor, chame `/v1/chat/completions` e `/health` e valide os campos que seu código lê, com um modelo GGUF pequeno. Rode esse teste antes de atualizar. Se seu script usava `--defrag-thold`, remova a flag antes de subir para a 1.x.

Fonte: [i-scoop, llama.cpp 1.0 gives local AI a version contract, 27/11](https://www.i-scoop.eu/llama-cpp-1-0/); [The Batch, DeepLearning.AI, 27/11](https://charonhub.deeplearning.ai/llama-cpp-makes-it-official/)

### 2. Antigravity 2.36.0: o modo Auto passa a aprovar edições fora do projeto

**O que aconteceu.** O changelog oficial do app Google Antigravity registra a 2.36.0 em 27/11: o modo Auto passa a aprovar edições consideradas seguras fora da pasta do projeto, e o composer vira flutuante em painéis maximizados; a versão lista 13 melhorias e 26 correções. A página não explica o critério de "segura" nas partes lidas. Nas versões anteriores da semana: 2.35.0 (23/11) com histórico local de conversas ilimitado por padrão e uma Conversation Management API; 2.35.1 (24/11) com retomada automática de conversas após reinício; 2.35.2 (25/11), coberta em 26/11.

**Por que importa para você.** A pasta do projeto costuma ser a fronteira mental de quem libera modo automático para um agente de código. Quando o agente pode escrever fora dela sem pedir, entram em jogo `~/.zshrc`, `~/.ssh/config`, `~/.gitconfig`, arquivos de configuração de outros agentes e de servidores MCP. É exatamente onde uma injeção de prompt vinda de um README ou issue tenta persistir.

**Como aplicar.** Antes de atualizar, leia a nota completa da 2.36.0 e as configurações do modo Auto para ver se a escrita fora do projeto pode ser desligada ou limitada por lista de caminhos. Enquanto não souber o critério, use o modo Auto só dentro de um contêiner ou VM, ou numa conta de usuário separada sem suas chaves. Ponha seus dotfiles sob git (ou faça um snapshot) para enxergar qualquer alteração com `git diff`.

Fonte: [Google Antigravity, changelog](https://antigravity.google/docs/changelog/?tab=cli)
